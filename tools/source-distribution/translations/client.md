# Design of the multiplatform phpvpn client

## Purpose

This document is the normative design of the native client for the phpvpn v1 protocol, with [plan3_client.md](plan3_client.md) as its historical basis. The description of requirements does not by itself confirm their implementation or testing. The client works as a briefly connected relay peer: it captures IPv4 packets from a virtual interface, encrypts them end-to-end for a specific recipient, sends them through the `data` endpoint, and writes received, verified packets back into the virtual interface.

The client MUST be **thread-safe**. It uses three VPN worker roles, each in its own thread, which share resources safely without data races and concurrent collisions. The engine handles errors returned by the bootstrap and by the operational `data` exchange. On a transient error of the operational `data` exchange it first performs a soft recovery without releasing the tunnel; on other recoverable errors, and after the soft recovery budget is exhausted, it performs a teardown and retries the connection according to the section Connection state machine. A non-recoverable error leads to `error` and requires user intervention. General recovery after a crash or an uncaught exception of any worker role is not provided.

The primary target is Windows. The design also separates the platform-independent core from the network interface and from operating system integration, so that it can be ported to other platforms. The Linux port is delivered according to the section [Linux](#linux), the macOS port according to the section [macOS](#macos). The Windows part uses C++20, MSVC, CMake/Ninja, Win32, WinHTTP and CNG without any new third-party library. The portable models contain no HWND, HANDLE, Win32 messages or dependency on the tray process.

The server knows neither the payload keys nor the IP content. The client handles key selection, AES-256-GCM protection of the payload, validation and handing packets over to the virtual L3 interface.

## Architecture

The client core must not depend on the API of a specific platform. It is divided into these modules:

| Module | Responsibility |
|---|---|
| `Config` | Loading, strict validation and in-memory holding of the configuration. |
| `Protocol` | Canonicalization, JSON/NDJSON, `health`, `info`, `data`, HMAC/HKDF and base64url. |
| `Crypto` | AES-256-GCM for the payload, secure erasure of secret values and IV generation from a CSPRNG. |
| `Transport` | HTTP/HTTPS POST, timeouts, response size checks and certificate policy. |
| `Tunnel` | Abstraction of reading and writing raw IPv4 packets to the virtual interface. |
| `Queues` | Outbound queues by destination VPN address, inbound queues by source VPN address, flush scheduling, logical per-peer reservations, memory limits and aggregate statistics of dropped packets. |
| `Runtime` | Connection state machine, three VPN worker roles, shutdown, recovery and a comprehensible log. |
| `Presentation` | Portable Contracts and Password SHA models, row validation and action identity without windows or IPC. |

`core/config/contracts_document.*` owns the original valid DOM, the preserving patch and full validation of the candidate. `core/presentation/contracts_model.*` and `password_key_model.*` are separate objects of the existing static library `phpvpn-core`. They add no library and no third-party dependency. They use the shared IPv4 helpers, JSON and `CryptoProvider`, without Windows headers or types. The service and the CLI do not pull in unused model objects. The native view, focus, scrolling and windows belong to `apps/tray`. `ContractsWindow` and `PasswordShaWindow` use the portable models; `ContractsSaveController` controls saving and its transport lifecycle.

The current Windows layer provides the implementation of the `Tunnel` interface using Wintun, the HTTP/HTTPS transport through WinHTTP and the cryptographic `CryptoProvider` through Windows CNG. It also provides local IPC, clocks, file operations, paths and network configuration through IP Helper. Service integration and the native tray belong to the respective applications. The Linux layer in `client/src/platform/linux` uses TUN, rtnetlink, libcurl, OpenSSL 3 and libsystemd according to the section [Linux](#linux). These libraries are not a dependency of the Windows client. The macOS layer in `client/src/platform/macos` uses `utun`, `PF_ROUTE`, SystemConfiguration and the shared POSIX files from `client/src/platform/posix` with the same libcurl transport and OpenSSL provider according to the section [macOS](#macos). The protocol requirement for pure PHP AES-GCM applies to the PHP implementations, not to the native client.

The source files are divided into `client/src/core` for the portable core in the static library `phpvpn-core`, `client/src/platform` for the interfaces and the Windows or Linux adapters in the static library `phpvpn-platform`, and `client/apps` for the separate service, CLI and tray entry points. The service owns the VPN traffic; the CLI and the tray control it through local IPC. The native Win32 windows and their handling are part of `apps/tray`, the Linux GTK windows are part of `apps/tray-linux`, not of the portable models.

### Runtime model

The data part of the VPN uses exactly three serially working roles, each running in its own thread; an implementation MUST NOT replace them with separate processes, workers or an equivalent event loop. Data ownership and the concurrency rules must stay the same.

1. **The tunnel input worker** is the only reader of the virtual L3 interface. It performs full validation of the IPv4 packet according to the rules below, requires the local virtual IP as the inner source and enqueues the packet exclusively into the appropriate flow sub-bucket of the peer queue of the contract matching its inner destination. It does not encrypt and does not wait for the network.
2. **The network worker** is the only owner of the `health`, `info` and `data` requests of its VPN context, of batch scheduling, encryption, response verification and decryption. At most one `data` request may be in progress at any moment.
3. **The tunnel output worker** is the only writer to the virtual L3 interface. It sequentially takes verified IPv4 packets from the inbound peer queues accounted by source VPN address. Between peers it alternates at most one write per pass, and inside a peer it selects from 16 sub-buckets using byte-based DRR. It preserves FIFO order inside each sub-bucket.

Queues are locked only briefly when inserting, removing or atomically taking over items and when changing their size counters. The lock must not be held during payload encryption, decryption, HTTP communication, waiting for a response or writing to the tunnel. The local HMAC for selecting the overflow bucket is part of the atomic admission under the queue lock. The first worker therefore keeps reading even while the network worker is processing the previous request.

The network role lasts from the successful start of the engine until shutdown. During recovery it terminates both tunnel I/O roles and the active tunnel session, resets the network context and clears both the inbound and outbound queues. The next bootstrap creates new queues and, after verifying the server and access, creates the tunnel session and the two I/O roles again. Pending packets of the cleared queues are not kept for the next attempt and their delivery is not guaranteed. The accepted configuration and the original initial checkpoints are preserved. An error returned by a tunnel read terminates the input role; `tunnel_io_failed` on write terminates the output role. The engine has no general supervision of their termination and no catch of uncaught runtime exceptions that would start recovery on its own.

The limited control handling, platform I/O callbacks and diagnostics are not additional VPN worker roles. `get-info` and `get-server-info` run concurrently with the VPN data, with their own transport and time. The Wizard probe also uses this separate path, but must not overlap any VPN `data` request. A new Connect safely interrupts it and waits for its terminal state before the bootstrap. The number of handling threads is not fixed at four.

## Configuration file

The configuration is JSON owned by the service. The fixed storage is `config.json` in the phpvpn directory under the system ProgramData; its actual absolute path is evaluated authoritatively by the service. The existing letter case of a `PHPVPN` directory is not migrated. IPC does not accept a path from the client, and a warning must show the actually expanded absolute path; the literal text `%ProgramData%` alone is not sufficient. The service loads it and strictly validates it on each new connection attempt; after successful validation it stays in memory for the duration of the connection and the regular data flow does not read the disk again. An invalid or incomplete configuration prevents VPN traffic from starting. Neither the tray nor the console application reads or writes the configuration file directly, and they do not validate it on behalf of the service. Through the public IPC, however, they can obtain or send the whole configuration JSON, and therefore they may temporarily hold its secret values in memory while handling `get-config` and `set-config`.

Each service start, after safe preparation of the directory and unambiguous recovery, classifies the authoritative `config.json` once. Only a genuinely missing file is created, through `ConfigStore::ensureDefaultAtStartup()` and the shared `createDefault()` in the atomic `createIfMissing` mode. Existing bytes, including an old, defective, unreadable, oversized or wrongly encoded file, are not changed. A target created concurrently is not overwritten. An error causes no automatic retry; IPC and diagnostics remain available, and an unresolved safe initialization blocks both publication and Connect. Connect creates nothing. Startup does not call the tray IPC, HTTP or Connect. The Wizard writes only on Finish; Edit Config can, with an explicitly confirmed Yes, restore a file deleted at runtime. An active VPN continues on its snapshot; Disconnect does not read the disk.

`serverSecret` uses its exact UTF-8 bytes. Only a value of length zero is normalized to `CHANGE_THIS_SERVER_SECRET` for cryptography, without rewriting the stored text. Any non-empty value, including 32 or 64 ASCII zeros, is preserved literally. There is no automatic migration and no trying of old secrets.

Different client computers may use the same virtual IP. phpvpn neither enforces nor reserves uniqueness; the system tolerates a collision, and fixing it is the operator's responsibility, as it is an error in their configuration. Separately, a `communicationContract` of one's own targeting the local `virtualIp` is prohibited. The number of remote peers below counts possible addresses, not the number of physical computers.

The Wizard metadata, their strict types and compatible fallbacks are bindingly described in the section Repairable document. The following example without them remains a valid older schema.

Proposed structure:

```json
{
  "masterSetup": {
    "serverSecret": "server-shared-secret",
    "serverUrl": "https://vpn.example.test/phpvpn.php",
    "httpHeaders": "Cache-Control: no-cache\r\nPragma: no-cache\r\nUser-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:155.0) Gecko/20100101 Firefox/155.0",
    "trustAnyTlsCertificate": true,
    "vpnCidr": "10.99.99.0/24",
    "virtualIp": "10.99.99.2",
    "accessKey": "64-char-lowercase-hex"
  },
  "runtime": {
    "maxOutboundQueueBytes": 134217728,
    "maxInboundQueueBytes": 134217728,
    "minOutboundPerPeerQueueBytes": 262144,
    "minInboundPerPeerQueueBytes": 262144,
    "maxQueuedPacketAgeMs": 5000,
    "maxResponseBodyBytes": 67108864,
    "maxNdjsonLineBytes": 67108864,
    "maxDataRecordsPerResponse": 65535,
    "responseTimeoutSeconds": 30,
    "timeSyncIntervalSeconds": 300
  },
  "communicationContracts": {
    "10.99.99.3": {
      "payloadKey": "64-char-lowercase-hex"
    }
  }
}
```

`serverUrl` contains the full URL of the server file `phpvpn.php`, and the client intentionally supports both HTTP and HTTPS. `vpnCidr` is the canonical IPv4 CIDR of the shared VPN address space with a prefix length strictly from `/24` to `/29`. When omitted, its default value is `10.99.99.0/24`. The value must contain the network address matching the given prefix, not a host address with non-zero host bits. `virtualIp` and all addresses in `communicationContracts` must belong to `vpnCidr` and at the same time satisfy the rules for valid client addresses of the shared configuration. The network address, the first host address and the broadcast address are reserved; valid clients are from network+2 to broadcast-1. `accessKey` corresponds to the protocol `ACCESS_KEY` and is exactly 32 bytes written as 64 lowercase hexadecimal characters. Each `payloadKey` is a fixed 32-byte protocol `PAYLOAD_KEY`. This client uses the single key from `communicationContracts` of the given peer both for sending to that peer and for receiving from it. The direction is distinguished by the AAD containing `src` and `dst`. The general wire contract and the binding of the key to an ordered pair of addresses are defined in [protocol.md](protocol.md), chapter 9.4. It is neither a user password nor a key derived at runtime.

The `/24` to `/29` range is enforced by a single shared validation in both full and repair mode, before a new Connect and before every publication through ConfigStore, including `set-config`, Save, Wizard Finish and the startup default. The previously valid `/16` to `/23` are now invalid, without automatic migration, prefix shortening or shortening of the peer list. `/30` has only one client address and no remote peer; `/31` and `/32` are not supported by the current model and are rejected. Edit Config makes the text available for repair, but Save does not bypass validation. What changes is configuration compatibility, not HTTP, the cryptographic wire format or the IPC schema.

`trustAnyTlsCertificate` has, by the current decision, the default value `true`. With HTTPS the client then intentionally accepts any certificate for the configured URL, including a self-signed certificate and a certificate issued by an unknown or untrusted certification authority. This is a knowingly accepted critical security risk: by default the client will not verify the chain of trust or the trustworthiness of the issuing authority. The client implementation intentionally accounts for this risk. A safer future profile may set the value to `false` and require standard chain and host name validation.

The configuration must not routinely be written to the log. The log may show the virtual IP and the list of remote IPs without keys and secrets. The exception for the URL and the fixed configuration path belongs only in the designated configuration responses and windows, not in the log. This does not restrict the intentionally public IPC commands `get-config` and `set-config`.

`maxOutboundQueueBytes` and `maxInboundQueueBytes` limit the actual packet bytes in the instance of a direction, including packets already selected into an in-progress request or tunnel send. The default limit of each direction is 128 MiB (`134217728`). `minOutboundPerPeerQueueBytes` and `minInboundPerPeerQueueBytes` define the separate logical reservation of each possible peer, by default 256 KiB (`262144`) in each direction. `maxQueuedPacketAgeMs` is the shared maximum age of a pending packet in milliseconds, by default `5000`.

All five fields and the whole `runtime` section are optional. The parser fills in missing defaults only in memory; it does not write them to the JSON automatically. The default editor document does not contain `runtime`. A regular edit of identities or contracts does not add missing fields and preserves explicit values. The fields are positive integers of type int64. Zero, a negative number, a non-integer number, bool, string, null and a value above int64 are invalid. The TTL has no disabled mode. The historical shared name of the peer reservation is rejected as an unknown member, without an alias or migration. Saving the configuration at runtime does not change the active queues. A new Connect loads the new valid configuration; recovery within the same epoch keeps the accepted configuration, including the TTL.

In the default `vpnCidr` `10.99.99.0/24` there are 253 valid client addresses `10.99.99.2` to `10.99.99.254`, so a single local client has at most 252 remote peers. For another supported `/24` to `/29`, `maxRemotePeers` is derived by the shared IPv4 helpers from the number of all possible valid client addresses after excluding the single local address. `/29` has five client addresses and four remote peers. The count and the multiplication of reservations are checked without overflow before allocation. This is not just the number of currently listed `communicationContracts`, but the number of all peers for which a queue can exist in the given address space. The target Communication contracts editor according to UX10 therefore has at most 252 native rows without virtualization or HWND recycling. This does not concern the additive Wizard candidates 13/14, which remain unchanged. The actual limit of the resulting JSON of 524288 bytes and the queue budgets are also checked separately within the supported range.

Before each connection attempt, the configuration MUST separately satisfy, for the outbound and inbound direction and without integer overflow:

```text
maxOutboundQueueBytes >= maxRemotePeers × minOutboundPerPeerQueueBytes
maxInboundQueueBytes  >= maxRemotePeers × minInboundPerPeerQueueBytes
```

Failure rejects the configuration before `health` and before the tunnel is created. The reservations apply to all possible peers of the prefix, not only to contracts or currently active peers. Queues are physically created only on admission. Construction allocates neither the global limit nor buffers for all possible peers.

### Symmetric flow queues and logical reservations

Each peer has exactly 16 sub-buckets. For a direction, denote the global limit G, the number of possible peers N and its per-peer minimum P. The derived sub-bucket minimum is M = P / 16, the remainder R = P % 16. M is not a separate configuration field. The default M is 16384 bytes, i.e. 16 KiB. Even a positive P smaller than 16 is valid; then M = 0. R remains an undivided part of the peer reservation.

For x[p,b] = pending bytes + bytes of selected packets, after each admission the following must hold:

```text
A = sum(x[p,b]) <= G
C[p] = R + sum(max(x[p,b], M))
L = N * P + sum(max(0, x[p,b] - M)) <= G
```

The baseline N * P therefore includes even unallocated peers and empty buckets. A heavy bucket can draw on the shared capacity above M, but it does not consume the minimums of the other buckets. Their short burst up to M can be admitted even after this shared capacity is exhausted. Running aggregates ensure admission without scanning all peers. The rejection reasons are ordered `global_limit`, `per_peer_reservation`, `sub_bucket_reservation`. The last reason distinguishes a violation of the inner reservations from the peer reservation itself.

With the default /24 the baseline is `66060288` bytes. The upper bound of actual bytes of a single peer, when the other peers are empty and its buckets are suitably filled, is `68419584` bytes (65.25 MiB). A single active bucket can have at most `68173824` bytes, because the other 15 minimums remain reserved. These are packet bytes and logical conditions. The process RSS additionally contains containers, metadata, the allocator, cryptography and transfer bodies.

The flow key is the directional five-tuple of source IPv4, destination IPv4, source port, destination port and protocol. Directions are not canonicalized. For unfragmented TCP, ports are read only from a complete minimal header with a valid data offset. UDP requires at least eight bytes and a length matching the datagram. A fragment with MF or a non-zero offset, an incomplete transport header and any other protocol use zero ports. DF alone does not cause the fallback. An otherwise valid IPv4 packet is not dropped because of missing ports.

An existing owner gets its slot; otherwise the flow gets the empty FIFO with the lowest index. When all 16 FIFOs are occupied, the index is determined as the last four bits of HMAC-SHA-256 over an explicit 13-byte network serialization of the whole five-tuple. A new random 32-byte key in a SecureBuffer is created at client start, survives reconnects and is shared by both directions. It is separate from the protocol keys. A failure of initialization or of the HMAC is an internal error, never a fallback to an unkeyed hash. The directory is directly in the 16 slots; there is no map of all overflow flows. The HMAC is computed only for overflow.

The owner is removed immediately after its last pending packet is taken. An empty FIFO releases ownership and resets the deficit even when held capacity exists. A non-empty bucket without an owner is not free. Only the first pending packet is a candidate for takeover, and its key must not own another slot. Promotion happens only when there are at most 64 pending packets, in which case the candidate's items are counted exactly. With a longer collision queue the bucket stays without an owner. The check is repeated when the head changes or on rollback and never scans a long backlog for the sake of the owner. FIFO applies inside a bucket. After an ownership change a flow can get a different slot; there is no global reorder buffer and no guarantee of the order of the whole flow across such a change.

### Monotonic expiration and in-progress packets

On first admission a packet gets a monotonic time in ms. It expires when `now - queuedAt >= maxQueuedPacketAgeMs`. The unsigned difference safely crosses the signed boundary and even one uint64 wrap; the wall clock has no influence. Before each selection only the contiguous expired prefix of the given FIFO is removed. The first fresh packet ends the cleanup and the rest is preserved.

Before a rejection due to capacity, the oldest expired heads are cleaned up until admission becomes possible or until the first fresh head. An indexed min-heap contains at most one item per non-empty bucket, i.e. 16 * N, without stale items and without traversing fresh backlogs. The key is the original admission order. The exceptional renumbering of sequences also includes live leases. The memory of the index grows only with allocated peers. Without a new operation, old packets can remain until the next selection or capacity pressure.

Selection moves a list node into a move-only lease without copying the packet data and without releasing capacity. `acceptedMessageIds` commit the corresponding records. Unconfirmed, deferred and all error paths return the nodes to their original buckets ahead of newer packets, with the same timestamp and sequence number. Rollback performs no new admission and needs no allocation. The held capacity therefore prevents the producer from consuming the space needed for the return. The lease destructor returns a selection that has not yet been decided. A lease belongs to a specific queue instance; its consumers are terminated before the queue is destroyed.

DRR accounts each local transfer attempt once, at selection. Rollback neither subtracts the deficit again nor returns credit. The TTL is checked at selection into a request or tunnel send; it does not interrupt an HTTP request already started and is not a guarantee of end-to-end latency. A retry does not renew the age. Expiration releases bytes, items and ownership just like regular removal and records exactly one `queue_expired` with the actual peer.

`maxResponseBodyBytes`, `maxNdjsonLineBytes`, `maxDataRecordsPerResponse` and `responseTimeoutSeconds` are user-configurable positive integers of type int64. When omitted, their default values are, in order, `67108864` bytes (64 MiB), `67108864` bytes, `65535` records and `30` seconds. Full configuration validation rejects zero, a negative value, a non-integer number or a value not representable by this type. `responseTimeoutSeconds` additionally has a maximum of `2147483` seconds for safe conversion to milliseconds for WinHTTP. For the other three values no further global upper cap is set beyond the type and the following relation.

`maxNdjsonLineBytes <= maxResponseBodyBytes` must hold. Equality is allowed. Violating this relation or the maximum of `responseTimeoutSeconds` is rejected by full validation and also by the repair analysis, which uses the same validation with a missing identity allowed.

`maxResponseBodyBytes` limits the number of exact bytes of the body of a single HTTP response. The transport counts it continuously while receiving `health`, `info` and `data` responses; when the limit is exceeded it terminates the request, does not use the incomplete response and does not pass it to the protocol parser. `maxNdjsonLineBytes` limits the number of bytes of one NDJSON line of a `data` endpoint response, including its terminating LF. The NDJSON parser checks the length continuously and rejects a line that is too long even before base64 decoding of its fields. `maxDataRecordsPerResponse` is the maximum number of records, i.e. NDJSON lines of type `data`, that the client accepts in one response of the `data` endpoint; after the limit is exceeded the parser rejects the whole response even before the subsequent cryptographic processing of the exceeding line.

`responseTimeoutSeconds` defines a single absolute monotonic deadline from the start of the HTTP request through DNS, connection, TLS, sending and headers up to the whole response body for `health`, `info` and `data`. Neither a partial block nor a phase transition renews it. A timeout starts a safe cancellation and, after a confirmed terminal state, returns the timeout, never a late success. A timeout of a VPN data request leads to regular recovery. A timeout of a refresh `health` during a connection by itself only sets `lastHealthVerified = no` and keeps the previous verified time snapshot according to the section Time synchronization. One-off diagnostics and the Wizard end without an automatic retry. Conversions and timeout settings are checked according to the section Shared HTTP transport. The limits on total response size, NDJSON line length, number of data lines and total time are checked separately, and none of them replaces the others.

`timeSyncIntervalSeconds` is a user-configurable positive integer defining the period at which a regular periodic attempt to refresh the verified server time is started. When omitted, its default value is `300`, i.e. 5 minutes. The validator adds no global upper cap beyond the int64 type and rejects zero, a negative value, a non-integer number and a value not representable by this type. Acceptance of a value by the validator is not a guarantee of the safety of all extreme time computations.

## Connection state machine

1. **Loading the configuration.** The client validates the URL, the canonical IPv4 form of `vpnCidr`, the membership of `virtualIp` and of all contract addresses in this prefix, the rules for valid client addresses, the hex format and lengths of keys, the uniqueness of contracts and the availability of a supported platform layer. On Windows, in this phase it may verify the distribution manifest, the DLL, the architecture and the mandatory Wintun API, but it MUST NOT yet create or open the adapter, start a Wintun session or change the network. Connect rejects a valid configuration whose `serverUrl` has the placeholder host `kPlaceholderServerHost` with the code `config_server_url_unset` before the Health step; the state remains `disconnected`.
2. **Health.** Before the first `info` or `data` it generates a new UUIDv4 `requestId`, records the monotonic `sendMono` and sends `auth-none` to `?action=health`.
3. **Server and time verification.** After receiving the whole response it records the monotonic `receiveMono`. If the response matches the `health` syntax and carries the state `running`, the client verifies the match of `requestId` and the GCM tag according to the protocol. Only then does it accept the authenticated UTC time of the server and atomically create the initial time estimate according to the following section; it never changes the local system time.
4. **Time margin.** The timestamp of each subsequent authenticated `info` or `data` request is created exclusively from the last verified server time estimate, the current monotonic time and the normative safety margin according to the following section. After synchronization it must not be derived directly from the current system clock.
5. **Info.** The client sends an authenticated `auth-semi` to `?action=info`, verifies and decrypts the response and stores the received limits and recommended operating values. It must respect the hard limits, especially the maximum request body size. The recommended polling intervals serve as a scheduler unless they are marked as binding in a future specification.
6. **Access key verification.** The existing network role performs an empty authenticated `data` poll before starting the tunnel and its two I/O roles. This verifies `ACCESS_KEY` as well as the complete `data` response. It processes received valid batches the same way as during regular polling and prepares them for the output worker.
7. **Contract publication.** Once per accepted Connect, an extended full-auth `info` with the whole masked list and include true is performed. After success it is not repeated during recovery. Any failure is final for this attempt and the tunnel does not start.
8. **Tunnel start and operation.** Only after a successful `health`, standard `info`, the first empty `data` poll and the contract publication does the service on Windows create or open its single own Wintun adapter, start a single session, configure its own address and routes and start the two tunnel I/O roles. The network role is already running and after a successful start it switches to regular operation. Reading the tunnel and regular polling of the `data` endpoint must not start earlier.
9. **Recovery.** An error returned by the bootstrap leads to a teardown of the existing tunnel roles, session and queues. An error of an operational `data` request first goes through the soft recovery described below; only its failure, a non-transient recoverable error or a non-recoverable error leads to a teardown. The next attempt is decided by the safe classification of the service error (`lastError.recoverable`). For example, a timeout, a DNS or connection failure and a recoverable server error lead to `recovering`. A non-recoverable error leads to `error`, for example a failure of the cryptographic verification of `health`, of the verification/decryption/validation of `info` or a rejection of `ACCESS_KEY` during the bootstrap. A failure of the periodic `health` alone is governed by the section Time synchronization and does not start recovery. The exception is a server of a different MAJOR version (`server_version_incompatible`, see Server version compatibility): a verified periodic `health` or a refresh after 401 with such a version ends the connection with a teardown into the `error` state without recovery.

Recovery, after a delay, repeats `health`, `info` and the empty authenticated `data` over new queues, completes a not yet performed contract publication as the fourth step, and then creates the tunnel session and both I/O roles again. It uses the configuration accepted by the original Connect; it does not read the disk again or take over changes saved in the meantime. It preserves the original initial checkpoints and the operating counters of the same logical connection. On an unsuccessful attempt it performs a teardown again and, depending on the recoverability of the error, schedules another attempt or moves to `error`.

The ladder of the basic backoff is **1/2/4/8/16/32/60 s**, with an added jitter from zero to **20 %** of the base value. After an error the index is increased before the delay is computed, so the first wait has a base of **2 s**, followed by **4/8/16/32/60/60… s**. The first interval is therefore 2–2.4 s, the last 60–72 s. A successful connection resets the index, as does a new logical Connect and a completed Disconnect. The wait can be interrupted by the control command Disconnect or stop. The recovery backoff is separate from regular data polling with its maximum of 5 s.

**Soft recovery.** A single unsuccessful operational `data` exchange MUST NOT by itself release the tunnel, because removing the VPN address and route terminates all TCP connections inside the tunnel (verified in [testing.md](testing.md): a single 502 response terminated an FTP transfer). A transient error of a `data` exchange in the `connected` state therefore switches the phase to `reconnecting` while the state stays `connected`: the tunnel session, both I/O roles and the queues remain unchanged, the outbound lease is returned to the queue and the network role repeats the exchange after a delay from the ladder **250/500/1000/2000/5000 ms** with a jitter of up to 20 %. A transient error according to `errorCodeIsTransient` is a recoverable transport error (DNS, connection, TLS, send, receive, response size exceeded, timeout), the server errors `server_unavailable`, `server_internal_error`, `server_unexpected_status` and `server_payload_too_large`, and a response that cannot be accepted or verified (`response_*`, `wire_*`). A `401` response in `reconnecting` is handled by at most one refresh `auth-none` `health` without a teardown; a second `401` in the same episode leads to the existing error classification. Other recoverable errors, for example `cancelled`, and all non-recoverable errors do not use soft recovery.

The budget of one soft recovery episode is a fixed engine constant `kSoftRecoveryGraceMs` of **90 s**, measured in monotonic time from the first unsuccessful exchange; it is not part of the configuration file. If no `data` exchange is verified within this window, the existing teardown, `recovering` and the basic backoff ladder follow. During soft recovery, `lastError` in `get-status` is `null`, `lastDataVerified` is `no`, `responsesRejected` increases with each unsuccessful exchange and `tunnelReady` stays `yes`. A successful exchange returns the phase to `running`, keeps `connectionStartedAt` and all counters, and counts the episode in `softRecoveryCount` and `lastSoftRecoveryAt` in `get-diagnostics`; `recoveryCount` and `lastRecoveryAt` count only full recoveries with a teardown. The wait between attempts can be interrupted by the command Disconnect or stop; packets in the queues are subject to regular expiration according to `maxQueuedPacketAgeMs`. Both the tray and the Linux indicator show `connected` with the phase `reconnecting` using the connecting icon.

The lifecycle and the backoff are verified by the existing scenarios `runtime.lifecycle_keeps_one_network_role_and_recreates_two_io_roles` and `runtime.lifecycle_recovery_tears_down_and_recreates_after_current_backoff` in the [runtime tests](client/tests/unit/test_runtime_status.cpp); the second scenario disables soft recovery with a zero budget. Soft recovery is verified by the scenarios `runtime.transient_error_classification_for_soft_recovery`, `runtime.soft_recovery_keeps_tunnel_and_queue_through_one_transient_failure`, `runtime.soft_recovery_401_refreshes_verified_time_once_without_teardown`, `runtime.soft_recovery_repeated_401_after_refresh_takes_the_full_path`, `runtime.soft_recovery_budget_exhausted_falls_back_to_full_recovery` and `runtime.soft_recovery_honours_disconnect_and_stop_during_backoff` in the same file. Further scenarios in the same file verify the accepted snapshot after Save and after deletion of the configuration, the retention of successful and unsuccessful initial checkpoints, an idempotent Connect and the reset after Disconnect. The fake driver verifies the engine lifecycle, not the real Wintun or general resilience against a role crash.

For each new logical connection attempt, the Windows Service maintains, besides the current phase, also the persistent results of four bootstrap checkpoints in the exact order **Server URL**, **SERVER_SECRET**, **ACCESS_KEY**, **Communication contracts**. Each checkpoint has the state `pending`, `success` or `failed`. A new logical attempt arises only by accepting `connect` in the `disconnected` or `error` state; all four results are then atomically set to `pending`. An idempotent `connect` in the `connecting`, `connected` or `recovering` state does not create a new attempt and does not change the results merely because the command is repeated.

The **Server URL** checkpoint changes to `success` after the transport is established and a syntactically usable `health` response is received, even before its cryptographic verification. The service publishes this result already at that moment, not only after the whole verification operation returns. Publication must not hold the state lock during cryptography or insert an artificial wait. **SERVER_SECRET** changes to `success` only after the cryptographic verification of the `health` response and after successful verification, decryption and full validation of the `info` response. **ACCESS_KEY** changes to `success` only after a successful empty authenticated `data` poll. **Communication contracts** changes to `success` after a verified extended `info`, including an empty local list. On failure, the correct checkpoint being evaluated at that moment is set to `failed` and later checkpoints not yet performed stay `pending`. A failure to start the tunnel happens only after these checkpoints, so all four can stay `success` while the overall state changes to `error`. The results of the initial bootstrap are kept until the next new logical attempt or a completed disconnect, so that they can be safely reconstructed even when UI polling skips a short phase. Automatic recovery neither clears them nor replaces them with the results of further recovery runs. The progress of recovery is expressed by the current state, phase and the safe last error. Green checkpoints document the result of the initial checks; they do not by themselves confirm a currently working connection. At service start and after a completed `disconnect`, all four checkpoints have the value `pending`.

The command output should briefly show the phases: connecting to the server, server available, `SERVER_SECRET` successfully verified, operating limits determined and tunnel state. Secrets and authentication tags are not printed.

## Time synchronization

All mutable state of the VPN time synchronization is owned exclusively by the network worker. The separate diagnostics `get-info`, `get-server-info` and ProbeClient have their own temporary TimeSnapshot and transport, with the same RTT verification and safety margin. They must not change the VPN time snapshot. No tunnel role may change it or create timestamps from it on its own. One complete time snapshot contains at least the verified server UTC timestamp from `health`, the estimate `serverTimeAtReceive`, the monotonic `receiveMono`, the measured RTT, the difference from the local system UTC time at the moment of synchronization, and the moment of synchronization. The snapshot is published or replaced only as one whole after successful verification of the response.

The first `health` MUST succeed before the first `info` or `data`. Immediately before starting the HTTP request, the network worker records `sendMono` from the monotonic clock, and immediately after receiving the whole response it records `receiveMono` from the same monotonic time source. It first verifies the exact expected `requestId`, the syntax of all fields and the GCM tag. Only on complete success does it compute:

```text
RTT = receiveMono - sendMono
serverTimeAtReceive = authenticatedServerTimestamp + RTT / 2
serverLocalOffsetAtSync = serverTimeAtReceive - localSystemUtcAtReceive
```

TimeSync rejects `receiveMono < sendMono`. It also checks for overflow of the sum of the server timestamp and half the RTT and of the sum used for the offset. These partial checks do not prove safety for all extreme inputs. `serverLocalOffsetAtSync` serves the synchronization state and the detection of a system clock change; after the snapshot is accepted it must not be used together with the current system clock as the primary source of timestamps of authenticated requests.

For each regular authenticated request the network worker reads the current monotonic time and computes:

```text
safetyMargin = max(1000 ms, RTT / 2 + 250 ms)
requestTimestamp = serverTimeAtReceive
                   + (currentMonotonic - receiveMono)
                   - safetyMargin
```

The result is written in the exact millisecond UTC format required by the protocol. After a successful synchronization the client MUST NOT use the current system date and time directly for this computation. A wall clock change therefore does not by itself shift the authentication timestamps being created. Its detection enters the recovery decision in the serial connected loop described below.

In the serial connected loop `VpnEngine::runNetworkThread`, the network worker first performs the data cycle and evaluates its result. On a `data` error it handles the error and possible recovery and no longer proceeds to the time refresh check in the same iteration. After a successful data cycle it checks whether the snapshot is missing, whether at least `timeSyncIntervalSeconds` has elapsed since its `synchronisedAtMonoMs`, or whether `TimeSync::systemClockChanged` detects a wall clock change. If so, it serially performs a new `auth-none` `health`. The period is therefore measured from the last successfully accepted snapshot, not from the last unsuccessful attempt. The default 300 s is neither an expiry of the estimate nor a deadline for stopping the VPN.

Wall clock detection compares the current system UTC time with its expected progression since the snapshot, with a default tolerance of 2000 ms. It is performed at the stated place of the connected loop; it does not provide event priority before each authenticated request. The synchronization `health` does not overlap a `data` request of the same VPN context. Isolated diagnostic health/info requests may run concurrently with the VPN data.

After a refresh `health` finishes, `lastHealthVerified` is set to `yes` on success and to `no` on failure. Only complete success replaces the whole verified time snapshot. An invalid, incomplete or cryptographically unverified response, or an error in creating the candidate, must not change the previous snapshot. A failure of this `health` alone starts neither recovery nor its backoff. The next iteration continues with the data cycle using the previous snapshot. If the refresh condition still holds in the following check, it tries another `health`. Recovery after a data request error is a separate path. A partially computed RTT, timestamp or offset is not published. The log MUST NOT contain request timestamps, the exact time offset, keys, HMAC or GCM tags or whole requests or responses; it may state only safe status information, for example that synchronization succeeded, failed or is waiting for a retry.

On Android, both `monotonicMs` and `leaseMonotonicMs` read the `CLOCK_BOOTTIME` clock, which runs even while the device sleeps, and `systemUtcMs` reads `CLOCK_REALTIME`. The timestamp calculation and the wall clock change detection do not change, but the monotonic progression includes the sleep time: the first request after wake-up carries the current timestamp and sleep is not evaluated as a shift of the system clock. The consequences for soft recovery, recovery and queue expiration are described in the section [HTTP transport, cryptography and clocks on Android](#http-transport-kryptografie-a-hodiny-na-androidu).

## Outbound packet flow and request scheduling

The virtual interface delivers complete IPv4 packets. Before enqueueing, the input worker must perform full structural validation according to the following subsection. The inner source must exactly match the local virtual IP and the inner destination must be a valid VPN IP with an existing `communicationContract`; the selection of the queue and of the payload key is therefore always based on the same ordered pair `(local IP, inner destination)`. A packet destined for the own virtual IP, a packet with an invalid header or a packet without a valid contract is not sent through the relay; the drop is logged only in aggregate by reason and destination.

The outbound per-peer queue is accounted by the destination VPN address of the packet. If inserting a new packet would violate the global `maxOutboundQueueBytes` or the logical per-peer reservation, the input worker drops only this new packet. It MUST NOT remove or reorder already enqueued packets because of it. The drop is recorded in aggregate by a stable safe reason and the destination peer, without packet content, keys, tags, ciphertext or other sensitive values.

For each request the network worker selects only a request-sized prefix of the queues. One data element belongs to exactly one ordered pair `src`, `dst` and carries a batch of packets only for this destination. The binary plaintext, byte order and validation rules are normatively defined in `protocol.md`. The network worker encrypts it with AES-256-GCM using the corresponding `PAYLOAD_KEY` and creates the normative `data` line.

### Full validation of inner IPv4 packets

The client considers an IPv4 packet valid only if it has at least 20 bytes, the first nibble indicates version 4, `IHL` is at least 5 and the header length does not exceed the buffer length. The `total length` field must be at least as large as the header length and must exactly equal the length of the whole buffer; the client must not accept trailing or missing bytes. The IPv4 header checksum must be valid. Before reading each field the implementation verifies its bounds and must not perform allocation or pointer arithmetic from unverified values.

The client does not reassemble fragments and does not interpret them as an incomplete packet. A valid IPv4 fragment may pass as a separate whole packet if it satisfies the structural check above and the check of inner addresses. Fragments must never bypass the address binding or create their own reassembly state.

When sending, the inner source must be identical to the local virtual IP and the inner destination identical to the destination of the contract into whose queue the packet was enqueued. After receiving, the inner source must be identical to `src` of the data line and the inner destination identical to the local virtual IP, which is at the same time `dst` of the data line. The check is performed after successful AES-GCM decryption and unpacking of the batch, but before any packet is inserted into the inbound queue or written to the tunnel. If even a single packet does not comply, the whole batch is invalid: the client drops it, passes on none of its packets and records the error only in aggregate.

### Polling interval

The approved maximum of the regular polling interval remains **5000 ms (5 s)**; the lower bound is 20 ms. After a verified `info` response, the current Windows runtime uses these bounds in `NetworkWorker::nextPollDelayMs`:

```text
low = max(20, minDataPollIntervalMs)
high = min(5000, maxDataPollIntervalMs)
```

After a VPN packet is actually handed over to the transport, or after a fully verified VPN packet is accepted into the incoming queue, the runtime restores the minimum and the whole fast window of **5000 ms** measured in monotonic time. Empty data exchanges before the boundary keep the minimum. The first successful empty exchange completed at or after the boundary doubles the interval; further empty exchanges continue with saturation at `high`. With 50/3200 ms the sequence is 100, 200, 400, 800, 1600, 3200 ms. Historical counters, an empty HTTP response, health, info and time synchronization do not restore the window. A deferred but actually handed-over TX counts as activity, mere queueing does not. The decisive moment is the completion of the data exchange before a subsequent health. A new data session, including recovery, gets its own whole window only after the bootstrap; a teardown discards the timing state.

Both the standard and the extended verified info must have a positive minimum, a maximum of at least the minimum and a non-empty intersection with the local range 20–5000 ms. Unusable bounds are rejected before publication. When the bounds change, the moment of the last packet is preserved, the interval is clamped into the new intersection and the new minimum is used during the fast window. A server maximum above 5000 ms is limited by the stricter local maximum. This correction of the bounds does not introduce the planned pre-poll backpressure.

The network worker polls even when the outbound queues are empty. The duration of a request, including a possible timeout, can extend the actual spacing between starts; the client does not open a parallel request because of it. The maximum of the regular interval is not an obligation to send data at least once every 5 s during a capacity blockage. The planned protection will be able to skip several intervals until capacity is freed. It is not yet wired into the runtime and can be marked as delivered only after B05 is implemented and accepted. Backpressure remains the last separate implementation block.

On Android the interval bounds do not change. The client holds no permanent wakelock (R6), so with the screen off and in Doze mode the system may extend the actual polling spacing and packet delivery. The measurement of this behavior is NOT RUN, see [VpnService, service and lifecycle](#vpnservice-služba-a-životní-cyklus).

On Windows, each actually started `data` poll is counted exactly once, at the moment its complete serialized body is handed over to the transport. At the same time it is classified into exactly one category: `empty` if it contains no outbound `data` line, or `withPayload` if it contains at least one outbound `data` line. The mandatory `auth-full` line alone does not constitute a payload. The empty authenticated poll used in the bootstrap check of `ACCESS_KEY` is therefore counted as `empty`. In every internally consistent snapshot, `dataPollsTotal = dataPollsEmpty + dataPollsWithPayload` MUST hold.

### Size-aware and fair scheduling

The worker uses the budget `maxRequestBodyBytes - 1024`. 1 KiB is a fixed reserve above the expected serialization overhead. It also respects `maxDataRecordsPerRequest` from the verified `info` response, i.e. the highest number of outbound `data` records in one request. The count bound is an additional limit and does not replace exact measurement of the body in bytes. The final check always measures the actually assembled body in bytes. If a packet, or the data element created from it, at the head of a sub-bucket FIFO cannot be inserted into the current batch but would fit into a separate otherwise empty valid request, it stays at the head of this FIFO queue for the next request.

If a packet or data element at the head of a sub-bucket FIFO does not fit even into a separate otherwise empty valid request after counting all exact overhead bytes of encryption, encoding, NDJSON and the authentication line, the network worker atomically removes it from the head of the queue and drops it permanently. This removal MUST NOT change the mutual FIFO order of the remaining packets. The client records the drop in aggregate by reason and destination; it MUST NOT write the packet content, keys, tags, ciphertext or other sensitive values to the log. The tunnel MTU and the configured or derived maximum size of a data element are preventive limits, but they do not replace this mandatory runtime decision and the exact measurement of the actually assembled request.

Selection preserves the round-robin order of peers. The first pass tries to add a packet of each peer within the limits of record count and bytes; further passes fill in already created records. After a request the starting peer is advanced. One data record contains only one peer, but it may combine several of its sub-buckets.

Inside a peer both consumers use the same byte-based Deficit Round Robin implementation. Each non-empty bucket gets the same quantum derived from the current maximum tunnel packet length, currently `65535` bytes. An in-progress visit continues across individual calls and requests without adding a new quantum. The actual length of the selected packet is subtracted from the deficit. An insufficient deficit is carried over to the next round; an empty bucket resets it. A single active bucket can use the available transfer budget without waiting. The inbound worker performs at most one send per peer per outer pass, while continuing the in-progress DRR visit inside.

Expiry, the size decision and removal form one atomic operation. A bucket whose head does not fit into the rest of the request is blocked only for this request. The other buckets are still tried, and the blocked one gets no further credit during the same request. A permanently oversized packet is dropped with `oversized_for_request` and selection continues. An unsuccessful write to the tunnel definitively consumes the selected packet, records the existing `tunnel_stopped` and writeFailures, and on `tunnel_io_failed` terminates the worker without an endless retry.

These rules describe the current outbound scheduling. The maximum of regular polling remains 5 s. Deferring polling in advance according to the capacity and reservations of the inbound queues, i.e. the planned pre-poll admission backpressure, is not yet wired into the runtime. Its description in the section Data reception represents a future requirement. The current limits of the outbound request and the admission of individual received packets do not prove its delivery.

## Data reception

The following full processing is mandatory for the normal bootstrap, recovery and operational polling, with the exception of the explicitly planned protection in item 7. The only separate diagnostic path is `wizard-check-access` in ProbeClient according to the general diagnostic exception of `protocol.md` 9.5. After complete verification of the envelope and of a zero result, it discards all payloads without GCM and without any use, and does not change the tunnel, queues, time, bootstrap checkpoints or operating counters.

The response to `data` is NDJSON: zero or more `data` lines, exactly one `data-result` and a final `data-mac`.

1. The transport first continuously applies `maxResponseBodyBytes` and `responseTimeoutSeconds`. The NDJSON parser then continuously applies `maxNdjsonLineBytes`, even before base64 decoding of a line that is too long, counts the lines of type `data` and rejects the whole response as soon as their number exceeds `maxDataRecordsPerResponse`; it must not process the exceeding line cryptographically before rejecting it. The client then verifies the structure of the response, `data-result` and the final `data-mac`. The latter protects the count, order and completeness of the data lines.
2. For each line it first verifies that `dst` is its local virtual IP. A foreign line is dropped even before the payload key is selected.
3. It looks up the contract by the exact pair `src`, `dst`. If none exists, it drops the line and logs it in aggregate.
4. It verifies canonical base64url and the lengths of the IV and tag, and performs AES-GCM decryption with the corresponding `PAYLOAD_KEY` and the normative AAD. An invalid GCM tag means dropping only the given line.
5. It verifies the format of the binary batch: the count header, the length table, the exact count and the boundaries of the raw bytes. It must not pass on a partially unpacked or unverified batch.
6. For each unpacked packet it performs full IPv4 validation. In addition it requires that its inner source exactly matches `src` of the data line and its inner destination the local virtual IP, i.e. `dst` of the data line. If even a single packet does not comply, it drops the whole batch before inserting any of its packets into the inbound queue.
7. **Planned, not yet delivered:** the pre-poll protection is to assess, before regular polling, both the global space `maxInboundQueueBytes` and the logical reservations of possible source peers, and to defer polling when capacity is insufficient. The current helper `DirectionQueues::canAdmitAnotherPacket` has no runtime call site. The helper uses the new bucket reservations including held bytes and cleans up expirations before the estimate. It is a conservative estimate for an unknown peer and flow. Its connection to the runtime remains a separate future backpressure block. The preliminary check is neither a reservation for the whole response nor a guarantee of losslessness. The runtime admission of each received packet according to item 8 remains delivered and mandatory.
8. The inbound per-peer queue is accounted by `src` of the data line. Before a final rejection it cleans up available expired prefixes. If the insertion would still violate the global `maxInboundQueueBytes`, the peer or the sub-bucket reservations, the client drops only this new packet. It MUST NOT remove fresh packets or reorder the FIFO inside a sub-bucket, and it records the drop in aggregate by a safe reason and the source peer, without packet content or sensitive values.
9. Valid packets are classified and enqueued in batch order into the respective sub-buckets. The output worker takes them sequentially according to the shared DRR and peer rotation. It preserves FIFO inside a bucket, not a common order across all flows of the original batch.

The protocol is at-most-once on the server buffer. A lost HTTP response or a crash after takeover can mean the loss of a batch; the client must not pretend guaranteed delivery. The default value `65535` for `maxDataRecordsPerResponse` is a generous client-side compromise without a protocol change. The user may lower the limit, but this can cause the rejection of a response containing batches that the server has already atomically picked up and removed from the buffer. Application layers above the VPN can use their own retransmissions.

## Security model and accepted risks

- The relay server has no payload keys and cannot decrypt the IP content; the confidentiality and integrity of a single payload are ensured by AES-256-GCM between the clients.
- `health` authenticates the server time and the public fields using `SERVER_SECRET`; `info` and `data` require exact protocol authentication.
- HTTP remains an intentionally supported operating mode. We are aware that an active attacker can replay a captured valid poll within the time window, pick up the ciphertext from the victim's inbound queue and irrecoverably remove it from the relay, even though without the payload key they cannot read the plaintext. We knowingly accept this risk of a replay attack and the related loss of availability; the client will be implemented with HTTP support and without a mechanism that would suppress this protocol replay on its own.
- If `trustAnyTlsCertificate` stays `true`, HTTPS does not reliably protect the client against server spoofing at the TLS level. The setting is a knowingly accepted compatibility risk and must be clearly visible in the configuration.
- The control named pipe is intentionally accessible to every local application without verification of the user, group, process or Windows token. Every local process can therefore read the state and diagnostics of the service, request `info` and the complete configuration including its secret values, save a new configuration and send the permitted commands including `connect` and `disconnect`. We knowingly accept this risk of unauthorized local control, configuration changes and disclosure of its data. Validation of the message format, the contract version and the command whitelist are not thereby abolished.
- The protocol does not prevent replay within a valid time window and provides neither exactly-once delivery, acknowledgement nor availability protection. The client is not to create its own replay cache unless the normative specification changes at the same time.
- Keys, tags, ciphertexts, whole requests and internal paths must not be written to logs. The configuration file is to have restricted access permissions as protection against direct reading from the file system; these permissions, however, do not restrict the intentionally public `get-config` and `set-config` over the named pipe.

### Logging and diagnostics

After safe preparation of the storage, the service enables the local text log `phpvpn-service.log` in the `logs` subdirectory of its data directory. The production data directory `PHPVPN` is derived from the system ProgramData through the Windows API; it is not a hard-coded absolute path.

The rotation threshold is **8 MiB (8388608 bytes)**. Before writing the next whole formatted line including its CRLF, the logger attempts rotation if the sum would exceed the threshold. On exact equality it does not rotate. It keeps at most **five historical files** `phpvpn-service.1.log` to `phpvpn-service.5.log`, where `.1.log` is the newest history. Writing and rotation within the process are serialized by a mutex, and the stream is flushed after each line.

This policy is neither a guarantee of successful disk I/O, nor of preserving diagnostics when it fails, nor a fixed bound of the file size for an arbitrarily long single message. The logger neither truncates nor splits a message, so a single formatted line can exceed the threshold even after rotation. A stream flush alone does not guarantee resilience against a power failure.

The logger accepts already safe text and **is not an automatic secret filter**. Callers must respect the ban on sensitive logging, including keys, HMAC/GCM tags, ciphertext, packet content, request timestamps, the exact time offset, whole bodies and internal paths. The exceptions for configuration responses and window fields do not extend this ban to the log.

## Shared HTTP transport

The implemented capacities of IPC connections and queues, the message size and the I/O deadline are defined in [Implementation limits of local control](#implementation-limits-of-local-control). The capacity and retention of receipts and the total Next budget are defined in [Wizard IPC lifetime and limits](#wizard-ipc-lifetime-and-limits). [Configuration file](#configuration-file) defines `responseTimeoutSeconds` in the range 1 to 2147483 seconds and the relation `maxNdjsonLineBytes <= maxResponseBodyBytes`. The fixed limits are 512 KiB of configuration, 4 MiB of encoded IPC, at most eight sessions and a heartbeat/lease of 15/60 s. These implemented limits are not the result of measuring memory, lease timer tolerance or responsiveness under load. Such verification must state the specific scenario, environment and measured results; scenarios not performed remain NOT RUN. Visual and runtime acceptance of the tray is defined in [UX14](tray_UX.md#ux14-ověření-a-velikost). Availability under unlimited flooding is not promised.

The transport and the Windows implementation are a shared part of the VPN, get-info and the Wizard probe. The Windows adapter `WinHttpTransport` uses asynchronous WinHTTP with an explicit owner of the request, the buffers and the callback context. Cancelling a synchronous call by closing the handle from another thread is not permissible. The return of `WinHttpCloseHandle` alone does not mean that the callbacks have ended. Keep the context until the final `WINHTTP_CALLBACK_STATUS_HANDLE_CLOSING` and the completion of all its users. Callbacks must not create a deadlock by waiting on each other. Reference: [Microsoft: WinHttpCloseHandle](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/nf-winhttp-winhttpclosehandle).

The same mechanism must cover Connect during a probe, a global Disconnect with an active operational request, a service stop on restart/update/uninstall, and Cancel, Reset, Escape and X of the Wizard. A race of completion, timeout and multiple cancelling events selects exactly one final result and exactly one close. Replacing a request, reconfiguring the transport and releasing its objects wait for the confirmed terminal state. The asynchronous WinHTTP transport waits for `WINHTTP_CALLBACK_STATUS_HANDLE_CLOSING` with `INFINITE`. Ownership of the context thus stays safe, but a universal upper bound of this wait is not documented. Cancellation latency can be documented only for a specific measured scenario. Prevent the use of a closed handle, double completion and double accounting of bytes read.

Each request gets, when started, a single absolute deadline from the monotonic clock and `responseTimeoutSeconds`; the default value is 30 s. One budget covers DNS, connection, the TLS handshake, sending the request, receiving the headers and the whole body. Neither partial blocks nor the transition to the next transport phase move it. The partial WinHTTP timeouts are supplementary; on their own they do not ensure the total deadline. Reference: [Microsoft: WINHTTP_OPTION_RECEIVE_TIMEOUT](https://learn.microsoft.com/en-us/windows/win32/winhttp/option-flags#winhttp_option_receive_timeout).

After the deadline expires, immediately start a safe cancellation, wait for the confirmed termination and return a timeout, not a late success. The deadline starts the cancellation; it does not define an upper bound of the subsequent wait for the closing callback. Check the conversions of seconds, the multiplication and the sum with the monotonic time, as well as all return values of timeout settings. Serve large supported values by safely splitting the platform waits, or explicitly reject a non-representable value before HTTP. Never wrap it around into a negative or infinite timeout or silently change the meaning of the configuration. The configuration maximum of 2147483 seconds ensures a safe conversion to milliseconds for WinHTTP.

After a timeout and cancel, the transport must be safely reusable. The VPN continues to account exactly once even a partial body and a block over the limit, and closes the accounting before a completed Disconnect. Diagnostics and the probe do not enter the VPN counters. The asynchronous transport preserves the three serial VPN roles and their ownership. The existing [WinHTTP tests](client/tests/unit/test_winhttp_accounting.cpp) contain `WinHttpDeadline.HeadersTlsAndTrickleBodyShareOneAbsoluteBudget`, `WinHttpDeadline.BoundarySettingsNeverBecomeInfinite` and `WinHttpLifecycle.ConcurrentCancellationThenReuse` as well as the accounting of partial and over-limit bodies. The [platform probe](client/tests/platform_plan3_probe.cpp) checks the closing callback and measures cancellation. Neither their existence nor an individual run confirms a universal bound of the OS callback or isolated coverage of all DNS/send phases.

### HTTP detail of an unsuccessful Wizard probe

Only the service operations `url` and `secret` enable `captureWizardHttpDiagnostics`. After a completed `HEADERS_AVAILABLE`, WinHTTP captures the application request and response before the check of the status, content type and size and before the protocol parser. The request uses the actual target URL with the action, the originally sent body and the available system headers. UTF-16 headers provided by WinHTTP are represented in UTF-8. These are not the original packet headers, TLS ciphertext or HTTP/2 frames. An unavailable HTTP version is marked `HTTP/?`. The origin of the headers is explicit, and their unavailability alone does not change a success into an error. Available response trailers are inserted after the natural EOF as a labelled group before the body, without additional network reads.

Before each exchange the probe discards the previous candidate. A successful `health` does not remain as the detail of a later `info` failure. Diagnostics belong only to a terminal error in processing an actually received response, including an unsuccessful HTTP status, parser, correlation and cryptography. The URL step still performs only a syntactic `health(false)`. DNS, TCP, TLS, timeout and cancellation do not publish diagnostics. `data`, the access step, regular operation and Show Server Info do not enable capture. The order of calls, cryptography, retries, timeouts, the parser body limit and the accounting of received bytes do not change.

The limit is computed separately over the bytes of the whole application message, including the start line, the headers, the empty line and the body. Up to and including 65536 bytes the prefix is the whole content and the suffix is empty. Above this bound the prefix is exactly the first 64512 bytes and the suffix exactly the last 1024 bytes. The separator is exactly `\r\n...\r\n...\r\n...\r\n...\r\n`, i.e. four separate dot lines and 22 ASCII bytes. It applies even when a single byte is omitted, without overlap. The collector holds only a bounded beginning, end and a uint64 counter; it does not create a second full copy of the body. For a response not read to the end, the size means the actually available content and the tab reports `Incomplete response: size refers to received content.`

In the first two steps, on such an error a red `Error detail` button appears. In the URL step it is immediately to the left of Verify, in the secret step immediately to the right of Back, with the standard spacing of 8 DIP. It opens the owned `Error detail` window with tabs exactly `Request` and `Response`, the shared tab renderer of Show Server Info and two read-only multiline EDIT controls. The window has no footer or OK/Cancel and is closed with X. The text remains selectable and copyable; the tabs preserve the selection and scroll position. The content is never interpreted as HTML or JavaScript.

The tab states `Original size` in KiB to two decimal places, with a decimal point and integer rounding without overflow. Truncation has a separate note outside the HTTP text box. Each byte of an invalid or incomplete UTF-8 sequence, NUL, C0 except TAB/CR/LF, and DEL is displayed as `\xHH`. Valid UTF-8 text and line endings are preserved. The prefix and suffix are decoded separately, and bytes from the hidden gap are never filled in. The use of the escape projection is announced by the tab. At most 65536 selected source bytes thus produce at most 262166 UTF-16 units including the separator.

## Management of the stored configuration

### Bounded reading, UTF-8 and snapshots

Introduce `ConfigAvailability = missing | unreadable | encoding_error | too_large | invalid | repairable | valid`. An unavailable service is a separate UI state and must not be presented as missing. `unreadable` means an access or read error, `encoding_error` means read bytes with an unsupported or corrupted encoding, and `too_large` means an exceeded read limit. `invalid` and `repairable` are determined only after a successful bounded read and UTF-8 verification.

`StoredConfigSnapshot` contains the availability, a safe reason code, an opaque `revisionToken`, the internal file identity and, for completely read content, the SHA-256 of the exact input bytes. For valid UTF-8 text within the limit it keeps the actual text for the editor even for invalid JSON, and for valid/repairable additionally the DOM for the Wizard. When reading, size or encoding is rejected, it provides neither the editor text nor the DOM, and an incomplete hash must not be presented as a content revision. The token serves to identify the snapshot and a confirmed publication, not to reject a stale Save/Finish. It must not be derived only from mtime, size or `ClientConfig::generation`.

A one-off read of the configuration has the limit `maxConfigFileBytes = 512 KiB` (524288 bytes), including a possible BOM. Enforce the limit in the file backend before allocation according to the declared size and continuously while reading. Even if the file grows, read at most the limit plus one detection byte; reject larger content as `config_too_large` without reading, hashing or parsing it completely. Use the same limit for the resulting document before Save/Finish/create-if-missing. The choice leaves room even for the worst-case sixfold JSON escaping of the text under the 4MiB IPC limit; the actual encoded envelope is still checked separately. Slow reading runs outside the capacity of get-status, Disconnect and service stop. There is no periodic refresh, watcher or cache requiring repeated disk access.

`config.json` must be valid, unambiguously decodable UTF-8 text. The strict decoder rejects invalid continuation bytes, incomplete and overlong sequences, surrogate code points and values outside Unicode. UTF-16/UTF-32, including their BOM, and any other unsupported encoding return `config_encoding_error`. No character replacement, encoding guessing, Unicode normalization or base64 transfer of defective bytes. Valid UTF-8 is the only interpretation of the input; the original encoding of byte-identical text is not guessed. U+0000 alone is a valid UTF-8 character, so when it occurs directly in the text it causes invalid JSON, not an encoding error. Because a Win32 EDIT cannot display an embedded NUL, this rare faulty document is displayed in the editor as an explicitly marked JSON string literal of the whole text. The conversion is lossless, and Save strictly decodes it before full validation. Unchanged text is passed by the editor to the model from the original bytes, including the original line endings.

The only input normalization is the removal of one optional UTF-8 BOM `EF BB BF` at offset 0 before parsing and handing the text to the editor. A BOM elsewhere or a repeated BOM is neither accepted as an encoding mark nor removed. U+FEFF inside a JSON string is a character of the value, not a BOM, and is preserved. Unchanged other characters, whitespace and line endings are transferred exactly. Save/Finish and the template write UTF-8 without BOM. Merely opening or Cancel does not change the original bytes on disk. Strict UTF-8/UTF-16 conversions in the tray must not lose characters or repair invalid sequences.

Proposed internal interfaces:

```cpp
Result<StoredConfigSnapshot> ConfigStore::refresh();
StoredConfigSummary ConfigStore::summary() const;
Result<WizardDocument> analyzeWizardDocument(std::string_view json);
Result<std::string> buildWizardDocument(
    const WizardDocument& original,
    WizardMode mode,
    const WizardFields& fields,
    bool createDefaultContracts);
Result<CommitReceipt> ConfigStore::commit(
    std::string_view completeValidatedJson,
    const CommitId& commitId);
Result<EditorDocument> ConfigStore::readForEditing();
Result<EditorDocument> ConfigStore::createDefaultIfMissing();
std::string makeDefaultEditorDocument();
```

`CommitReceipt` contains `commitId`, the new revision and the confirmed state. On an indeterminate result from the operating system, the file backend must claim neither success nor a safe non-write without verifying the actual state.

### Repairable document

A repairable document is an otherwise valid configuration that is missing only `virtualIp`, `accessKey` or both fields. A wrong type, an invalid value or any other error means invalid and in the Wizard requires Reset or a repair through the editor. Do not weaken `parseAndValidateConfig`. A separate analysis must prove that all errors found are exclusively the absence of the two permitted fields. It is not sufficient to catch the first validator error and declare the rest valid.

The shared validation of structure, known members, URL, secret, TLS, canonical CIDR `/24` to `/29`, runtime limits and contracts also applies to repair. In analysis mode the check of a missing IP/key and the binding of contracts to a not yet known own IP can be skipped. This binding is mandatorily verified when the IP is filled in and again at Finish. A missing identity never turns an unsupported CIDR into repairable. Typed incomplete data must not arise as a falsely valid `ClientConfig` with a dummy key.

`masterSetup` accepts three optional strict JSON booleans: `useDefaultServerSecretInWizard`, `autoDetectIpAddressInWizard` and `useDefaultAccessKeyInWizard`. The complete editor template and a new/reset Wizard draft use false for `useDefaultServerSecretInWizard`, so that the secret field is editable after installation, and true for both remaining flags. When absent, the secret flag is derived from an exact match with `CHANGE_THIS_SERVER_SECRET`, automatic IP as false with a valid stored IP and true with a missing IP, and the default key as false with a valid stored key and true when it is absent. Each flag is derived separately. An explicit false takes precedence even in repair without a specific value; the field then stays empty and editable. Another type, a duplicate or an unknown member is an error. The metadata is changed only by the Wizard; regular runtime uses exclusively the stored concrete values of the secret, IP and key.

### Value preservation and Wizard Reset

In edit/repair mode, patch the four concrete values and the three `InWizard` flags in the original DOM and, with an effective true, additively fill in missing contracts. Do not reconstruct the document from `ClientConfig`. The values, types and presence of other members are preserved; changes to whitespace and JSON formatting are allowed.

Wizard Reset creates a new draft with the URL `https://change-this-server-url.invalid` (the shared placeholder `kPlaceholderServerUrl`), the secret `CHANGE_THIS_SERVER_SECRET`, `trustAnyTlsCertificate=true`, `vpnCidr=10.99.99.0/24`, the current runtime defaults, three true InWizard flags and a newly decided set of contracts. Runtime can be omitted in the JSON and the shared defaults used. After Reset, the original content is used neither for merging nor as a write condition. The different complete editor default is defined in the section Edit Config: actual content, creation and Reset.

With unreadable, a new draft can be filled in after Reset, but Finish must not bypass the file access error. If at publication the service still cannot safely work with the current target and recovery after the error, it rejects the write and guides the user to repair access. It does not require a match with the revision at opening. Reset neither repairs the ACL nor redirects the path.

### One-off check after an action and menu reactions

Neither the tray start, its periodic timer nor merely opening the menu reads the configuration. The five-second tray timer continues to read only the in-memory `get-status`. No periodic five-second `get-config-state`, no preliminary menu check, no direct `exists` on ProgramData and no automatic disk refresh after Save/Finish. The menu does not disable configuration-dependent items based on an old or unknown file state. Connect/Disconnect toggles according to the in-memory VPN state.

After a specific action is chosen, the service reads the current file once within the bounds of the section Bounded reading, UTF-8 and snapshots and uses this snapshot both for the check and for performing the action. Connect, Show Info, Statistics and Contracts require a valid snapshot; otherwise they show a specific error or guidance only after the click. Connect and get-info have the check directly in the command handler, Edit Config and manual Contracts in a single `get-config-document`, and the Wizard in `wizard-open`. For a chosen Statistics, a one-off `get-config-state` can be used, whose result directly decides whether the window opens, without a second read of the configuration. Merely opening the menu sends none of these commands. Another separate action later reads a new snapshot; no stored revision blocks Save/Finish.

The editor accepts syntactically invalid JSON only as valid UTF-8 text. `get-config` and get-info must not return or use an old stored cache after finding an invalid disk. An active connection keeps its already accepted snapshot. Disconnect does not read the configuration at all and uses the independent tray control path according to the rules of the independent Disconnect.

All configuration-dependent items remain clickable. The table describes the result of handling after a click, not preliminary disabling of items based on the file:

| State found during the action | Connect with inactive VPN | Disconnect with active VPN | Wizard | Edit Config | Contracts | Show Info / Statistics |
|---|---|---|---|---|---|---|
| valid | perform Connect | send without reading the file | edit | actual UTF-8 text | regular window | perform the action |
| repairable / invalid JSON in valid UTF-8 | error and repair guidance | send without reading the file | repair or Reset offer | actual UTF-8 text including invalid JSON | explanation without a window | error and repair guidance |
| unreadable | access error | send without reading the file | error and Reset offer according to the section Value preservation and Wizard Reset | access error, no substitute | explanation without a window | access error |
| encoding_error | encoding error | send without reading the file | error and Reset offer | encoding error, no document | explanation without a window | encoding error |
| too_large | size error | send without reading the file | error and Reset offer | size error, no document | explanation without a window | size error |
| missing | guidance to create, no Connect | send without reading the file | create | Yes/No to create, after Yes write and editor | warning without a window | guidance to create |
| service unavailable | specific service/IPC error | attempt to send, visible error on failure | explanation, without checks and Finish | explanation of unavailability | explanation of unavailability | explanation of unavailability |

A not yet known configuration is not missing; it is evaluated only during the action. Exit and About always remain available; About only shows the client version, the MIT license and the copyright without IPC ([tray_UX.md](tray_UX.md)). Open Statistics continue to use the in-memory get-status; they do not watch file changes in the background and do not reset the cache because of them. Choosing Statistics again performs the one-off check again. Save fully validates the submitted document including UTF-8 and size, and the safety of publication, not the content validity or revision match of the existing file. It may thus repair invalid content and also save an older draft according to the rule of the last successful publication.

### Atomic write: the last successful save wins

All service writes, including the startup creation, set-config, Finish and the confirmed creation of the default file from the editor, go through a single ConfigStore and the same serialization gate. Between Save and Finish, the order of successful publication of whole documents decides. A later Save of an old editor may overwrite Finish, and a later Finish of an open Wizard may overwrite Save, and likewise two sessions of the same type. An old revision by itself causes no conflict, re-opening, overwrite confirmation or automatic merging. A foreign save does not invalidate the draft and its evidence merely because the stored revision changed. The Wizard assembles the whole document from its original and draft according to edit/repair/reset, not from a foreign document saved in the meantime.

The Finish procedure:

1. Verify the live session, the match of the service instance, the connection epoch, the network evidence and exactly seven fields. Assemble the resulting document and run the full validator even before creating the temp file.
2. Enter the write serialization gate. Determine the current existence and safe identity of the target and of the directory for publication and recovery after an error. Do not require content, existence or a revision identical to those at the opening of the window. Save/Finish can save even after a manual edit or a regular delete/recreate of the target, as long as the current publication operation is safe.
3. A new file and temporary files may be created only in the authoritative protected directory during an approved save operation: Finish, a validated set-config/Save or a confirmed create-if-missing of the editor. The temporary name contains a random ID and is created with CREATE_NEW, never as a shared `config.json.tmp` with truncation. Forbid reparse redirection of the target and an unexpected identity of the directory. Set the canonical ACL with Full Control only for SYSTEM/Administrators and Read & Execute for Users before the configuration bytes are written.
4. Write the whole body, verify the byte count and perform `FlushFileBuffers` on the actual file handle. `ostream::flush` alone is not sufficient for this purpose. See [Microsoft: FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).
5. Without network work, verify the current publication conditions. Save/Finish have no create-only condition derived from opening the window. Choose an atomic publication for the current state of the target and safely resolve a change of its existence during publication. Only the explicit `createDefaultIfMissing` must not overwrite a file created in the meantime; in that case it reads the actual current content or returns a specific error. For an existing target, use the platform replace with a backup in the same directory, checking the ACL and the actual result. Do not use `REPLACEFILE_WRITE_THROUGH` as a guarantee, because it is not supported. See [Microsoft: ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).
6. Successful publication is the commit point. Only then publish the new stored generation in memory and the receipt. The active configuration does not change by this. After the commit, a regular cancelled must no longer be returned as if the disk had remained unchanged.
7. On error, remove only the own temp file, never a foreign `config.json`. For partial errors of the replacement API, verify the location of the original file and the backup, and if necessary safely restore the original target. Do not blindly delete the backup or a foreign new file. A restart must be able to recognize its own unfinished commit from a minimal record without keys and must not automatically complete a Finish that has not yet been performed.

Atomic publication and protection against overwriting older content are different properties. The second one is not required; the last save may replace content changes made in the meantime. Serialization of the supported IPC writers and the safety of file operations remain mandatory, even with direct administrator intervention during the publication section. Tests must prove that there is no truncation caused by the service, no wrong ACL, no deletion of the wrong target during rollback and no false claim that nothing was written. Do not require compare-and-swap against the original content or an oplock merely to prevent an approved overwrite. The contract consists of the publication procedure in this section and [bounded reading, UTF-8 and snapshots](#bounded-reading-utf-8-and-snapshots). The existing [ConfigStore tests](client/tests/unit/test_config_store.cpp) cover revisions, complete serialized saves and create-if-missing; the [ConfigFiles tests](client/tests/unit/test_config_files_win.cpp) cover identities, reparse, write/flush/publication errors, crash boundaries and concurrent creation. Real Windows file scenarios require a corresponding NTFS environment and token; without being performed they are recorded as NOT RUN. Users intentionally have the right to read, including backups, not the right to write.

Backups have the same access restrictions as the configuration. Keep at most the last own known version; do not create an unlimited history of secrets. The backup serves safe recovery after an error, not revision-based blocking of Save/Finish. A power failure and a media failure have their own recovery result; recovery on a physically non-functional disk cannot be promised.

Android platform deviation: POSIX platforms back up the original file with the hard link `config.previous` (section [Linux](#linux)), but on Android SELinux forbids the application hard links in its data. Android therefore publishes with the `exchange` strategy, i.e. by swapping the names with `renameat2(RENAME_EXCHANGE)` and then moving the original inode to `config.previous`, with the same journal and one additional intermediate recovery state. The procedure is described in the section [Configuration file in private storage](#konfigurační-soubor-v-soukromém-úložišti). The guarantees of this section apply unchanged.

### Edit Config: actual content, creation and Reset

The existing `get-config-document` is used by Edit Config and by the manual Communication contracts. A single read of the fixed path returns the availability and the actual document from the same snapshot. Contracts opens the model only for a valid document according to the section Communication contracts: native editor and saving. Edit Config may open the actual UTF-8 text within the bounds of the section Bounded reading, UTF-8 and snapshots even with missing mandatory fields, another configuration error or syntactically invalid JSON. The only normalization is the removal of the optional leading BOM. Invalid JSON is replaced neither by the default nor by an old cache. The original direct `get-config` remains for valid configuration JSON; an invalid document is made available only by the new text envelope. Unreadability of an existing file is an access error. Invalid UTF-8 or another encoding raises a specific encoding error without a document and without character replacement, guessing or a base64 fallback. An oversized file raises a size error. None of these errors starts the creation of a substitute.

When the file genuinely does not exist, Edit Config shows Yes/No with the actually evaluated absolute path. Yes sends `create-default-config`; the service fully validates the shared template and atomically creates the missing file according to the section Atomic write: the last successful save wins. The editor opens the actual result of the operation. If the target was created in the meantime, it must not be overwritten by the template. No creates no file and opens no new document. Cancel of the editor after a confirmed creation does not delete the already created file.

On Windows the configuration directory MUST have SYSTEM or Administrators as the owner and a protected DACL. SYSTEM and Administrators MUST have effective Full Control. BUILTIN\Users have inherited Read & Execute on the whole data tree, on all current and future files and subdirectories. A regular local user can, without UAC, open the folder, list its content, traverse it and read or copy any file. Direct writing, replacing, creating, deleting, renaming, changing the ACL or the owner are forbidden for a regular user. Configuration changes still go through Edit Config, the Configuration Wizard or the supported public IPC, and the service always validates and atomically publishes the result. Directly saving the original file from an unprivileged editor remains forbidden.

This is a deliberate compromise of local confidentiality: readable are the whole `config.json` including keys, the hard-link backup `config.previous` including historical and removed keys, in-progress `config.stage.*.tmp`, `config.publish-journal`, `ownership.json` and its temporary files, logs and other current and future descendants. The public IPC already exposes the current configuration document; the broader file system access additionally reveals historical and not yet confirmed configurations and internal metadata. The user explicitly accepts this scope. This Users read policy also applies to the history at every service start; it is not a temporary exception only for the current configuration. Read-only access grants no direct write and does not bypass validation, serialization and safe atomic publication by the service. The hard-link backup and its shared ACL are preserved, as are the journal, identities and recovery.

Validation assesses the security properties of the permissions, not the exact number of ACEs. An additional allow ACE may grant at most a safe Read & Execute, including safe inheritance. It must not restrict the full access of SYSTEM/Administrators. Unprivileged rights to write, create, delete and change security, including inherited and inherit-only ACEs, raise a fail-closed error at runtime. At every start the privileged service creates a missing directory and checks and, if needed, restores the canonical ACL of the existing data tree, including removing an explicit user Full Control added by Explorer, without changing the configuration bytes. An identical canonical descriptor is not rewritten. This is not a one-off migration. Reading and copying do not change the ACL and are not an error. A mere deletion of `config.json` by an administrator with the permissions preserved does not prevent a new confirmed creation with the same running service, even with a remaining confirmed publication journal and backup.

The startup normalization rejects reparse points and hard links with a name outside the data tree, without following the link or repairing the ACL of such a file. A regular internal hard link remains supported. It keeps ancestors and objects pinned against renaming and checks their identities and the number of internal names before and after the repair. The user knowingly accepts a narrow concurrent exception valid at any start: Windows allows adding a new external hard link even to a pinned inode. If this new name is created exactly during the actual ACL repair, it shares the repaired ACL of the same already checked file. A subsequently detected change of the link count stops initialization. This is not an opportunity to substitute a different external file for a pinned name, nor a permission for unprivileged writing.

A successfully read directory descriptor that does not match this policy raises `config_directory_security_invalid` during backend construction, recovery and publication. An API failure while reading the descriptor remains `config_unreadable` and is not evidence of a permission change. The missing state means only the absence of the file. Permissions are checked again on write even after a successful read, because they can change during the confirmation dialog.

For `config_directory_security_invalid` the tray shows the authoritative path from the service and English guidance to ask an administrator to restart the PHPVPN service. The service start restores the expected directory permissions. A restart interrupts an active VPN and, with a missing target, attempts to create the default. After a successful start, check the actual file through Edit Config; another Yes may not be needed. If another recovery or publication error appears, it is handled separately. Neither the journal nor the backup is deleted preventively. The tray performs no restart and no automatic ACL change; Reset does not repair the ACL. For this error it offers neither the Wizard nor copying the configuration as a remedy. File errors outside the network steps of the Wizard contain no Next advice. Other write errors offer checking the error and the current file and explicitly invoking the action again after the fix, without automatic retry or a claim that nothing was certainly written.

The Reset button in the editor asks Yes/No to restore the default configuration. Yes replaces only the in-progress text and marks it as changed; No keeps the existing text. The disk changes only after a successful Save with the same full validation as Connect. Cancel, Escape and X with a changed draft first ask for confirmation of discarding. During Save they do not close the editor. These editor rules do not replace Wizard Reset.

Both creation and Reset of the editor use a single factory `makeDefaultEditorDocument` in the shared client code. The service provides the same template through `get-default-config`; the tray does not keep its own copy of the JSON. The Wizard shares the constants and the key derivation algorithm, but keeps its placeholder URL and the optional additive filling in of the candidate set of 13/14 contracts. The complete editor template is:

```json
{
  "masterSetup": {
    "serverSecret": "CHANGE_THIS_SERVER_SECRET",

    "httpHeaders": "Cache-Control: no-cache\r\nPragma: no-cache\r\nUser-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:155.0) Gecko/20100101 Firefox/155.0",

The default `serverUrl` is the placeholder `https://change-this-server-url.invalid` (the constants `kPlaceholderServerUrl` and `kPlaceholderServerHost` in `config.h`): the host is a valid name under the reserved domain `.invalid` (RFC 2606), which never resolves, so the document passes validation and the identity, the contracts and the editor work. The service rejects Connect with it with the code `config_server_url_unset` even before the first network step, and the clients offer the wizard on this code (see Errors and security of the IPC extensions). ## Configuration Wizard

The wizard has four named configuration steps and a conditional step zero for global disconnection. Server URL has a hidden and disabled Back, also after a completed disconnection. The disconnection gate has no Back and cannot be returned to. The service owns loading, saving and all network checks. Before Finish the Wizard must not write the configuration, a backup or a temp JSON. Cancel and Reset preserve the original file byte for byte. A successful confirmed Finish truthfully announces the save, closes the Wizard session and closes the wizard. It does not automatically open Communication contracts and does not connect the VPN. Later manual opening of Communication contracts from the tray menu is a new separate action over the currently stored configuration, not a continuation of the Wizard or a handoff of a specific publication. No IP reservation and no new wire endpoints are introduced.

### Wizard states

`WizardMode = create | edit | repair | reset`. The steps are `disconnectGate`, `serverUrl`, `serverSecret`, `identity`, `contracts`. Besides the step, the model keeps `loading`, `editing`, `checking`, `waitingDisconnect`, `interruptedByConnect`, `sessionExpired`, `committing`, `commitUnknown`, `completed` or `closed`. A stale stored revision has no error state of its own.

Each network step has the result `pending | success | failed`. The results are bound to the exact inputs, not to the fact that the user has already pressed Next once. The first URL step has a visible disabled Back. The sidebar has four informative steps and does not allow skipping. The internal Next event means one manual Verify & continue action, in the disconnection gate Disconnect & continue, or Continue if disconnected/idle is already confirmed.

| Event | Precondition and result |
|---|---|
| opening | load the service, configuration, epoch and a new sessionId. An active VPN leads to disconnectGate, otherwise to serverUrl or to an error requiring Reset. An explicit useDefaultAccessKeyInWizard takes precedence. Only when this metadata is absent is an existing accessKey loaded as an own value with the switch off, and a missing key in a new/reset or repair draft starts in default mode. A match of the key with the algorithmic default does not change this fallback. |
| Next on disconnectGate | The text explains the global impact in advance. Disconnect & continue is the only consent, without a second Yes/No. Send one disconnect and wait for both the actual disconnected and idle, not merely the IPC acceptance. Then move to serverUrl with one wizard-resume. If the VPN is already disconnected/idle, an explicit Continue performs only the resume. The focus of the gate starts on Cancel. |
| Next serverUrl | local validation and check-url. Only success moves to serverSecret. |
| Next serverSecret | check-secret with a new health and info. Only complete success moves to identity and, if applicable, fills in missing suggestions once. |
| Next identity | local validation, contract collision check, warning about message consumption and check-access. Only success moves to contracts. |
| Back | contracts → identity → serverSecret → serverUrl. Keep the draft. Back alone does no network work and no write. The next Next verifies its step again. |
| URL change | invalidate all network results, the verified time, info and suggestions depending on the old server. Do not discard manually entered values. |
| secret/default checkbox change | invalidate the secret and access results, the time and info. |
| IP/Access Key/default checkbox change | invalidate the access result, recompute the collision with the own contract and the preview of the contract count. If **Use default access key** is checked, every user or system change of the IP immediately regenerates the Access Key as well. Checking it from the own-value mode immediately overwrites the text box with the default. Unchecking keeps the currently displayed value and enables the field; it never restores an earlier own value from `config.json`. |
| Reset | safely cancel the own check, after the work ends create a new draft and clear the results. No disk operations and no revision condition for a later Finish. |
| Cancel / Escape / X | outside a commit, cancel the own operation and session, close the window, erase the draft. Do not send Connect or an additional Disconnect. |
| Finish | full service validation and atomic write according to the rule of the last successful publication, without further data polling. During the short commit a successful Cancel cannot be pretended. |
| successful Finish | receipt confirmed → announce the successful save → one wizard-close → close the Wizard. Do not open Communication contracts or any other follow-up window, do not send Connect and do not read further configuration. Loss of the close response cannot reverse a confirmed publication. |
| Finish error | stay on contracts, keep the draft and show a specific remedy. A stale revision alone is not an error and does not trigger an overwrite confirmation. |
| lost Finish response | commitUnknown; an explicit Verify save sends one wizard-get-commit for the original commitId. Do not repeat Finish, do not verify automatically and do not claim that the file was not changed. A confirmed receipt continues with the same single sequence of announcement and close. |
| lease expiry | sessionExpired; stop checks and Finish, announce the end of the session and offer re-opening. Do not revive the old session with a late confirmation; verify the result of an in-progress commit separately. |

Each Next creates one current attempt. A green result and progress are allowed only after the success of this attempt has been delivered to and verified in the tray. An error anywhere in the chain tray → service → server → service → tray ends the attempt, shows a red message on the same step and keeps the texts. Non-delivery within the final time limit is a timeout; other errors have their actual cause. Do not use an earlier success, and do not automatically repeat the start or any part of the check, including health/info and a retry after 401. Another attempt arises exclusively from a new Next and can consume messages again, even if the previous one succeeded on the server.

After an error or timeout, the tray marks the attempt locally as closed and ignores a late success. If work in the service is still running, it requests its cancellation if the operation is known. With a lost start acknowledgement it uses the correlation of the current attempt and cancellation according to the section Configuration and Wizard commands; it does not send the start again. The next Next can start only after confirmed termination of the previous work, or it receives busy. Continuous reading of a still running operation is not a new attempt. Reset and Cancel are available even on a load error, except for the short undecided commit section.

### Local Wizard lifecycle interface for Exit and end of session

WizardWindow provides a non-mutating WizardLifecycleSnapshot: open, dirty, committing, commitUnknown, the generation of the window, session, draft, attempt and operation, the current attemptSequence, connectionEpoch and the original absolute commitDeadlineMs if Finish has already started. The snapshot reads neither IPC nor native text and contains no keys or document. A loaded draft is clean. An accepted edit, toggling an option, Reset or a change of fields by a verified IP suggestion marks the draft dirty and advances its generation. Undo must not restore an old permission to discard. Opening a new window gets a new identity even after the previous instance has ended. Open, Reset and Resume invalidate the local session generation and old results, without changing the service rules for attemptSequence, epochs and evidence.

Finish establishes one absolute monotonic deadline in 15000 ms. The snapshot exposes it even in commitUnknown. Polling, heartbeat, reading the snapshot or an Exit request do not renew it. The new coordinator must asynchronously track the original deadline and the terminal result during committing. approvedDiscard accepts only an exact, still valid snapshot outside committing and outside an ongoing announcement of a confirmed success. After the joint confirmation it cancels the local window without another dialog and without IPC, including Finish, get-commit, configuration reads, retry, Connect, Contracts and Disconnect. It revokes delivery to the existing readers. This path relies on the remote lease for cleanup and is not a rollback of an already accepted publication. The regular interactive Cancel and a confirmed Finish continue to use their own wizard-close.

endSession is a terminal and idempotent interface only for the Wizard participant. WM_QUERYENDSESSION returns TRUE without mutation, WM_ENDSESSION(FALSE) keeps the draft and WM_ENDSESSION(TRUE) calls endSession. This invalidates the generations, revokes delivery to readers, stops the local timer, empties the native fields and undo, releases the draft and closes the window without a dialog, synchronous wizard-close, waiting for IPC, reader join or a deadline. Both WizardReader and WizardStatusReader use the existing separate shared state of CommandReader. The worker holds its own request and endpoint and has no this, WizardWindow or TrayApplication callback. Revocation holds only a short result publication mutex and signals cancel; completion of the I/O and release of the last shared state belong to the worker. Already queued messages have no pointer or result payload and cannot pick up an abandoned operation. Pending Wizard fields and transport buffers are overwritten on a best-effort basis; native text/undo and the original model are released. This is not a guarantee of overwriting all internal copies in the model, the allocator, the OS or the user's clipboard.

The Wizard gate still has a 400 ms status read and at most one unclaimed request. Wizard IPC keeps the 5000 ms budget and the heartbeat of 15 s / lease of 60 s. TrayApplication uses wizardLifecycleSnapshot, approvedDiscardWizard and endWizardSession in the joint coordination described in the section Shared Exit and system end of session. The separate Wizard participant tests are not by themselves proof of a complete application logoff, which has its own isolated broadcast test.

### Foreign Connect and epochs

The service introduces an internal non-negative 64-bit `connectionEpoch`, increased when each new logical Connect is accepted. An idempotent Connect in an active state does not increase the epoch. The epoch is reset only by a new service instance, which has a new `serviceInstanceId`. When the numeric range is exhausted it fails closed, it does not overflow.

The Wizard records the epoch at opening and after a confirmed disconnection. Each check and commit verify the match. This also catches a Connect and Disconnect completed between two UI polls. The event must not be derived only from the current name of the state.

The information text: `A VPN connection was started while setup was open. Your entries are kept, but the checks must be repeated.` Do not state an invented user or process; the public IPC does not track identity.

On interruption, keep the filled-in texts, end the own probe, mark the network results pending and offer the disconnection gate. If at the time of handling the state is already disconnected again, still show the information about the Connect that took place and require the checks to be repeated from serverUrl, but a further unnecessary Disconnect is not needed. After an explicit disconnection and taking over the new epoch, perform all checks again only through individual manual Next actions. The original document of the draft is not switched by a foreign save, and its revision does not block Finish.

The commit guard and the acceptance of Connect have an unambiguous order. A Connect accepted before the commit invalidates the save. A Connect accepted only after the commit loads the newly saved configuration. Neither of these orders may require blocking Connect for the whole duration of the wizard.

## Wizard network steps and data rules

### Server URL

Use the existing `parseServerUrl`: HTTP/HTTPS, without userinfo, query and fragment. Keep support for a different script name and path, because the existing validator and tests accept, for example, `vpn.php` and `relay.php`. The help text recommends the full URL of phpvpn.php; it does not create a new mandatory suffix rule. Reject the placeholder `https://change-this-server-url.invalid` (host `kPlaceholderServerHost`, case-insensitive comparison, any scheme, port and path) in the wizard with the help "Replace change-this-server-url.invalid with your server address." before DNS.

The TLS policy and limits come from the preserved context or from new defaults. Never change `trustAnyTlsCertificate=false` to true just so that the check passes. Do not allow redirects, proxies or automatic transport authentication compared to today's transport.

The probe sends one new `auth-none`. Split ResponseParser into `parseHealthSyntax` and `verifyHealth`, used jointly also by the regular NetworkWorker. The first step verifies the HTTP status, the shape of the response, the status running, the UUID correlation, the time syntax and the canonicity/lengths of the IV and tag. It does not verify the GCM tag, does not accept the server time into TimeSync and does not mark the server as cryptographically verified.

### Server version compatibility

The client communicates only with a server of the same MAJOR version, as specified by section 14 of [protocol.md](protocol.md). The rule and the safe display of the version are in `core/protocol/server_version`; the check is performed by the core in the service, so it applies equally to Windows, Linux and macOS, to the tray and to the CLI:

- Wizard: the Server URL step checks the not yet verified version from `health`, the SERVER_SECRET and IP/Access Key steps check the verified version from `health` and `info`. The error `server_version_incompatible` has the field according to the step, no HTTP status and no HTTP diagnostics. The description names both the client and the server version; the remedy asks for installing a client and a server of the same MAJOR version. In the Server URL step the URL field is highlighted.
- Connect, recovery, the periodic time synchronization `health` and the refresh after 401 check every verified `health` and `info` response; see Recovery and the UX05 catalog.
- `get-info` (`phpvpn info`) and `get-server-info` (Server information) return the IPC error `server_version_incompatible`; instead of the general text, the Server information window shows `The server uses a different major version than this client (X.Y.Z). Server information cannot be loaded.`
- The server version is displayed only as at most 32 characters from `[0-9A-Za-z.+-]`, otherwise as `unrecognised`.

### SERVER_SECRET

The secret checkbox is governed by `useDefaultServerSecretInWizard`, and only when it is absent by an exact match with `CHANGE_THIS_SERVER_SECRET`. True shows this default in a disabled field, false the exact stored value in an editable field. Switching it on overwrites the draft with the default; switching it off keeps the displayed text. Each toggle invalidates the secret/access evidence, and Finish saves both the value and the flag.

Preserve the exact UTF-8 bytes without trimming, case changes or Unicode normalization. The Win32 conversion must not silently terminate the secret at NUL. For existing control characters, use an explicitly marked display as a JSON string literal and strict decoding in this mode; for regular text a plain field. The display of escape sequences must not confuse the literal characters `\n` with an actual line ending. An unchanged value is taken from the original bytes of the model.

Next performs a new health, verifies the GCM, builds a separate TimeSnapshot according to the normative RTT and safety margin, then sends info, verifies the envelope and decrypts. `InfoResponse::clients` is a list of `{Ipv4Address address, int64 lastSeenMs}`. Require the clients array, valid items, canonical addresses, unique addresses and a valid millisecond UTC lastSeen. Unknown fields of the info plaintext continue to be ignored in accordance with the protocol. A statistical time in the future is a valid value and can be the result of a marker; it must not automatically be confused with a missing client.

### IP and Access Key

The IP must be canonical and satisfy `vpnCidr.isValidClientAddress`, i.e. not the network address, the first reserved host address or broadcast. The key must be exactly 64 lowercase hex characters; no automatic lowercasing or whitespace removal.

The original automatic IP suggestion remains in the range `10.99.99.2–.15`. For a repairable file, restrict it to valid client addresses of the preserved CIDR and exclude collisions with existing contracts. If the set is empty, request a manual IP with an explanation of the preserved CIDR. Extending the contract generation rule to another `10.A.B.0/24` does not by itself add a new protocol for automatic IP allocation.

From the verified clients, choose the lowest address of the candidate set that is missing. If all are present, choose the oldest lastSeen, and on a tie the lower IP. The last octet is compared as a number. `clients` is not an authoritative record of free addresses or a reservation. Different client computers may have the same virtual IP; phpvpn does not enforce its uniqueness and the system does not reject such a collision. The UI must truthfully say that the suggestion is not a reservation, that a duplicate is technically permissible and that a possible collision is the responsibility, or rather a configuration error, of the operator. The service itself does not add `ACCESS_KEYS` on the remote server. Separately: the local `virtualIp` must not at the same time remain the key of an own `communicationContract`, because the contract would point to this computer itself.

Below the IP field is **Automatically detect IP address** according to `autoDetectIpAddressInWizard`. With true the IP is disabled and waits for a verified suggestion from the last successful secret check. The suggestion replaces even a non-empty placeholder IP; with false the manual IP is preserved. Without a suggestion, Next on identity does not continue; the UI explains the option to switch off the automatic mode and enter the IP or to return to the secret check. Switching it on uses only a still valid suggestion and does not start HTTP by itself. A change of the URL/secret, Reset, Connect, expiry or resume invalidates the suggestion and the related evidence. Back/Next keeps the options; resume keeps the in-progress values and all options, but requires new checks.

Below the Access Key field is **Use default access key**, initialized from `useDefaultAccessKeyInWizard` with the fallback above only when it is absent. With true the field is disabled and contains `hex2(lastOctet)` repeated 32 times, for example 32×`11` for `.17`. With false the stored value stays editable even when it matches the default. Each actual IP change with true recomputes the key; an invalid IP, including an address outside the CIDR, empties it.

The stored flags always take precedence over derivation. A match of the stored key with the algorithmic default does not by itself activate the default mode. Back/Next keeps the current option and text.

While the checkbox is checked, every IP change, regardless of the source of the change, immediately regenerates the field from the new last octet. This applies to user typing, an IP suggestion from the server `clients`, returning with Back/Next, Reset and any other system update of the model. An invalid or incomplete IP must not create a seemingly valid key or keep the key of the previous IP as the current default. In such an intermediate state the UI shows the field disabled and completes validation only after a valid IP.

After the checkbox is unchecked, the field becomes enabled and the user may edit the currently displayed value, which must still pass the exact validation of 64 lowercase hexadecimal characters. Checking it, without further confirmation, immediately discards any manually entered or originally loaded content and replaces it with the default key from the currently valid IP. Subsequent unchecking keeps the last generated value as the editable initial text and does not restore the original own key from `config.json`. Finish saves both the concrete `accessKey` and `useDefaultAccessKeyInWizard`; the service verifies their consistency and the exact fields in check-access and in Finish.

Before the check is performed, a warning is permanently visible: `Each Verify & continue check may permanently remove waiting messages for this IP, even if no result arrives. Messages are discarded, not delivered to the VPN. Checks are never retried automatically.` The Verify & continue button is explicit consent to this one attempt, without any further mandatory modal confirmation.

Each check-access attempt obtains a fresh verified health and info in its own context, so that long form filling and a change of the system time do not use an old estimate or old server limits. It then performs at most one empty data request. All health requests use auth-none. No automatic retry of any step of the sequence, not even after 401. Another attempt is a new press of Next and starts again with a fresh health. Refreshing the verified time after 401 in the Wizard happens only in this new explicit attempt. Recovery of the regular VPN is not changed by this.

The empty request has only auth-full and LF. Require HTTP success, the complete NDJSON structure, the body/line/count limits, the correct requestId in data-result and data-mac, the canonicity of all records and a correct HMAC. For an empty sent list, additionally require empty accepted/deferred ID lists and zero acceptedRecords/acceptedBytes. Verify the match of the destination IP and the permissibility of the routing fields of the returned data; do not present the MAC as proof of a valid payload plaintext.

After this verification, discard all data records. `wizard-check-access` in ProbeClient uses exclusively the general one-off diagnostic exception from `protocol.md` 9.5. Do not check the payload GCM and do not decrypt. Do not store any received payload, deliver it to the network layer, enqueue it in an operational queue, pass it to another part of the client or use it in any other way. Do not call `ingestRecord`, do not allocate per-peer queues, do not remove an item from the operational outbound queue and do not change the tunnel, the active state, the time, the checkpoints or the operating counters, including drop/ciphertext. The check verifies the Access Key and the authenticated structure of the server response; it does not prove the authenticity, integrity or readability of the plaintext of individual payloads. The normal bootstrap, recovery and operational data polling continue to fully verify the payload GCM after data-mac and process valid data according to the regular rules. The protocol MAC does not hash the whole ciphertext, so the UI must not claim that it has verified the end-to-end content of messages.

On 401, state that authentication was rejected and that ACCESS_KEYS for the specific virtual IP should be checked in the file at the given server URL. Do not automatically label a timeout, 503 or an invalid MAC as a wrong Access Key. A web URL does not mean that the PHP source is accessible through a browser. The help text is to recommend opening the file in the hosting administration or contacting the administrator, not to present the URL as a server file system path.

### Contracts

In all modes create/reset/edit/repair, `Add missing default communication contracts` is always shown, checked at every new opening, even for a complete set. The UI shows the number of all original contracts, of missing default contracts and of the planned additions. When unchecked, the addition is zero and both the original content and the presence of the object are preserved. Outside `10.A.B.0/24` the checkbox stays checked but disabled with an explanation, and the effective request is false. The service rejects a smuggled true for another CIDR. The contract option is not stored in the JSON.

The shared `defaultContractCandidates()` and `missingDefaultContractPeers()` select from `.2` to `.15` in the supported CIDR, skip the own IP and all original peers. There are 13 or 14 candidates without self; the number of new items is only the missing difference. Each original contract and its exact payload key remain even when the own IP changes and outside the default range. Adding a complete set is a content no-op. A new create/reset draft does not take over the original contracts; with false it has an empty object. New payload keys are SHA-256 over ASCII `minNumericIp_maxNumericIp` in numeric order, with a single underscore and without LF, output as lowercase hex. The preview and the publication are based on the same original session DOM and do not merge a later foreign Save. The last successful complete publication wins.

The own IP must not collide with an existing contract. The conflict is checked before check-access and again before publication; automatic addition removes no original contract.

## IPC v1 extensions

### Shared rules of the IPC extensions

Accepting pipe connections, reading and sending the response must be asynchronous. Dispatch may start only after the message has been completely received and validated. Waiting for an incomplete request or an unconsumed response must not occupy the capacity of short control. `get-status` and the acceptance of Disconnect have available capacity independent of long diagnostics and of slow reading, decoding, hashing or parsing of the configuration. Neither the in-memory state lock nor ConfigStore is held during HTTP or cryptography. At most one control network operation, `get-info` or a Wizard check, may run at a time; another one gets `busy` without an unbounded queue.

The number of connections, the message size, the work queues and the I/O deadline are defined in the section [Implementation limits of local control](#implementation-limits-of-local-control). Excess connections and work are rejected in a controlled way. Merely increasing the number of synchronous workers is not sufficient. An unbounded `FlushFileBuffers(pipe)` is forbidden, and the overlapped I/O context lives until confirmed completion or cancellation. Stopping the service has a separate path through the SCM independent of the pipe and safely terminates waiting IPC and HTTP. The pipe explicitly rejects remote clients.

IPC uses `ipcVersion=1`, the fixed pipe `\\.\pipe\phpvpn-control-v1`, UTF-8 JSON, one request and one response per connection, a UUIDv4 requestId and a limit of 4 MiB per complete encoded message. All new requests have a closed set of fields and strict types. Reject duplicates, superfluous members, an unknown command, an invalid ID and an operation for another session before any side effect.

The new commands do not use the direct formats of get-config/get-info. They have the envelope `{ipcVersion, requestId, result}` or the standard `{ipcVersion, requestId, error}`. `result` is an exactly defined object for each command below. Extend the builders separately from the original acknowledgement envelope, which has `result:"ok"`.

The get-status schema must not change because of the path or secrets. `serviceInstanceId`, epochs and the configuration belong in the new responses. Existing status parsers must continue to pass without a change in the meaning of the counters. The order of JSON members is not semantic.

#### Implementation limits of local control

The Windows IPC server has at most **32 slots including listeners**. Each of the following classes has a separate serial executor with its own thread:

| Work class | Implementation capacity |
|---|---|
| `shortControl` | At most 16 pending tasks; the task currently executing does not count towards this number. |
| `file` | At most 4 pending tasks; the task currently executing does not count towards this number. |
| `diagnostic` | At most one task in total, including the one currently executing. |

`get-status` and `disconnect` use `shortControl`; `connect`, `get-config` and `set-config` use `file`. `get-info` uses `diagnostic`, and the scheduling of Wizard network checks shares the same capacity. Classification takes place only over the complete message, and schema validation precedes the effects of the command.

Reading the request and writing the response each have their own absolute monotonic I/O deadline of **5000 ms**. A partial transfer does not renew it. Reading counts it from the start of the first read after connecting, writing from the start of sending the response. Waiting for the client to close after the write uses the original output deadline. This is not a total budget for executing the command. The event loop schedules a maintenance tick after **250 ms** and wakes up earlier on an event or a nearer I/O deadline. The maintenance callback must not block or perform I/O.

The limit of one complete encoded message is **4 MiB (4194304 bytes)**, including the JSON envelope and escaping, separately for the request and for the response. It is different from the 512 KiB limit of the configuration document. The pipe is local only; the Windows server creates it with `PIPE_REJECT_REMOTE_CLIENTS` and rejects remote clients.

These capacities limit the number of slots, pending work and message size. By themselves they determine neither the total RSS of the process nor guarantee availability under arbitrary flooding. The availability of short control under a defined load is verified by the existing `ipc_availability` tests in [test_ipc_availability_win.cpp](client/tests/unit/test_ipc_availability_win.cpp). Their existence is neither a run result nor a substitute for a separate memory measurement.

The label "session" in the table means the two mandatory fields `serviceInstanceId` and `sessionId`, not a nested object. All listed result members are mandatory unless explicitly marked as optional. `null` is a member value, not its omission. No further members are allowed.

Each row lists the additional request fields beyond the mandatory triple. A session is always identified by the pair `serviceInstanceId` and `sessionId`, both UUIDv4.

When opening a create/reset draft or a repair document, a still missing IP or key in `fields` is represented by an empty string, not by a falsely valid runtime configuration. A rejected original document has fields/context null and provides no text through these fields. Selecting mode reset on content rejection does not by itself perform Reset; the network and Finish are disabled until an explicit `wizard-reset`.

`fields` contains exactly five strings `serverUrl`, `serverSecret`, `virtualIp`, `accessKey`, `httpHeaders` and three mandatory booleans `useDefaultServerSecretInWizard`, `autoDetectIpAddressInWizard`, `useDefaultAccessKeyInWizard`. `context` contains exactly `httpHeaders` and `vpnCidr` as strings, `trustAnyTlsCertificate` as bool and ten positive integer members `maxOutboundQueueBytes`, `maxInboundQueueBytes`, `minOutboundPerPeerQueueBytes`, `minInboundPerPeerQueueBytes`, `maxQueuedPacketAgeMs`, `maxResponseBodyBytes`, `maxNdjsonLineBytes`, `maxDataRecordsPerResponse`, `responseTimeoutSeconds` and `timeSyncIntervalSeconds`. The service derives them from its own original or from the reset draft; it must not trust TLS or CIDR smuggled in by the client. `contractCount` is a non-negative integer. `availability` is exactly one ConfigAvailability value, `mode` one WizardMode value; `vpnState` and `vpnPhase` use the original get-status enumerations. `connectionEpoch` is a non-negative 64-bit integer. `createDefaultContracts` is bool. `reasonCode` is a safe string or null; `configPath` is the absolute string of the fixed storage. `revisionToken` is an opaque random revision identifier within the service instance, not a published hash of the secret or an expected commit revision.

`existingDefaultContractPeers` is a mandatory array of at most 14 canonical, unique and numerically sorted candidate IPv4 strings from the original session DOM. The count must not exceed `contractCount`, which includes all original contracts. Outside the supported CIDR the array is empty. With fields/context null the array must be empty and the count zero, as with a create/reset draft without contracts. Finish accepts neither client-claimed counts nor this list. The eight-item fields form both the access evidence and the commit fingerprint. A true default secret/key must match the concrete value, a true auto IP the suggestion stored by the service at the last valid secret check. A change of any flag requires new access evidence. The same commitId with different fields is rejected; an identical receipt does not repeat the write.

The service and the tray use the new closed schema together. The exact historical four-item and seven-item fields and the original URL/secret requests without httpHeaders are `wizard_unsupported`; other defective schemas are `ipc_malformed`. No downgrade, no omission of metadata and no direct write by the tray. Old configurations without metadata are still accepted, but only if they satisfy the current full validation including `/24` to `/29`. No automatic migration takes place and the original seven IPC commands do not change.

For missing, `get-config-document` returns document/revisionToken null; for UTF-8 text within the bounds of the section Bounded reading, UTF-8 and snapshots it returns the actual text after removal of a possible leading BOM, and the availability. For unreadability it returns a specific access error, for an invalid or unsupported encoding `config_encoding_error`, for exceeding the size `config_too_large`, always without a document. The text string in the envelope allows syntactically invalid JSON only if it is valid UTF-8 text. Neither IPC nor the tray may repair bytes or convert them through base64. `create-default-config` accepts neither a path nor content. When the file is created concurrently, it returns `created:false` and its actual UTF-8 text within the limit, or a specific access, encoding or size error. Opening it is not tied to the JSON validity of this foreign text. After a successful creation it returns `created:true`. Save continues to use the original set-config with the complete document and its service validation including encoding and size. With unsupported new commands, the tray announces that a new service is required and uses neither an old cache nor creation through a fallback.

`get-config-state` has only one-off use: handling a chosen Statistics and the explicit verification of an unclear Finish after a service restart. It is not called at tray start, on the timer, when the menu opens or automatically after Save/Finish. `wizard-open`, `get-config-document`, Connect and get-info perform their own single authoritative check without a preceding get-config-state. The manual Communication contracts use a single `get-config-document`. `availability` and the safe reasonCode in configuration responses distinguish all states of the section Bounded reading, UTF-8 and snapshots, including encoding and size errors. On content rejection, `wizard-open` returns fields/context null, contractCount 0 and mode reset, and allows only a Reset offer or a remedy according to the section One-off check after an action and menu reactions.

`clientAttemptId` is the UUIDv4 of one press of Next and serves correlation, not automatic renewal of the start. Each of the three wizard-check requests additionally contains `attemptSequence`, a positive 64-bit sequence number of the attempt within the session. The tray increases it on each new manual Next, never when polling the result. The service keeps only the highest accepted sequence and the current attempt. A start with the same or a lower sequence is rejected without network work and never re-executes a discarded attempt. A higher sequence during a still running operation gets busy and does not start later on its own. Even a valid start closed in this way advances the highest sequence without changing the still running operation. Reset and interruption by Connect do not clear the highest sequence; a new sessionId starts a new series. Overflow is rejected. There is no history of UUIDs and no reason to force the user to re-open the Wizard after a regular number of attempts. The local `attemptSequence` limits repeated starting of a control operation and is not a wire replay cache according to `protocol.md` 6.3.

The tray sends the start exactly once. It does not repeat it on a lost response. `wizard-cancel-attempt` allows closing an attempt even without a delivered operationId: the service remembers its sequence, cancels the corresponding work and rejects a late start of this or a lower sequence. An old cancellation must not affect a newer attempt, and a mismatching ID of the same current sequence is rejected. If the cancellation cannot be delivered, the HTTP deadline and the lease continue to limit the lifetime of the work. A new Next respects busy and the wait for confirmed termination. A successfully delivered continuous get-operation only reads the state of an already known operation and does not start a new check.

Finish has separate unchanged idempotence rules: the same commitId with an identical complete input returns the same result, a changed input is rejected and the write is not repeated. A lost confirmation is read through get-operation or wizard-get-commit, not by a new write. This rule must not be confused with the abolished renewal of network attempts.

`OperationResult` contains `operationId`, `kind` from the fixed enumeration url/secret/access/finish, `operationState` from pending/running/cancelling/succeeded/failed/cancelled/interrupted, `connectionEpoch`, `clientAttemptId` and `attemptSequence` for checks (null for finish), `error` or null and `payload` or null. The payload is closed according to kind. For success of `url` it contains exactly `verified:true` (verification of availability and syntax, not of cryptographic identity). For `secret` it contains exactly `verified:true` and `suggestedIp` as a canonical IPv4 string or null. For `access` it contains exactly `verified:true` and `discardedRecordCount` as a non-negative integer. For `finish` the payload is directly the receipt with the mandatory `commitId` (UUIDv4), `revisionToken` (string) and `commitState:"confirmed"`. For other states the payload is null. Error is null on success and for an unfinished error-free operation; on failure it contains the structured error described below. `wizard-get-commit` returns a receipt only for confirmed and an error only for failed; otherwise both are null. `wizard-cancel-operation` returns exactly `operationId` and `operationState` from the permitted states above. `wizard-reset` and `wizard-resume` return the same closed structure as `wizard-open`. The UI can compute the text of the key derived from the IP with a shared pure function; the service always verifies it independently as input of check-access.

Each check evidence stored by the service binds the exact relevant values, the draft generation, the TLS/runtime context, serviceInstanceId, connectionEpoch and the current attempt. Finish requires a match with all necessary evidence. After returning with Back and changing a text, it is therefore impossible to save through IPC values other than those that were verified. A change of the stored revision by a foreign Save/Finish does not by itself invalidate the evidence. `createDefaultContracts` does not change the validity of the access verification, but at Finish the service verifies its permissibility for the given mode/CIDR.

`wizard-resume` must not disconnect on its own or accept a client-claimed disconnected. The service verifies the current state, phase and the absence of a pending Connect. The global disconnection itself remains the original disconnect command.

### Wizard IPC lifetime and limits

A terminal failed `url` or `secret` operation may contain, besides the original eight mandatory members, a single optional `httpDiagnostic`. When absent, the field is omitted; an explicit null is an error. Its closed schema is:

```json
{"format":"http-octets-v1","action":"health","responseComplete":true,"requestHeadersSource":"winhttp","responseHeadersSource":"winhttp","request":{"originalSizeBytes":1,"prefix":"x","separator":"","suffix":""},"response":{"originalSizeBytes":1,"prefix":"x","separator":"","suffix":""}}
```

The example describes the shape of the object, not an actual HTTP exchange. `action` allows health/info, URL operations only health. The request source allows winhttp/merged/application, the response source winhttp/available/unavailable. Both messages require a positive integer `originalSizeBytes` in the uint64 range and exact lengths of the prefix, suffix and separator according to the cut described above. Each original octet is represented in the transfer JSON string by a scalar U+0000 to U+00FF. The tray first reverts this reversible encoding to the original bytes and only then creates the Unicode projection. A larger scalar, an unknown member, a duplicate, a wrong length, type or format means rejection of the whole operation as `ipc_malformed`.

The detail is bound by the parent operationId, kind, connectionEpoch, clientAttemptId and attemptSequence. It is transferred only with an error and a null payload. A diagnostic error does not transfer a redundant serverUrl/configPath; code has at most 128 UTF-8 bytes, description and suggestedAction 4096 each, and field corresponds to the step. The worst-case sixfold JSON escaping of both directions together with the other fields has a proven upper bound of 852232 bytes, under the unchanged limit of 4194304. There is no new fetch command, chunked IPC or second connection for opening the detail.

A new attempt, an input edit, a step change, reset/resume, cancellation, interruption by an epoch, the end of the session and lease expiry remove the detail available to the application. The UI closes and empties its owned window. On invalidation of a failed detail it sends the existing `cancel_attempt` once with the original identity, so that the service also erases the terminal copy. An undelivered cleanup is covered by a new start or lease expiry. A late cancel must not remove a new attempt. X of the detail window alone allows re-opening within the same failed attempt. Raw data does not go into Error.detail, logs, the configuration or telemetry. No automatic copying to the clipboard takes place.

IPC remains version 1. The new tray accepts the original eight-field shape without the detail. An old strict tray rejects the new field, so the service and the tray are deployed together. Successful operations and errors without diagnostics keep the existing schema.

At most eight in-progress Wizard sessions per service, each with one draft and one current check. Each open session has a renewable lease, a default confirmation every 15 s and expiry after 60 s without valid contact. The service compares elapsed monotonic time, not the number of missed pings. A valid request for the given live session may renew the contact. While the user is merely filling in fields, the tray sends a short wizard-keepalive. Neither the general get-status/get-config-state nor the traffic of another session renews its lease.

The heartbeat is local IPC only; it does not start HTTP, persists nothing and is not a retry of Next. It extends neither the HTTP deadline nor the limit for delivering the result to the tray. Use the existing session management and the service timer; do not introduce a new thread or PID tracking because of the lease. Changing the intervals requires a simultaneous update of the normative documentation and the tests.

After expiry, first mark the session as invalid, then safely cancel the in-progress check and, after its terminal state, release the draft and resources. An object used by a callback or a thread is not released prematurely. The slot in the limit stays counted until the cleanup is complete. A late request does not revive the session. A regular interactive close requests cleanup immediately. The explicitly approved local approvedDiscard and the system endSession send no IPC and leave the remote cleanup to the lease. Also on a tray crash/hang, logoff or IPC outage, cleanup occurs at the latest after the lease time plus the defined timer tolerance and the final cancellation time. After resume, the service evaluates the elapsed time before the next lease renewal; the time source used must take the sleep time into account. Expiry is not proof of process death and disconnects neither the global VPN nor another Wizard.

The tray's wait for the result of one Next has a separate finite monotonic budget from the press, covering the IPC start, at most 1/2/3 HTTP requests for URL/secret/access, local processing and delivery of the result. The total budget is `1/2/3 × responseTimeoutSeconds × 1000 + 15000 ms` for URL/secret/access in this order. With the default 30 seconds per HTTP request, this is **45/75/105 s**. The IPC start has its own limit of **5000 ms**, which is included in the total budget and not added on top. The budget computation is protected by the validation of responseTimeoutSeconds and 64-bit arithmetic; the addition to the single non-negative monotonic start is checked for overflow. Neither polling nor keepalive renews the final deadline. A timeout or other error of any IPC call of the check ends the current Next in the UI, cancels further reading of its result and requests safe termination of the work. A late succeeded no longer changes the step. A new Next is always manual and can obtain new data and consume further messages.

A commit and its receipt have a safe lifetime separate from the editing lease. Neither expiry nor closing may revert an already published write or mark it as not performed. Before the publication section, reserve a slot for the result record. The registry has at most **128 receipts**, including reserved records of still ongoing commits. When it is full, reject a new commit before the write, rather than evicting a needed confirmation. The receipt is kept for the whole live session. After the session is closed, including by expiry, the terminal result may be removed at the earliest **600000 ms** after the close. If the commit ends only after the session has closed, retention is counted from its completion, so it is not shortened. A pending commit or a record with a non-terminal operation is not removed merely because time has elapsed. wizard-get-commit can only read an existing record under the original triple serviceInstanceId/sessionId/commitId; it neither renews the lease nor allows another write. A terminal confirmation is immutable and documents a specific publication, even if a later Save has already overwritten it. Evicted or expired sessions are never recreated through a repeated Finish.

A service crash cancels sessions and network evidence. On a restart during an unclear Finish, the client, as part of resolving this in-progress action, reads the new config-state once and shows an explicit verification of the result; it does not automatically start a new write. This is neither a check at a regular tray start nor a periodic refresh. The persistent commit recovery record identifies only the publication and the revision and contains no further copy of secrets. An undetermined result stays unknown; an automatic retry is never derived from it. These rules preserve the idempotence of Finish and the resolution of an unclear write. The ban on automatic retry applies to the network checks.

The message limit includes JSON escaping. The separate limit of the file and of the resulting document is 512 KiB according to the section Bounded reading, UTF-8 and snapshots and is enforced already when reading, before complete hashing and parsing. A document that does not fit into v1 together with the envelope is rejected before further checks and the write, with information about the size; it is not split into undocumented pieces. Add tests of both upper boundaries, escaping and strict UTF-8. The responseTimeoutSeconds limits must not wrap around by multiplication into a negative or infinite timeout when converted for WinHTTP.

### HTTP detail of an unsuccessful Connect

The initial Connect health/info is, after a received but rejected HTTP response, a terminal attempt without automatic retry. This applies to invalid protocol content, HTML instead of JSON, invalid JSON, a parsing or cryptographic verification failure and a rejected HTTP status. The runtime moves to `error` and the public error has `recoverable: false`. The decision is based on the actual result of the exchange, not on the availability of the diagnostic object. The red panel and the available Error detail stay stable until explicitly invalidated by the user. Transient communication errors without a usable received response keep the existing backoff/recovery and have no Error detail. The Configuration Wizard remains one attempt per click. This rule does not change recovery after ACCESS_KEY, tunnel or operational data errors.

Connect reuses the bounded capture, `http-octets-v1`, the Unicode projection and the same `HttpErrorDetailWindow` as the Configuration Wizard. Capturing is explicitly enabled only for the individual initial health/info exchanges. It does not carry a successful health response as the detail of a failed info and does not capture ACCESS_KEY, the tunnel, data requests, time synchronization or recovery requests. DNS, TLS, local validation, timeout and cancellation without a processable received response create no diagnostics. Raw content is not written to logs, the configuration or the regular `lastError`.

The status carries two mandatory correlation fields: `connectionEpoch` as a non-negative uint64 and `connectAttemptId` as a UUIDv4, null at epoch zero. The UUID is created for each newly accepted Connect. An idempotent Connect does not change the identity. The combination prevents confusion even after a service restart. The optional `httpDiagnostic` has exactly the shared schema described in the section Wizard IPC lifetime and limits. Null, unknown fields, defective lengths, an invalid action or an inconsistency with the state, the error and the checkpoints reject the whole status. A response without the detail has 25 members in the inner status object, a response with the detail 26. The limit of the whole UTF-8 message remains 4194304 bytes. Both directions keep the whole content up to 65536 bytes; above this bound the first 64512 and the last 1024 bytes with exactly four separate `...` lines. The display of the size in KiB to two decimal places and the safe display of invalid text bytes do not change.

The red `Error detail` button is on the right in the Connect error panel. The text and the button have separate areas; in a narrow window the button is below the text, aligned to the right. It is reachable in the Tab order after URL/IP and uses the same red component and high-contrast palette as the Wizard. The dialog is owned by the Connect form, has read-only Request/Response, no footer and is closed with the cross. Closing the detail alone allows re-opening the same error.

A new Connect, success, Disconnect, cancellation, replacement of the identity and termination of the service remove the service diagnostics. Closing the error form empties the local model and the owned dialog and sends `dismiss-connect-diagnostic` with the exact original identity pair. The closed request schema is `ipcVersion`, `requestId`, `command`, `connectionEpoch`, `connectAttemptId`. The epoch must be a positive uint64 and the ID a valid UUIDv4. The service deletes only the diagnostics of the matching attempt, leaves the other identity alone and returns the regular acknowledgement `result: "ok"`. The command changes neither the VPN, the configuration nor the network. On an IPC outage the remote cleanup is not confirmed; the copy is still invalidated by the next Connect, Disconnect or service termination. After invalidation the model does not accept late diagnostics of the same attempt. The caches of the tray icon and statistics do not keep raw content.

The service and the tray are deployed together. An older strict status parser does not accept the new correlation fields. The server HTTP protocol and protocol verification are not changed.

### Errors and security of the IPC extensions

The stable codes include `config_unreadable`, `config_directory_security_invalid`, `config_encoding_error`, `config_too_large`, `wizard_session_expired`, `wizard_prerequisite_failed`, `wizard_attempt_closed`, `wizard_connection_interrupted`, `wizard_commit_unknown`, `wizard_contract_self_conflict` and `wizard_unsupported`; further distinguish busy, timeout and a file publication error. Do not introduce config_conflict for a stale stored revision. Do not change the original errors into raw system output.

The code `config_server_url_unset` ("The server URL has not been configured yet.", group `config_*`, non-recoverable) is returned by `connect` when the stored configuration is valid but `serverUrl` has the placeholder host `kPlaceholderServerHost`. Nothing is contacted and the state remains `disconnected`; automatic connection at service start publishes it as `error` with this code. On this code the tray on Windows, Linux and macOS asks, instead of showing an error dialog, the Yes/No question "The server URL has not been configured yet. Do you want to set it up now?", and Yes opens the Configuration Wizard at the Server URL step; No does nothing. Android shows the same dialog over screen 02 with the buttons Set up and Not now (see Android). The CLI returns an error envelope as for the other `config_*` codes.

Android adds to the IPC v1 vocabulary the code `tunnel_permission_missing` in the `tunnel_*` group ([error.h](client/src/core/base/error.h)) with the description "The permission to create the VPN interface is missing or was revoked.". It means that the system VPN consent is missing or was revoked at the moment the engine needs to create the interface, for example on Connect from the BootReceiver or Always-on after the consent was revoked. It is non-recoverable: `recoverable: false`, state `error`, no retry. `get-status` reports it in `lastError` under its own public code `tunnel_permission_missing`, not as `tunnel_start_failed`, so that the UI can show the consent screen (37) instead of a server error. Windows, Linux and macOS never return it. The platform rules are set by the section [Android](#vpnservice-služba-a-životní-cyklus).

A Wizard error has exactly the mandatory members `code`, a ready-made English `description`, `recoverable`, `field` or null, `httpStatus` or null, `suggestedAction` as a ready-made safe English string, and only the optional permitted `serverUrl`/`configPath` as strings. `code` and `description` are strings, `recoverable` is bool, `field` is null or one of the values serverUrl/serverSecret/virtualIp/accessKey/configuration, `httpStatus` is null or an integer 100–599. A superfluous field is rejected. The URL and the path come from the draft and the fixed storage, not from an unverified server body. Map the network cause to DNS, connect, TLS, timeout, rejected authentication, invalid format and invalid cryptographic verification. Do not execute or display an unexpected HTML response as HTML.

The ban on sensitive logging also applies to the error detail. `Error::message()` appends the detail, so requests, keys or raw bodies must not be put into the regular Error.detail. Wizard diagnostics have their own permitted fields and must not leak into get-status, progress, Statistics, the tooltip or the logger. The configuration fields of the Wizard and the editor may of course, according to their purpose, display the values the user enters.

Keep the deliberately public access for local applications, without impersonation and without a PID check. The pipe must explicitly reject remote clients. The commands accept no file system path, HTTP method, custom action, arbitrary headers or executable command. The UI has no new permission to write to ProgramData. Do not add a network allowlist that would remove the existing support for local HTTP servers.

## Shared Win32 infrastructure

The normative appearance, English texts, accessibility, focus, DPI and resize are defined by [tray_UX.md](tray_UX.md), especially UX00 to UX03 and the test section UX14. The shared `ui_style.h`, `layout.*`, `window_utils.*`, `ui_resources.*` and `ui_controls.*` separate portable DIP constants, texts and geometry from Win32 windows, resources and the message loop. The layer uses native EDIT/BUTTON controls and only small GDI drawing, without a new library, bitmap background or custom GUI framework. Accessible names, roles, checked/disabled state, keyboard, selection, undo and user-controlled clipboard stay native. A layout change must not restore text or create substitute controls. A native interface for other platforms remains future work.

All tray windows use a single shared monitor selection helper. A new child uses the monitor of its valid parent. A main window opened from the tray menu uses the monitor of the stored point at which the menu was actually shown. Without a parent and a menu point, it follows the monitor of the valid foreground window, then the monitor under the cursor and finally the primary monitor. The window is centered in the work area outside the taskbar. Coordinates are signed, including monitors to the left of or above the primary one. Sizes are computed for the DPI of the target monitor; the outer frame is added to the client area stated in UX03, and the whole is clamped to the available work area.

Reactivation does not move an existing window to the monitor of the new click. A minimized window is restored. If it lies entirely within the usable work area of any available monitor, its exact position and size are preserved. After a monitor is disconnected or a usable position is lost, the window is moved to the nearest available monitor and its geometry is changed only by the necessary minimum. The check is performed on reactivation and on a change of DPI, resolution or work area. Merely connecting a monitor does not move a visible window. The sizes in UX03 are exact default client areas in DIP without the title bar and outer frame, not the physical dimensions of the PNGs.

Each window owns a small RAII cache of reused fonts, icons, brushes and pens. It is created at initialization for the target DPI and released when the window is destroyed. Fonts and icons are refreshed on a change of DPI or asset identity. A change of High Contrast or of its system palette refreshes the color resources even at the same DPI. A regular `WM_PAINT` must not load icons or create GDI resources. Only visually changed regions are invalidated. Full invalidation is allowed on creation, a DPI change, a major layout recomputation or recovery after a batch move failure. The tray keeps the last actually published icon identity and the exact tooltip and calls `Shell_NotifyIcon(NIM_MODIFY)` only when they change, not on every identical status snapshot.

This tray version is English only. Localization, language selection and reacting to the Windows language are out of scope. No translation framework, resource catalog or stable ABI of localization keys is created. The English constants may share a small common text catalog. The layout continues to measure the actual text and allows wrapping; Statistics use English thousands grouping independently of the system locale. Future localization requires a separate specification.

`apps/tray/layout.*` provides the pure functions `selectMonitor`, `initialWindowRect`, `usableWindowRect`, `computeContentLayout` and `revealScrollPosition`. The Win32 adapter `window_utils.*` supplies the actual monitors, target DPI, parents and the menu context. `sizeAndCenter` attaches a small placement subclass that detaches automatically on WM_NCDESTROY. A repeated call does not re-center an already initialized window. Reactivation of the new adapters is provided by `reactivateWindow`; it restores a minimized window and leaves a maximized one maximized. Changes of resolution/work area are corrected by the same helper; the DPI-suggested rect is accepted with only a minimal clamp. The menu point has the signed coordinates actually passed to TrackPopupMenu. A keyboard-opened menu uses the available position of the shell icon. The point is copied to the asynchronous action; a later cursor movement or opening another menu does not change it.

`ui_style.h` contains the English presentation constants, the palette, the font roles and the exact client DIP areas of UX03. `UiResources` owns fonts, icons, brushes and pens and creates them outside paint. If preparation fails, it keeps the previous cache. After a DPI change, the adapter must assign the new fonts to the controls and recompute the layout before the next paint. System and stock handles are borrowed and are never released as owned. `UiResources::update` compares High Contrast on every call and, with High Contrast active, also the current system colors. At the same DPI, HINSTANCE and status icon request, on a change it refreshes only the palette, brushes and pens and keeps the font and icon handles. If the palette also matches, the cache does not change. The Contracts, Password SHA, Editor, Connect and Statistics adapters also call this update on `WM_SETTINGCHANGE` and `WM_SYSCOLORCHANGE`. Outside High Contrast the own light palette remains. `ui_controls.*` measures the actual text, draws the card from the cache and moves existing controls. A failure of Begin/Defer/EndDeferWindowPos repeats all individual moves and fully invalidates the parent; a regular change invalidates only the designated region. The parent uses WS_CLIPCHILDREN. The exact uint64 formatting `englishInteger` uses neither double nor the system locale.

`TrayApplication(TrayRuntime)` owns the explicitly passed endpoint, the mutex name, the shell adapter and an optional exact tooltip. Production values exist only in the thin `wWinMain`. All of StatusReader, CommandReader and WizardReader, as well as Editor Reset, Wizard cleanup and Progress, receive the same explicit endpoint without a production default or fallback. Empty runtime dependencies are rejected before IPC. The application owns the individual windows, terminates the readers and the timer and removes the icon before releasing resources, the mutex and the shell adapter. `ShellIcon` compares the last successfully published icon identity and the whole tooltip, does not call NIM_MODIFY when they match, and an unsuccessful publication remains retryable. Re-construction after destruction releases the own mutex; two different names allow isolated instances.

The specialized windows in `apps/tray` use this shared base and explicit runtime dependencies. The isolated runner is described in the section [Isolated development and GUI preview](#isolated-development-and-gui-preview). The historical record is kept by the [documentation audit saved on 8 September 2026](client/tests/implementation-plan3-fix3-wp07.md); its results are not a new verification of the current state. The test backend and parser remain exclusively in the opt-in UI target outside the production EXE; the tests use synthetic data and private endpoints. The narrow filters TrayGeometry, TrayShell, TrayResources, TrayControls, TrayPlacement, TrayReaders and TrayApplicationSeam document the shared interface, not that all screens are finished. The full visual and runtime gate is bindingly defined in [UX14](tray_UX.md#ux14-ověření-a-velikost), including warmup, three runs and a truthful NOT RUN. The geometry test does not replace a physical unplug, a screen reader or a visual check.

### Shared Exit and system end of session

TrayApplication coordinates the authoritative lifecycle snapshots of the Editor, the Wizard and Contracts, never the content or enabled state of native controls. A manual Exit during saving asynchronously waits for the original deadline of each operation or its earlier terminal result. It establishes no new deadline or write, does not disable independent editors or Disconnect, and also includes a newly started operation. After the writes end, it shows one joint confirmation for all remaining dirty or unknown drafts, with the default No. For dirty it uses Discard unsaved changes?, for unknown The file may already have changed. Close without checking the save result?, and for both at once both sentences in one dialog. No cancels the whole Exit without any prior discarding. After Yes it re-verifies the whole approved set by generations and then uses approvedDiscard without second dialogs. It keeps the consent during a temporary veto by an ongoing announcement of a confirmed Finish; a change of a live draft invalidates it. A participant that has already closed separately does not require a new dialog.

The production hidden top-level host is not HWND_MESSAGE and receives the actual system session broadcast. WM_QUERYENDSESSION returns TRUE without mutation. WM_ENDSESSION(FALSE) keeps the drafts. WM_ENDSESSION(TRUE) terminally revokes delivery, stops the timers, calls endSession of the Editor, Wizard, Contracts, Progress and read-only Editor before destruction and closes the local windows. It shows no dialog, does not wait for a worker join, deadline or IPC, does not publish, does not repeat a request and sends no Disconnect or rollback. The remote Wizard session is cleaned up by the lease on this path.

CommandReader and the general StatusReader use a separate shared state with value captures of the endpoint and the request, without this or a UI callback. Abandon revokes notifications under a short mutex, signals cancel and returns without waiting. The worker owns the resources until the I/O actually completes. The regular StatusReader continues to keep the queue of explicit requests and the 400 ms read; the tray 5 s and Progress 500 ms polling do not change. Before destruction, Progress abandons both readers; its regular state and display model do not change. Late messages carry no pointer and cannot pick up an abandoned state. Owned keys, the candidate, the DOM and temporary adapter texts are overwritten on a best-effort basis; native EDIT content and undo are emptied. Overwriting all internal copies in the builder, parser, allocator, OS or the user's clipboard is not guaranteed. The service, the configuration on disk, the global VPN and other sessions are unaffected by the tray terminating.

The Wizard can have its own 500 ms polling of the state of a still running operation and of the epoch, only while it is open. When it is not performing any check, its lease is kept by a 15 s keepalive or by another valid request of the given session. The original five-second tray timer for the in-memory get-status and the 500 ms timer of the Connecting progress window remain independent and do not start configuration reads. The service checks the epoch and state of an open session at each of its valid contacts. It reports an epoch change with the structured error `wizard_connection_interrupted`, even for a keepalive, whose regular successful response remains `alive:true, leaseDurationMs:60000`. An ongoing get-operation also returns the current epoch. No new command and no disk get-config-state for polling the epoch is introduced. Resume may pass the last epoch confirmed to the given session or the current epoch of the service, because a keepalive error does not contain the current epoch. The service accepts Resume only in the current disconnected/idle state without a pending Connect, takes over the current epoch and invalidates all previous evidence. It rejects any other epoch. Closing the Wizard ends its polling and keepalive. A response may change the UI only if windowGeneration, serviceInstanceId, sessionId, operationId, clientAttemptId and attemptSequence match, and if the attempt has not yet ended and its final deadline has not expired. An old confirmation or success must not affect a new attempt.


### Portable core of Communication contracts

The data contract consists of `ContractsDocument`, `ContractsModel` and `PasswordKeyModel`. When the model is created, the complete configuration is verified again; neither a repairable nor an invalid document creates a table. The shared range `/24` to `/29`, the validity of the own address and the number of at most 252 peers are checked before allocating rows. The computation uses the first and last client address with overflow-free arithmetic. Rows are sorted numerically by remoteIp, self is absent, `/24` has 252 and `/29` four peers. The displayed pair is the canonical numeric `minIP_maxIP`; the JSON identity remains the remoteIp alone.

A present valid contract has Enabled true and keeps the exact payloadKey. A missing contract has an empty Key and Enabled false in the draft. Opening the editor does not derive a key. After a row is enabled, the user must fill in a valid key, otherwise the row blocks saving. This is the whole set of peers, not the additive Wizard defaults 13/14. Key is exactly `[0-9a-f]{64}`, without trimming, lowercase conversion or truncation. An active invalid value blocks the candidate; an inactive invalid value has a local error but is not published and does not block. The error is `Key must contain exactly 64 lowercase hexadecimal characters.`. The model provides the number of all blocking rows and the first remoteIp + Key column, independently of the viewport. The sum of the current UTF-8 texts of Key has a limit of 524288 bytes. An over-limit change is rejected entirely, keeping the original value, dirty and focus. An invalid 65 characters are kept for repair.

Dirty expresses the difference of the resulting publishable state from the original. A row is dirty when Enabled changes or when the key of an enabled row differs. The draft is dirty if at least one row is dirty. An identical key after Random, filling in the default or confirming Password SHA, or a return to the original result, does not force dirty. Editing the key of a row that was originally and still is disabled is not published and creates no dirty state. Disabling an originally enabled contract, on the other hand, is a change. Generation does not change Enabled. The result-based dirty does not cancel saveUnknown or the generation protection during Save and the shared Exit. Random No/Escape/X is passed to the model as an unconfirmed action without a crypto call. A confirmed Random obtains exactly 32 bytes from `CryptoProvider::randomBytes`; an error keeps the key. The action target `ContractTarget` carries the immutable remoteIp, the canonical pair and the identity and generation of the parent model. It provides the exact confirmation `Replace the key for {contractId} with a new random key?` and the title `Password SHA - Contract {minIP_maxIP}` for the follow-up view. Several targets of the same row stay valid; the last confirmed key wins. Focus of another action does not redirect them; a foreign model or a discarded generation is not applied.

`PasswordKeyModel::update` synchronously hashes the exact UTF-8 bytes of the borrowed UTF-16 input with an explicit length. The limit is 255 Unicode scalar values, at most 510 UTF-16 units or 1020 UTF-8 bytes. A valid surrogate pair counts once, a combining character separately; nothing is normalized, trimmed or case-changed. An over-limit edit does not call crypto and keeps the previous output and count; the adapter keeps the input and selection and shows an error. Unpaired surrogates and unsupported single-line control characters are rejected without repair or truncation. Precisely, these are C0 U+0000 to U+001F, DEL/C1 U+007F to U+009F and the separators U+2028/U+2029. Invalid UTF-16, a control character or a crypto error invalidates the output and disables its confirmation. An empty actual input has the standard hash `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`; the cue `CHANGE-THIS-PASSWORD` is not passed on. The password is neither stored in the model nor sent to the service. The working UTF-8 buffer and the digest are erased after each return through `secureWipe`; the output is an owned `SecureBuffer`.

The draft owns one original valid DOM and lightweight rows, without a DOM copy per row. `prepareSave` takes a complete snapshot of the confirmed rows and creates a separate immutable `ContractsCandidate`. The patch changes only communicationContracts: enabled inserts under remoteIp an object with payloadKey, and unchecked removes it. Other values, types and presence of members, including runtime, CIDR, TLS and the Wizard metadata, are preserved. An originally absent communicationContracts stays absent without being added; an originally present one stays `{}` after everything is removed. The strict schema does not allow unknown members, and the resulting document is not reconstructed from ClientConfig. Whitespace changes are allowed.

The candidate goes through serialization and full shared validation within the limit of 524288 bytes. The mandatory integration adapter `ContractsEnvelopeSizer` measures the actual encoded envelope of the candidate with the existing builder and releases its temporary copy. `validateContractsEnvelopeSize` rejects more than 4194304 bytes without overflow. The adapter is synchronous, has no side effects and must not change the model during measurement. Only success freezes edits, increases the save generation and discards earlier child targets. A local error keeps the draft and the generation. After a correlated definitive rejection or a proven non-send, the controller can call `resumeEditing` with the same save generation. Unknown, the actual transfer and the deadline are owned by ContractsSaveController, the closing of children and the confirmation of closing by its native ContractsWindow; the model itself does not save. `matchesDocument` verifies a valid current document and compares the whole DOM regardless of the order of object members, preserving types and absent/present differences; it is not a historical receipt.

Model mutations have one owner and are called serially. The row texts and their default comparison values are SecureBuffers; the original DOM and the candidate are erased on a best-effort basis on destruction. A candidate shared as const lives until the last user releases it, so closing the parent does not outrun the reader. Inputs and copies created by the existing parser, the allocator, the native text box and undo require their own lifetime limits; this is not a guarantee of erasing all copies. The models log nothing. The native and IPC adapters must clean up their own buffers. Local creation and the patch have a bounded number of rows and bytes; synchronous UI use must later document the performance gate of [UX14](tray_UX.md#ux14-ověření-a-velikost); a unit test alone does not confirm it.

## Platform specifics

### Windows

The target of the Windows part is only Windows AMD64 (x64). Windows x86 (32-bit) and ARM64 are out of scope. The Linux implementation is described in the separate section [Linux](#linux), the macOS implementation in the section [macOS](#macos) and the Android implementation in the section [Android](#android). Windows is the primary platform. The client MUST use exclusively Wintun as the L3 TUN for IPv4. It MUST NOT use TAP, its own kernel driver or automatically switch to another tunnel backend if Wintun is missing or fails. Installation, creating or configuring the adapter and route changes require administrator privileges; actually running these operations belongs exclusively to the Windows Service.

The service mode is intended for long-term operation and automatic recovery. The console application remains a local client of the service for diagnostics and supported control operations; it does not run the VPN itself. Version v1 uses split tunnel exclusively. After a successful bootstrap, the service adds the local `virtualIp` with the prefix from `vpnCidr` and exactly one explicit route of the exact `vpnCidr` prefix through its own adapter. It adds no default route, does not change DNS and introduces no kill switch. Full tunnel, DNS changes and a kill switch are outside v1 and require a future separate specification. The relay server at the configured URL MUST remain reachable through the existing network path outside the phpvpn tunnel both before and after the change.

The platform layer provides one sequential packet source for the input worker and one sequential destination for the output worker. Any asynchronous I/O completion is serialized at these boundaries.

#### Wintun baseline and distribution integrity

The baseline of the first version is the official precompiled and digitally signed Wintun (the latest stable version) downloaded from `wintun.net`, and only for the architectures supported by the specific phpvpn release. The project MUST NOT compile Wintun itself, modify it or rename `wintun.dll`. The distribution MUST NOT extract or separately ship `.sys`, `.cat` or `.inf` files; it uses the upstream architecture-specific `wintun.dll` in the form and distribution model defined by Wintun and includes the corresponding upstream license text.

The signed release manifest MUST state, for each supported architecture, the Wintun version, the expected architecture and the SHA-256 of the exact bytes of the shipped `wintun.dll`. `install.bat` or its signed helper installer MUST, before registering the service and before any network change, verify the manifest signature, the SHA-256 match, a valid digital signature of the DLL and the match of the DLL architecture with the installed service and the operating system. Any mismatch is a non-recoverable error of the given package; the installation fails closed and MUST NOT create the adapter, install the service or change addresses, DNS or routes.

The official Wintun ZIP (the latest stable version) has the published SHA-256 `07c256185d6ee3652e09fa55c0b673e2624b565e02c4b9091c79ca7d2f24ef51`. This value verifies exclusively the original ZIP archive when preparing a release; it is NOT the hash of any individual `wintun.dll` and MUST NOT replace the per-DLL hashes in the signed release manifest of the client package.

`wintun.dll` MUST be stored in an installation directory protected against writing by an unprivileged user. The service loads it only by an absolute canonical path using `LoadLibraryExW` with the flags `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32`. It MUST NOT load it through `PATH`, the current working directory, a relative path, the user profile, a temporary directory or any other writable location.

The platform layer has a fixed allowlist of the APIs needed by the first version: `WintunCreateAdapter`, `WintunOpenAdapter`, `WintunCloseAdapter`, `WintunGetRunningDriverVersion`, `WintunStartSession`, `WintunEndSession`, `WintunGetReadWaitEvent`, `WintunReceivePacket`, `WintunReleaseReceivePacket`, `WintunAllocateSendPacket` and `WintunSendPacket`. Before the first network change, the service safely loads the DLL and resolves all these symbols. A missing symbol, a wrong architecture or another statically detectable incompatibility causes an error without creating an adapter, session, address or route. The compatibility of the actually running version is verified immediately after creating or opening the adapter according to the following section and before starting a session or changing addresses and routes; no fallback is allowed.

#### Adapter and session ownership

The Wintun DLL, the adapter and the session may be used only by the Windows Service. Neither the tray nor the console application MAY load `wintun.dll`, call its API, open the adapter or change the tunnel directly; they continue to communicate only over IPC. Within one process and for one phpvpn installation, at most one open adapter and one active session may exist. The adapter uses the fixed name `phpvpn` and the fixed tunnel type `phpvpn`; the implementation uses a stable installation identity of the adapter and MUST NOT create further adapters with derived names on repeated connections.

The service may create or open the adapter and start the session only after a successful bootstrap of `health`, `info`, an empty `data` poll and after a successful fail-closed preflight described below. Immediately after creating or opening the adapter, it verifies using `WintunGetRunningDriverVersion` that the actually running Wintun belongs to the supported compatible release range. A non-compliant result closes the adapter and ends without starting a session and without configuring addresses and routes. For the first version, `WintunStartSession` has a ring buffer capacity of exactly 4 MiB (`4194304` bytes), i.e. a power of two within the range allowed by the API; any other value requires prior load, overflow and memory tests and an update of this specification.

Before the first network change, the service performs a fail-closed preflight: it loads the persistent ownership record, determines the actual state of adapters, IPv4 addresses and routes and checks for collisions of the intended address, prefix, route and foreign resources. If it detects a collision or cannot reliably distinguish its own resource from a foreign one, it ends with a safe error without creating, removing or changing any network resource. A mere match of the adapter name, VPN address or prefix MUST NOT be proof of ownership.

The ownership record is a persistent file in a protected directory of the Windows Service. It contains the format version and the stable identity of the installation, the stable identity of the own adapter, each address and prefix created by the service and each own route including its destination and prefix, next hop, explicit interface and explicit metric. For each network step it records exactly the state `planned`, `created` or `removed`. It MUST NOT contain keys, secrets, payloads, packet content, ciphertexts or authentication tags.

Each creation or removal of an adapter, address or route is a small persistently journaled transaction: before performing the step, the service safely writes and durably stores the intended creation or removal operation with the state `planned`; after verified success of the step, it atomically stores the corresponding confirmed state `created` or `removed`. Each route MUST specify the destination prefix, next hop, the specific interface and the metric. The implementation MUST NOT vaguely look up the "best" interface or route, change global priorities or rely on an automatically chosen metric.

After the session has been successfully created and the preflight completed, the service adds only its `virtualIp` with the prefix from `vpnCidr` and a single explicitly recorded split-tunnel route of the exact `vpnCidr` prefix through its own adapter. It immediately verifies that the default route and DNS remained unchanged and that the relay server remains reachable through a non-phpvpn interface; a failure completes a safe rollback of only the unambiguously own steps according to the record.

Recovery after a crash or a restart of the service or the system is idempotent: the service compares the actual state with the persistent record and completes or reverts only the unambiguously own unfinished steps. Before a new successful bootstrap it MUST NOT create or open the adapter or start a session, and it must not blindly delete identical-looking foreign network configuration. If the record is missing, corrupted, has an unknown version or its identity and the actual state do not match in such a way that ownership cannot be unambiguously proven, reconciliation MUST NOT remove or overwrite anything, and the service moves to a safe error state requiring administrator intervention.

Windows startup reconciliation does not use the Wintun API. It first verifies the installation identity in the journal and waits read-only for at most 5 s for the OS cleanup to finish. An inactive orphaned PnP instance can be removed only after a match of the actual GUID, alias, LUID, the exact instance `SWD\WINTUN\{GUID}`, the network class and a verified `IsPresent=false`. Removing the driver package or interfering with a live device is not used. Before the journal is retired, the absence of the identity and of all its rows is verified again. Ambiguity or a Windows request for a restart keeps the journal and blocks the service start. The native SetupAPI removal has no cancel/deadline of its own and no atomic condition against a concurrent intervention by another administrator. The lifecycle of the own instance must be serialized.

#### Sequential I/O and packet ownership

The input worker is the only caller of `WintunReceivePacket`. Each successfully returned buffer is owned by the Wintun session, and the worker MUST return it exactly once with `WintunReleaseReceivePacket` after copying or completing validation, even for an invalid, non-IPv4, oversized or otherwise dropped packet. It MUST NOT store a pointer into the receive ring in a FIFO, pass it to another thread or use it after `WintunReleaseReceivePacket`. Invalid and non-IPv4 packets are safely dropped and recorded only by an aggregate counter; IPv4 validation and enqueueing into peer queues with 16 flow sub-buckets are otherwise governed by the shared rules of this document.

If no packet is immediately available, the worker waits interruptibly for the event from `WintunGetReadWaitEvent` together with its own termination event. It MUST NOT poll in a busy loop. Disconnect, service stop, a session error, sleep/hibernate and recovery must wake the wait or otherwise terminate it in a controlled way, so that the worker can be joined without unbounded blocking.

The output worker is the only caller of `WintunAllocateSendPacket` and `WintunSendPacket`. For each already verified IPv4 packet, it first allocates exactly the needed buffer in the send ring, copies the packet into it and hands ownership to the session with a single `WintunSendPacket`. It MUST NOT send the buffer twice, use it after handing it over or share it with another thread. Lack of space in the ring must not lead to memory overwriting or a busy loop; the worker uses a bounded interruptible wait/backpressure and on stop safely drops a not yet allocated packet according to the existing limits and FIFO rules.

#### Disconnect, upgrade and rollback

Disconnect does not read the configuration and uses the independent control path even during Show Info or other long diagnostics. Stopping the service through the SCM does not depend on the pipe. All reasons for a stop, Connect against a probe and Cancel/Reset/Escape/X of the Wizard use the shared safe HTTP cancellation. The terminal state of the request and the callbacks must be confirmed before resources are replaced or released; a partial VPN body is accounted exactly once.

Disconnect MUST proceed in this order: stop starting new `data` polls and cancel the single existing request or let it finish safely; signal termination to the network worker and both tunnel workers, wake their waits and join all threads; remove only the own routes and the own address; call `WintunEndSession` at most once; and finally call `WintunCloseAdapter` at most once. The individual steps and the whole procedure are idempotent, tolerate partial initialization and are completed after a crash through ownership reconciliation. The `disconnected` state must not be announced before this sequence completes.

Upgrade uses the same procedure as the [current installation](#distribution-and-installation-on-windows). The package is verified before installation changes, the files are copied to the `releaseVersion` directory and `current.generation` is switched even before the original service is stopped. The installer does not test creating the adapter and the session before confirming the installation. This is not a fully transactional upgrade; no installation journal, automatic rollback or crash-safe joint recovery of the pointer and the SCM registration is implemented. A failure after writing has started can leave a partially changed installation. The service start does not verify the signature of the whole application generation.

The current installer has no separate path for a compatible return to an older application, so a verified rollback or restoration of the previous running state cannot be promised. Neither installation, upgrade nor a regular uninstall automatically calls `WintunDeleteDriver`, because the system Wintun may be used at the same time by WireGuard or another application. Reverting the application must not be a reason for a blind downgrade of the shared kernel driver.

#### Windows Service, console and tray

For regular operation the client is implemented as a Windows Service. The service exclusively owns the configuration, the connection state, the Wintun adapter and session, all network traffic, all three worker roles and the global operating counters. The separate tray application runs in the user session and, together with the console application, is only a local IPC client of the service. Both applications may control the service exclusively through the local IPC defined below; they must not load the Wintun DLL, open the tunnel, perform VPN traffic or keep their own authoritative copy of the state or counters. Through `get-config` and `set-config`, however, they can temporarily receive or send the configuration including `SERVER_SECRET`, `ACCESS_KEY` and `PAYLOAD_KEY`. Every local application connected to the pipe has the same access.

The network worker role is created on a successful start of the service engine, handles both the bootstrap and the operation, and its thread lasts until the engine shuts down. In the disconnected state it waits for commands without VPN polling. The tunnel and its session are created only after a successful bootstrap of `health`, `info` and an empty authenticated `data`. Then the service starts two separate I/O roles, the single reader and the single writer of the tunnel. Their lifetime is tied to the tunnel session. A completed Disconnect terminates these two roles and the session; the network role remains available for the next Connect.

On one computer, at most one instance of the Windows Service may run for a given phpvpn installation, and this service may own at most one global VPN instance. The service singleton, the connection state machine, the Wintun adapter, the session, the worker roles, the queues and the operating counters are global for the whole installation and MUST NOT be created separately for individual users or interactive sessions.

The diagnostic requests `get-info` and ProbeClient are not counted in any of the nine operating counters or in the operational drop/ciphertext statistics.

The service keeps the following counters only in memory and provides them to all tray and console sessions as one global snapshot:

- `dataPollsTotal`
- `dataPollsEmpty`
- `dataPollsWithPayload`
- `serializedDataRequestBodyBytes`
- `serializedDataResponseBodyBytes`
- `ipv4PacketsSent`
- `ipv4PacketsReceived`
- `ipv4BytesSent`
- `ipv4BytesReceived`

`serializedDataRequestBodyBytes` is the sum of the exact byte counts of the application bodies of `data` requests handed over to the transport. `serializedDataResponseBodyBytes` is the sum of the exact byte counts of the application bodies of `data` responses actually read from the transport. The transport sums the read blocks locally, and the service publishes the sum exactly once when the attempt completes, on both success and error. A read in progress is not reflected in the global counter continuously. Also counted are partial bodies before a timeout, cancellation or read error, an already read block exceeding the size limit, bodies with an unsuccessful HTTP status and subsequently rejected bodies. The number of bytes read must not be lost when an error result is returned. The accounting requires neither an additional copy of the body nor global per-byte locking. Neither counter includes HTTP headers, TLS overhead, TCP/IP or lower layers, or `health` and `info` requests and responses.

`ipv4PacketsSent` and `ipv4BytesSent` are increased exactly once for each original validated IPv4 packet when it is included in a complete serialized `data` request that is handed over to the transport. The byte increment is the exact length of the original IPv4 packet before binary packing, encryption, encoding and NDJSON serialization. `ipv4PacketsReceived` and `ipv4BytesReceived` are increased exactly once, only after complete verification of the whole response and the respective batch, decryption, full validation of the original IPv4 packet and its successful acceptance into the client inbound queue. The byte increment is the exact length of the original IPv4 packet accepted in this way. Including the same packet again in a new actually sent request is counted as a new transfer attempt, but never more than once within one request. The statistics therefore measure transfer attempts, not unique packets or only receipts confirmed by the server. A 100-byte packet handed over to the transport in two requests increases the outbound counters by 2 packets and 200 IPv4 bytes. Receiving the response must not count the same send again. A packet that is unverified, rejected or not accepted into the inbound queue is not counted as received.

All counters are atomically reset when a new logical `connect` arises from the `disconnected` or `error` state. An idempotent `connect` during `connecting`, `connected` or `recovering` does not reset them, and recovery of the same logical connection keeps them. Before `disconnect` completes, the running request is completed or cancelled and its read body is accounted. Then the existing counters are discarded and the snapshot of the disconnected state returns zeros. A late completion must not increase the counters of the disconnected state or of a new logical connection. A restart or crash of the service naturally resets them. The counters MUST NOT be stored in the configuration, the registry, the log or any other persistent storage.

The tray application MAY run simultaneously in every interactive user session, and the console application may also run in every session. All these processes are equal IPC clients of the single existing service: with the `get-status` command they read and display the same global state of the service and the VPN, not the state of their own session or process. `connect` and `disconnect` are global and idempotent operations on the single VPN instance, regardless of which IPC client or which session invoked them. Concurrent or repeated commands MUST NOT start a second bootstrap, a second tunnel, a second session or a second set of worker roles.

Neither the tray process nor the console application owns the service, the VPN, the adapter, the tunnel session or the global Connect. Temporary Wizard sessions have a separate lease; their closing or expiry cleans up only their own work according to the section Wizard IPC lifetime and limits. A user logoff, or the termination or crash of any tray or console application, therefore MUST NOT disconnect the VPN, stop the Windows Service, change resource ownership or affect other user sessions. The Windows Service MUST work autonomously even without a logged-in user, MUST NOT show windows, modal dialogs, a tray icon or any other UI, and MUST NOT depend on the existence or lifecycle of a user session for bootstrap, operation, recovery or teardown.

At each new interactive logon, the tray starts in the given user session, connects to the already existing Windows Service and, without invoking `connect`, `health`, `info` or `data`, first reads the current global state with the `get-status` command. If the VPN is already running, the tray only displays this state and does not take over ownership of the service or the VPN.

Installation, uninstallation, registration, starting and stopping of the Windows Service itself are not IPC operations. Installation and uninstallation are handled exclusively by `install.bat`, `uninstall.bat` and the Windows Service Manager. The console application must not bypass this boundary with a control command sent through the pipe.

##### Public local IPC

IPC is a Windows named pipe with a fixed versioned contract v1. The pipe name is a fixed implementation constant containing the version; the client must not look up the pipe by user input or accept an unmarked or different contract version. Messages are UTF-8 JSON, and each request contains `ipcVersion`, `requestId` and `command`; `set-config` additionally contains exactly one field `config`. For this contract, `ipcVersion` is the integer `1`, `requestId` is a fresh UUIDv4 and `command` is exactly one of the permitted values. An unknown version, an unknown command, a duplicate field or a superfluous field is rejected with a brief safe IPC error without performing the operation.

The installer sets an explicit Windows ACL on the control pipe that allows every local application to connect regardless of its user, group or effective Windows token. Access must not require a special account, group membership or a permission created by the installer. When a client connects, the service performs neither impersonation nor authorization of the client identity and must not decide by process name, PID, executable path or data in the message. The only protective boundary of IPC remains the fixed versioned contract, full message validation and the exclusive list of permitted commands.

Contract v1 keeps the original seven commands listed below and extends the whitelist with the exact configuration and Wizard commands and `dismiss-connect-diagnostic` described in the section IPC v1 extensions:

- `get-status`;
- `connect`;
- `disconnect`;
- `get-info`;
- `get-config`;
- `set-config`;
- `get-diagnostics`.

The pipe MUST NOT support a continuous state subscription, a service restart, starting an arbitrary process or command, or a general command for working with keys. Configuration and Wizard commands may carry only fields according to their closed schemas. It must not provide a general extension command through which these restrictions could be bypassed.

Successful responses, except for `get-info` and `get-config`, contain `ipcVersion`, the original `requestId`, the command result and only the fields permitted for the given command. An error contains the original `requestId`, a stable brief code, a safe user description and an indication whether the error is recoverable. It must not contain exception details or system error text. The fixed configuration path and the URL are permitted only in the designated new configuration and Wizard responses, not in the status, statistics, a regular IPC error or the log. The `get-info` and `get-config` responses have a special direct format described below.

`get-status` returns a local snapshot with safe public fields and a single explicit exception for raw data, the optional bounded HTTP detail of Connect described above. The correlation pair `connectionEpoch` and `connectAttemptId` belongs to the whole atomic snapshot. The snapshot further contains:

- the state, exactly from the set `disconnected`, `connecting`, `connected`, `recovering`, `error`;
- the phase, exactly from the set `idle`, `health`, `info`, `access-key-check`, `communication-contracts-check`, `starting-tunnel`, `running`, `reconnecting`, `stopping`;
- the UTC time of the last state change;
- the fixed fields `serverUrlCheck`, `serverSecretCheck`, `accessKeyCheck` and `communicationContractsCheck`, each with exactly the value `pending`, `success` or `failed`, which keep the results of the four bootstrap checkpoints for the current or last logical attempt;
- a separate state of server reachability and a state of its cryptographic verification, each as `unknown`, `yes` or `no`;
- the tunnel state;
- the safe last error, or `null` if there is none;
- the recovery count and the fixed integer fields `dataPollsTotal`, `dataPollsEmpty`, `dataPollsWithPayload`, `serializedDataRequestBodyBytes`, `serializedDataResponseBodyBytes`, `ipv4PacketsSent`, `ipv4PacketsReceived`, `ipv4BytesSent` and `ipv4BytesReceived`;
- the client version and the IPC contract version.

The order of members of local IPC JSON objects is not binding. Clients look up fields by name, and tests of the meaning of a response compare the structure and values independently of the member order. Serialization may be stably ordered for readability. This rule does not change the order of JSON array elements, type validation, rejection of duplicates or the canonical form of network messages according to `protocol.md`.

All nine operating fields are non-negative integer values with a range of at least 64 bits. The implementation MUST use checked increments and MUST NOT allow overflow or a return to a lower value. If it does not use a wider internal type, the counter saturates at the highest representable value. When the range is exhausted, the triple of polling counters is atomically frozen at the last representable combination satisfying the invariant. The whole `get-status`, including the state, phase, checkpoints and all counters, is one internally consistent snapshot. In particular, `dataPollsTotal = dataPollsEmpty + dataPollsWithPayload` always holds, and no client may assemble a result from values read at different moments.

The `get-status` snapshot MUST NOT contain the URL or any part of it, the configuration, VPN or other IP addresses, keys, authentication or GCM tags, ciphertexts, the content of requests or packets, internal paths or raw system or detailed network errors. A safe error reason may distinguish an unavailable or invalid endpoint, a failure of server or `SERVER_SECRET` verification, an actually rejected `ACCESS_KEY`, a tunnel start failure and incomplete verification or communication, including a separate timeout. The service creates `lastError` with a safe stable `code`, a ready-made English `description` and the flag `recoverable`. Both the tray and the console take over the same result and do not derive the cause from the checkpoints. Raw internal codes, for example individual DNS or TLS errors, are mapped to these safe categories. This is only a read of already existing state and counters from memory. The command must not by itself start `health`, `info`, `data`, the tunnel or recovery, change the state, block the workers for the duration of a network or cryptographic operation or wait for the network. The overhead of taking the snapshot MUST remain negligible.

`connect` starts within the service the bootstrap in the exact order `health`, standard `info`, an empty authenticated `data` poll and an extended `info` with publication of masked contracts and `includeMaskedCommunicationContracts: true`. The bootstrap is performed by the already existing network role, whose thread is created on a successful engine start and lasts until its shutdown. The service may start the tunnel, its session, the two tunnel I/O roles and regular VPN operation only after all four steps have succeeded. If connecting, operation or recovery is already running, the command is idempotent and returns the current state without starting a second bootstrap, tunnel or set of worker roles. The accepted configuration snapshot and the rules of the bootstrap checkpoints do not change by this.

`disconnect` performs within the service the exact order from the section "Disconnect, upgrade and rollback": it stops new polls, terminates the workers, removes only the own routes and address, ends the Wintun session and closes the adapter. The command is idempotent and recovery-safe; if already disconnected, it returns the current state. The completion of the command must not be announced before further VPN polling is stopped and all these steps are safely completed.

`get-info` reads and fully validates the current file once, and then, in a separate limited diagnostic path of the service, performs a one-off `health` and, after its successful verification, a one-off `info`. The service verifies and decrypts both responses. It uses its own temporary transport and time context and shares no mutable VPN state, queues or counters. At most one long control diagnostic, `get-info`, `get-server-info` or the Wizard, may run at a time; another one gets `busy`. The command must not start the tunnel, the worker roles or `data` polling and must not change the state of a disconnected client to connected. No part of this one-off diagnostic is repeated automatically after an error, including 401. On success the service sends through the pipe, without its own IPC envelope, the exactly validated decrypted plaintext `info` object from the server, i.e. the object with the fields `serverVersion`, `generatedAt`, `clients` and `limits`. It does not return the encrypted response wrapper, keys, tags or ciphertext. On failure it returns only a brief safe IPC error. Neither the service, the tray nor the console application MAY write or create a local file with the result because of this command; the tray and the console application display the plaintext directly.

`get-server-info` is a new command in the IPC v1 whitelist. The request contains exactly `ipcVersion`, a fresh `requestId` and `command: "get-server-info"`. In the same diagnostic class as `get-info`, it reads the current valid configuration once and computes the local masked contracts from this single immutable snapshot. It performs its own one-off `health` and an extended `info` only with `includeMaskedCommunicationContracts: true`, without publication of contracts. It changes neither the active VPN configuration, its state nor the operating counters, and starts neither the tunnel, `data` nor automatic repetition. The successful correlated envelope contains exactly `ipcVersion`, `requestId` and `result`. The result has exactly `infoPlaintext` (the original validated UTF-8 plaintext as a string), `localAddress` and `localMaskedCommunicationContracts`. The local list contains only `peer` and `hash` pairs, never keys or the secret. The 4 MiB limit applies to the actually serialized UTF-8 IPC message including escaping. Both the service and the tray validate the whole result before using it. An error has the regular safe correlated envelope. The snapshot exists only in memory and creates no local file.

`get-config` reads the current file once and returns through the pipe, without its own IPC envelope, its valid configuration JSON after the single permitted leading BOM normalization. It rejects an invalid file and does not return an old cache. The actual valid UTF-8 text within the limit with invalid JSON is made available exclusively by the new envelope `get-config-document`. Any local application may request it regardless of user, group or Windows token. After opening the Connecting progress window, the tray uses it once and takes over from the valid JSON only the displayed `serverUrl` and the local `virtualIp`. It must not log the whole received document including sensitive values, and its temporary copies have a limited lifetime. Because `get-config` reads the currently stored document and Connect uses its own immutable active snapshot, with a concurrent external change the displayed URL/IP may belong to a newer stored configuration than the currently active connection. This trade-off is knowingly accepted in order to keep the existing IPC. The configuration JSON is not sent in the log or in an error response, but its exposure through the public pipe is a knowingly accepted risk of this client.

`set-config` accepts the whole configuration JSON in the `config` field. Before writing, the service verifies the JSON syntax and the full validity of the configuration with the same rules as when connecting; on error it writes nothing and returns a safe IPC error. On success the service atomically stores the configuration in the fixed configuration file, publishes the stored snapshot and returns a regular successful IPC response. It saves the whole document through the shared ConfigStore according to the last successful publication, without a revision conflict, an additional overwrite confirmation or merging. An active VPN keeps its immutable snapshot. The command itself neither disconnects nor connects the VPN; the stored configuration is used at the next connection attempt.

`get-diagnostics` returns an extended one-off safe snapshot of the local state. It contains the state, version and uptime of the service; the result of configuration validation and safe warnings; the results of the last verification of `health`, `info` and `data` and of the last recovery (`recoveryCount` and `lastRecoveryAt` for full recoveries with a teardown, `softRecoveryCount` and `lastSoftRecoveryAt` for soft recovery); tunnel readiness; for the input and output queues the number of items, the occupied bytes and the effective limit; the aggregated operating counters; and the safe last error including an indication of its recoverability. The command is read-only, starts no new network requests, tunnel or recovery, and MUST NOT return the URL, VPN or other IP addresses, keys, tags, ciphertexts, packet content, internal paths or detailed system or network errors.

`outboundQueue` and `inboundQueue` contain `itemCount` (pending and held items), `queuedItemCount` (pending only), `occupiedBytes` (actual waiting + held packet bytes), `inFlightBytes` (the held part), `limitBytes`, `peerQueueCount` (allocated peers including held-only peers) and `activeSubBucketCount` (non-empty pending FIFOs). Logical reservations are not reported as physically occupied RAM. The `counters` group contains `queueExpiredPackets`, `outboundQueueExpiredPackets` and `inboundQueueExpiredPackets`. The total expiration is the sum of the directional counters and is already included in `packetsDropped`; it is not added a second time. The lock order is queue → drops; the queue does not call the engine or IPC. Flow keys, ports, the hashing secret and packet content are not transferred to diagnostics.


The tray obtains the state with the `get-status` command at a basic fixed interval of 5 seconds and additionally immediately after each `connect` or `disconnect` command. The Connecting progress window has, for the whole time it is open, its own periodic `get-status` every 500 ms. This timer neither shifts, replaces nor stops the basic interval and ends when the window closes. Neither interval changes adaptively. After a one-off service check of the validity of the current configuration triggered by a click, Statistics may use the last available in-memory snapshot or trigger a single immediate `get-status` that does not affect the basic timer. Open Statistics are then updated from the periodic five-second snapshots. The contract uses neither streaming nor a subscription to state changes.

The tray uses the exact source files `assets/disconnected.ico`, `assets/connecting.ico` and `assets/connected.ico`, embedded in the PE resources. The application icon of all EXEs and top-level windows is `assets/default.ico`. The status icons do not affect the icon of the forms. All icons are original PHPVPN artwork (a blue, red, orange or green field with a vertical and a horizontal rectangle and a center), in vector form in `assets/phpvpn*.svg`. The user interface of both platforms MUST NOT use a shield-with-lock motif or other Material Symbols icons. The distribution keeps the license notices of the bundled components.

The tray application menu has exactly this order:

1. **Connect/Disconnect**, toggled according to the in-memory VPN state. Connect starts the global bootstrap and the Connecting progress window. Disconnect is sent immediately through the independent control path and tracked until it actually completes.
2. Separator.
3. **Configuration Wizard**, described below.
4. **Communication contracts**, the actual editor over the currently stored valid configuration. It opens only through this explicit choice, which performs exactly one `get-config-document`. Wizard Finish does not open it.
5. **Edit Config**, the actual UTF-8 text from `get-config-document`, with the buttons **Save**, **Reset** and **Cancel** according to the rules below.
6. Separator.
7. **Show Info**, a one-off `get-server-info`. The separate Server information window is shown only after the whole result has been validated. The **Who is online** tab shows the contracts, the local time of the last contact and the state according to UX06. The **Raw server information** tab contains the exact received authenticated plaintext, read-only. The current server returns indented JSON using `JSON_PRETTY_PRINT`; the client does not reformat it and also supports an older compact response. The native EDIT allows the original LF as well as CRLF through EM_SETEXTENDEDSTYLE, available since Windows 10 1809. The text is not re-serialized for display or copying. #### Distribution and installation on Windows

The authoritative and binding methodology for building the distribution, its structure, completeness and verification is defined in [distribution.md](distribution.md). The following rules define the behavior of the client installation and operation; the requirements on Wintun and integrity remain in the section Wintun baseline and distribution integrity of this document.

The installer does not own a JSON template. The first successful initialization of the service after installation creates a missing default; every further start keeps the existing bytes. At runtime, a deleted file can be created by a confirmation in Edit Config or by a successful Wizard Finish. The service and the tray must be updated together.

[make-dist.ps1](client/tools/make-dist.ps1) prepares a standalone Windows offline package: `phpvpn-service.exe`, `phpvpn-tray.exe`, the console `phpvpn.exe`, the graphical entry points `install-phpvpn.exe` and `uninstall-phpvpn.exe`, the unrenamed `wintun.dll` of the corresponding architecture, the Wintun license, and the installation and uninstallation BAT/PowerShell scripts. It requires an explicit `-OutputDirectory <path>` under the project `work` or `dist`; the `dist` root itself is not allowed. The whole server and client distribution is created by [tools/make-distribution.ps1](tools/make-distribution.ps1) according to [distribution.md](distribution.md). `release-manifest.json` is a compact single-line UTF-8 JSON without BOM with a list of files and SHA-256. The detached RSA-PKCS1-SHA256 signature is in `release-manifest.sig`, the public certificate in `release-signing.cer`. The `SignBinaries` option at build time additionally signs all five EXEs; it does not replace the manifest signature. The package contains the necessary components without downloading them during installation.

`install.bat` passes the arguments to the bundled [install.ps1](client/tools/package/install.ps1). A regular installation requires administrator privileges; if they are missing, the script requests elevation. The current procedure has this order:

1. It verifies the presence of the manifest, the signature and the certificate, the single-line form of the manifest without BOM, the JSON and `manifestVersion = 1`. It requires the RSA-PKCS1-SHA256 algorithm, a match of the pinned identity `ExpectedThumbprint` with the certificate, the signature record and the manifest, and a valid signature of the exact bytes of the manifest. The development pin is not a permanent identity of the specification.
2. It verifies the presence and SHA-256 of each file listed in the manifest. It requires all three EXE names in the list and rejects unlisted `.exe` and `.dll` files in the package root. This is not a ban on all superfluous files; this check does not reject an unlisted text file.
3. It verifies a valid Authenticode signature of `wintun.dll` and a publisher subject containing `WireGuard`. It compares the PE architecture of the service and of the DLL with each other and with the architecture from `PROCESSOR_ARCHITECTURE`.
4. It runs the bundled service binary with `--verify-tunnel` and requires exit code zero. This mode loads the DLL and verifies the mandatory API without creating an adapter or session. `install.bat -VerifyOnly`, or `install.ps1 -VerifyOnly`, ends after this step. It does not require elevation and does not proceed to installation writes, service registration or autostart. A verification error before these writes rejects the package.
5. It prepares the installation root under `ProgramFiles\phpvpn` and a subdirectory according to `releaseVersion` with the installation ACL. Before the first copy, it asks the installed tray processes, through `WM_CLOSE` of the main window, for a regular Exit, including confirmation of unsaved changes. It waits at most 30 seconds for each process. A refusal, timeout or unavailable session aborts the installation without forced termination. Then it stops the existing service and requires the Stopped state. It verifies that the existing target files are released and only then copies the manifest files and the three verification artifacts. The order applies even with an identical `releaseVersion`. Existing target files are copied with overwriting; this is not a separate immutable staging generation. The ProgramData data tree is prepared by the service; the installer does not rewrite it recursively with an ACL.
6. It writes the version to `current.generation.new` and moves it to `current.generation` with `Move-Item -Force`. This switch alone does not guarantee a transactional recovery of the whole installation.
7. If the `phpvpn` service exists, it calls `--uninstall` from the new generation and requires a successful exit code. Its `--install` follows, the exit code check and `Start-Service`. The service itself creates the public local pipe `phpvpn-control-v1`; the installer checks for its presence in at most 50 attempts with a 200 ms wait. A missing pipe ends the installation with an error without an automatic rollback.
8. Only after the pipe is available does it set the `phpvpn-tray` item in `HKLM\Software\Microsoft\Windows\CurrentVersion\Run` to the quoted tray path in the new generation for further interactive logons. Finally it tries to start the tray in the current session. This last step suppresses start errors and is not a confirmation of a visible icon.

[uninstall.ps1](client/tools/package/uninstall.ps1), called through `uninstall.bat`, evaluates the generation according to the pointer. If the console and a running service are available, it requests disconnection through `phpvpn.exe disconnect` and waits two seconds. Then it terminates the tray processes and unregisters the service through the service binary, or uses Stop-Service and an SCM fallback. It removes the HKLM Run item and the installation directory, while leaving an installation root marked as a reparse point. A regular uninstall keeps the configuration, the ownership journal and the logs in ProgramData. Removing them requires an explicit `uninstall.bat -RemoveData` or `uninstall.ps1 -RemoveData`. The script does not call `WintunDeleteDriver`. This description provides no guarantee of a transactional uninstall or of the undelivered recovery after a crash.

#### Mandatory Windows integration and lifecycle tests

Each supported release and architecture MUST pass at least these scenarios before publication:

1. a clean installation from the complete Windows x64 distribution folder according to [distribution.md](distribution.md), the first bootstrap and creation of exactly one `phpvpn` adapter and one session with a 4MiB ring;
2. installation and operation on a system where Wintun is used at the same time by WireGuard or another application, without changing or removing its adapter and driver;
3. fail-closed rejection after a change of the DLL hash, an invalid signature of the manifest or the DLL, a wrong architecture, a missing mandatory API and an unsupported running version, always without a new service and network change;
4. repeated connect/disconnect cycles, partial failure of each initialization and teardown phase, and a check that no own address, route, second adapter or session remains;
5. a crash and restart of the service in each phase, including reconciliation of own leftovers without interfering with foreign network configuration;
6. sleep, hibernate and resume while waiting for the receive event, during a polling request and with a full send ring, without a busy loop and deadlock;

29. repeated concurrent calls of `get-status` during full data traffic read only memory, start no network, tunnel or recovery, change neither the state nor the counters and cause no measurable blocking of the three worker roles; neither the snapshot nor an IPC error contains any secrets or other forbidden data, and opening the **Statistics** window introduces no new IPC command and does not change the fixed five-second tray polling.
30. recovery after a successful and an unsuccessful initial bootstrap keeps the original checkpoints. A new logical connect atomically resets them, an idempotent connect does not. The tray takes over the current triple without accumulation. The success of Server URL must be readable in the snapshot before the cryptographic verification starts, verified by a controlled run without an artificial wait in the production code.
31. a timeout in each step of the initial bootstrap distinguishes an unsuccessful completion of the check from a key rejection. The tray and the console receive the same safe codes, English descriptions and recoverability. A non-authorization error is not a key rejection, and an outage of a running connection is not automatically a tunnel start error.
32. a partial body before a timeout, cancellation, read error or exceeding the size limit is counted once at the completion of the attempt, including the read block over the limit. Before disconnect completes, the accounting is closed and reset; a later read stays zero.
33. a 100-byte packet deferred by the server and resent in a second request adds 2 packets and 200 IPv4 bytes. Each attempt is counted only when the request is handed over, never a second time after the response.
34. nine uint64 counters above 2^53 and around INT64_MAX and UINT64_MAX pass from the service through JSON into the Statistics model without loss of precision. The ten native fields keep the order and format of [UX07](tray_UX.md#ux07-statistics): poll and packet counts stay exact integers with English commas, bytes are shown in B or in rounded decimal kB/MB/GB/TB/PB. Verify 999/1000 B, round-half-up, unit transitions after rounding and the highest PB. Total size must first exactly sum both source counters, including the carry above UINT64_MAX, not their rounded texts. Reordering JSON members does not change the parser. An invalid read keeps the whole snapshot with the stale text; before the first snapshot dashes are shown. Resize, tab order, copying and scrolling to focus must work even for the longest value.
35. the separate 500 ms polling of the existing `get-status` in the progress window does not change the deadlines of the basic five-second polling, even when Statistics is open. Closing the progress window ends its timer; the basic timer continues. On opening, Progress performs exactly one existing `get-config`, shows only the URL and the local IP and logs neither the whole config nor sensitive values. A controlled concurrent change of the stored document proves the accepted possibility that the details belong to a newer stored configuration than the active connection. Edit Config shows the configuration URL and keys in accordance with its function. Only the designated configuration and Wizard error may show the fixed path or URL according to its schema, never keys. Both scroll bars of the editor work even after resize and DPI change.

### macOS

The macOS client is the third platform over the same portable core `phpvpn-core`, the same IPC v1 contract and the same split into service, CLI and tray as Windows and [Linux](#linux). The rules of the core, configuration, Wizard, IPC, security model and tray UX from the other parts of this document and from [tray_UX.md](tray_UX.md#macos-appkit) apply unchanged unless this section explicitly states a macOS deviation. The v1 split tunnel also applies: the service adds only `virtualIp` with the prefix from `vpnCidr` and a single explicit route of the exact `vpnCidr` prefix through its own interface; it MUST NOT change the default route or DNS and introduces no kill switch. The platform layer is in the shared folder `client/src/platform/posix/` and in `client/src/platform/macos/`, the application entry points in `client/apps/service/service_main_macos.cpp`, `client/apps/cli/main.cpp` and `client/apps/tray-macos/`, and the installation files in `client/packaging/macos/`. The design was created according to [plan-macos-v001.md](Plans/2026-10-30-18-08-06/plan-macos-v001.md). The port is developed on Windows without a physical Mac; compilation, tests and packaging run in GitHub Actions (`.github/workflows/client-macos.yml`, runner `macos-15`, Apple Silicon). #### Build and installed components

macOS is built in C++20 without language extensions with Apple clang from Xcode, CMake at least 3.28 and the Ninja generator for the **arm64** architecture with a minimum system of **macOS 14**. The [root CMake file](client/CMakeLists.txt) accepts Windows, Linux and macOS (`PHPVPN_PLATFORM` `macos`). For Apple clang it enables `-Wall -Wextra -Wpedantic -Werror`, `-fstack-protector-strong`, PIE and `_FORTIFY_SOURCE=2` in optimized configurations; the GNU ld options (`relro`, `now`, `noexecstack`) do not exist on Darwin. The service and the CLI require OpenSSL 3 (`libcrypto`) linked **statically** from the prefix `PHPVPN_OPENSSL_ROOT` (typically Homebrew `openssl@3`) and libcurl at least 8.4 **from the macOS SDK** (the system `libcurl.4.dylib`, no bundled library). The tray requires only the system frameworks AppKit, Foundation and UserNotifications. The option `PHPVPN_BUILD_TRAY=OFF` builds the service and the CLI without the tray. The script `client/tools/macos/build.sh <preset>` performs configure, build and unprivileged ctest.

| Preset | Configuration | Meaning |
|---|---|---|
| `macos-debug` | `Debug` | clang with `BUILD_TESTING=ON`. |
| `macos-release` | `RelWithDebInfo` | Optimized build with debug information; used by CI and packaging. |
| `macos-asan` | `Debug` | AddressSanitizer and UndefinedBehaviorSanitizer (`PHPVPN_ENABLE_ASAN=ON`). |
| `macos-headless` | `RelWithDebInfo` | Without the tray (`PHPVPN_BUILD_TRAY=OFF`). |

All macOS presets have `BUILD_TESTING=ON`, `CMAKE_OSX_DEPLOYMENT_TARGET` 14.0, `CMAKE_OSX_ARCHITECTURES` arm64 and a separate directory `work/build/<preset>`. A universal binary with x86_64 is not part of this stage: it requires a second static build of OpenSSL for x86_64 and `lipo`. The installation rules target the volume root (`cmake --install` with `DESTDIR` into the package staging):

| File | Role |
|---|---|
| `/Library/PrivilegedHelperTools/phpvpn-service` | Daemon. The only owner of the configuration, the `utun` interface, the address, the route, the three VPN worker roles, the global counters and the VPN state. |
| `/usr/local/bin/phpvpn` | CLI, a pure IPC client. Needs neither root nor a graphical session. |
| `/Applications/phpvpn Tray.app` | Menu bar application in AppKit (`LSUIElement`, no Dock icon), a pure IPC client. |
| `/Library/LaunchDaemons/com.pilandrome.phpvpn.plist` | Registration of the daemon in launchd. |
| `/Library/LaunchAgents/com.pilandrome.phpvpn-tray.plist` | Tray autostart after each user's logon (the counterpart of HKLM Run and XDG autostart). |

Neither the tray, the CLI nor any other application MAY open `utun`, change addresses, routes or interfaces, or read and write the configuration file. They control the service exclusively through IPC. Installation, uninstallation, registration, starting and stopping of the daemon are not IPC operations; registration is performed by the installation package and control by `launchctl`. The service has no `--install` or `--uninstall` switches.

#### Package, installation and uninstallation

The client is shipped as the installation package `phpvpn-<version>-arm64.pkg` (`pkgbuild` + `productbuild`, identifier `com.pilandrome.phpvpn`) with `preinstall` and `postinstall` scripts. The binaries and the tray bundle are signed **ad hoc** (`codesign -s -`), and the package is neither signed with a Developer ID nor notarized. This is a deliberately documented limitation of the same nature as the development certificate of the Windows package: Gatekeeper blocks a double-click on a downloaded `.pkg`, while installation through `sudo installer -pkg … -target /` from a terminal or through the supplied `install.sh` succeeds. The composition of the distribution folder `client/macOS` is defined in [distribution.md](distribution.md#macos); the user guide is the bundled [README.md](client/packaging/macos/dist/README.md). The package does not own `/Library/Application Support/phpvpn`; `config.json` is written by the service; both an upgrade and removal of the package keep the configuration.

The installation entry point is [install.sh](client/packaging/macos/dist/install.sh) (`sudo sh install.sh [--headless] [--verify-only]`). It is fail closed and changes nothing until all verifications pass, in this order: root (once through `sudo`), macOS at least 14 and arm64 (`sw_vers`, `uname -m`), the manifest signature (the SHA-256 of the public key from `release-signing.cer` MUST match the pin in `install.sh`, and `release-manifest.sig` MUST verify the canonical `release-manifest.json` with the same RSA PKCS#1 v1.5 SHA-256 mechanism as on Linux, verified by the system `openssl`), the size and SHA-256 of each file from the manifest on a private copy owned by root, `installer -pkg`, `postinstall` (`launchctl bootstrap system` of the daemon, `kickstart`, waiting at most 30 s for the socket, registration of the tray LaunchAgent in `gui/<uid>` of the logged-in user unless `--headless`) and `phpvpn status`. `--verify-only` ends after the hash check without root. [uninstall.sh](client/packaging/macos/dist/uninstall.sh) (`sudo sh uninstall.sh [--remove-data]`) first requests `phpvpn disconnect` on a best-effort basis, performs `launchctl bootout` of the agent and the daemon, and removes the package files according to `pkgutil --files` and `pkgutil --forget`. The configuration, state and logs are preserved; only `--remove-data` removes them.

#### Paths and permissions

The production paths are fixed constants ([paths_macos.h](client/src/platform/macos/paths_macos.h), shared logic in [paths_posix.h](client/src/platform/posix/paths_posix.h)). They are not derived from the environment, the configuration or IPC. Because the trusted directory walk opens each component with `O_NOFOLLOW`, and `/var` and `/etc` are symbolic links into `/private` on macOS, the canonical paths `/private/var/…` are used. `/Library` has the sticky bit and is writable by the `admin` group, which the shared rule allows.

| Path | Owner and mode | Content |
|---|---|---|
| `/Library/Application Support/phpvpn/` | `root:wheel`, `0700` | Configuration directory. |
| `/Library/Application Support/phpvpn/config.json` | `root:wheel`, `0600` | Configuration. The publication files `config.publish-journal`, `config.previous` and `config.stage.<uuid>.tmp` are in the same directory, mode `0600`. |
| `/private/var/db/phpvpn/` | `root:wheel`, `0700` | Service state, `ownership.json` (`0600`). |
| `/private/var/run/phpvpn/` | `root:wheel`, `0755` | Runtime directory, created by the daemon at each start. |
| `/private/var/run/phpvpn/control-v1.sock` | `root:wheel`, `0666` | Public IPC v1 control socket. |
| `/private/var/run/phpvpn/service.lock` | `root:wheel`, `0600` | Service singleton lock. |
| `/private/var/log/phpvpn/` | `root:wheel`, `0755` | `phpvpn-service.log` with 8 MiB rotation and five historical files, `launchd.log` with the daemon's stdout/stderr. |

At each start the service normalizes its directories in the same way as on Linux: it creates a missing directory, requires root as the owner and sets the exact mode; each ancestor must belong to root and must not be writable by the group or others without the sticky bit. A symbolic link, a foreign owner or an unsafe ancestor means fail closed with `config_directory_security_invalid`. An unusable configuration or state directory does not stop the service, and IPC reports a safe configuration error; an unusable runtime directory, log directory or an unobtained singleton lock ends the start. The hidden service switches `--config-dir`, `--state-dir`, `--runtime-dir`, `--log-dir` and `--adapter-name`, the CLI switch `--socket` and the tray variables `PHPVPN_TRAY_TEST_SOCKET`, `PHPVPN_TRAY_TEST_SERVER_UID`, `PHPVPN_TRAY_TEST_OPEN_WINDOW` and `PHPVPN_TRAY_TEST_CAPTURE_DIR` serve only isolated tests and CI; neither the package, the LaunchDaemon nor the LaunchAgent sets them.

#### Service and launchd

[service_main_macos.cpp](client/apps/service/service_main_macos.cpp) shares the portable composition [service_runtime](client/apps/service/service_runtime.h) with Windows and Linux. The service MUST run with effective uid 0. Modes:

| Switch | Behavior |
|---|---|
| `--launchd` | Default if the parent is launchd (`getppid() == 1`) or `XPC_SERVICE_NAME` is set. Logs to the file `/private/var/log/phpvpn/phpvpn-service.log` with rotation as on Windows. A VPN state change is logged; launchd has no counterpart of `STATUS=`. |
| `--foreground`, `--console` | Default otherwise. Runs in a terminal with logging to stdout until SIGINT or SIGTERM. |
| `--verify-tunnel` | Verifies the kernel control `com.apple.net.utun_control` (`CTLIOCGINFO`) without creating an interface and prints the kernel version. Requires root. |

SIGTERM and SIGINT are set to `SIG_IGN` and received through `kqueue` with `EVFILT_SIGNAL`; SIGHUP and SIGPIPE are ignored. Stop performs the shared ordered teardown `ServiceRuntime::stop`. At most one instance is ensured by an exclusive non-blocking `flock` on `service.lock`. The automatic Connect according to `autoConnectOnStartup` starts only after the IPC server has started, as the counterpart of SCM RUNNING and `READY=1`.

The plist [com.pilandrome.phpvpn.plist](client/packaging/macos/launchd/com.pilandrome.phpvpn.plist) starts `/Library/PrivilegedHelperTools/phpvpn-service --launchd` with `RunAtLoad`, `KeepAlive` `SuccessfulExit=false` and `ThrottleInterval` 5. launchd restarts only after an unsuccessful exit and at the earliest after 10 s; the three-step series 5/17/60 s from systemd and Windows has no counterpart in launchd. `ExitTimeOut` of 45 s limits termination. launchd offers no systemd sandbox (capabilities, `ProtectSystem`, syscall filter); the daemon runs as root without further restriction, which is an accepted platform limitation.

#### Public local IPC over a Unix socket

macOS uses the same `SOCK_STREAM` Unix socket, `u32` big-endian + JSON frame, 4 MiB limit, 32 slots, 5000 ms deadline, 250 ms tick, executors and `busy` response as Linux, with the shared implementation [ipc_unix.h](client/src/platform/posix/ipc_unix.h). The fixed path is `/private/var/run/phpvpn/control-v1.sock` (`kIpcSocketPath`). The differences are only in the system primitives ([event_wait.h](client/src/platform/posix/event_wait.h)): `kqueue` with `EVFILT_READ`, `EVFILT_WRITE` and `EVFILT_TIMER` instead of `epoll` and `timerfd`, `pipe` instead of `eventfd`, `accept` with `fcntl` instead of `accept4`, `SO_NOSIGPIPE` instead of `MSG_NOSIGNAL`. Before sending any byte, the client MUST verify through `getpeereid` (the counterpart of `SO_PEERCRED`) that the peer runs with uid 0. The access model, error codes, the CLI `hint:` lines and the save classification are identical to Linux; the macOS hint for a service that is not running states `sudo launchctl bootstrap system /Library/LaunchDaemons/com.pilandrome.phpvpn.plist`.

#### Configuration file on disk

The shared implementation [config_files_posix.cpp](client/src/platform/posix/config_files_posix.cpp) keeps the semantics, file names, the `PHPVPN-CONFIG-1` journal, recovery states and the publication order from the section [Linux](#configuration-file-on-disk). macOS deviations: creating a missing file uses `renameatx_np(RENAME_EXCL)` instead of `renameat2(RENAME_NOREPLACE)`; synchronization of the journal and publication uses `fcntl(F_FULLFSYNC)` with a fallback to `fsync`; the file system is assessed by `statfs.f_fstypename`, and network and FUSE file systems (`nfs`, `smbfs`, `afpfs`, `webdav`, `cifs`, `osxfuse`, `macfuse`, `fuse`, `ftp`) are rejected with the error `not_supported`. The ownership record `ownership.json` is written durably through the shared `durableReplaceFile` with `F_FULLFSYNC`.

#### utun interface and ownership

The tunnel uses exclusively the macOS kernel control `utun` ([tunnel_utun.cpp](client/src/platform/macos/tunnel_utun.cpp)): `socket(PF_SYSTEM, SOCK_DGRAM, SYSPROTO_CONTROL)`, `CTLIOCGINFO` for `com.apple.net.utun_control` and `connect` to `sockaddr_ctl`. The client MUST NOT use a kext, TAP, Network Extension or any other backend; Network Extension remains the path for iOS and a possible App Store distribution. `loadAndVerify` verifies the availability of the kernel control and creates nothing. The interface is created only after a successful bootstrap and preflight.

The name `utunN` is assigned by the kernel and cannot be chosen. The configured `adapterName` `phpvpn` is a logical name written to the journal and the log; the actual name is logged at creation. The ownership tag `phpvpn-owner:<GUID>` (GUID `{a1c4e7b2-6d3f-4a8e-9b0c-5e2d7f1a3c64}`) is stored in the **interface description** (`SIOCSIFDESC`, the counterpart of the Linux `ifalias`), and the interface identity is `(ownerTag << 32) | ifindex` according to [interface_identity.h](client/src/platform/macos/interface_identity.h), with the same protection against index recycling as on Linux. Immediately after creation the service sets the description, MTU **1500** and `IFF_UP` and verifies everything. No IPv6 address is configured; the kernel assigns none to a fresh `utun`.

`utun` is a datagram interface with a 4-byte protocol family header before each packet. The input worker reads with `recvmsg` into the caller's buffer; a packet longer than the buffer, recognized through `MSG_TRUNC`, is counted in `oversizedReceiveCount` and not delivered; a packet of a family other than `AF_INET` is dropped and counted. The output worker writes one packet with one `writev` including the header. A full queue leads to a bounded interruptible wait of 200 × 5 ms through `poll` and then to `busy`. Both waits include the stop pipe. `endSession` keeps the descriptor so that the kernel client removes the route and address from the live interface; `closeAdapter` closes the descriptor and waits at most 2 s for the interface to disappear. On a crash or kill of the service, the macOS kernel removes the interface itself, which is the main safety property of recovery. A persistent `utun` does not exist: `removeOwnedPhantomInterface` is a success only when the identity is absent; a live interface with the tag is `journal_ambiguous`. `runningDriverVersion` returns 0.

#### Network configuration through PF_ROUTE

[netconfig_route.cpp](client/src/platform/macos/netconfig_route.cpp) is its own small routing socket client without another library: `socket(PF_ROUTE, SOCK_RAW, AF_INET)`, sequence numbers and PID for response correlation, a 2 s timeout. Encoding and decoding of `rt_msghdr` with aligned `sockaddr` structures is in the pure [route_codec](client/src/platform/macos/route_codec.h), testable without privileges. Error texts contain only the `errno` number.

The address is added with `SIOCAIFADDR` on a point-to-point interface with both `ifra_addr` and the destination equal to `virtualIp` and the mask from `vpnCidr`. The route is added with an `RTM_ADD` message with `RTF_UP|RTF_STATIC`, the destination and mask from `vpnCidr` and the `sockaddr_dl` gateway of the own interface (a route of type `-interface`); a next hop different from 0.0.0.0 uses `RTF_GATEWAY`. macOS routes have no metric: `routeMetric` from the shared core is not written to the system, the snapshot states metric 0, and a match of an existing route is assessed by destination, mask, interface and gateway. An already existing address or route is a success only on an exact match. Removal from an own interface that no longer exists is a success. Before each change the service verifies that the interface with the given index still carries the tag in its description; it does not modify a foreign interface.

`snapshot()` contains the IPv4 addresses of all interfaces (`getifaddrs`), IPv4 unicast routes from `sysctl(NET_RT_DUMP)` without cloned and ARP entries, the default route `0.0.0.0/0` and the DNS servers from SystemConfiguration (`State:/Network/Global/DNS`, `ServerAddresses`, IPv4 only, sorted without duplicates, [dns_snapshot.h](client/src/platform/macos/dns_snapshot.h)). A missing key means no server; an unavailable dynamic store is a snapshot error and fails closed. `isHostReachableOutsideInterface` uses `getaddrinfo` and `RTM_GET`; the shared core does not call it yet.

#### HTTP transport, cryptography and clocks

The transport is the shared [transport_curl.cpp](client/src/platform/linux/transport_curl.cpp) over libcurl from the macOS SDK, with the same behavior as the WinHTTP adapter (one deadline, body limit, no redirects, no proxy, no cookies, HTTP/1.1, TLS at least 1.2, `trustAnyTlsCertificate`). The system libcurl uses Apple's TLS backend (SecureTransport or LibreSSL depending on the system version); `trustAnyTlsCertificate=true` disables both certificate and host name verification, the same as on Linux. The wire value `"winhttp"` in the Wizard diagnostics remains. The cryptographic `CryptoProvider` is the shared [crypto_openssl.cpp](client/src/platform/linux/crypto_openssl.cpp) over the statically linked OpenSSL 3; `SecureBuffer` erases through `memset_s`. The clocks ([clock_macos.cpp](client/src/platform/macos/clock_macos.cpp)) map `monotonicMs` to `CLOCK_UPTIME_RAW` (stops during sleep, the counterpart of the Linux `CLOCK_MONOTONIC`), `leaseMonotonicMs` to the Darwin `CLOCK_MONOTONIC` (runs during sleep too, the counterpart of `CLOCK_BOOTTIME` and `GetTickCount64`) and `systemUtcMs` to `CLOCK_REALTIME`.

#### Tray in AppKit

The macOS tray is a native AppKit application in Objective-C++ (`NSStatusItem` in the menu bar, `NSWindow` windows) without Qt, Electron, WebView and without a third-party library. It uses the portable models, texts, colors and IPC timeouts shared with Windows and Linux and is a pure IPC client. Exit, logoff, termination or a crash of the tray MUST NOT disconnect the VPN. At most one instance runs in each session (bundle `com.pilandrome.phpvpn-tray`); a second launch passes `--show-window` or `--installation-complete` to the primary instance and exits. Autostart is provided by the LaunchAgent; the installation notice is shown through UserNotifications. The tray implements all windows of the Windows tray; the mapping of UX, menu, icons and deviations is defined in [tray_UX.md, macOS (AppKit)](tray_UX.md#macos-appkit). Configuration error texts state the path `/Library/Application Support/phpvpn/config.json`.

Neither the existence of the implementation nor an individual test run is a claim of complete acceptance; verification results belong in dated reports.

#### Packages, installation and uninstallation

The Linux client is shipped as two binary packages in RPM format for Fedora ([phpvpn.spec](client/packaging/linux/rpm/phpvpn.spec)) and DEB format for Ubuntu ([debian/control](client/packaging/linux/debian/control)). The composition of the distribution folder `client/Linux/x64` is defined in [distribution.md](distribution.md#linux-x64); the user guide is the bundled [README.md](client/packaging/linux/dist/README.md).

| Package | Content | Dependencies and license |
|---|---|---|
| `phpvpn` | Service, CLI, systemd unit, NetworkManager snippet, `phpvpn(1)`, `phpvpn-service(8)`. | Only the service and CLI libraries from automatic soname dependencies, no graphical dependency. License `MIT`. |
| `phpvpn-tray` | Tray, launcher, autostart, hicolor icons, `phpvpn-tray(1)`. | Exactly the same release of `phpvpn` (RPM `= %{version}-%{release}`, DEB `= ${binary:Version}`), GTK 3 and libayatana-appindicator3 from soname dependencies, RPM additionally `hicolor-icon-theme`. A weak Recommends dependency on `gnome-shell-extension-appindicator`, but the extension is not enabled. License `MIT` like `phpvpn`; the icons are original PHPVPN artwork. |

An RPM build with `--without tray` creates only `phpvpn`. The packages do not own `/etc/phpvpn` or `/var/lib/phpvpn`; the directories are created by systemd and `config.json` is written by the service. Upgrading and removing the package therefore keep the configuration. `apt purge phpvpn` removes both directories; RPM never owns them. After an upgrade the package restarts the service (RPM `%systemd_postun_with_restart`, DEB `dh_installsystemd --restart-after-upgrade`). The package itself follows the distribution convention: RPM performs `%systemd_post`, so the service is enabled only according to Fedora presets and stays disabled without a preset. DEB enables and starts the service with the default `dh_installsystemd`.

The installation entry point is [install.sh](client/packaging/linux/dist/install.sh) (`sudo sh install.sh [--headless | --with-tray] [--no-weak-deps] [--verify-only]`). It is fail closed and changes nothing until all verifications pass, in this order:

1. Root privileges. Without them the script re-runs itself once through `sudo`, and if `sudo` is not available, it refuses the installation.
2. The distribution from `/etc/os-release`: Fedora or Ubuntu on x86_64 in the minimum version from the signed manifest.
3. The manifest signature. The SHA-256 of the public key (DER SubjectPublicKeyInfo) from `release-signing.cer` MUST match the pin in `install.sh`, and the detached RSA PKCS#1 v1.5 SHA-256 signature in `release-manifest.sig` MUST verify the canonical `release-manifest.json`.
4. The size and SHA-256 of each file from the manifest, verified on a private copy owned by root, which is then the only source of the installation. An unlisted package or script in the folder causes the installation to be refused.
5. Installation of the local packages through `dnf install` or `apt-get install`. Their dependencies come from the distribution repositories.
6. `phpvpn-tray` is added if the folder contains it and the system has a graphical login, i.e. the default target `graphical.target` and an existing `display-manager.service`. `--with-tray` always installs it, `--headless` never. An already installed `phpvpn-tray` is always updated together with `phpvpn` because of the dependency on the exact release, even with `--headless`.
7. `systemctl enable --now phpvpn.service`.
8. Waiting at most 30 s for the socket `/run/phpvpn/control-v1.sock`.
9. `phpvpn status`.

After completion the service is always enabled and running, as after installation on Windows. `--verify-only` ends after step 4, installs nothing and does not need root. `--no-weak-deps` does not install weak dependencies, on Fedora through `install_weak_deps=False` and on Ubuntu through `--no-install-recommends`. Running it again with a newer folder updates the packages. A running tray is not stopped; the new version takes effect at the next logon.

[uninstall.sh](client/packaging/linux/dist/uninstall.sh) (`sudo sh uninstall.sh [--remove-data]`) first asks the service for `phpvpn disconnect` on a best-effort basis, then performs `systemctl disable --now phpvpn.service` and removes `phpvpn-tray` and `phpvpn`. The configuration `/etc/phpvpn` and the state `/var/lib/phpvpn` are preserved. Only `--remove-data` removes them, the counterpart of the Windows `-RemoveData`.

#### Paths and permissions

The production paths are fixed constants ([paths_linux.h](client/src/platform/linux/paths_linux.h)). They are not derived from the environment, the configuration or IPC:

| Path | Owner and mode | Content |
|---|---|---|
| `/etc/phpvpn/` | `root`, `0700` | Configuration directory. |
| `/etc/phpvpn/config.json` | `root`, `0600` | Configuration. The publication files `config.publish-journal`, `config.previous` and `config.stage.<uuid>.tmp` are in the same directory and have mode `0600`. |
| `/var/lib/phpvpn/` | `root`, `0700` | Service state. |
| `/var/lib/phpvpn/ownership.json` | `root`, `0600` | Ownership record of the tunnel interface for recovery. |
| `/run/phpvpn/` | `root`, `0755` | Runtime directory. |
| `/run/phpvpn/control-v1.sock` | `root`, `0666` | Public IPC v1 control socket. |
| `/run/phpvpn/service.lock` | `root`, `0600` | Service singleton lock. |

Only root reads the configuration file. This is the Linux convention for a file with secrets and satisfies the requirement of protecting the configuration from direct access through the file system. The intentionally public `get-config` and `set-config` over IPC are not restricted by this. A user obtains the configuration through `phpvpn get-config`, Edit Config or the Wizard.

At each start the service normalizes its directories as the counterpart of the Windows ACL repair. It creates a missing directory; its parent must exist. It requires root as the owner and sets the exact mode from the table. Each ancestor must belong to root and must not be writable by the group or others unless it has the sticky bit. A symbolic link, a foreign owner or an unsafe ancestor means fail closed with `config_directory_security_invalid` without any change. An unusable configuration or state directory does not stop the service: IPC stays available and reports a safe configuration error. An unusable runtime directory or an unobtained singleton lock ends the service start.

The hidden service switches `--config-dir`, `--state-dir`, `--runtime-dir` and `--adapter-name`, the CLI switch `--socket` and the tray variables `PHPVPN_TRAY_TEST_SOCKET` and `PHPVPN_TRAY_TEST_SERVER_UID` serve only isolated test instances. The production unit, launcher and autostart MUST NOT use them.

#### Service and systemd

[service_main_linux.cpp](client/apps/service/service_main_linux.cpp) shares with the Windows host the portable composition [service_runtime](client/apps/service/service_runtime.h): the engine, ConfigStore, the automatic startup Connect, the Wizard, the dispatcher, the IPC work classification and the IPC server, with the same order of construction and termination. The service MUST run with effective uid 0, otherwise it refuses to start. Modes:

| Switch | Behavior |
|---|---|
| `--systemd` | Default if `NOTIFY_SOCKET` is set. Runs under `Type=notify`: `READY=1` after the IPC server starts, `STATUS=VPN <state> (<phase>)` on a state change and `STOPPING=1` on termination. The log goes through stderr to journald. |
| `--foreground`, `--console` | Default without `NOTIFY_SOCKET`. Runs in a terminal with logging to stdout until SIGINT (Ctrl+C) or SIGTERM. Creates a missing runtime directory. |
| `--verify-tunnel` | Verifies that `/dev/net/tun` is the character device 10:200, can be opened, and that `TUNGETFEATURES` offers `IFF_TUN` and `IFF_NO_PI`. Prints the offered features and the kernel version. Creates no interface and does not change the network. |

It receives SIGTERM and SIGINT through `signalfd` and ignores SIGHUP and SIGPIPE. Stop performs the shared ordered teardown `ServiceRuntime::stop` as on Windows: it cancels the startup Connect, stops the IPC server, terminates the Wizard and the engine, including removal of the route, address and interface, and only then does the process exit. At most one instance is ensured by an exclusive non-blocking `flock` on `/run/phpvpn/service.lock`; a second instance ends with the error `service_already_running`. The automatic Connect according to `autoConnectOnStartup` uses the same logic as on Windows and starts only after `READY=1`, in foreground mode after the initial message. This is the counterpart of the SCM RUNNING notification.

The unit [phpvpn.service](client/packaging/linux/systemd/phpvpn.service) starts `/usr/libexec/phpvpn/phpvpn-service --systemd` as `Type=notify` with `User=root`, `Wants=` and `After=network-online.target` and `WantedBy=multi-user.target`. The restart policy `Restart=on-failure`, `RestartSec=5s`, `RestartSteps=2` and `RestartMaxDelaySec=60s` gives delays of 5 s, about 17 s and 60 s as the counterpart of the Windows recovery 5/15/60 s and requires systemd at least 254. `TimeoutStopSec=45s` limits termination. The directories are created by systemd through `ConfigurationDirectory=phpvpn` (`0700`), `StateDirectory=phpvpn` (`0700`) and `RuntimeDirectory=phpvpn` (`0755`).

The unit MUST keep minimal privileges and a sandbox: `CapabilityBoundingSet=CAP_NET_ADMIN`, `NoNewPrivileges=yes`, `UMask=0077`, `ProtectSystem=strict` with `ReadWritePaths=/etc/phpvpn`, `ProtectHome=yes`, `PrivateTmp=yes`, `DevicePolicy=closed` with `DeviceAllow=/dev/net/tun rw`, `ProtectKernelTunables=yes`, `ProtectKernelModules=yes`, `ProtectKernelLogs=yes`, `ProtectControlGroups=yes`, `ProtectClock=yes`, `ProtectHostname=yes`, `RestrictNamespaces=yes`, `RestrictRealtime=yes`, `RestrictSUIDSGID=yes`, `LockPersonality=yes`, `MemoryDenyWriteExecute=yes`, `SystemCallArchitectures=native`, `SystemCallFilter=@system-service` and `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK`. Root without `CAP_DAC_OVERRIDE` works only with files it owns; a foreign owner means fail closed. `ProtectKernelTunables=yes` is possible because the service does not write to `/proc/sys` and disables IPv6 on the tunnel through netlink. Extending capabilities or weakening the sandbox requires a change of this specification.

#### Public local IPC over a Unix socket

The Linux IPC is a `SOCK_STREAM` Unix socket at the fixed path `/run/phpvpn/control-v1.sock` (`kIpcSocketPath`), the counterpart of the fixed pipe `\\.\pipe\phpvpn-control-v1`. The path contains the contract version, and the production client MUST NOT take it from user input. The message schema, the command whitelist, the response envelopes, the errors and the contract version are identical to the section [Public local IPC](#public-local-ipc) and [IPC v1 extensions](#ipc-v1-extensions).

Each message has a frame: the length of the UTF-8 JSON body as a `u32` big-endian, followed by the body. The body has at most **4 MiB (4194304 bytes)**, separately for the request and the response. One connection carries exactly one request and one response. The explicit length distinguishes a complete response from a truncated one, on which the classification of a save as confirmed or unknown depends. The server closes a connection with a zero or over-limit length without a response.

[IpcSocketServer](client/src/platform/linux/ipc_unix.h) uses `epoll`, `timerfd` with a maintenance tick of **250 ms**, at most **32 connection slots**, `accept4` with `SOCK_CLOEXEC|SOCK_NONBLOCK` and a read and write deadline of **5000 ms**. Reading is counted from the acceptance of the connection to the complete request, writing from the start of sending the response to the close by the client. After writing the response, the server performs `shutdown(SHUT_WR)` and waits for the client to close within the output deadline, the same as on Windows. If all slots are occupied, further clients wait in the listen backlog. The executors, queues, the `busy` response and the drain on termination are shared with Windows in [ipc_executors](client/src/platform/iface/ipc_executors.h), with the same capacity `shortControl` 16, `file` 4 and `diagnostic` 1 according to the section [Implementation limits of local control](#implementation-limits-of-local-control). The work classification is a shared service function for both platforms.

The access model does not change: the socket has mode `0666` and every local process may use it. The server does not authorize the client by uid, gid, PID, program path or data in the message. The risk of unauthorized local control, configuration changes and disclosure of its secret values is accepted the same as on Windows according to the section [Security model and accepted risks](#security-model-and-accepted-risks). The replacement for `FILE_FLAG_FIRST_PIPE_INSTANCE` against socket spoofing is the directory `/run/phpvpn` owned by root and not writable by others, the service singleton lock and the rule that the server replaces an existing path only if it is a socket owned by root. Another file in place of the socket, a foreign owner or a writable directory ends the IPC start with the error `ipc_unavailable`. On termination the server removes only the socket with its own identity (`st_dev`, `st_ino`).

The client ([IpcSocketClient](client/src/platform/linux/ipc_unix.h)) MUST verify through `SO_PEERCRED`, before sending any byte, that the peer runs with uid 0. Otherwise it ends with `ipc_unavailable` and sends nothing, in particular not `set-config` with secrets. A missing socket or `ECONNREFUSED` means that the service is not running, `EACCES` or `EPERM` denied access. Both return `ipc_unavailable`. On a full listen backlog the client retries until its deadline, then returns `timeout`. A close before the first byte of the response is `ipc_unavailable`, a close inside the frame or a zero length is `ipc_malformed`, and an announced length above the limit is `ipc_message_too_large`. The client records whether the whole request was sent, for the save classification in the tray.

The CLI keeps the commands, outputs, the `code: description` format on stderr, the exit codes 0/1/2 and the 10 s timeout from Windows. Linux only adds, after an unreachable service, a second `hint:` line with the probable cause (service not running, socket missing, access denied, peer is not root). The error codes do not change. On Linux the Wizard IPC accepts as `configPath` only an absolute normalized POSIX path without control characters, empty segments, `.` and `..`.

#### Configuration file on disk

[config_files_linux.cpp](client/src/platform/linux/config_files_linux.cpp) implements the `ConfigFiles` interface with the same semantics, file names and journal format `PHPVPN-CONFIG-1` as Windows. The recovery states `clean`, `confirmed`, `notPublished` and `unknown` are identical. It keeps the directory open with `O_DIRECTORY|O_NOFOLLOW` and performs all operations relative to it through `*at` calls. Before an operation it verifies again that the fixed path through safe ancestors still leads to the same directory.

Publication proceeds in this order:

1. The stage file `config.stage.<uuid>.tmp` is created through `openat(O_CREAT|O_EXCL|O_NOFOLLOW, 0600)`. The mode and owner are verified even before the first secret byte is written.
2. The exclusively created journal `config.publish-journal` is written and synchronized with `fsync` of the file and the directory.
3. The content is written to the stage, `fsync` is performed, the stage is reopened read-only and its identity and SHA-256 are verified.
4. The existing `config.json` is backed up by the hard link `config.previous` (`linkat`).
5. Replacement uses `renameat`, creation of a missing file `renameat2(RENAME_NOREPLACE)`. `fsync` of the directory and verification of the published identity (`st_dev`, `st_ino`) follow.
6. `CONFIRMED` is appended to the journal and `fsync` is performed.

On opening, the configuration file must be a regular file owned by root, not writable by the group or others, with `nlink == 1`. The only exception is the transient pair `config.json` and `config.previous` of the same inode created by the publication itself. The directory must belong to root and must not be writable by the group or others. Network and FUSE file systems (NFS, SMB, CIFS, SMB2, FUSE, 9P, Ceph, AFS, kAFS and Coda according to `statfs`) are rejected with the error `not_supported`. This is the counterpart of the requirement for local NTFS.

The ownership record `ownership.json` is written durably through `durableReplaceFile`: a temporary file is created exclusively with `O_NOFOLLOW` and mode `0600`, followed by `fsync`, `renameat` over the target and `fsync` of the directory. After a power failure the target therefore contains either the previous or the complete new content.

#### TUN interface and ownership

The tunnel uses exclusively the Linux kernel TUN device `/dev/net/tun` as the L3 interface for IPv4 ([tunnel_tun.cpp](client/src/platform/linux/tunnel_tun.cpp)). The client MUST NOT use TAP, its own kernel module or any other tunnel backend. `loadAndVerify` verifies the character device 10:200 and the offer of `IFF_TUN|IFF_NO_PI` and creates nothing. As on Windows, the interface is created only after a successful bootstrap and preflight.

`createAdapter` opens `/dev/net/tun` with `O_RDWR|O_CLOEXEC|O_NONBLOCK` and through `TUNSETIFF` creates an interface with the exact name `phpvpn` and the flags `IFF_TUN|IFF_NO_PI|IFF_TUN_EXCL`, without `IFF_MULTI_QUEUE` and without `TUNSETPERSIST`. The interface is non-persistent and lives only while the service holds the descriptor. Thanks to `IFF_TUN_EXCL`, an existing interface of the same name is a collision, not an attachment. It ends with the error `netconfig_preflight_conflict` without interfering with the foreign interface. `openAdapter` returns `not_supported`; the shared core does not call it on Linux. Immediately after creation the service sets through netlink:

- `IFLA_IFALIAS = phpvpn-owner:<GUID>` as the ownership tag. The GUID is the fixed Linux installation identity in canonical lowercase form.
- MTU **1500**, the default value of the Linux kernel for TUN. The MTU of the Wintun adapter has not been measured; another value requires measurement and a change of the specification.
- `IFLA_INET6_ADDR_GEN_MODE = none` even before `IFF_UP`, so the interface gets no IPv6 address, including link-local. Without IPv6 support in the Linux kernel the step is skipped.
- `IFF_UP`.

The service then verifies the name, the tag, `IFF_UP` and the MTU. A mismatch is an error without a session. The input worker reads through `readv` into the caller's buffer with a one-byte overflow field. A packet longer than the buffer is counted in `oversizedReceiveCount` and not delivered. The output worker writes one packet with one `write`. A full queue leads to a bounded interruptible wait of 200 × 5 ms through `poll` and then to `busy`, the same as with Wintun. Both waits include the stop `eventfd`; neither polls in a busy loop. The ring capacity has no counterpart on Linux and is ignored.

`endSession` stops the session but keeps the descriptor, so that the shared core removes its own route and address from the live interface in the same order as on Windows. `closeAdapter` closes the descriptor; the Linux kernel removes the interface together with remaining addresses and routes, and the service verifies its disappearance through netlink, waiting at most 2 s. On a crash or kill of the service, the Linux kernel removes the interface itself. This is the main safety property of Linux recovery. The ownership record and startup recovery use the shared core `tunnel_session` unchanged, including the read-only wait of at most 5 s for the interface to disappear. `removeOwnedPhantomInterface` may remove only a persistent single-queue TUN interface without an attached descriptor, without an owner other than root, and with an identical name, tag and identity. Every other state is `journal_ambiguous`, fail closed. Because the client does not use `TUNSETPERSIST`, this path does not occur in regular operation. `runningDriverVersion` returns 0.

The basic implementation uses one TUN file descriptor and three shared worker roles. Linux multiqueue TUN is an optional optimization; it must not change the shared rules of flow classification, DRR, sub-bucket FIFO, queue limits or packet ownership.

#### Network configuration through netlink

[netconfig_netlink.cpp](client/src/platform/linux/netconfig_netlink.cpp) is its own small rtnetlink client without another library: a `NETLINK_ROUTE` socket with `SOCK_CLOEXEC`, sequence numbers, `NLM_F_ACK`, checking of `nlmsgerr`, a send and receive timeout of 2 s, and repetition of a dump marked `NLM_F_DUMP_INTR` at most three times. Message encoding and decoding is in the pure [netlink_codec](client/src/platform/linux/netlink_codec.h), testable without privileges. Error texts contain only the `errno` number, not the localized system text.

On Linux the `interfaceLuid` field carries the platform interface identity `(uint64(ownerTag) << 32) | ifindex` ([interface_identity.h](client/src/platform/linux/interface_identity.h)). `ownerTag` is the first four bytes (big-endian) of the SHA-256 of the canonical installation GUID, never 0. A non-zero tag is given only to an interface whose `IFLA_IFALIAS` exactly matches the tag `phpvpn-owner:<GUID>`; foreign interfaces have tag 0. After the own interface disappears and its ifindex is recycled by a foreign interface, the old identity therefore does not exist and a false match cannot arise. Before each change of an address or route, the service verifies that the interface with the given ifindex still carries the tag. It rejects a change of a foreign interface.

The address is added with an `RTM_NEWADDR` message with `IFA_LOCAL`, `IFA_ADDRESS`, the prefix from `vpnCidr`, `NLM_F_CREATE|NLM_F_EXCL` and the flag `IFA_F_NOPREFIXROUTE`. Without it, the Linux kernel would add its own prefix route and the explicit route of the service would end with `EEXIST`. The route is added with an `RTM_NEWROUTE` message in the `main` table with `RTPROT_STATIC`, `RTA_OIF`, `RTA_PRIORITY` equal to the metric **5** from the shared core and `NLM_F_CREATE|NLM_F_EXCL`. A next hop of 0.0.0.0 uses `RT_SCOPE_LINK`, any other next hop `RT_SCOPE_UNIVERSE` with `RTA_GATEWAY`. An already existing address or route is a success only on an exact match of the ifindex, address, prefix, destination, next hop and metric. Removal from an own interface that no longer exists is a success, because the Linux kernel has removed the resource.

`snapshot()` for the fail-closed preflight and the check of an unchanged default route and DNS contains the IPv4 addresses of all interfaces and the IPv4 unicast routes of all tables except `local`, without cloned entries, with the interface identity, metric and next hop. The default route is `0.0.0.0/0` with the lowest metric in the `main` table. The DNS servers are the sorted deduplicated IPv4 addresses from two sources ([dns_snapshot.h](client/src/platform/linux/dns_snapshot.h)):

- `nameserver` lines of `/etc/resolv.conf`. After the usual symbolic link resolution, the file must be a regular file of at most 64 KiB. A missing file means no server. An unreadable file, another type or a file that is too large is a snapshot error and fails closed.
- The `DNS` property of the `org.freedesktop.resolve1.Manager` interface through sd-bus, and only if the name `org.freedesktop.resolve1` has an owner on the system bus. The service thus never activates systemd-resolved. Waiting on the bus is limited to 2 s. Unavailability of resolved or of the bus is not an error, because the client does not assume a specific network manager.

`isHostReachableOutsideInterface` is implemented with the Windows semantics (`getaddrinfo` for IPv4 and `RTM_GETROUTE` for each address). The shared core does not call it on any platform yet.

#### HTTP transport, cryptography and clocks

[transport_curl.cpp](client/src/platform/linux/transport_curl.cpp) implements the `Transport` interface through libcurl with the same behavior as the WinHTTP adapter: one absolute monotonic deadline for DNS, connection, TLS, sending, headers and the whole body, a response body limit, accounting of read bytes across every failure, optional header capture for Wizard diagnostics and immediate cancellation. Each transport owns one persistent easy handle and its own multi handle, which holds the connection pool. Reuse of keep-alive connections between requests thus corresponds to a WinHTTP session. `configure` discards the pool, the same as closing a WinHTTP session. Requests run serially through `curl_multi_poll`. `cancelCurrentRequest` only marks the request and wakes the wait through `curl_multi_wakeup`. The owner then removes the easy handle, which interrupts DNS, the connection, the TLS handshake and a slow read. Each request starts with `curl_easy_reset`, so a cancelled or expired transfer leaves no state and the transport remains usable. A late success after the deadline or after cancellation is never returned.

The transport options are fixed: only `http` and `https`, no redirects, an empty proxy with `NOPROXY "*"`, so that even the `http_proxy` variables are ignored, no `.netrc`, no HTTP authentication, no cookie engine, `CURLOPT_NOSIGNAL`, TLS at least 1.2 and enforced **HTTP/1.1**. `trustAnyTlsCertificate=true` disables both certificate and host name verification; otherwise the system CAs are used. The headers come from the `httpHeaders` block. The transport adds `Content-Type` according to the action and `Connection: Keep-Alive` like WinHTTP, and suppresses the implicit `Accept:` and `Expect:` (no 100-continue). `Host` and `Content-Length` are filled in by libcurl. User-Agent comes only from the block. Header values go on the wire as the configured UTF-8. A `Content-Length` mismatch or a prematurely terminated body is `transport_receive_failed`; exceeding `maxResponseBodyBytes` is `transport_response_too_large`. The mapping of errors to the DNS, connect, TLS, timeout and cancelled codes corresponds to WinHTTP.

The wire value `"winhttp"` in the `requestHeadersSource` and `responseHeadersSource` fields of the IPC v1 Wizard diagnostics remains unchanged, because IPC v1 is a fixed contract. On each platform it means "the headers were captured by the platform transport", so on Linux by libcurl through `CURLOPT_DEBUGFUNCTION` and `CURLOPT_HEADERFUNCTION`. The capture limits and the fallback version `HTTP/?` are the same as on Windows.

The cryptographic `CryptoProvider` uses OpenSSL 3 EVP ([crypto_openssl.cpp](client/src/platform/linux/crypto_openssl.cpp)): SHA-256, HMAC-SHA256 through `EVP_MAC`, AES-256-GCM and `RAND_bytes`. Intermediate buffers are erased with `OPENSSL_cleanse`, `SecureBuffer` on Linux with `explicit_bzero`. The clocks ([clock_linux.cpp](client/src/platform/linux/clock_linux.cpp)) map `monotonicMs` to `CLOCK_MONOTONIC`, `leaseMonotonicMs` to `CLOCK_BOOTTIME`, which includes suspend like `GetTickCount64`, and `systemUtcMs` to `CLOCK_REALTIME`.

#### Logging to journald

Linux uses neither the file log nor the 8 MiB rotation and five historical files from the section [Logging and diagnostics](#logging-and-diagnostics). In `--systemd` mode the service writes each record with one call to stderr with the sd-daemon priority prefix: `<7>` for trace and debug, `<6>` info, `<4>` warning, `<3>` error and `<2>` critical. It replaces CR and LF inside a message with a space, so that journald does not split the record and lose the priority. It omits the ISO timestamp of the formatted line, because journald assigns the time. The level, component and message remain. Retention and rotation are governed by the journald configuration. In `--foreground` mode the complete formatted lines go to stdout. The content rules of the log apply unchanged: no keys, tags, ciphertexts, packet content, whole bodies or internal paths. The log is read with `journalctl -u phpvpn`, extended diagnostics with `phpvpn diagnostics`.

#### NetworkManager, firewall and SELinux

The implementation does not assume a specific firewall or network manager, and their integration remains optional. The service has no dependency on NetworkManager, systemd-networkd or firewalld. The package installs the passive snippet `/usr/lib/NetworkManager/conf.d/90-phpvpn.conf` with the section `[device-phpvpn]`, `match-device=interface-name:phpvpn` and `managed=0`, so that NetworkManager neither manages the interface nor adds addresses, routes or DNS to it. The snippet does not replace the administrator's `unmanaged-devices` list. Without NetworkManager it has no effect. The client does not configure the firewall and adds no rules. Assigning the `phpvpn` interface to zones or rules is up to the system administrator.

On Fedora with SELinux in enforcing mode, the service runs without its own SELinux policy in the `unconfined_service_t` domain. The project ships neither a SELinux policy nor an AppArmor profile.

#### Tray in GTK

The Linux tray is a native GTK 3 application with an indicator through libayatana-appindicator3 (StatusNotifierItem). Both are system components of the target desktops, not a bundled framework. Qt, Electron and WebView are not used. The tray uses the portable models, texts, colors and IPC timeouts shared with the Windows tray and is a pure IPC client. As on Windows, it owns neither the service nor the VPN. Exit, logoff, termination or a crash of the tray MUST NOT disconnect the VPN.

The tray without a usable graphical display (neither `WAYLAND_DISPLAY` nor `DISPLAY` works) ends with code 1 and a clear message on stderr that it belongs in a desktop session and that without one the `phpvpn` command is used. The behavior is described by the manual page `phpvpn-tray(1)`.

In each desktop session at most one `GtkApplication` instance with the ID `org.phpvpn.Tray` runs. A second launch passes its arguments to the primary instance and exits. The autostart `/etc/xdg/autostart/phpvpn-tray.desktop` starts the tray without arguments for all users, as the counterpart of the Windows HKLM Run value. The launcher in the application menu starts `phpvpn-tray --show-window`, which shows the control window of the running instance. `--installation-complete` shows the installation notice through `org.freedesktop.Notifications`. When the desktop has no `org.kde.StatusNotifierWatcher`, for example Fedora Workstation with GNOME without the AppIndicator extension, the tray opens a fallback control window and once shows a notification with instructions for enabling the extension. The tray does not change desktop settings. The mapping of UX, menu, icons and windows is defined in [tray_UX.md, Linux (GTK)](tray_UX.md#linux-gtk). Configuration error texts state the path `/etc/phpvpn/config.json`.

The Linux tray implements all windows of the Windows tray: the Configuration Wizard with the HTTP headers dialog and HTTP error detail, Connect and Disconnect progress, Edit Config, Communication contracts, Password SHA, Server Information and Statistics. It registers them in the production build through opening hooks and the lifecycle registration of `TrayApp` ([tray_app.h](client/apps/tray-linux/tray_app.h)). Their Linux deviations are listed in [tray_UX.md, Application windows](tray_UX.md#okna).

### Android

The Android client is the fourth platform over the same portable core `phpvpn-core` and the same IPC v1 contract. Unlike Windows, [Linux](#linux) and [macOS](#macos), it has no separate service, CLI or tray: a single application combines the user interface, the foreground service `VpnService` and the native runtime in one process. The rules of the core, configuration, Wizard, IPC, security model, time synchronization, queues and DRR, soft recovery and recovery, and the server major version check from the other parts of this document apply unchanged unless this section explicitly states an Android deviation. The v1 split tunnel also applies: the client creates the interface only with `virtualIp` and the prefix from `vpnCidr` and a single route of the exact `vpnCidr` prefix; it MUST NOT change the default route or DNS and introduces neither a kill switch nor lockdown. The Internet, DNS, LAN and IPv6 of other applications remain on the underlying network. The supported versions are Android 14 (API 34) and later; older versions are neither supported nor tested. The platform layer is in `client/src/platform/android/` and in the shared `client/src/platform/posix/`, the JNI entry point and the runtime host in `client/apps/android-jni/`, the Kotlin project in `client/android/` and the tools in `client/tools/android/`. The design was created according to [plan-android-v001.md](Plans/2026-10-31-09-40-08/plan-android-v001.md) and the [screen map](Plans/2026-10-31-09-40-08/android-screen-map.md). The results of the work packages are in [android-client-report-2026-10-31.md](client/tests/android-client-report-2026-10-31.md) and in the partial reports `client/tests/android/wp*-report-2026-10-31.md`. The client is a development version and is not distributed yet (decision R2). Neither the existence of the implementation nor an individual test run on an emulator is a claim of complete acceptance; tests on a real device are NOT RUN so far.

#### Build and native library

The native part is built in C++20 without language extensions with clang from NDK r28c (`28.2.13676358`) and CMake 3.31.6 from the SDK, which Gradle runs. With `CMAKE_SYSTEM_NAME` `Android`, the [root CMake file](client/CMakeLists.txt) sets `PHPVPN_PLATFORM` `android` and does not build the service, the CLI or the tray, and the [application CMake](client/apps/CMakeLists.txt) adds only the target `phpvpn-android` (`libphpvpn-android.so`) from `client/apps/android-jni/`. It also compiles the shared `apps/service/service_runtime.cpp`, `startup_connect.cpp` and the tray models `contracts_save_machine.cpp` and `save_response.cpp`. For clang it enables `-Wall -Wextra -Wpedantic`, `-fstack-protector-strong`, `-fcf-protection` on x86_64, `-fPIC` instead of PIE (the output is a shared library; `-pie` is not used), `_FORTIFY_SOURCE=2` in optimized configurations and `-Wl,-z,relro,-z,now,-z,noexecstack`. The STL is `c++_static`. The library is linked with `-Wl,--exclude-libs,ALL` and the version script `libphpvpn-android.map`, so only `JNI_OnLoad` is exported from it and native methods are registered exclusively through `RegisterNatives`.

Cryptography and HTTP require statically linked OpenSSL 3.5.9 (3.5 LTS) and libcurl 8.23.0. They are built by [build-deps.sh](client/tools/android/build-deps.sh) (description in [README.md](client/tools/android/README.md)) on Linux, i.e. on a CI runner, in the Fedora VM or in WSL, with fixed versions and SHA-256 of the tarballs, for API 34, only as static libraries, curl only with HTTP and HTTPS, the OpenSSL backend, the threaded resolver and IPv6, without compression, HTTP/2, a CA bundle and a CA path. The output `<root>/<abi>/{include,lib}` with `manifest.json` is passed to CMake in the variable `PHPVPN_ANDROID_DEPS`. Gradle takes it from the property `phpvpn.androidDeps` in `client/android/local.properties` or from the environment variable `PHPVPN_ANDROID_DEPS`. Without it, the configuration passes, but compiling `phpvpn-android` ends with a readable `#error`. The Windows host does not compile the dependencies; it uses only a finished tree (R3).

The Kotlin project `client/android` uses Gradle 9.8.2 through the wrapper, Android Gradle Plugin 9.5.0 with the built-in Kotlin 2.4.21, Jetpack Compose with Material 3 (BOM 2026.09.00), Navigation Compose, Lifecycle, kotlinx.serialization and kotlinx.coroutines. It uses no network library; HTTP is handled by the native core. `minSdk` is 34, `targetSdk` 36 and `compileSdk` **37.2**: the current androidx libraries require compiling against API 37, and runtime behavior is determined by `targetSdk` 36. The ABIs are only `arm64-v8a` for devices and `x86_64` for the emulator (R4); `abiFilters` also exclude the 32-bit libraries of the dependencies. The native libraries have LOAD segments aligned to 16 KB (the NDK r28 default) and the APK passes `zipalign -c -P 16`. The application version is read from `project(phpvpn-client VERSION …)` in `client/CMakeLists.txt`; `versionCode` is `major × 10000 + minor × 100 + patch`.

#### Storage and permissions

All client data are in the application's private storage under `Context.getNoBackupFilesDir()`, which is protected by FBE encryption and is not backed up. The paths are composed by the runtime host [android_host.cpp](client/apps/android-jni/android_host.cpp) from the path passed by Kotlin in `nativeStart`. They are not derived from the configuration or IPC:

| Path under `noBackupFilesDir` | Mode | Content |
|---|---|---|
| `phpvpn/` | `0700` | Root of the client data. |
| `phpvpn/config/` | `0700` | Configuration directory. |
| `phpvpn/config/config.json` | `0600` | Configuration. The publication files `config.publish-journal`, `config.previous` and `config.stage.<uuid>.tmp` are in the same directory. |
| `phpvpn/state/` | `0700` | State, `ownership.json` (adapter journal). |
| `phpvpn/run/` | `0700` | Unused; Android has no socket. |
| `phpvpn/logs/` | `0700` | `phpvpn-service.log` with 8 MiB rotation and five historical files. |

The owner is the application uid (`getuid()`). On Android, the trusted directory walk of the shared [paths_posix.cpp](client/src/platform/posix/paths_posix.cpp) has a trust anchor (`trustRoot`) in `noBackupFilesDir`. It does not check the ancestors of the anchor, for example `/data` owned by `system`, because isolation is guaranteed by the application sandbox. The anchor MUST belong to the application uid and MUST NOT be writable by others; group permissions are not checked for it, because Android creates application directories with `0771`. Components under the anchor are subject to the same rules as on Linux. Without an anchor, the walk on Android fails with `invalid_argument`. The runtime normalizes the directories at every start. A symbolic link or a foreign owner does not stop the runtime: IPC runs and reports `config_directory_security_invalid`. On Android the text of this error refers to restarting the application, not to the administrator and a service restart.

`android:allowBackup="false"` and `dataExtractionRules` exclude all domains from cloud backup and from device-to-device transfer. Wrapping the configuration with a key from Android Keystore is not part of v1 (R5). Screens that display or edit secrets have `FLAG_SECURE`: 13 HTTP headers, 14 Server secret, 15 IP and access key, 20 and 22 contract detail, 21 Key from password, 23 and 39 editor and 42 default editor content. The flag counts references per window, so a transition between two secured screens does not remove it. Screen 18 does not repeat secrets and does not have the flag. Erasing secrets in the Kotlin layer is best effort: `SecretText`, character and byte arrays are zeroed; copies in immutable `String` (Compose fields, kotlinx.serialization) remain until GC cleanup. None of this is logged.

The application requests exactly six permissions: `INTERNET` (curl sockets), `ACCESS_NETWORK_STATE` (network snapshot), `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SYSTEM_EXEMPTED`, `POST_NOTIFICATIONS` and `RECEIVE_BOOT_COMPLETED`. The release build exports only the launcher activity `MainActivity`, the service `PhpvpnVpnService` protected by `BIND_VPN_SERVICE` and `BootReceiver`. The manifest removes androidx add-ons that would add the permission `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` or an exported `ProfileInstallReceiver`. The permission `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` is not used.

#### VpnService, service and lifecycle

The UI and the native runtime run in one process. `NativeRuntime.ensureStarted` starts `ServiceRuntime` on first use from `Application`, the service or the BootReceiver and keeps it for the whole life of the process. In the `disconnected` state without the service, the system may terminate the process. The configuration is on disk, and recovery (`ConfigStore::recover`, `recoverPreviousRun`) takes place at the next start. The automatic Connect of the core (`StartupConnect`) never runs at runtime start on Android; `autoConnectOnStartup` is evaluated by the BootReceiver.

[PhpvpnVpnService](client/android/app/src/main/kotlin/phpvpn/android/service/PhpvpnVpnService.kt) is a `VpnService` and at the same time a `TunnelHost`. It runs as a foreground service of type `systemExempted`, which the Android documentation allows for applications with a declared `VpnService`, because the bootstrap and recovery run at a time when the interface does not exist yet or no longer exists, and the system could otherwise terminate the process in the background. The service state is owned by its main thread; blocking calls run on IO. In `onCreate` the service **first** registers `TunnelHost` and only then starts the runtime, so no Connect reaches `loadAndVerify` without a host. The pure decisions (R9, service end, notification, schedule, fallback explanation) are in [ServicePolicy.kt](client/android/app/src/main/kotlin/phpvpn/android/service/ServicePolicy.kt) without a dependency on the Android framework. Lifecycle:

1. **Connect (02 → 03 → 04):** all Connect paths in the application, i.e. Connection (02, 06, 37), screen 25 Changes saved, Wizard 17 and the BootReceiver, go through the service ([ServiceConnectActions](client/android/app/src/main/kotlin/phpvpn/android/service/ServiceConnectActions.kt)). Consent is obtained through the Activity Result API, because the system dialog (03) stores consent only for a caller started this way. A refusal leads to screen 37 and is never shown as a server error; with lasting consent, 03 is skipped. With consent, the application calls `startForegroundService(ACTION_CONNECT)`, and the service immediately in `onStartCommand` enters the foreground with the notification "Connecting", writes `wantConnected=true` and sends `connect`. Android rejects the foreground type `systemExempted` without VPN consent with a `SecurityException`. A Connect without consent, for example from screen 25 after "Forget VPN", therefore starts the service through `startService` without a foreground phase and ends with `tunnel_permission_missing` (screen 37).
2. **Bootstrap and tunnel:** the engine performs `health`, `info` and the `ACCESS_KEY` check, and then `TunnelSession::start` creates the interface through `TunnelHost.establish` in the service (section [VpnService interface and ownership](#rozhraní-vpnservice-a-vlastnictví)).
3. **Recovery:** the teardown closes the descriptor and the system removes the VPN network. The service stays in the foreground with the notification "Reconnecting" (05); the next bootstrap calls `establish()` again.
4. **Disconnect (01 → 07 → 02):** Disconnect from the notification, from the UI and from Exit goes as `ACTION_DISCONNECT` to the running service, which sends `disconnect`. `wantConnected` is cleared already on the request, not only after confirmation, so that killing the process between the request and the confirmation does not override the user's Disconnect with a reconnect. The service and the notification are ended only by a confirmed idle state `disconnected` or `error` (phase `idle`, no own command in progress). Ending also in the `error` state is a deliberate deviation from the plan: in `error` nothing runs in the engine and screen 06 has no Disconnect, so a persistent notification could not be removed. Neither a timeout nor an unreadable state ever stops the service; in the UI they lead to screen 38, never to a false confirmation.
5. **`onRevoke()`:** another VPN application took over the single VPN slot (a work profile has its own). The service clears `wantConnected`, records the reason for screen 02 and sends `disconnect`. This is a regular Disconnect, not an error or recovery, and the service never reconnects. Android does not distinguish a takeover of the slot from revoking consent with "Forget VPN", so both cases show the same text about a takeover by another VPN on 02.
6. **Always-on:** when the system starts the service with the action `android.net.VpnService`, the service enters the foreground and connects only with `get-config-state` `valid`; otherwise it writes this to the log and ends. It publishes `isAlwaysOn()` and `isLockdownEnabled()` for Settings (10) and About (34). Lockdown is not supported; the UI and the log only warn about it.
7. **`autoConnectOnStartup`:** on Android it means "after device startup". [BootReceiver](client/android/app/src/main/kotlin/phpvpn/android/service/BootReceiver.kt) (`BOOT_COMPLETED`) starts the runtime, reads `get-config-document` and sends Connect through the service only for a valid document with a strict `autoConnectOnStartup: true` and with `prepare() == null`, i.e. lasting consent. Every other branch only writes the reason to the log. This behavior MUST NOT be presented as Always-on.
8. **Exit (35):** "Disconnect and close" sends Disconnect through the service, waits at most 30 s for a confirmed state and at most 3 s for the service to stop, and only then closes the task (`finishAndRemoveTask`). An unconfirmed disconnection closes the dialog and shows Connection (07 or 38). "Close window, stay connected" closes only the window (`finish`); the VPN, the service and the notification remain. The process is never forcibly terminated.
9. **Service destruction while running:** when the system destroys the service (`onDestroy`) while the engine is still working and the service was not ending by itself, it sends `disconnect`, waits at most 5 s for confirmation and only then unregisters `TunnelHost`.
10. **Process kill during an active connection (R9):** the descriptor, and thus the interface, disappears with the process, without `onRevoke`. `onStartCommand` always returns `START_STICKY`. The state file `phpvpn/state/intent.json` (`{"version":1,"wantConnected":…,"restartsElapsedMs":[…],"notice":…}`) is written by the service from Kotlin atomically (temporary file `0600`, `fsync`, `rename`, `fsync` of the directory); unreadable content means "do not connect". `wantConnected` is written on an accepted Connect (UI, boot, Always-on, R9) and cleared on Disconnect already on the request, on `onRevoke`, on Exit and on every confirmed end. A restart with an empty intent decides in this order: flag, limit, `prepare(this) == null`, `get-config-state` `valid`; the first failure ends it, so `prepare()`, which takes the slot of another VPN, is not called without the flag or after the limit is exhausted. The limit is at most three automatic reconnects in 10 minutes without a confirmed `connected`; the fourth restart in the window gives up, and a confirmed `connected` resets the series. Giving up (no consent, no valid configuration, limit) clears the flag, stores the local reason `process_restarted` (it is not an IPC code) and ends the service without entering the foreground. Screen 02 then explains that the connection ended because the system terminated the application. Without the flag nothing is shown. The flag never replaces the core state; the actual state is always `get-status`.

**Accepted limitation R9:** Android 14 and 15 often do not restart a sticky service after a process kill with an established VPN interface. On SIGKILL the system also releases its binding to `VpnService` and does not schedule a restart: on API 35 the restart took place in none of four attempts, on API 34 in one of five (R9 then connected correctly). Without an established interface (connecting, recovering) the restart always takes place. R9 therefore remains, but the usual visible behavior is the fallback explanation: every new application process (started by the UI, a receiver or a restart) checks after 10 s the `wantConnected` flag, a service that is not running and a confirmed idle state `disconnected`, clears the flag, and screen 02 shows the text about the system terminating the application. The fallback explanation never connects. If nobody starts the process, nothing is shown. Verification with a real LMK on a device belongs to WP11.

The notification (screen 09, [VpnNotifications.kt](client/android/app/src/main/kotlin/phpvpn/android/service/VpnNotifications.kt)) has the channel "VPN connection" with the importance `IMPORTANCE_LOW`, is persistent and alerts only once. The title is the state (Connected, Connecting, Reconnecting, Disconnecting, error, unavailable state), the text is the host of `serverUrl` and `virtualIp` from the public configuration members. It has the Disconnect action only in the connected, connecting and reconnecting states. Three monochrome icons derived from `assets/phpvpn-*.svg` differ in shape, not in color. Tapping the notification (and the configure intent of `Builder`) opens the application like the launcher icon: a new task starts on Connection, an open task returns unchanged, so an editor or Wizard in progress is not lost. Without the `POST_NOTIFICATIONS` permission the service keeps running. The first press of Connect asks for the permission; the result does not block Connect, and after a refusal the application shows an explanation once. The service reads the state through `nativeStatus()` off the main thread every 500 ms during its own command, after it until its settled result (at most 30 s) and during transitional states, otherwise every 5 s. A read that overlapped with the start or end of its own command is discarded and repeated. It rewrites the notification only on a change of state, phase or text. There is neither a one-second timer nor a push channel.

The client holds no permanent wakelock (R6). With the screen off the CPU sleeps and Doze restricts the network, so polling and packet delivery may be delayed. Settings offers a link to the system battery optimization settings (`ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`). The measurement of the behavior (T-A20) is NOT RUN, and the decision about a wakelock depends on its result.

#### In-process IPC

Android has no local socket, named pipe or other channel that another process could open, so the attack surface of the public local IPC disappears. The exact JSON contract of IPC v1, the work classification, `busy` responses and the shutdown order are preserved. [InProcessIpcServer](client/apps/android-jni/inprocess_ipc_server.h) is an `IpcServer` over the shared [IpcExecutors](client/src/platform/iface/ipc_executors.h) (`shortControl` 16, `file` 4, `diagnostic` 1) with the same classifier and busy response as the desktop. The Wizard `onTick` runs on its own thread every 250 ms. Shutdown follows the order of `IpcSocketServer::stopLocked`, and a stopped server is not started again; the runtime builds a new one at every start.

JNI `NativeBridge.nativeDispatch(request: ByteArray, timeoutMs: Int): ByteArray?` passes the UTF-8 request and blocks the calling thread at most until the caller's timeout. Strings cross JNI only as UTF-8 `byte[]`, never as `jstring`, whose modified UTF-8 would corrupt the data. A length above `kIpcMaxMessageBytes` (4 MiB) is rejected before copying. `null` means "no response": a timeout, a runtime that is not running, or an empty, over-limit or unclassifiable request for which the desktop closes the connection. An expired wait does not cancel the task; it finishes on its executor. Both the request and the response are overwritten with `secureWipe` on release. `nativeStatus()` returns a `get-status` snapshot with a fixed `requestId` for the service notification.

The Kotlin client (`IpcClient` in the `bridge` module) calls `nativeDispatch` exclusively on the limited dispatcher `Dispatchers.IO.limitedParallelism(8)`, never on the main thread, so a 30-second Connect does not block a 400 ms status. It uses the tray timeouts from [ipc_timeouts.h](client/apps/tray/ipc_timeouts.h): `get-status` 400 ms, commands 30 s, Wizard 5 s, progress 500 ms and auto refresh 5 s. It parses responses with a strict parser with the same rules as `core/protocol/json.cpp` (duplicate members, strict UTF-8, depth, the full uint64 range) and rejects unknown members where the desktop rejects them. Expiry of `get-status` or a `null` response is the "Status unavailable" state (screen 08), never success, and the next read may return any confirmed state. A Disconnect timeout is screen 38. `get-status` is queried only with a visible UI, every 500 ms in transitional states and during its own Connect or Disconnect, otherwise every 5 s. Error texts come exclusively from Android resources by code, never from a received `description`.

The portable models `ContractsModel`, `PasswordKeyModel`, `ServerInfoModel`, `contracts_save_machine` and `save_response` are available through JNI ([jni_models.cpp](client/apps/android-jni/jni_models.cpp)). As of 2026-11-01 the application uses the native `ServerInfoModel` and the native document check (`documentMatches`). For contracts, the password and save classification it uses Kotlin stand-ins in the package `phpvpn.android.standin` with the same test cases as the C++ models. Their configuration validation is only a structural subset; the service validation at `set-config` is always complete. `status_model`, `progress_model`, `poll_schedule.h`, `statistics_model.h` and `reconnect_controller.h` are rewritten in Kotlin with the adopted tests.

#### Configuration file in private storage

The content of the file is the same JSON document as on the desktop, because the editor shows the actual content and `ConfigStore` hashes the exact bytes. The shared [config_files_posix.cpp](client/src/platform/posix/config_files_posix.cpp) keeps the file names, the journal `PHPVPN-CONFIG-1`, the recovery states and the publication order from the section [Linux](#linux) with a single backup deviation. The SELinux policy `untrusted_app` forbids the application hard links in its data (`linkat` returns `EACCES`), so the backup `config.previous` cannot be created with a hard link. The backup strategy is determined by `PosixConfigFilePolicy::backupStrategy`: `hardLink` is the default on Linux and macOS, `exchange` on Android. macOS rejects the `exchange` strategy with `not_supported`, because it has no `RENAME_EXCHANGE`. Publication over an existing `config.json` with the `exchange` strategy:

1. The stage, the journal, their `fsync` and the verification of the identity and SHA-256 of the stage are unchanged.
2. Revalidation: `config.json` MUST be safe and have the identity of the original file from the journal, and `config.previous` MUST NOT exist. Otherwise nothing is published and the result is `config_write_failed`, so a target replaced during saving is never overwritten.
3. `renameat2(stage, config.json, RENAME_EXCHANGE)` is the publication point. The stage name now holds the original inode. A `fsync` of the directory follows.
4. Verification that the stage name holds the original identity, `renameat2(stage, config.previous, RENAME_NOREPLACE)` and `fsync` of the directory.
5. Verification of the identity of `config.json` and writing `CONFIRMED` to the journal, the same as with `hardLink`.

Creating a missing file is identical for both strategies (`renameat2(RENAME_NOREPLACE)`). The journal format does not change and the strategy is not recorded, because the inode identities distinguish every intermediate state. Recovery therefore does not depend on the configured strategy. The strategy adds a single intermediate state: `config.json` is the new stage, the stage name holds the original inode and `config.previous` is missing (a crash between steps 3 and 4). Recovery evaluates it as `confirmed`, completes the move to `config.previous` with `fsync` of the directory and then cleans up as after a `hardLink` publication. The step is repeatable. The guarantees of the section [Atomic write](#atomický-zápis-poslední-úspěšné-uložení-vyhrává) apply unchanged. T-N03 verified publication and recovery in the application sandbox on API 34 and 36.

The editor does not create a missing configuration silently. Opening the editor from screens 00, 10 and 36 first sends `get-config-document`. With `availability` `missing` it shows the confirmation dialog 36a with the actual absolute path from the service. Yes sends `create-default-config` without a path and content, and the editor opens the actual result; with `created:false` this is the document that was created in the meantime, without overwriting. No creates nothing. Cancel in the editor after a confirmed creation does not delete the file. Reset in the editor still uses `get-default-config` and changes only the draft. This is the same behavior as [Edit Config on the desktop](#edit-config-skutečný-obsah-vytvoření-a-reset).

The default configuration created at service start carries the placeholder `https://change-this-server-url.invalid`. Screen 02 recognizes it by the host (`WizardRules.PLACEHOLDER_HOST`, a mirror of `kPlaceholderServerHost`) in the summary from `get-config-document` and, instead of the notice "Configuration ready", shows a notice that the server address is not set, with a Set up button leading to step 12. Connect is offered for such a configuration anyway (the user can change the configuration in the editor at any time); the service rejects it with the code `config_server_url_unset` and the application shows the dialog "The server URL has not been configured yet. Do you want to set it up now?" with the buttons Set up and Not now; Set up opens 12, Not now closes the dialog without further text. Welcome 00 remains only for a missing file.

#### VpnService interface and ownership

An application without root has a single path to an L3 interface, `VpnService`, and the client MUST NOT use another backend. The descriptor from `Builder.establish()` behaves like a Linux TUN with `IFF_NO_PI`, i.e. a plain IPv4 packet without a header. The address, route and MTU are set by `Builder` atomically before the interface is created; a later change means a new `establish()`. [AndroidTunnelDriver](client/src/platform/android/tunnel_android.cpp) and [AndroidNetConfig](client/src/platform/android/netconfig_android.cpp) therefore share state through a single process-wide object [AndroidVpnContext](client/src/platform/android/vpn_context.h). It is created by `nativeStart` before `ServiceRuntime::start` and destroyed by `nativeStop` after `ServiceRuntime::stop`. Without an installed context, the factories return an object whose every operation fails with `tunnel_driver_unsupported`, never a null pointer. The core does not change; the order of `TunnelSession::start` remains `snapshot → preflight → loadAndVerify → createAdapter → addUnicastAddress → addRoute → snapshot → startSession`:

- `loadAndVerify` verifies consent through `NetworkHost.isConsentGranted()` (`VpnService.prepare(applicationContext) == null`); without consent it returns `tunnel_permission_missing`. With consent but without a registered `TunnelHost` it returns the non-recoverable `tunnel_driver_unsupported` with the description "the VPN service is not running", the same as without a context or without `NetworkHost`. In the tunnel start phase the core reports it publicly as `tunnel_start_failed` with `recoverable: false`, so a Connect without the service ends in the `error` state, not in an endless `recovering`. It creates nothing. A `TunnelHost` missing only in `establish()` (the service ended between the verification and the creation of the interface) remains the recoverable `tunnel_adapter_failed`.
- `createAdapter` assigns the synthetic identity `(0x414E << 48) | counter` (`0x414E` = "AN"; the counter is process-wide and a new context never repeats it), clears the interface specification and freezes the last snapshot taken without the adapter as the baseline.
- `addUnicastAddress` and `addRoute` do not change the system. They write into `VpnSpec` exactly `virtualIp` with the prefix and the `vpnCidr` route with the next hop 0.0.0.0 for the current identity; they reject a different value or identity with `netconfig_apply_failed`. The core's verification snapshot passes trivially, because nothing has been applied yet.
- `startSession` calls `TunnelHost.establish(spec)` in the service. The service builds a `Builder` with the session `phpvpn`, the address, the `vpnCidr` route, MTU **1500**, `addDisallowedApplication` of its own package, `allowFamily(AF_INET6)`, `setMetered(false)`, without a DNS server and with a configure intent to the main activity, and returns `detachFd()`. Immediately afterwards the driver compares a new snapshot with the baseline (`sameDefaultRouteAndDns`). A mismatch, a missing baseline or an unreadable snapshot closes the interface and returns `netconfig_verify_failed`. The descriptor gets `O_NONBLOCK` and `FD_CLOEXEC` and is served by [FdTunnel](client/src/platform/posix/fd_tunnel.h) shared with Linux: reading with `readv` with an overflow byte and the `oversized` counter, writing one packet with one `write`, `poll` with an `eventfd` stop and bounded waiting of 200 × 5 ms on a full queue.
- Kotlin never closes the descriptor; it is owned exclusively by the native driver. `endSession` leaves the descriptor open; `removeRoute` and `removeUnicastAddress` are a success without a system operation for the own identity. `closeAdapter` closes the descriptor and waits at most 2 s for the VPN network to disappear; without the service it only writes a warning to the log. `openAdapter` returns `not_supported`, `runningDriverVersion` 0.
- The `tunN` name is assigned by the system. The configured `adapterName` `phpvpn` and the GUID `{c2e5a8d1-7b4f-4e2a-8d3c-6f1b9e0a4d27}` are only an internal journal tag. `interfaceExists` is true only for the identity for which the process currently holds a descriptor. The interface disappears when the descriptor is closed or the process dies, which is the same security property as on Linux and macOS. After a process crash, `recoverPreviousRun` only cleans up the journal. `removeOwnedPhantomInterface` rejects an identity held by this process with `journal_ambiguous`.

A new interface gets a link-local IPv6 address from the kernel and the application cannot set `addr_gen_mode`. After creation the kernel therefore sends several IPv6 packets (MLD, router solicitation) into the tunnel. The input worker drops them as invalid, so after connecting the statistics show several dropped packets.

The JNI hosts ([jni_vpn_bridge.cpp](client/apps/android-jni/jni_vpn_bridge.cpp)) have different lifetimes. The process-wide `NetworkHost` (`snapshotNetworks()`, `isConsentGranted()`) is registered by `NativeRuntime` before `nativeStart`, because `recoverPreviousRun` and `ConfigStore::recover` run even without the service. The service-bound `TunnelHost` (`establish`, `lastEstablishError`, `waitVpnNetworkGone`) exists only with a live service. A native thread attaches to the JVM on the first call and detaches at its end. An exception in Kotlin is converted to a code and its text does not go to the log. JNI is called only from the engine's network thread (bootstrap) and from the teardown, never from the tunnel roles and never with a locked queue. `VpnService.prepare()` takes over the VPN slot from another application if consent persists, so it is called only on Connect and from the BootReceiver, never periodically.

#### Network configuration through ConnectivityManager

An application with `targetSdk` 30 and higher must not read the routing table through netlink. `snapshot()` therefore reads `ConnectivityManager` and `LinkProperties` of all networks through `NetworkHost` as JSON (version 1, at most 1 MiB, at most 64 networks, closed schema, an unknown member is `netconfig_apply_failed`). Conversion to `NetworkSnapshot`:

- Every network with `TRANSPORT_VPN` is skipped. The own VPN is not searched for by name: a foreign VPN is replaced by our `establish()` anyway, and its routes must not fail the preflight.
- The identity of addresses and routes of the underlying network is the interface ifindex with the upper 32 bits zero, so it never collides with the synthetic identity of the own interface. An unknown ifindex gives `0xFFFFFFFF`, never 0.
- The snapshot contains only IPv4 addresses and IPv4 unicast routes. The default route is the first IPv4 `isDefaultRoute()` of the active network; `defaultRouteMetric` is always **0**, because Android does not expose the metric (the same deviation as on macOS). DNS servers are the `dnsServers` of the active network in system order, both IPv4 and IPv6. An active VPN or a missing active network means no default route and no DNS.
- The preflight rejects with `netconfig_preflight_conflict` an address or route of the underlying network that reaches into `vpnCidr`, for example a Wi-Fi network that itself uses `10.99.99.0/24`. Switching the active network between the baseline and the verification after `establish()` ends with `netconfig_verify_failed` and is handled by the normal error classification of the core.
- `LinkProperties.getStackedLinks()` (464XLAT) is not a public API. On an IPv6-only network with clat the snapshot therefore has no IPv4 default route, but the baseline and the verification are consistent.
- `isHostReachableOutsideInterface` uses `getaddrinfo` and the longest match among the routes of the active underlying network. The core does not call it yet.

The client's own traffic (bootstrap, data, Wizard, `get-info`, `get-server-info`) never enters the tunnel thanks to `addDisallowedApplication`, even if the server address overlapped with `vpnCidr`. The preflight rejects such a server anyway. Other applications are subject to the VPN only for `vpnCidr`. The VPN has no DNS server, so the Android resolver uses the DNS of the underlying network. `allowFamily(AF_INET6)` prevents Android from blocking IPv6 for applications under a VPN without an IPv6 address and route. `setMetered(false)` takes over the meteredness of the underlying network. Spike T-A01b verified this on API 34, 35 and 36 emulators as uid 2000 before, during and after the creation of the VPN: DNS including a new name outside the resolver cache, TCP 443, HTTPS with a verified certificate, IPv6 to the emulator router and LAN over both ICMP and TCP worked unchanged. No DNS query and no packet outside the prefix arrived in the tunnel. The fallback path `addDnsServer` with the DNS servers of the active network is therefore not enabled, and the `dnsServers` field in the specification is reserved and empty. The per-uid VPN rules take effect only a moment after the VPN network is announced, so the first packet to the prefix within the first second may not arrive. Verification on a real device, with mobile data and with a real connection to the relay (T-A04) is NOT RUN.

#### HTTP transport, cryptography and clocks on Android

The transport is the shared [transport_curl.cpp](client/src/platform/linux/transport_curl.cpp) over the statically linked libcurl 8.23.0 with OpenSSL 3.5.9 without a change of logic: the same deadline, cancellation, byte accounting and header capture for `http-octets-v1` with the wire value `"winhttp"` as on Linux. Android provides no CA store readable through OpenSSL `CApath`; the files are named by the old hash `subject_hash_old`. With `trustAnyTlsCertificate=false` the platform hook `configureTlsTrust` therefore sets `CURLOPT_SSL_CTX_FUNCTION`, and [tls_trust_android.cpp](client/src/platform/android/tls_trust_android.cpp) loads the system CAs into one `X509_STORE`: preferably from `/apex/com.android.conscrypt/cacerts`, from `/system/etc/security/cacerts` only when APEX yields no certificate. User-added CAs are not loaded, the same as in the default Android policy. The store is loaded once per process, a failure is retried at the next request, and the error is `transport_tls_failed` without a path. On Linux and macOS the hook is empty. According to R8, `trustAnyTlsCertificate` has the same semantics as on the other platforms: `true` loads nothing and disables both certificate and host name verification. T-N04 verified in the application sandbox on API 34, 35 and 36 the loading of 134, 145 and 149 certificates from APEX, a verified HTTPS connection and the rejection of an expired certificate and of a foreign host name.

The cryptographic `CryptoProvider` is the shared [crypto_openssl.cpp](client/src/platform/linux/crypto_openssl.cpp) unchanged. On Android `SecureBuffer` erases with the C23 `memset_explicit` (bionic since API 34), because bionic has no `explicit_bzero`. This is the only Android change in `core/base`.

The clocks ([clock_android.cpp](client/src/platform/android/clock_android.cpp)) map both `monotonicMs` and `leaseMonotonicMs` to `CLOCK_BOOTTIME` and `systemUtcMs` to `CLOCK_REALTIME`. The Linux `CLOCK_MONOTONIC` stops during suspend, and a phone falls asleep many times per hour: the first authenticated request after wake-up would carry a timestamp lagging by the length of the sleep, and `TimeSync::systemClockChanged` would evaluate every sleep as a shift of the system clock. With `CLOCK_BOOTTIME` these deliberately accepted consequences apply:

- the request timestamp keeps running through sleep and the first request after wake-up is valid,
- the system clock shift detection does not falsely trigger after sleep,
- packets parked in the queues expire according to `maxQueuedPacketAgeMs` including the sleep time,
- a request interrupted by sleep measures an RTT including the sleep or its deadline expires, which is one transient error that soft recovery retries,
- the soft recovery budget of 90 s and the recovery backoff count the sleep time, so an episode started just before a long sleep ends after wake-up with a full recovery with a new `establish()`.

The core does not change. Verification on a device (T-A20: after 10 min with the screen off no 401 and at most one recovery in the log) is NOT RUN.

#### Logging to logcat

The logger writes to the file `phpvpn/logs/phpvpn-service.log` with 8 MiB rotation and five historical files as on Windows and macOS and at the same time to logcat through `__android_log_write` with the tag `phpvpn`. In logcat the ISO time and the level are omitted from the line; the level is carried by the priority (from trace as VERBOSE to critical as FATAL). Logcat receives only what the logger lets through; the content rules of the section [Logging and diagnostics](#logování-a-diagnostika) apply unchanged. Logcat is set up right at the beginning of `nativeStart`, so it also contains a storage error. The file is written only when the storage is usable, and the file is configured once per process.

## Recommended order of further work

The current Windows core, the WinHTTP/CNG adapters, the three VPN roles, the queues, the aggregated payload, the Wintun integration and the native tray are already part of the implementation. The same applies to the Linux platform layer, the systemd service, the CLI and the GTK tray according to the section [Linux](#linux). Implementing them again is not the next step. The existence of these parts does not mean that all integration, visual or performance test obligations are fulfilled.

1. When delivered parts change, verify the respective contract with the existing targeted tests. 2. The future pre-poll admission backpressure remains undelivered. Its requirement in the section Data reception may be marked as delivered only after implementation and corresponding verification. 3. The macOS port according to the section [macOS](#macos) is verified exclusively in GitHub Actions; manual acceptance on a physical Mac, the Intel architecture and a universal binary remain open and belong in dated reports. ## Configuration HTTP headers

`masterSetup.httpHeaders` is a mandatory string with at least one line `name: value`. JSON escapes the separators as `\r\n` or `\n`; the transport normalizes them to CRLF. One trailing separator is allowed. Empty lines, a lone CR, invalid names, control characters and embedded request/status lines are rejected.

The names `Content-Type`, `Content-Length`, `Connection`, `Host` and `Transfer-Encoding` belong to the application or the transport and are forbidden regardless of letter case. The error states the path, the line number and the forbidden name, never its value. A rejected document is not saved and the active configuration is preserved. An old file without `httpHeaders` is neither automatically migrated nor rewritten. User-Agent comes only from this block; when it is removed, at least one other header must remain. UTF-8 values are converted for WinHTTP as Unicode, without the system code page.

Each user name may appear in the block at most once. A second occurrence of the same name, including a different letter case, rejects the whole document with the line number and the name, without the value. The sending path neither deduplicates, filters nor merges anything.

For this validation, IPC and the editor carry only predefined error descriptions with the item path, the line number and, where applicable, the header name. Other internal error details continue to be replaced by a fixed safe description.

### Automatic connection at service start

`masterSetup.autoConnectOnStartup` is an optional strict JSON boolean with the default value `false`. A missing field in an old document means false, and reading alone does not rewrite the file. A new configuration and a wizard reset contain false as the last member of masterSetup, immediately after `useDefaultAccessKeyInWizard`. Saving the wizard keeps an explicit value and adds false to an old document. The option has no checkbox of its own.

The value is evaluated at service start; a change of the document at runtime does not by itself trigger it. An automatic Connect may happen only on a reliably read true and uses the regular validation and connection operation. An unreadable or corrupted document causes no automatic Connect; the service stays controllable and exposes a safe error in the status and the log.
The startup preference is read once asynchronously on the file executor, only after IPC is available and SCM RUNNING has been reported. A full queue leaves one pending task. A manual Disconnect and shutdown invalidate its generation. A newer manual Connect invalidates the startup request through the connection epoch, even if it has already ended with an error. A read, JSON or type error creates no network attempt. A readable true uses the same admission and connect sequence as a manual Connect, including full validation and recovery. An error before acceptance is published without a fictitious connection epoch, and after a fix a manual Connect can be used.

### Tray registration at logon

A direct `phpvpn-service.exe --install`, after successful registration of the service, writes a single REG_SZ value `phpvpn-tray` into the 64-bit `HKLM\Software\Microsoft\Windows\CurrentVersion\Run`. The content is the absolute quoted path to the existing `phpvpn-tray.exe` next to the service, without arguments. Windows starts it for the interactive user at logon. The service does not create the tray process. A command over 260 characters is rejected as a supplementary error.

Repeated registration of the same service succeeds. A different existing SCM registration is safely rejected, and a generation change uses an explicit package upgrade, which first removes the old registration. A missing service or Run value during uninstallation means success. Uninstallation attempts the SCM and the removal of its own Run value independently.

A failure of the autostart does not change a successful critical SCM result. The CLI prints a visible `WARNING` with the numeric Win32 code to standard output, so that Windows PowerShell does not treat the supplementary diagnostics on stderr as a fatal error. Repeating install/uninstall repairs the supplementary step. An actual SCM error still returns exit 1.


Package install/uninstall rely on the service EXE even when the service is already missing. Only when the binary is missing does the uninstall fallback separately remove its own value from the explicit Registry64 view. A registry error is a warning and does not stop the cleanup. The development switch `-WithTrayAutostart` remains compatible but is redundant. No new HKCU entry is created. An old entry of the current profile is removed only on an exact match with the build currently being handled. Other old profiles or paths require their own local check; no global migration takes place.

### Embedded Windows icons and package verification

The service, tray and CLI EXEs have the icon group ID 100 from the root `assets/default.ico`. The tray additionally contains IDs 101/102/103 from `disconnected.ico`, `connecting.ico`, `connected.ico`. Separate ICO files are not needed at runtime. CMake shares the resource configuration with the test UI hosts.

`phpvpn-icon-resource-tests <apps-directory> <source-assets>` verifies read-only all groups and the byte-for-byte match of the embedded frames, their Windows decoding, the manifest and the version resource. It is part of CTest. `verify-package.ps1` also runs it over the package, by default from the Release build or from the path `-IconResourceTest`. `uv run --with pillow client/tools/check_icons.py` verifies the four source ICOs and the mapping.

On a rollback to an old binary, first safely disconnect and stop the service, back up the current config and prepare a compatible document by removing only `autoConnectOnStartup`, or use a corresponding older backup while keeping the new user changes. The old validator rejects the new field. Verify the SCM and Run path again for the chosen generation.
### Headers in the Wizard draft and the shared template

The first step offers `HTTP headers`. An owned modal dialog edits a separate copy of the text. OK uses the shared validator and accepts CRLF without a trailing separator into the local draft. Cancel, Escape and closing the window discard the copy. Reset of the dialog only loads the default headers into its field. Without OK, the literal original value is kept, including LF and a permitted trailing separator.

Each URL, secret and access attempt uses the current `fields.httpHeaders`. The value in `context.httpHeaders` describes the original context and does not override the current field of the attempt. A change of the headers invalidates the URL, secret and access evidence. The service binds the evidence and the commit fingerprint to the exact header value, including the cases of returning, Resume and a repeated commitId. TLS, CIDR and limits continue to come from the service-owned context. Invalid headers are rejected before the network request.

Only Finish publishes the whole validated document with one existing atomic save. The limit of 524288 bytes applies to the final UTF-8 JSON including escaping, the other fields and the generated contracts. Opening the dialog, OK, Reset of the dialog and the checks neither create nor overwrite the file.

The shared default template for a missing configuration, Edit Config and its Reset contains `communicationContracts: {}`. No sample contract is inserted into it. Existing contracts do not change. The separate Wizard option for additive generation of default contracts and its deterministic keys remain preserved.
