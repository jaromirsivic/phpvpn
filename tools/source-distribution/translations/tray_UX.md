# Normative UX of the PHPVPN tray application

## UX00: Validity and sources

This document is the normative specification of the tray UX. The following overview distinguishes the implementation status from the actual scope of verification. It was created on 7 September 2026 according to the [assignment](notes/2026-09-07-11-19-48_notes.processed.md). The current implementation contains global validation, portable models, shared Win32 infrastructure, specialized windows, a common lifecycle and an isolated development runner. Their contract is defined by the corresponding parts of this document and by `client.md`. The historical order is preserved in [plan3_fix3.md](plan3_fix3.md), the past scope of verification in the [documentation audit saved on 8 September 2026](client/tests/implementation-plan3-fix3-wp07.md). Historical results are not a new test run. Full visual, accessibility and production runtime acceptance according to UX14 is not automatically fulfilled by the mere existence of the implementation. The distribution is not changed by this development path.

The words MUST, MUST NOT and MAY are binding. The identifiers UX01 to UX14 are test targets. [protocol.md](protocol.md) remains the authority for the wire protocol, [client.md](client.md) the authority for the other client rules and [distribution.md](distribution.md) the authority for the full release. The current contract is read from these specifications. Historical plans and handover reports preserve the origin of changes and the evidence of their time; they are not proof of the current code nor the single place where a requirement is defined.

Use Segoe UI; if it is unavailable, the system UI font. Configuration JSON, full keys, URLs and technical counter names use Consolas or an available monospaced font. The following sizes are logical font heights in DIP at 96 DPI, not typographic points. The native title bar uses the system metric.

The spacing base is 4 DIP. Between a label and a field 8, between related elements 12, between sections 24, the inner padding of a card 24 and the margin of the main content 32 DIP. On a small area the margin can be reduced to 16 DIP. Table rows have at least 48 DIP, the header 40 DIP. One-pixel lines are scaled to at least one physical pixel. Reference cards have an 8 DIP corner radius, text fields and buttons 4 DIP. Square corners of the native rendering, explicitly approved by the user, are a permitted visual deviation and are not a defect. This exception does not change dimensions, spacing, availability of actions or the other UX14 tolerances. A subtle shadow can be drawn as one extra line; an effects library is not necessary.

A button is at least 36 DIP high and 88 DIP wide, with 16 DIP horizontal padding. Longer labels determine a larger width by measuring the text. A field is at least 36 DIP high. The click area of a checkbox/switch includes the label and is at least 32 DIP high. On a small area the layout changes; neither the font nor the buttons shrink below a readable size.

## UX02: Shared components and rendering

The primary button is blue with white text, the secondary one is white with a border, the text button has a transparent background and blue text. Reset is a text action with its own confirmation. A destructive confirmation action uses red text or red fill and a verbal description of the consequence. A disabled action accepts neither mouse, keyboard nor programmatic invocation of the command. The default of a destructive operation confirmation is always No or Cancel.

An editable field is white with a border. A read-only field has a slightly tinted background, but allows focus, selection and explicit copying. A disabled field is not the same as read-only. A valid field uses the ordinary border, an invalid one a red border, a text error and an accessible invalid state. Validation does not delete or correct input without the user's instruction.

A checkbox in the table has a standard check mark. The Wizard uses a visual switch with the same two-state boolean semantics. The implementation may adjust the drawing of the native BUTTON; it must preserve the role, the checked/disabled state and Space operation. The state must not be merely a painted image without an accessible control.

Status icons have both a shape and a textual meaning: a green circle with a check mark and Success/Completed, a red one with a cross and Failed, pending an amber dot and Pending, a future Wizard step a grey number and Upcoming. The active Wizard step has a blue number and a tinted background. The doubled numbers from some images are not reproduced.

The table has a fixed header, horizontal separators, white rows and a visible focus of the currently operated element. Vertical scrolling moves only the rows. Horizontal scrolling of the table moves the header and the content synchronously. Editors of long keys have their own horizontal scrolling, so they do not lose data on a narrow area. The UI must not resolve overflow by cutting off access to Actions or OK.

The information and error panels have a heading, a short description and a possible remedy. They contain no raw stack trace, HTML or entire configuration documents. Repainting covers all newly exposed areas without flicker and stripes. The Win32 implementation uses the existing `window_utils.h`, native EDIT/BUTTON/scrollbar and limited GDI drawing of cards. Each window owns a small RAII cache of repeatedly used fonts, icons, brushes and pens. It is created at initialization for the target DPI and released when the window is destroyed. Fonts and icons are refreshed on a change of DPI or of asset identity. A change of High Contrast or of its system palette refreshes the color resources even at the same DPI. An ordinary `WM_PAINT` must not load icons or create GDI resources. Only visually changed regions are invalidated. Full invalidation is allowed on creation, on a DPI change, on a substantial layout recalculation or on recovery after a failed batch move. The tray keeps the last actually published icon identity and the exact tooltip, and calls `Shell_NotifyIcon(NIM_MODIFY)` only when they change, not on every identical status snapshot. When a batch HWND move fails, individual moves and full invalidation of the exposed parent remain functional.

Portable are colors and DIP constants, text catalogs, geometry with passed text metrics, state models, validation, hashing through CryptoProvider and IPC schemas. HWND, drawing, font handles, the message loop, system focus, accessibility adapters, modality and tray integration are implemented natively on macOS and Linux. Linux implements them in GTK 3 according to the section [Linux (GTK)](#linux-gtk); macOS has no supported build. The implementation does not introduce Qt, Electron, WebView or any other large framework. Windows does not introduce a new third-party library; Linux uses the system libraries GTK 3 and libayatana-appindicator3.

The portable core consists of `core/config/contracts_document.*`, `core/presentation/contracts_model.*` and `password_key_model.*` as separate objects of the existing static `phpvpn-core`. The DOM and full validation remain in config, the pure row models and Password SHA in presentation. They share IPv4, JSON and `CryptoProvider`. The headers contain no Windows types; service/CLI do not pull in unused model objects. The native ContractsWindow, PasswordShaWindow and ContractsSaveController use this portable core without Windows dependencies in the model.


The common Win32 adapter consists of `window_utils.*`, `ui_resources.*` and `ui_controls.*`, the portable constants and geometry `ui_style.h` and `layout.*`. Text is measured with the actual font; controls preserve native roles, names, selection, undo and user-driven clipboard. `UiResources::update` reacts to a change of High Contrast and, in active High Contrast, to a change of system colors. With unchanged DPI, HINSTANCE and request for status icons it replaces only the palette, brushes and pens, and keeps fonts and icons. An identical palette and identical assets do not trigger a refresh. The Contracts, Password SHA, Editor, Connect and Statistics adapters also call the update on `WM_SETTINGCHANGE` and `WM_SYSCOLORCHANGE`. Outside High Contrast the light palette remains. System brushes are borrowed. After a failure of any part of the batch, `positionControls` repeats all individual moves and a full invalidation of the parent with WS_CLIPCHILDREN. `invalidateChanged` does not invalidate an ordinary identical value. `TrayApplication` holds one explicit endpoint for all readers, its own mutex and shell adapter, without a production fallback. The shared cache is provided by `UiResources`, the shell interface by `ShellIcon`; specialized rendering is attached by the individual windows in `apps/tray`. The testing obligations and limits of proof are set by UX14; the results of specific runs belong in dated reports.

## UX03: Focus, modality, DPI and small area

All tray windows use a single shared monitor selection helper. A new child uses the monitor of a valid parent. A main window opened from the tray menu uses the monitor of the stored point at which the menu was actually shown. Without a parent and without a menu point, the monitor of a valid foreground window follows, then the monitor under the cursor and finally the primary monitor. The window is centered in the work area outside the taskbar. Coordinates are signed, including monitors to the left of or above the primary one. Dimensions are computed for the DPI of the target monitor; the outer frame is added to the client area given below and the whole is clamped to the available work area.

Reactivation does not move an existing window to the monitor of the new click. A minimized window is restored. If it lies entirely within the usable work area of any available monitor, it keeps its exact position and size. After a monitor is disconnected or the usable position is lost, it moves the window to the nearest available monitor and changes the geometry only by the necessary minimum. The check is performed on reactivation and on a change of DPI, resolution or work area. Merely connecting a monitor does not move a visible window. The dimensions below are exact default client areas in DIP without the title bar and the outer frame, not the physical dimensions of the PNGs.

| Window | Default DIP | Priority when shrinking |
|---|---|---|
| Connect | 940 × 560 | Vertical scroll of the whole content, without changing the data and the result. |
| Disconnect | 760 × 192 | The result panel remains fully visible; on further shrinking a vertical scroll is used. |
| Edit Config | 1080 × 560 | Heading/path and actions are kept, the editor shrinks. |
| Statistics | 1000 × 650 | Top cards stacked, then vertical scroll. |
| Wizard | 1000 × 680 | Sidebar 230 DIP, content scrolls, footer stays. |
| Contracts | 1180 × 680 | Table scroll, footer and own IP available. |
| Password SHA-256 | 540 × 360 | Fields across the width, a longer hash horizontally scrollable. |

At a width below 760 DIP, Statistics switch to one column. Below a width of 760 DIP the Wizard sidebar changes to a compact horizontal list of four numbers with the name of the current step. Resize and state repainting preserve the HWNDs of input fields, text, selection and undo. Back restores the text and the selection of the corresponding field. The sidebar is not interactive navigation. Reset can be moved to its own footer row, as can a longer primary action. The footer height is derived from the actual rows of buttons. At 480 × 320 DIP all actions must be available; the content may scroll. If the physical work area is even smaller, the clamp takes precedence over the window minimum, and further wrapping and scrolling are used, not an off-screen button. Simultaneous display of all sections on an arbitrarily small area cannot be promised.

A DPI change recalculates fonts, metrics, layout and scrollbar, and preserves input, text selection, logical focus and the visible row. Verify 100/125/150/200 %, moving between monitors and repeated resizing of all edges and corners. The light client content matches the mockups even in the dark system mode; the title bar may be the system one. A separate dark palette is not a requirement of this stage. High Contrast uses system colors and a visible focus instead of a forced palette. Ordinary text has a contrast of at least 4.5:1, and large text and essential control boundaries at least 3:1.

Tab and Shift+Tab advance in visual order. Enter triggers the enabled primary action unless another button has focus. In a multiline editor Enter inserts a new line. Escape corresponds to cancelling the respective window, not to Disconnect. The visible focus has an outline of at least 2 DIP. The accessible name of a field derives from its label; repeated Key/Random/Password SHA additionally from the row identity. A screen reader must receive names, roles, values, state and error also for drawn elements. Information text must not be available only on hover.

Contracts is a resizable modeless form. Configuration Wizard, Contracts and Edit Config can be used simultaneously over their independent whole drafts. They do not disable, merge or refresh each other; the last confirmed publication wins. Opening again activates the existing form without a new read or a reset of dirty. Basic status polling, repainting and the independent global Disconnect remain functional.

Only the Random confirmation temporarily disables its parent form, with the default No. Password SHA is modeless, does not disable the parent and allows multiple children even for the same remoteIp. The target, generation and system title are captured at opening and neither focus nor scrolling changes them. Tab stays in the currently operated window. Ordinary closing of a child returns focus to the Password SHA of the same contract. A creation failure changes neither the draft nor the availability of the parent. The main OK first freezes the candidate, then closes its children without applying unconfirmed changes and disables only the form being saved.

The common manual Exit uses lifecycle snapshots of all three editors. During saving/committing it waits asynchronously only until their original final deadlines and continuously takes new operations into account, without disabling independent editing. Then it shows a single common Yes/No dialog with the default No. Dirty uses Discard unsaved changes?, unknown The file may already have changed. Close without checking the save result?, and when both coincide, both sentences in the same dialog. No keeps all drafts. Yes applies to the exact generations; before the first discard the entire set of snapshots is verified. approvedDiscard must not open a second dialog. A temporary veto of a confirmed Finish does not cause a repetition of an already valid common consent.

The system host is a hidden top-level window, not HWND_MESSAGE. WM_QUERYENDSESSION returns TRUE without mutation and WM_ENDSESSION(FALSE) keeps the drafts. WM_ENDSESSION(TRUE) performs a terminal non-blocking endSession of all participants before destruction. No UI, save, retry, Disconnect, rollback, waiting for a worker or extending a deadline. Readers own shared state without a this/UI callback; abandon revokes delivery and signals cancel. The existing polling and the Progress/Statistics models are not changed. Keys, DOM, candidate and own working texts are cleaned up on a best-effort basis; native content and undo are emptied. A remote Wizard cleans up the lease; the saved config, the service and the global VPN remain untouched. Complete overwriting of all copies in the OS or the allocator is not guaranteed.

## UX04: Menu and data boundaries

The menu order remains: Connect/Disconnect, separator, Configuration Wizard, Communication contracts, Edit Config, separator, Show Info, Statistics, About, separator, Exit. Only the letter case in `contracts` changes, in accordance with the mockup title. About opens a local information dialog `About PHPVPN` without IPC and without reading the configuration: at the top `PHPVPN version <client version>`, below it `PHPVPN is freeware and open source software.`, `License: MIT` and `Copyright © www.pilandrome.com`. Windows shows the version as the TaskDialog heading; the GTK dialog states it as the first line of text. Neither the start, opening the menu nor the basic five-second timer read the configuration. Items are not disabled on the basis of an old file availability result.

After the window opens, Connect calls the existing `get-config` once, takes only the displayed `serverUrl` and the local `virtualIp` from the valid configuration JSON, and does not log the whole received config. Show Info validates the file in the service handling of the action. Statistics performs one `get-config-state`, then uses only `get-status`. Contracts is opened only by a later explicit user choice from the tray menu. It obtains the check and the document with the single existing `get-config-document`, without a preceding `get-config-state`. Only availability valid allows the model to be opened. Wizard Finish does not open Contracts, does not read any further configuration and does not pass the document. The production tray action of the Wizard has no callback opening another editor. Details are defined by UX05, UX08 and UX10–UX12.

| Detected state | Contracts | Edit Config | Wizard |
|---|---|---|---|
| valid | Open the editor. | Actual document. | Edit. |
| repairable | No editor; offer the Wizard to complete the identity. | Actual text. | Repair. |
| invalid | No editor; repair instructions. | Actual valid UTF-8 text even with a JSON error. | Offer Reset or repair. |
| unreadable | Access error without a substitute. | No document. | Reset does not bypass access. |
| encoding_error | UTF-8 error without a substitute. | No document. | Offer Reset. |
| too_large | 512 KiB limit error. | No document. | Offer Reset. |
| missing | Warning without creation; instructions for Wizard/Edit Config. | Yes/No to create. | Create. |
| service / IPC unavailable | Service error, not missing. | Same. | No checks and no Finish. |
| config_directory_security_invalid | Administrator procedure below, no corrective ACL editing. | Same. | No ACL Reset and no Wizard as an ACL remedy. |

A directory security error takes precedence over the general advice to create a configuration. It states only the authoritative `configPath` from the service and the instruction to ask an administrator to restart the PHPVPN service. It clearly states that the restart interrupts the VPN and may create a missing default, and then recommends verifying the actual file in Edit Config. A failure to load the descriptor is unreadable, not proof of an invalid ACL. The tray does not repair the ACL, does not delete the journal and does not perform a restart.

The URL/IP in Connect belong only in the two designated fields. Because of them, the one-time existing `get-config` transfers the entire valid JSON including sensitive values into the tray, which is knowingly accepted. The tray uses only `serverUrl` and the local `virtualIp` from it, does not log the whole config and limits the lifetime of its copies. `get-status`, Statistics, the tooltip, general errors and the log still must not contain the URL, the IP configuration, secrets or paths. Because `get-config` reads the currently stored document and Connect uses its immutable active snapshot, during a concurrent external change the displayed URL/IP may belong to a newer stored configuration than the currently active connection. This trade-off is accepted in order to keep the existing IPC. Edit Config and the configuration fields of Wizard/Contracts may display their designated values including keys. The exception does not apply to error descriptions or logging.

## UX05: Connect and Disconnect

The top context, the card and the result panel use on both sides the same margin as the shared button footer of the Wizard, normally 16 DIP and on an exceptionally narrow area at most one eighth of the width. The vertical outer margin remains 32 DIP, 16 DIP on a narrow area. There are at least 8 DIP between the top context and the following card or panel. The 28 DIP section headings of the card are followed by 16 DIP of space; ordinary rows of details and checks have a 40 DIP step. On a narrow area the details and the checks are stacked. The height is still derived from the measured text; on a smaller area the whole content is accessible by vertical scrolling.

The title is `PHPVPN connection`. The vertical composition begins with a single static top text `Connecting client to the server.`, followed by a white card and a dynamic result panel. The top text does not change while waiting, on success, on error or when the status is unavailable. The card contains `Connection details`, two rows `Server URL` and `Virtual IP`, a separator and `Connection checks`. The checks are exactly `Server URL`, `Server secret`, `Access key`, `Communication contracts`, with an icon and `Pending`, `Success` or `Failed`. They correspond to `serverUrlCheck`, `serverSecretCheck`, `accessKeyCheck`, `communicationContractsCheck`. The fourth item verifies the publication of the extended info before the tunnel is started and does not disclose the values of the secrets.

The URL is displayed as the literal validated configuration value without automatically opening a browser, the IP as canonical text. A long URL must be fully accessible by selection and horizontal scrolling of the read-only field. Missing context is displayed as `Unavailable`, never as a sample URL/IP. It is, however, knowingly allowed that values from the currently stored document are newer than the active connection snapshot after an external change, according to UX04. SERVER_SECRET, ACCESS_KEY, payloadKey, tag, ciphertext, packet, an internal path or a raw network/system error must not be displayed.

At the start, the static top context remains and the card shows orange pending checks. The window has no status symbol; the state is carried by the top text, the checks and the result panel. The native window icon is the PHPVPN application icon. The four checks are taken over as a whole, without accumulating previous green items. A new epoch means a new attempt; recovery does not overwrite the bootstrap history. Progress uses independent 500 ms polling of the existing `get-status` according to UX04 and the `get-status` contract in `client.md`. It performs no HTTP and no repeated reading of the configuration and does not change the deadlines of the basic polling. The single `get-config` takes place when the window opens, only for the two displayed details.

Success is permissible only at `connected`, `running` and a ready tunnel, which the service publishes only after starting the worker roles. The top context does not change and all checks are green. The bottom green panel has `Connected successfully`, below it `This window will close automatically.` and on the right a numeric countdown `Closing in 3 seconds`, then `Closing in 2 seconds` and `Closing in 1 second`. On a narrow area the countdown moves below the panel text.

The time starts with the first actual display of the success. The concrete boundary is the completion of `WM_PAINT` of the visible result panel heading `Connected successfully` or `Disconnected`, if it intersects the client area and the parent is not minimized. Receiving the status alone or `WM_PRINT` does not start the time. The model uses a monotonic deadline of +3000 ms; the remaining seconds are rounded up. Neither polling nor another paint renews the deadline. After expiry, close at the next UI handling, at the latest one existing 500 ms tick later if the UI is not blocked. After sleep/resume an already expired deadline does not create a new countdown. The native text announces the success; the tick changes only the countdown text, not the whole screen again.

Failure keeps the static top context. A dynamic heading and remedy from the single fixed catalog below are displayed in the red result panel, selected by the safe code from the service. The raw errorDescription is not used. An unknown code uses communication_failed. The catalog does not interpret individual checks or the raw server response.

| Cause code | Description | Panel / remedy |
|---|---|---|
| endpoint_unavailable_or_invalid | The server endpoint is not reachable or not valid. | Cannot connect to the server / Check the Server URL and network connection, then try again. |
| server_verification_failed | The server could not be verified with the configured SERVER_SECRET. | Cannot verify the server / Check the configured SERVER_SECRET and server settings. |
| access_key_rejected | The server rejected the configured ACCESS_KEY. | Cannot connect to the server / Check the configured ACCESS_KEY and try again. |
| communication_contracts_verification_failed | Communication contracts could not be verified. Check server compatibility. | Cannot verify communication contracts / Check server compatibility, then reconnect. |
| tunnel_start_failed | The local tunnel could not be started. | Cannot start the VPN tunnel / Ask your administrator to check the PHPVPN service and tunnel setup. |
| communication_failed | Communication with the server could not be completed. | Cannot complete the connection / Check the network and server availability, then try again. |
| communication_timeout | The server did not respond in time. Verification could not be completed. | Connection timed out / Check the network and server availability, then try again. |
| delivery error of the existing status IPC | The connection status is unavailable. | Cannot read connection status / Check that the PHPVPN service is running. |

An endpoint failure fails at the first item, server verification at the second, access at the third. On a timeout, the item currently being performed fails. Later unperformed items remain pending; on a tunnel error all may be green. An IPC delivery error keeps the last complete set of four, shows a separate unavailability and continues waiting for a valid status; it must not invent a server item error. An error of the one-time config read only sets the details to Unavailable. An ordinary operational outage is not automatically tunnel_start_failed. The actual codes and recoverability are still determined by the service. A timeout, 503 and an invalid MAC must not be presented as a rejected key.

The final result of the window is kept even during subsequent recovery; an error window never closes automatically. A new local Connect resets the presentation. X/Escape closes only the progress. Enter alone connects nothing, repeats nothing and disconnects nothing. The read-only detail fields are in the order URL, IP and support copying. A foreign completed Disconnect closes a not yet finished presentation according to the existing lifecycle. No timer surviving the destruction of the window may change a new window.

Disconnect has the title `PHPVPN disconnection` and a single static top text `Disconnecting client from the server.`. It has no card of details or checkpoints. All state remains in the dynamic panel, which shows `Disconnecting...` while waiting, `Disconnected` with a countdown on success and `Disconnect not confirmed` with a remedy on an unconfirmed disconnection. The same paint boundary and automatic close interval apply to a successful Disconnect.

## UX06: Edit Config and Server Information

With the default client area the header begins 16 DIP from the top edge. It is 72 DIP high including the spaces between the heading, the path and the editor, so the top edge of the text field lies at 88 DIP. With a limited height the header is limited by the available space above the footer.

Title `PHPVPN configuration`, heading `Edit configuration`, below it the actual `configPath` returned by the service. The hard-coded sample `C:\ProgramData\phpvpn\config.json` is not used as a substitute for the authoritative path. Below the header there is a single large native multiline editor with a vertical and a horizontal scrollbar and without word wrap. The footer has Reset on the left, Cancel and the blue Save on the right.

`EditorDocument` remains: unchanged input comes from the original bytes, not from the Win32 CRLF presentation conversion. Syntactically defective JSON in valid UTF-8 is repairable text. A single initial BOM is normalized according to `client.md`. A raw NUL uses the explicitly marked `JSON string literal` mode, strict decoding and no truncation at the first NUL. Opening and Cancel do not change the disk.

Save sends the entire text to the service, which validates UTF-8, JSON, all configuration invariants, size and safe atomic publication. Success closes the editor and announces `The configuration was stored. It takes effect on the next connection attempt.`. Save uses a single original 30 s deadline and generations of the window, the draft and the operation. The response must be complete, correlated and from a valid generation. An unsent request and a safely confirmed rejection before publication keep the text and undo and return focus to the editor. After a write attempt, a timeout, a lost confirmation, a defective/foreign response or an ambiguous error transitions to unknown. The message explicitly says that the file may already have been changed and recommends closing and reopening Edit Config to check. The draft remains read-only; Save and Reset are not available. A lost confirmation must not lead to automatic resending. During saving, text edits, a second Save, Reset, Cancel, Escape and X are blocked. The original deadline runs even when an old Reset completes late.

Reset uses Yes/No: `Restore the default configuration in this editor? The file will change only after you choose Save.`. Yes asynchronously loads `get-default-config`; only success replaces the draft and marks it dirty. No, an error or a response of an old generation do not change the text. Missing on opening uses the existing confirmed `create-default-config`, which writes even before the editor opens. Cancel does not remove an already created file.

Focus starts in the editor. Tab moves to Reset, Cancel, Save, Shift+Tab in reverse. Enter in the text inserts a new line; Ctrl+A/C/V and ordinary editing shortcuts remain. Escape/Cancel/X with dirty request Discard unsaved changes? with the default No. Unknown additionally warns about a possible change of the file and requests confirmation of closing without checking the result. No keeps the exact draft; Yes closes it only if the lifecycle snapshot is still identical. During Save, closing is not available. A clean window closes directly. Choosing Edit Config again only activates the already open window. Resize preserves both scrollbars, the caret, the selection, the header and the buttons, and does not add the original vertical artifact next to Cancel. ## UX12: Saving, concurrency and dirty state of contracts

It preserves all unrelated members, values, types and their presence, including the omitted runtime, CIDR, TLS and Wizard metadata. The resulting document is not reconstructed from ClientConfig. An originally missing communicationContracts remains missing if nothing is switched on; an existing object remains `{}` after everything is switched off. Whitespace may change during DOM editing.

The local part is provided by `prepareSave`: it passes a complete snapshot of the confirmed rows to the preserving patch, serialization and the shared full validation within the 512 KiB limit. The mandatory synchronous `ContractsEnvelopeSizer` measures the actual encoded envelope with the existing builder without transmission and without changing the model. Above 4 MiB the candidate is rejected. Only success creates the shared const candidate, increments the save generation, retires earlier targets and disables mutations of the model. An error keeps both the draft and the generation. `resumeEditing` requires a correlated save generation and a decision of the controller; old child targets are not restored by it. `matchesDocument` requires a valid current document and compares the whole DOM independently of the order of object members, preserving types and absent/present. `ContractsModel` prepares the data. IPC, closing windows and the Save/unknown workflow are controlled by `ContractsSaveController` in cooperation with the native window.

The strict current schema does not allow arbitrary unknown members. Preserving the DOM is not permission for unknown or invalid fields. Full validation is repeated by the service before the temp file; all publications use the single ConfigStore and serialization gate. After a confirmed save, the connection state is verified by a fresh correlated in-memory get-status. Connected invokes a Yes/No dialog: `Your changes have been saved. It is strictly required that you disconnect and connect again to apply them. Do you want to disconnect now?` The default is Yes; Enter confirms it. Yes, after re-verifying the same connection identity, starts the standard Disconnect with its progress window, without an automatic Connect. No, Escape, closing or a dialog error do not disconnect. Neither an unknown state nor a rejected/unknown/matched Save result starts a disconnection. The editor generation and the connection identity are checked even after the modality. The editor closes after a confirmed success. Saving does not overwrite the active snapshot. The change is applied only on a new logical connection, not on recovery of the current one.

With an active VPN display `Changes take effect on the next connection.`. Concurrent sessions write whole documents; the last successful publication wins. An older revisionToken is not a conflict and does not trigger CAS, automatic merge, refresh or a new overwrite confirmation. A change or delete/recreate of the target while open does not change the draft. If the publication is safe, OK may restore a deleted file or replace content changed in the meantime, just like the editor's Save. It does not take over parts of a newer configuration.

On a confirmed rejection before publication, editing/invalid returns with the entire draft and a safe cause. A write/flush/publish error or a lost, defective or uncorrelated response after a possible send is saveUnknown, unless a final unpublished result is proven. In saving, the fields, OK and closing are locked only for the final IPC budget. After it elapses, `The save result is unknown. The file may already have changed. Check the current configuration before saving again.` is displayed.

The existing set-config has no traceable commit receipt. The editor therefore must not invent it from requestId or the current revision. In saveUnknown it offers `Check current configuration`, which is an explicit one-time `get-config-document` action. It compares the whole DOM of the current valid document with the sent candidate, including types and the presence of members. A match allows announcing `The current configuration matches your changes.` and closing; it is not a historical confirmation of the original write. A mismatch or missing keeps the draft, displays `The current configuration differs. Your draft has been kept.` and offers either closing or an explicit `Save draft again` with confirmation of replacing the current whole document. This exception applies only to resolving unknown, not to ordinary concurrent saving. It is not an automatic retry. Unreadable/ACL/encoding_error/too_large are first resolved according to UX04 and do not permit a blind new publication.

X/Escape in clean closes directly. In dirty it displays `Discard unsaved changes?`; Yes discards them, No/Escape/X of the confirmation returns. In saveUnknown the text is `The file may already have changed. Close without checking the save result?`, default No. Closing does not revert an already published file. A late response after closing or a new generation does not open a dialog and does not perform another write.

## UX13: Security and limits

The tray never opens, writes or tests the existence of `config.json` via the filesystem. Temporary JSON, the password, keys and the DOM are only in memory until the approved service publication. All logs, errors, test reports and screenshots of real configurations must be free of secrets. Tests use exclusively synthetic values. The UI itself copies nothing to the clipboard.

Owned sensitive buffers of the adapter and the model are overwritten on a best-effort basis via secureWipe/SecureBuffer before release, also on a crypto error and on cancellation. The native EDIT content and undo are emptied before destruction; overwriting of internal Windows copies cannot be guaranteed. Working UTF-8/UTF-16 strings, received IPC bodies, the original DOM and the candidate have a limited lifecycle and as few copies as possible. Best-effort erasure of owned memory is not a guarantee of removing all copies in the builder, parser, OS, allocator or a user-created clipboard. The password never goes via IPC or into the configuration, only the resulting key in the confirmed JSON.

The limit of the stored configuration is 524288 bytes and of an encoded IPC message 4194304 bytes including escaping and the envelope. The check takes place before allocation according to an untrusted length and also before sending/publication. The existing validator and the UTF-8 and JSON depth/token limits are not weakened. The editor has at most 252 native rows according to the global range `/24` to `/29` and the sum of Key texts in progress is at most 524288 bytes. Exceeding the limit rejects the new edit with an explanation and keeps the existing draft. There is no unlimited history of keys or buffers.

Row Key texts, default comparison keys and the text of the immutable candidate are owned by SecureBuffer. The model cleans its own original DOM and the candidate cleans its copy of the DOM only after the last user. Borrowed input, native fields/undo and the temporary IPC envelope are cleaned up by their adapter. A Key change is checked before allocating the replacement, with a safe subtraction of the old length and an overflow-free sum check; a rejection changes neither the value nor the focus. Local calls are serial; synchronous use in the UI must separately pass the runtime acceptance in UX14.

The public local pipe, the prohibition of remote clients, the closed schema, correlation, finite deadlines and the separate Disconnect/get-status capacity remain. Within this UX plan no new IPC command is added. Connect, Contracts and Wizard use only existing commands. SHA-256 and CSPRNG are local calls of the existing cryptographic abstraction. Configuration options do not change the wire format, AAD, HKDF, IV or the end-to-end check.

## Application and status icons (2026-09-19)

The application icon of all top-level windows and system dialogs is `assets/default.ico`, set for both ICON_SMALL and ICON_BIG. The VPN state does not change it. It is also loaded in windows that do not need status icons. On a DPI change the whole new set is loaded first and the HWND is switched, and only then are the old handles released. A failed load keeps the original set.

The notification area uses the exact embedded resources: disconnected=101, connecting=102 and connected=103. An unavailable or invalid current status takes precedence and shows disconnected. An ongoing local Connect/Disconnect, stopping, connecting, recovering and connected with the reconnecting phase (soft recovery) use connecting. Connected is reserved for a healthy connected/running with tunnelReady=yes without an error. Disconnected, error and an inconsistent state use disconnected.

An accepted Disconnect changes the icon immediately, even over the last connected snapshot. Acceptance of the RPC alone does not end the wait for the teardown. A terminal status or an error ends the local progress. An invalid response and a timeout mark the status as unavailable and request a new read. A read started before the command is discarded.

State tracking continues after the Disconnect response and also after its window is closed. A live window delivers the current state directly to the tray; after it is closed, the tray reads it again. After 30 seconds of unconfirmed progress the wait ends, the window allows another action and the tray requests a new authoritative state.

## Linux (GTK)

The Linux tray `phpvpn-tray` ([client/apps/tray-linux](client/apps/tray-linux)) is a native GTK 3 application with an indicator via libayatana-appindicator3 (StatusNotifierItem). Sections UX00 to UX14 and Application and status icons apply unchanged to content, order, texts, colors, states, validation, IPC commands, timeouts and behavior. This section replaces the Win32 mechanisms, i.e. HWND, GDI, `Shell_NotifyIcon`, `WM_*` messages and pixel geometry, with GTK equivalents. The tray shares with Windows the portable models and catalogs `menu_model.h`, `status_model`, `progress_model`, `progress_details`, `reconnect_controller.h`, `poll_schedule.h`, `save_response`, `ui_style.h` and `ipc_timeouts.h`. Neither Qt, Electron nor WebView is used. The platform rules for the service, the socket and the installation are set by [client.md, Linux](client.md#linux).

### Widgets, style and geometry

The windows use standard GTK 3 widgets with native roles for AT-SPI. The style is supplied by a single `GtkCssProvider` generated exclusively from the palette and font roles of `ui_style.h` (UX01). The `phpvpn-*` classes are common to all windows: primary, secondary and error button, card, information, error and warning panel, check states, read-only field and a visible 2 px wide focus in the focus color (UX03). The shield-with-lock motif and other Material Symbols are not drawn. Where a window needs an icon, it uses the application icon `phpvpn` from the icon theme.

The geometry does not use the pixel coordinates of the Win32 layout. The windows compose GTK layout containers with the default size from the DIP constants of `ui_style.h` and with minimum widths where the layout needs them. Scaling is handled by GTK. Pixel parity with Win32 is not required; content, order, texts, colors and behavior MUST remain identical. The control and progress windows have their content in a vertical scroller, so access to actions is not lost on a small area (UX03). The height of the control window follows the natural height of the content, so on a 1024 × 768 screen with the GNOME top bar the whole window including the Exit button is visible. The application icon of all windows and dialogs is `phpvpn` from the icon theme; the VPN state does not change it.

Yes/No dialogs and error messages are modal `GtkMessageDialog` with a nested loop like the Win32 `MessageBox`, so IPC and timers keep running during the dialog. They get a transient parent only if the parent is visible. A destructive confirmation has the default choice No; only the non-destructive question about reconnecting after saving has the default Yes (UX02).

### Indicator, menu and icons

The indicator registers with the ID `phpvpn` and the category `ApplicationStatus`. The status icons are the names `phpvpn-disconnected`, `phpvpn-connecting` and `phpvpn-connected` from the hicolor theme. Their selection follows exactly the rules of the section Application and status icons, including the precedence of an unavailable status and the immediate change after an accepted Disconnect. The icons installed into `/usr/share/icons/hicolor/<n>x<n>/apps/` in 16, 22, 24, 32, 48, 64 and 128 px and into `/usr/share/icons/hicolor/scalable/apps/` are generated reproducibly by `client/tools/make_linux_icons.py` from the vector sources `assets/phpvpn*.svg`, which match the Windows ICO in both shape and colors. Rectangle edges are aligned to the pixel grid of each size. The `--check` mode verifies that the committed PNG and SVG match.

AppIndicator has no tooltip. The status text of the tooltip from `ui_style.h`, with the same precedence as on Windows, is therefore displayed as the first inactive menu item, followed by a separator, and also as the indicator title and the icon description. After the separator the menu has exactly the items, order and texts of UX04 from the shared `menu_model.h`, including switching Connect/Disconnect according to the VPN state. The status item and the separator are the only deviation from UX04. The indicator publishes a change only on an actual change of the icon, the status text or the toggle label, not on every identical status snapshot (UX02). Activation of an item is performed only from an idle callback, so that a modal dialog does not block dbusmenu handling.

### Fallback control window

The indicator is visible only when the desktop provides `org.kde.StatusNotifierWatcher`. Fedora Workstation with GNOME does not have it without the AppIndicator extension. The tray monitors the presence of the watcher on the session bus. On every transition to the state "watcher missing" it opens the fallback control window and, at most once per process lifetime, shows a notification with instructions: enable the extension with the command `gnome-extensions enable appindicatorsupport@rgcjonas.gmail.com` and log in again. If the watcher appears later, the indicator registers itself and nothing else changes. The tray MUST NOT enable the extension itself or change desktop settings. Outside X11 the substitute `GtkStatusIcon` of the ayatana library is not used, because XEmbed exists only on X11.

The control window with the title `PHPVPN` contains a compact card with the blue PHPVPN application icon (48 DIP) and the status text, and below it one button for each menu item in the same order and with separators according to UX04. Connect/Disconnect is the primary button, the others are secondary. The actions are identical to the menu items and, just like activation of a menu item, are performed only from an idle callback. Closing the window or Escape only hides the window; the tray, polling and the indicator keep running. This keeps ordinary control available even without a tray icon.

### Startup, single instance and notifications

In each desktop session at most one instance of `GtkApplication` with the ID `org.phpvpn.Tray` runs. A second start passes its arguments to the primary instance and exits. The autostart `/etc/xdg/autostart/phpvpn-tray.desktop` starts the tray without arguments like the Windows Run value: it shows the indicator, first loads `get-status` and never calls Connect. The launcher `phpvpn-tray.desktop` in the application menu starts `phpvpn-tray --show-window`, which shows the control window of the running instance. `--installation-complete` shows the installation notice with the same texts as Windows. The Wayland `app_id` and the X11 window class are `phpvpn-tray`, so that the windows match the launcher.

Notifications use `org.freedesktop.Notifications` via GDBus on the session bus with the icon `phpvpn` and the hint `desktop-entry=phpvpn-tray`. Visibility, display duration and do-not-disturb mode are determined by the desktop notification service, just like the Windows shell. A notification that is not accepted is only logged.

On Wayland the application cannot position windows; the placement is determined by the compositor. The UX rules about placing a window above an available parent are fulfilled on Linux by a transient parent, not by an absolute position. The tray MUST NOT depend on the absolute position of a window.

### IPC, Exit and end of session

Each IPC exchange runs in a worker thread and the result is passed to the GLib main loop. An abandoned channel does not deliver the result and the wait is cancelled without blocking the UI. Before sending, the client verifies that the peer of the socket runs as root. Timeouts and intervals are shared with Windows in `ipc_timeouts.h`: status 400 ms, commands and `set-config` 30 s, Wizard request 5 s, Wizard close 1 s, editor reset 5 s, the save deadline of Edit Config and Contracts 30 s, polling 5000 ms, in the progress window 500 ms and automatic refresh of Server Info 5 s.

Exit follows UX03 and the common Exit from `client.md`: it asks about discarding changes only when one of the editing windows is dirty or in the unknown state, and the Wizard veto is checked first. For the end of the session, `GtkApplication` registers with the session manager only for notification and never blocks `query-end`, like the Windows `WM_QUERYENDSESSION → TRUE`. The `shutdown` signal, SIGTERM, SIGINT, SIGHUP and a completed Exit start the same terminal cleanup. It stops the timers and polling, abandons the IPC channels without waiting, calls `endSession` of the registered editing windows, closes the progress windows, the HTTP error detail and all dialogs with the answer No, and removes the indicator and the control window. It saves nothing, repeats nothing and does not call Disconnect. Exit, logout and a crash of the tray MUST NOT disconnect the VPN.

### Windows

The Connect and Disconnect progress windows correspond to UX05 and are governed by the shared `ProgressModel`: 500 ms polling of `get-status`, for Connect one `get-config` for the URL and the local IP and a card with the four checks, the result panel and the close countdown after success, which starts with the first actual rendering of the heading. X and Escape close only the presentation, never Disconnect. When the HTTP detail window is closed, `dismiss-connect-diagnostic` is sent.

Configuration Wizard including the HTTP headers dialog, Edit Config, Communication contracts, Password SHA-256, Server Information, Statistics and HTTP error detail follow on Linux sections UX05 to UX12 with GTK widgets and the same texts, element order, validation, states, IPC commands and timeouts as the Windows windows. They are attached to the tray via opening hooks and registration of the lifecycle state of the editing windows for Exit, end of session and the question about reconnecting after saving. A window without a registered hook only shows an information message that it is not available in the given build. A production build MUST register all windows, and the Linux tray registers all of them.

GTK triggers the "click" action of a button invoked via AT-SPI inside the D-Bus call of the assistive technology. The nested loop of a modal dialog would block this call and all further accessibility requests to the tray. Every handler of a button, menu item or key that can open a Yes/No question or a message therefore only schedules its action into an idle callback of the main loop (`DeferredCalls` in [gtk_util.h](client/apps/tray-linux/gtk_util.h)) and opens the dialog only from there. This applies to the control window, the indicator items, the first step of Exit, Error detail in the progress window, the Wizard, HTTP headers, Edit Config, Communication contracts and Refresh in Server Information. The visible order and content of the dialogs are not changed by this.

Compared to the Windows windows, Linux has these deviations:

- Disconnect gate in the Wizard: the Wizard has no Cancel button; cancellation is done by the close button and Escape as on Windows. The focus of the gate therefore starts on the non-destructive Reset, so that an accidental Enter on opening does not confirm the global Disconnect, as required by UX09. The Windows window without a focusable field in the gate content gives focus to the primary `Disconnect & continue`; the Linux choice is safer.
- HTTP headers: the window uses the default client area of 760 × 420 DIP and the minimum of 480 × 260 DIP according to UX09. The Windows window opens with a size of 950 × 420; the UX09 value remains valid.
- Server Information: the minimum window size is 320 × 480 DIP as on Windows. So that the tab headers and a pager of up to 13 page buttons do not enlarge it, the tab header scrolls with arrows on a narrow window and the pager scrolls horizontally. All tabs and pages thus remain accessible. If the footer does not fit on one row, OK wraps below the pair Refresh and Auto refresh. The accessible order Refresh, Auto refresh, OK does not change with wrapping.
- Communication contracts: the default client area is 1000 × 680 DIP as for the Wizard, limited by the monitor work area, because 1180 × 680 would not fit on a 1024 × 768 screen. The Actions column has the actual width of the Win32 table, 116 DIP (Key = max(260, viewport − 446)), so the default window shows the whole table without horizontal scrolling. A narrower window scrolls the table and the pager with 36 DIP page buttons horizontally inside the window; the table header and the footer remain visible.
- Wizard: Reset, Back, Error detail and the primary action remain in one footer row as long as they fit, even in the compact layout below 760 DIP, as with the Windows `computeButtonFooterLayout`. A single-row footer in GTK determines the minimum window width, so it wraps already when exactly this width is reached and the window can be narrowed further.
- The single-line fields of the Wizard are `GtkEntry` with the internal GTK limit of 65 535 characters; the Windows Wizard fields accept up to `kMaxConfigFileBytes`. Valid values of the URL, secret, IP address and key are orders of magnitude shorter and the document is limited to 524288 bytes, so the limit has no effect on validation or the result. The multiline fields HTTP headers, Edit Config, raw Server Information and HTTP error detail are `GtkTextView` without this limit.
- First Wizard after installation: at startup the service creates a missing default configuration (`ensureDefaultAtStartup` in the shared `service_runtime`), so the first Wizard draft is based on this default configuration, i.e. Server URL `https://change-this-server-url.invalid`, and not on empty fields. The service rejects Connect with this placeholder with the code `config_server_url_unset`, and instead of an error the tray asks the question "The server URL has not been configured yet. Do you want to set it up now?"; Yes opens the Wizard. This is shared service behavior, not a difference of the Linux tray.

## macOS (AppKit)

The macOS tray `phpvpn-tray` ([client/apps/tray-macos](client/apps/tray-macos)), bundle `phpvpn Tray.app` with the identifier `com.pilandrome.phpvpn-tray`, is a native AppKit application in Objective-C++ with ARC and an `NSStatusItem` in the menu bar. Sections UX00 to UX14 and Application and status icons apply unchanged to content, order, texts, colors, states, validation, IPC commands, timeouts and behavior. This section replaces the Win32 mechanisms, i.e. HWND, GDI, `Shell_NotifyIcon`, `WM_*` messages and pixel geometry, with AppKit equivalents. The tray shares with Windows and Linux the portable models and catalogs `menu_model.h`, `status_model`, `progress_model`, `progress_details`, `reconnect_controller.h`, `poll_schedule.h`, `save_response`, `contracts_save_machine`, `statistics_model.h`, `ui_style.h`, `wizard_text.h` and `ipc_timeouts.h`, and from the Linux tray, without GTK dependencies, `lifecycle.h`, `editor_model`, `server_info_presenter`, `contracts_view` and `wizard_dialog_text`. The Configuration Wizard workflow is a copy of the Linux `wizard_controller` connected to the macOS `ipc_async`. Neither Qt, Electron, WebView, SwiftUI nor any third-party library is used. The platform rules for the service, the socket and the installation are set by [client.md, macOS](client.md#macos).

### Widgets, style and geometry

The windows use standard AppKit controls (`NSTextField`, `NSTextView`, `NSButton`, `NSSwitch`, `NSTableView`, `NSTabView`, `NSAlert`) with native roles for VoiceOver. The colors are the palette tokens of `ui_style.h` (UX01) as sRGB `NSColor`; the font is the system font and its monospaced variant. Logical font heights in DIP are converted to points by a factor of 0.85, which corresponds to the line height of the system font. All windows have a forced light Aqua appearance, so the client content matches the mockups even in the system dark mode (UX03). The title bar, system dialogs and menus remain system ones.

The geometry uses neither the pixel coordinates of the Win32 layout nor Auto Layout constraints. The windows are composed by a small frame layout (`PVStackView` in [mac_ui.h](client/apps/tray-macos/mac_ui.h)) with vertical and horizontal groups, measured text wrapping, cards with an 8-point corner radius, colored panels and a footer that wraps into two rows on a narrow area (UX06). The default sizes are the DIP constants of `ui_style.h` (1 DIP = 1 point), limited by the visible area of the screen under the cursor. Retina scaling is handled by AppKit; there is no custom DPI handling. Pixel parity with Win32 is not required; content, order, texts, colors and behavior MUST remain identical. The buttons are native push buttons of size `NSControlSizeLarge` (about 28 points instead of 36 DIP) with blue primary and red destructive tinting. The content of windows with variable height is in a vertical scroller, so access to actions is not lost on a small area.

Yes/No dialogs and error messages are application-modal `NSAlert` with a nested loop like the Win32 `MessageBox`. The heading of the alert is the dialog title, the body its text. IPC delivery, deferred actions and timers run in the common run loop modes, so they continue even during a dialog and an open menu. A destructive confirmation has No as the default (Return) button and Yes is marked as destructive. Only the non-destructive question about reconnecting after saving has the default Yes; Escape in it corresponds to No (UX02). Escape and Return without modifiers are handled by the window itself (analogous to the Win32 dialog manager): Escape corresponds to cancelling the window, Return to the primary action; in a multiline editor it inserts a new line.

### Status item, menu and icons

`NSStatusItem` displays the colored status icons `phpvpn-disconnected`, `phpvpn-connecting` and `phpvpn-connected` from the generated PNGs `assets/linux/hicolor` (16 px and 32 px as `@2x`), the same as on Linux. They are not template images, because the color carries the meaning of the state in both the light and the dark menu bar. The icon selection follows exactly the rules of the section Application and status icons, including the precedence of an unavailable status and the immediate change after an accepted Disconnect. The application icon `phpvpn.icns` is created at build time by the `iconutil` tool from `phpvpn.png` 16 to 128 px, and the VPN state does not change it.

macOS has a tooltip: the status text from `ui_style.h`, with the same precedence as on Windows, is the tooltip and the accessible name of the item. The menu has the same status text as its first inactive item, followed by a separator, because the tooltip is not displayed while the menu is open. After the separator the menu has exactly the items, order and texts of UX04 from the shared `menu_model.h`, including switching Connect/Disconnect. The status item and the separator are the only deviation from UX04. The item publishes a change only on an actual change of the icon, the status text or the toggle label (UX02). The action of a menu item is performed only from a deferred call after the menu closes.

The menu bar may hide the item (display notch, menu bar overflow, hiding in System Settings). The control window `PHPVPN` therefore, just like the Linux fallback window, offers the application icon, the status text and one button for each menu item in the same order. It is shown by `--show-window` and by reopening the running application from Finder, Launchpad or with the `open -a` command. Closing or Escape only hides the window; the tray, polling and the status item keep running.

### Startup, single instance and notifications

The LaunchAgent `com.pilandrome.phpvpn-tray` starts the tray in every graphical Aqua session without arguments like the Windows Run value: it shows the status item, first loads `get-status` and never calls Connect. `LSUIElement` and the Accessory activation policy ensure that the tray has no icon in the Dock. In each login session at most one instance runs: a `flock` lock in the user's temporary directory and a check of `NSRunningApplication` with the same bundle ID. A second start passes `--show-window` or `--installation-complete` to the primary instance via `NSDistributedNotificationCenter` and exits with code 0; without arguments it passes nothing. `--help` prints usage without the window server and without the service.

`--installation-complete` shows the installation notice with the same texts as Windows via `UNUserNotificationCenter`. The first notice requests permission for notifications. A denied permission, a delivery error or running outside the bundle shows the same text in an `NSAlert`. Visibility, display duration and Focus modes are determined by macOS, just like the Windows shell.

Window placement is controlled by AppKit. A new window is centered in the visible area of the screen under the cursor and its size is limited by this area; reopening keeps the position and size. The custom monitor selection and position correction model from UX03 is not used; AppKit keeps windows on available screens by itself.

### IPC, Exit and end of session

Each IPC exchange runs in a worker thread and the result is passed to the main run loop via `CFRunLoopPerformBlock` in the common modes, i.e. also during a modal dialog and menu tracking. The GCD main queue is not used, because delivery would stop in a nested modal loop started from a main queue block. An abandoned channel does not deliver the result and the wait is cancelled by writing to a `pipe` without blocking the UI. Before sending, the client verifies that the peer of the socket runs as root. The monotonic time for deadlines is `CLOCK_UPTIME_RAW`. Timeouts and intervals are shared with Windows in `ipc_timeouts.h`, the same as on Linux. The variables `PHPVPN_TRAY_TEST_SOCKET` and `PHPVPN_TRAY_TEST_SERVER_UID` serve only isolated tests. The variables `PHPVPN_TRAY_TEST_OPEN_WINDOW` (one of `control`, `wizard`, `contracts`, `edit`, `info`, `statistics`) and `PHPVPN_TRAY_TEST_CAPTURE_DIR` (an absolute directory) serve only screenshots in CI ([capture-tray.sh](client/tests/ui/macos/capture-tray.sh)): 1.5 s after start the tray opens the chosen window by the same path as its menu item, after a further 4.5 s it writes into the directory PNGs of the status item and of each visible window rendered from its own views (`cacheDisplayInRect:`, without the Screen Recording permission) and exits with the same cleanup as Exit. An unknown window name or a relative directory is a startup error. Neither the package, the LaunchDaemon nor the LaunchAgent set these variables.

Exit follows UX03 and the common Exit from `client.md` with the shared `ExitCoordinator`: it asks about discarding changes only when one of the editing windows is dirty or in the unknown state, and the Wizard veto is checked first. Logout, restart and termination by the system (`applicationShouldTerminate:`) as well as the signals SIGTERM, SIGINT and SIGHUP (for example `launchctl bootout`) never block termination and start the same terminal cleanup as a completed Exit. It stops the timers and polling, abandons the IPC channels without waiting, calls `endSession` of the registered windows, closes the progress windows, the HTTP error detail and a running dialog with the answer No, and removes the status item and the control window. It saves nothing, repeats nothing and does not call Disconnect. Exit, logout and a crash of the tray MUST NOT disconnect the VPN.

The configuration error texts state the path `/Library/Application Support/phpvpn/config.json`. The error "The PHPVPN service did not complete the command." and an unavailable service during the one-time configuration check additionally state the instruction for the administrator `sudo launchctl bootstrap system /Library/LaunchDaemons/com.pilandrome.phpvpn.plist`. The tray does not start or register the service itself.

### Windows

The Connect and Disconnect progress windows, Configuration Wizard including the HTTP headers sheet, Edit Config, Communication contracts, Password SHA-256, Server Information, Statistics and HTTP error detail follow on macOS sections UX05 to UX12 with the same texts, element order, validation, states, IPC commands and timeouts as the Linux windows, because they use the same models without GTK. They are attached to the tray via opening hooks and registration of the lifecycle state of the editing windows for Exit, end of session and the question about reconnecting after saving. The production build registers all windows.

Compared to the Windows windows, macOS has these deviations:

- Disconnect gate in the Wizard: as on Linux, the Wizard has no Cancel button and the focus of the gate starts on the non-destructive Reset, so that an accidental Return on opening does not confirm the global Disconnect (UX09). The close button and Escape cancel the Wizard's own work.
- The Wizard switches and Auto refresh are `NSSwitch` with a clickable label; Space toggles the focused switch and the accessible name is the label.
- HTTP headers: the dialog is a sheet of the Wizard window, i.e. modal only with respect to the Wizard, with a default area of 760 × 420 points and a minimum of 480 × 260. It can be resized; maximizing a sheet does not exist on macOS.
- Edit Config and HTTP headers: `NSTextView` without wrapping with both scrollbars. Tab and Shift+Tab move focus; smart quotes, dashes, substitutions and spell checking are turned off. Text with an unpaired surrogate is rejected before Save with the existing message about an invalid Unicode sequence.
- Communication contracts: as on Linux, the table displays pages of 20 rows with actual Enabled, Key and Change controls. Change opens Password SHA, which offers Default and Random. The table header scrolls horizontally together with the rows; the default area of 1180 × 680 is limited by the screen. Ctrl+End, PageUp and PageDown have only the native scroller behavior.
- Password SHA-256: the password goes to `PasswordKeyModel` as an exact UTF-16 array including unpaired surrogates. Each edit of the Password and Key fields is verified in advance as a whole (`NSFormatter`), and an over-limit or unsupported edit is rejected entirely.
- Server Information: the minimum size is 320 × 480 points; the pager scrolls horizontally on a narrow window. The `Who is online` table uses the native `NSTableView` header and native keyboard navigation instead of Ctrl+End.
- Connect and Disconnect: the close countdown starts with the first actual rendering of the visible result heading in a window that is on screen and is neither minimized nor occluded. Should layer composition skip rendering the heading, the nearest 500 ms tick of such a window counts as the first display.
