# Návrh multiplatformního klienta phpvpn

## Účel

Tento dokument je normativní návrh nativního klienta pro protokol phpvpn v1, s historickým podkladem [plan3_client.md](plan3_client.md). Popis požadavků sám nepotvrzuje jejich implementaci ani testování. Klient funguje jako krátce připojovaný relayový peer: zachytává IPv4 pakety z virtuálního rozhraní, end-to-end je šifruje pro konkrétního příjemce, odesílá je přes endpoint `data` a přijaté, ověřené pakety opět zapisuje do virtuálního rozhraní.

Klient MUSÍ být **thread-safe**. Používá tři VPN pracovní role, každou ve vlastním vlákně, která bezpečně sdílejí zdroje bez datových závodů a souběžných kolizí. Engine obsluhuje chyby vrácené bootstrapem a provozní výměnou `data`. U obnovitelných chyb provede teardown a opakuje připojení podle části Stavový automat připojení. Neobnovitelná chyba vede do `error` a vyžaduje zásah uživatele. Obecná obnova po pádu či nezachycené výjimce libovolné pracovní role není poskytována.

Primárním cílem je Windows. Návrh současně odděluje platformně nezávislé jádro od síťového rozhraní a integrace operačního systému, aby jej bylo možné přenést na macOS a Linux. Tato etapa používá C++20, MSVC, CMake/Ninja, Win32, WinHTTP a CNG bez nové knihovny třetí strany. Přenosné modely neobsahují HWND, HANDLE, Win32 zprávy ani závislost na tray procesu.

Server nezná payload klíče ani IP obsah. Klient zajišťuje výběr klíče, AES-256-GCM ochranu payloadu, validaci a předání paketů virtuálnímu L3 rozhraní.

## Architektura

Jádro klienta nesmí záviset na API konkrétní platformy. Je rozděleno do těchto modulů:

| Modul | Odpovědnost |
|---|---|
| `Config` | Načtení, přísná validace a držení konfigurace v paměti. |
| `Protocol` | Kanonizace, JSON/NDJSON, `health`, `info`, `data`, HMAC/HKDF a base64url. |
| `Crypto` | AES-256-GCM pro payload, bezpečné mazání tajných hodnot a generování IV z CSPRNG. |
| `Transport` | HTTP/HTTPS POST, časové limity, kontrola velikosti odpovědi a politika certifikátů. |
| `Tunnel` | Abstrakce čtení a zápisu surových IPv4 paketů do virtuálního rozhraní. |
| `Queues` | Odchozí fronty podle cílové VPN adresy, příchozí fronty podle zdrojové VPN adresy, plánování flushů, logické per-peer rezervace, limity paměti a souhrnné statistiky zahozených paketů. |
| `Runtime` | Stavový automat připojení, tři VPN pracovní role, ukončení, recovery a srozumitelný log. |
| `Presentation` | Přenosné modely Contracts a Password SHA, řádková validace a identita akcí bez oken nebo IPC. |

`core/config/contracts_document.*` vlastní původní validní DOM, preserving patch a úplnou validaci kandidáta. `core/presentation/contracts_model.*` a `password_key_model.*` tvoří samostatné objekty existující statické knihovny `phpvpn-core`. Nepřidávají knihovnu ani závislost třetí strany. Používají sdílené IPv4 helpery, JSON a `CryptoProvider`, bez Windows hlaviček nebo typů. Service a CLI nepřitahují nepoužité modelové objekty. Nativní pohled, focus, scroll a okna patří do `apps/tray`. `ContractsWindow` a `PasswordShaWindow` používají přenosné modely, `ContractsSaveController` řídí ukládání a jeho transportní lifecycle.

Současná Windows vrstva poskytuje implementaci rozhraní `Tunnel` pomocí Wintun, HTTP/HTTPS transport přes WinHTTP a kryptografický `CryptoProvider` přes Windows CNG. Zajišťuje také lokální IPC, hodiny, souborové operace, cesty a síťovou konfiguraci přes IP Helper. Integrace služby a nativního tray patří do příslušných aplikací. libcurl nebo jiné transportní a kryptografické adaptéry jsou pouze budoucí možností při portování na macOS a Linux, nejsou současnou závislostí klienta. Požadavek čistého PHP AES-GCM z protokolu se týká PHP implementací, nikoli nativního klienta.

Zdrojové soubory jsou rozděleny do `client/src/core` pro přenosné jádro ve statické knihovně `phpvpn-core`, `client/src/platform` pro rozhraní a Windows adaptéry ve statické knihovně `phpvpn-platform` a `client/apps` pro samostatné vstupy service, CLI a tray. Služba vlastní VPN provoz, CLI a tray ji ovládají přes lokální IPC. Nativní Win32 okna a jejich obsluha jsou součástí `apps/tray`, nikoli přenosných modelů.

### Běhový model

Datová část VPN používá právě tři sériově pracující role, z nichž každá běží ve vlastním vlákně; implementace je NESMÍ nahradit samostatnými procesy, workery ani ekvivalentním event-loopem. Vlastnictví dat a pravidla souběhu musí zůstat stejná.

1. **Vstupní pracovník tunelu** je jediným čtenářem virtuálního L3 rozhraní. Provede úplnou validaci IPv4 paketu podle pravidel níže, vyžaduje lokální virtuální IP jako vnitřní zdroj a zařadí jej výhradně do FIFO fronty kontraktu odpovídajícího jeho vnitřnímu cíli. Nešifruje ani nečeká na síť.
2. **Síťový pracovník** je jediným vlastníkem `health`, `info` a `data` requestů svého VPN kontextu, plánování dávek, šifrování, ověřování odpovědí a dešifrování. V jednom okamžiku smí existovat nanejvýš jeden probíhající `data` request.
3. **Výstupní pracovník tunelu** je jediným zapisovatelem do virtuálního L3 rozhraní. Sekvenčně odebírá ověřené IPv4 pakety z příchozích per-peer FIFO front účtovaných podle zdrojové VPN adresy a zapisuje je do virtuálního rozhraní. V každé peer frontě zachovává FIFO; vzájemné pořadí obsluhy různých zdrojových peerů tato specifikace neurčuje.

Fronty se zamykají pouze krátce při vložení, odebrání nebo atomickém převzetí položek a při změně jejich velikostních počítadel. Zámek nesmí být držen během šifrování, dešifrování, HTTP komunikace, čekání na odpověď ani zápisu do tunelu. První pracovník proto pokračuje ve čtení i v době, kdy síťový pracovník zpracovává předchozí request.

Síťová role trvá od úspěšného startu engine do shutdown. Při recovery ukončí obě tunelové I/O role a aktivní tunelovou session, resetuje síťový kontext a vyčistí příchozí i odchozí fronty. Další bootstrap vytvoří nové fronty a po ověření serveru a přístupu znovu vytvoří tunelovou session a dvě I/O role. Čekající pakety vyčištěných front se neuchovávají pro další pokus a jejich doručení není garantováno. Přijatá konfigurace a původní úvodní checkpointy zůstávají zachované. Chyba vrácená čtením tunelu ukončí vstupní roli, `tunnel_io_failed` při zápisu ukončí výstupní roli. Engine nemá obecný dohled jejich ukončení ani catch nezachycených běhových výjimek, který by sám zahájil recovery.

Omezená řídicí obsluha, platformní I/O callbacky a diagnostiky nejsou další VPN pracovní rolí. `get-info` běží souběžně s VPN daty s vlastním transportem a časem. Wizard probe rovněž používá tuto oddělenou cestu, ale nesmí překrýt žádný VPN `data` request. Nový Connect jej bezpečně přeruší a před bootstrapem počká na terminální stav. Počet obslužných vláken není pevně určen číslem čtyři.

## Konfigurační soubor

Konfigurace je JSON ve vlastnictví služby. Pevné úložiště je `config.json` v adresáři phpvpn pod systémovým ProgramData, jeho skutečnou absolutní cestu autoritativně vyhodnotí služba. Existující velikost písmen adresáře `PHPVPN` se nemigruje. IPC nepřijímá cestu od klienta a varování musí zobrazit skutečně rozbalenou absolutní cestu, samotný doslovný text `%ProgramData%` nestačí. Služba ji načte a přísně validuje při každém novém pokusu o připojení; po úspěšné validaci zůstává po dobu připojení v paměti a běžný datový tok znovu nečte disk. Chybná nebo neúplná konfigurace brání spuštění VPN provozu. Tray ani konzolová aplikace konfiguraci přímo nečtou ani nezapisují do souboru a nevalidují ji za službu. Přes veřejné IPC však mohou získat nebo odeslat celý konfigurační JSON, a proto mohou při obsluze `get-config` a `set-config` dočasně držet i jeho tajné hodnoty v paměti.

Každý start služby po bezpečné přípravě adresáře a jednoznačné recovery jednou klasifikuje autoritativní `config.json`. Pouze skutečně chybějící soubor vytvoří přes `ConfigStore::ensureDefaultAtStartup()` a sdílené `createDefault()` v atomickém režimu `createIfMissing`. Existující bajty včetně starého, vadného, nečitelného, nadlimitního či chybně kódovaného souboru nezmění. Souběžně vzniklý cíl nepřepíše. Chyba nezpůsobí automatický retry, IPC a diagnostika zůstanou dostupné, nevyřešená bezpečná inicializace blokuje publikaci i Connect. Connect nic nevytváří. Startup nevolá tray IPC, HTTP ani Connect. Wizard zapisuje až při Finish, Edit Config může výslovně potvrzeným Yes obnovit soubor smazaný za běhu. Aktivní VPN pokračuje na svém snímku, Disconnect disk nečte.

`serverSecret` používá přesné UTF-8 bajty. Pouze hodnota délky nula se pro kryptografii normalizuje na `CHANGE_THIS_SERVER_SECRET`, bez přepisu uloženého textu. Jakákoli neprázdná hodnota, včetně 32 nebo 64 ASCII nul, zůstává doslova zachována. Neexistuje automatická migrace ani zkoušení starých secretů.

Různé klientské počítače smějí používat stejnou virtuální IP. phpvpn jedinečnost nevynucuje ani nerezervuje, systém kolizi připouští a její náprava je odpovědností provozovatele, jde o chybu jeho konfigurace. Samostatně platí zákaz vlastního `communicationContract` mířícího na lokální `virtualIp`. Počet vzdálených peerů níže počítá možné adresy, nikoli počet fyzických počítačů.

Metadata Wizardu, jejich striktní typy a kompatibilní fallbacky jsou závazně popsány v části Opravitelný dokument. Následující příklad bez nich zůstává platným starším schématem.

Navržená struktura:

```json
{
  "masterSetup": {
    "serverUrl": "https://vpn.example.test/phpvpn.php",
    "trustAnyTlsCertificate": true,
    "serverSecret": "server-shared-secret",
    "vpnCidr": "10.99.99.0/24",
    "virtualIp": "10.99.99.2",
    "accessKey": "64-znakový-malý-hex"
  },
  "runtime": {
    "maxOutboundQueueBytes": 67108864,
    "maxInboundQueueBytes": 67108864,
    "minPerPeerQueueBytes": 131072,
    "maxResponseBodyBytes": 67108864,
    "maxNdjsonLineBytes": 67108864,
    "maxDataRecordsPerResponse": 65535,
    "responseTimeoutSeconds": 30,
    "timeSyncIntervalSeconds": 300
  },
  "communicationContracts": {
    "10.99.99.3": {
      "payloadKey": "64-znakový-malý-hex"
    }
  }
}
```

`serverUrl` obsahuje celou URL serverového souboru `phpvpn.php` a klient záměrně podporuje HTTP i HTTPS. `vpnCidr` je kanonický IPv4 CIDR společného VPN adresního prostoru s délkou prefixu výhradně `/24` až `/29`. Při vynechání má výchozí hodnotu `10.99.99.0/24`. Hodnota musí obsahovat síťovou adresu odpovídající uvedenému prefixu, nikoli host adresu s nenulovými host bity. `virtualIp` i všechny adresy v `communicationContracts` musí patřit do `vpnCidr` a současně splňovat pravidla platných klientských adres společné konfigurace. Síťová adresa, první host adresa a broadcast jsou rezervované, platní klienti jsou od network+2 do broadcast-1. `accessKey` odpovídá protokolovému `ACCESS_KEY` a je přesně 32 bajtů zapsaných jako 64 malých hexadecimálních znaků. Každý `payloadKey` je pevný 32bajtový protokolový `PAYLOAD_KEY`. Tento klient používá jediný klíč z `communicationContracts` daného peeru pro odesílání tomuto peeru i pro příjem od něj. Směr rozlišuje AAD obsahující `src` a `dst`. Obecný wire kontrakt a vazbu klíče na uspořádanou dvojici adres definuje [protocol.md](protocol.md), kapitola 9.4. Nejde o uživatelské heslo ani o klíč odvozovaný za běhu.

Rozsah `/24` až `/29` vynucuje jediná sdílená validace v plném i repair režimu, před novým Connectem a před každou publikací přes ConfigStore, včetně `set-config`, Save, Wizard Finish a startup defaultu. Dříve platné `/16` až `/23` jsou nově neplatné, bez automatické migrace, zkrácení prefixu či seznamu peerů. `/30` má pouze jednu klientskou adresu bez vzdáleného peera, `/31` a `/32` současný model nepodporuje a odmítá je. Edit Config zpřístupní text k opravě, Save však validaci neobchází. Mění se kompatibilita konfigurací, nikoli HTTP, kryptografický wire formát nebo IPC schema.

`trustAnyTlsCertificate` má podle současného rozhodnutí výchozí hodnotu `true`. Při HTTPS pak klient záměrně přijme libovolný certifikát pro nakonfigurovanou URL, včetně self-signed certifikátu a certifikátu vydaného neznámou nebo nedůvěryhodnou certifikační autoritou. Jde o vědomě přijaté kritické bezpečnostní riziko: klient nebude ve výchozím stavu ověřovat řetězec důvěry ani důvěryhodnost vydávající autority. Implementace klienta s tímto rizikem záměrně počítá. Bezpečnější budoucí profil může nastavit hodnotu na `false` a vyžadovat standardní validaci řetězce a názvu hostitele.

Konfigurace nesmí být běžně vypisována do logu. Log smí zobrazit virtuální IP a seznam vzdálených IP bez klíčů a secretů. Výjimka pro URL a pevnou konfigurační cestu patří pouze do určených konfiguračních odpovědí a oken, nikoli do logu. To neomezuje záměrně veřejné IPC příkazy `get-config` a `set-config`.

`maxOutboundQueueBytes` je celková maximální velikost paketů načtených z virtuálního L3 rozhraní, které čekají na odeslání na server. `maxInboundQueueBytes` je celková maximální velikost ověřených a dešifrovaných paketů čekajících na zápis do tohoto rozhraní. `minPerPeerQueueBytes` je minimální logická rezervace pro každou možnou per-peer frontu v každém směru. Všechny tři hodnoty jsou uživatelsky konfigurovatelná kladná celá čísla v bajtech; při vynechání mají první dvě výchozí hodnotu 64 MiB (`67108864`) a třetí 128 KiB (`131072`).

Ve výchozím `vpnCidr` `10.99.99.0/24` existuje 253 platných klientských adres `10.99.99.2` až `10.99.99.254`, takže jeden lokální klient má nejvýše 252 vzdálených peerů. Pro jiný podporovaný `/24` až `/29` se `maxRemotePeers` odvodí sdílenými IPv4 helpery z počtu všech možných platných klientských adres po vyloučení jediné lokální adresy. `/29` má pět klientských adres a čtyři vzdálené peery. Počet a násobení rezervací se ověří bez přetečení před alokací. Nejde pouze o počet právě uvedených `communicationContracts`, ale o počet všech peerů, pro které v daném adresním prostoru může existovat fronta. Cílový editor Communication contracts podle UX10 má proto nejvýše 252 nativních řádků bez virtualizace nebo recyklace HWND. Nejde o aditivní Wizard kandidáty 13/14, které zůstávají beze změny. Skutečný limit výsledného JSON 524288 bajtů i rozpočty front se kontrolují samostatně také v podporovaném rozsahu.

Před každým pokusem o připojení MUSÍ konfigurace pro odchozí a příchozí směr samostatně splnit:

```text
maxOutboundQueueBytes >= maxRemotePeers × minPerPeerQueueBytes
maxInboundQueueBytes  >= maxRemotePeers × minPerPeerQueueBytes
```

Nesplnění kteréhokoli invariantu konfiguraci odmítne ještě před `health` a před vytvořením tunelu. `minPerPeerQueueBytes` je pouze logická rezervace pro admission účetnictví; implementace NESMÍ fyzicky předalokovat 252 bufferů ani jiný maximální počet per-peer front. Skutečná fronta a její paměť vznikají líně až při prvním přijatém paketu daného peeru.

Při každém pokusu o zařazení nového paketu se v příslušném směru použije obsazenost po hypotetickém vložení a MUSÍ platit obě podmínky: skutečný součet obsazeností všech peer front nepřekročí odpovídající `maxQueueBytes` a současně

```text
sum(max(obsazenostPeerFronty, minPerPeerQueueBytes)) přes všechny možné peer fronty <= maxQueueBytes
```

Odchozí směr používá jako `maxQueueBytes` hodnotu `maxOutboundQueueBytes` a účtuje fronty podle cílové VPN adresy; příchozí směr používá `maxInboundQueueBytes` a účtuje je podle zdrojové VPN adresy. Z uvedeného invariantu plyne, že jediná peer fronta může dosáhnout nanejvýš `maxQueueBytes - (maxRemotePeers - 1) × minPerPeerQueueBytes`. Pro výchozí hodnoty je tato mez 32.625 MiB, tedy 32 MiB + 640 KiB (`34209792` bajtů). Logická rezervace se počítá v každém směru samostatně a neznamená vlastnictví předem přidělené fyzické paměti.

`maxResponseBodyBytes`, `maxNdjsonLineBytes`, `maxDataRecordsPerResponse` a `responseTimeoutSeconds` jsou uživatelsky konfigurovatelná kladná celá čísla typu int64. Při vynechání mají po řadě výchozí hodnoty `67108864` bajtů (64 MiB), `67108864` bajtů, `65535` záznamů a `30` sekund. Úplná validace konfigurace odmítne nulu, zápornou hodnotu, necelé číslo nebo hodnotu nereprezentovatelnou tímto typem. `responseTimeoutSeconds` má navíc maximum `2147483` sekund pro bezpečný převod na milisekundy pro WinHTTP. Pro ostatní tři hodnoty není stanoven další globální horní strop nad rámec typu a následujícího vztahu.

Musí platit `maxNdjsonLineBytes <= maxResponseBodyBytes`. Rovnost je dovolená. Překročení tohoto vztahu i maxima `responseTimeoutSeconds` odmítá úplná validace i repair analýza, která používá tutéž validaci s povolenou chybějící identitou.

`maxResponseBodyBytes` omezuje počet přesných bajtů těla jedné HTTP odpovědi. Transport jej průběžně počítá při přijímání odpovědí `health`, `info` i `data`; při překročení limitu request ukončí, neúplnou odpověď nepoužije a nepředá ji protokolovému parseru. `maxNdjsonLineBytes` omezuje počet bajtů jednoho řádku NDJSON odpovědi endpointu `data`, včetně jeho ukončovacího LF. NDJSON parser délku kontroluje průběžně a příliš dlouhý řádek odmítne ještě před base64 dekódováním jeho polí. `maxDataRecordsPerResponse` je maximální počet záznamů, tedy NDJSON řádků typu `data`, které klient přijme v jedné odpovědi endpointu `data`; parser po překročení limitu odmítne celou odpověď ještě před následným kryptografickým zpracováním překračujícího řádku.

`responseTimeoutSeconds` určuje jediný absolutní monotónní deadline od zahájení HTTP requestu přes DNS, spojení, TLS, odeslání a hlavičky až po celé tělo odpovědi pro `health`, `info` i `data`. Dílčí blok ani přechod fáze jej neobnoví. Timeout spustí bezpečné zrušení a po potvrzeném terminálním stavu vrátí timeout, nikdy pozdní úspěch. Timeout datového requestu VPN vede do běžné recovery. Samotný timeout obnovovacího `health` během připojení pouze nastaví `lastHealthVerified = no` a zachová předchozí ověřený časový snímek podle části Synchronizace času. Jednorázová diagnostika a Wizard skončí bez automatického retry. Převody a nastavení timeoutů se kontrolují podle části Společný HTTP transport. Limity celkové velikosti odpovědi, délky NDJSON řádku, počtu datových řádků a celkového času se kontrolují samostatně a žádný z nich nenahrazuje ostatní.

`timeSyncIntervalSeconds` je uživatelsky konfigurovatelné kladné celé číslo určující periodu zahájení běžného pravidelného pokusu o obnovení ověřeného času serveru. Při vynechání má výchozí hodnotu `300`, tedy 5 minut. Validátor nepřidává globální horní strop nad rámec typu int64 a odmítne nulu, zápornou hodnotu, necelé číslo i hodnotu nereprezentovatelnou tímto typem. Přijetí hodnoty validátorem není zárukou bezpečnosti všech extrémních časových výpočtů.

## Stavový automat připojení

1. **Načtení konfigurace.** Klient validuje URL, kanonický IPv4 tvar `vpnCidr`, příslušnost `virtualIp` a všech adres kontraktů do tohoto prefixu, pravidla platných klientských adres, hex formát a délky klíčů, jedinečnost kontraktů a dostupnost podporované platformní vrstvy. Na Windows v této fázi smí ověřit distribuční manifest, DLL, architekturu a povinné Wintun API, ale NESMÍ ještě vytvořit ani otevřít adaptér, zahájit Wintun session nebo měnit síť.
2. **Health.** Před prvním `info` nebo `data` vygeneruje nový UUIDv4 `requestId`, zaznamená monotónní `sendMono` a odešle `auth-none` na `?action=health`.
3. **Ověření serveru a času.** Po přijetí celé odpovědi zaznamená monotónní `receiveMono`. Pokud odpověď odpovídá syntaxi `health` a nese stav `running`, klient ověří shodu `requestId` a GCM tag podle protokolu. Teprve potom přijme autentizovaný UTC čas serveru a atomicky vytvoří počáteční časový odhad podle následující části; lokální systémový čas nikdy nemění.
4. **Časová rezerva.** Timestamp každého následujícího autentizovaného `info` nebo `data` requestu vznikne výhradně z posledního ověřeného odhadu serverového času, aktuálního monotónního času a normativní bezpečnostní rezervy podle následující části. Po synchronizaci se nesmí přímo odvozovat z aktuálních systémových hodin.
5. **Info.** Klient autentizovaně odešle `auth-semi` na `?action=info`, ověří a dešifruje odpověď a uloží obdržené limity a doporučené provozní hodnoty. Tvrdé limity, zejména maximální velikost těla požadavku, musí dodržet. Doporučené intervaly pollingů slouží jako plánovač, pokud nejsou v budoucí specifikaci označené za závazné.
6. **Ověření přístupového klíče.** Existující síťová role ještě před spuštěním tunelu a jeho dvou I/O rolí provede prázdný autentizovaný polling `data`. Tím ověří `ACCESS_KEY` i úplnou odpověď `data`. Přijaté platné dávky zpracuje stejně jako při běžném pollingu a připraví je pro výstupní pracovník.
7. **Spuštění tunelu a provoz.** Teprve po úspěšném `health`, `info` a prvním prázdném `data` pollingu služba na Windows vytvoří nebo otevře jediný vlastní Wintun adaptér, zahájí jedinou session, nakonfiguruje vlastní adresu a routy a spustí dvě tunelové I/O role. Síťová role již běží a po úspěšném spuštění přejde do pravidelného provozu. Čtení tunelu a pravidelný polling endpointu `data` nesmějí začít dříve.
8. **Obnova.** Chyba vrácená bootstrapem nebo provozním `data` requestem vede k teardown existujících tunelových rolí, session a front. O dalším pokusu rozhoduje bezpečná klasifikace chyby služby (`lastError.recoverable`). Například timeout, selhání DNS či spojení a obnovitelná serverová chyba vedou do `recovering`. Neobnovitelná chyba vede do `error`, například selhání kryptografického ověření `health`, ověření/dešifrování/validace `info` nebo odmítnutí `ACCESS_KEY` při bootstrapu. Samotné selhání periodického `health` se řídí částí Synchronizace času a recovery nespouští.

Recovery po prodlevě opakuje `health`, `info` a prázdný autentizovaný `data` nad novými frontami, potom znovu vytvoří tunelovou session a obě I/O role. Použije konfiguraci přijatou původním Connectem, nečte znovu disk ani nepřebírá mezitím uložené změny. Zachová původní úvodní checkpointy i provozní čítače stejného logického spojení. Při neúspěšném pokusu znovu provede teardown a podle obnovitelnosti chyby naplánuje další pokus nebo přejde do `error`.

Žebřík základního backoffu je **1/2/4/8/16/32/60 s**, s přičteným jitterem od nuly do **20 %** základní hodnoty. Po chybě se index zvýší ještě před výpočtem prodlevy, proto první čekání má základ **2 s** a následují **4/8/16/32/60/60… s**. První interval je tedy 2–2,4 s, poslední 60–72 s. Úspěšné připojení index resetuje, stejně jako nový logický Connect a dokončený Disconnect. Čekání lze přerušit řídicím příkazem Disconnect nebo stop. Recovery backoff je oddělený od běžného datového pollingu s maximem 5 s.

Lifecycle a backoff ověřují existující scénáře `runtime.lifecycle_keeps_one_network_role_and_recreates_two_io_roles` a `runtime.lifecycle_recovery_tears_down_and_recreates_after_current_backoff` v [runtime testech](client/tests/unit/test_runtime_status.cpp). Další scénáře téhož souboru ověřují přijatý snapshot po Save a smazání konfigurace, uchování úspěšných i neúspěšných úvodních checkpointů, idempotentní Connect a reset po Disconnectu. Fake driver ověřuje lifecycle enginu, nikoli skutečný Wintun nebo obecnou odolnost proti pádu role.

Windows Service pro každý nový logický pokus o připojení udržuje vedle aktuální fáze také trvalé výsledky tří bootstrap kontrolních bodů v přesném pořadí **Server URL**, **SERVER_SECRET**, **ACCESS_KEY**. Každý bod má stav `pending`, `success` nebo `failed`. Nový logický pokus vzniká pouze přijetím `connect` ve stavu `disconnected` nebo `error`; všechny tři výsledky se při něm atomicky nastaví na `pending`. Idempotentní `connect` ve stavu `connecting`, `connected` nebo `recovering` nový pokus nevytváří a výsledky nemění jen kvůli opakování příkazu.

Kontrolní bod **Server URL** přejde na `success` po navázání transportu a přijetí syntakticky použitelné odpovědi `health`, ještě před jejím kryptografickým ověřením. Služba tento výsledek zveřejní již v tomto okamžiku, nikoli až po návratu celé ověřovací operace. Publikace nesmí držet stavový zámek během kryptografie ani vkládat umělé čekání. **SERVER_SECRET** přejde na `success` až po kryptografickém ověření odpovědi `health` a po úspěšném ověření, dešifrování a úplné validaci odpovědi `info`. **ACCESS_KEY** přejde na `success` až po úspěšném prázdném autentizovaném pollingu `data`. Při selhání se správný právě vyhodnocovaný bod nastaví na `failed` a pozdější neprovedené body zůstanou `pending`. Selhání spuštění tunelu nastává až po těchto bodech, takže všechny tři mohou zůstat `success`, zatímco celkový stav přejde do `error`. Výsledky úvodního bootstrapu se zachovají do dalšího nového logického pokusu nebo dokončeného odpojení, aby je bylo možné bezpečně rekonstruovat i po přeskočení krátké fáze pollingem UI. Automatická obnova je nemaže ani nenahrazuje výsledky dalších recovery běhů. Průběh obnovy vyjadřuje aktuální stav, fáze a bezpečná poslední chyba. Zelené kontrolní body dokládají výsledek úvodních kontrol, samy nepotvrzují aktuálně funkční spojení. Při startu služby a po dokončeném `disconnect` mají všechny tři kontrolní body hodnotu `pending`.

Příkazový výstup má stručně ukazovat fáze: připojování k serveru, dostupný server, úspěšně ověřený `SERVER_SECRET`, zjištěné provozní limity a stav tunelu. Tajemství ani autentizační tagy se nevypisují.

## Synchronizace času

Veškerý proměnný stav synchronizace času VPN vlastní výhradně síťový pracovník. Oddělené diagnostiky `get-info` a ProbeClient mají vlastní dočasný TimeSnapshot a transport, se stejným ověřením RTT a bezpečnostní rezervou. Nesmějí měnit časový snímek VPN. Žádná tunelová role jej nesmí měnit ani z něj samostatně vytvářet timestampy. Jeden úplný časový snímek obsahuje alespoň ověřený serverový UTC timestamp z `health`, odhad `serverTimeAtReceive`, monotónní `receiveMono`, naměřené RTT, rozdíl od lokálního systémového UTC času v okamžiku synchronizace a okamžik synchronizace. Snímek se zveřejní nebo nahradí pouze jako jeden celek po úspěšném ověření odpovědi.

První `health` MUSÍ skončit úspěchem před prvním `info` nebo `data`. Síťový pracovník bezprostředně před zahájením HTTP requestu zaznamená `sendMono` z monotónních hodin a bezprostředně po přijetí celé odpovědi zaznamená `receiveMono` ze stejného monotónního časového zdroje. Nejprve ověří přesný očekávaný `requestId`, syntaxi všech polí a GCM tag. Pouze při úplném úspěchu vypočte:

```text
RTT = receiveMono - sendMono
serverTimeAtReceive = authenticatedServerTimestamp + RTT / 2
serverLocalOffsetAtSync = serverTimeAtReceive - localSystemUtcAtReceive
```

TimeSync odmítá `receiveMono < sendMono`. Kontroluje také přetečení součtu serverového timestampu s polovinou RTT a součtu použitého pro offset. Tyto dílčí kontroly nedokládají bezpečnost všech extrémních vstupů. `serverLocalOffsetAtSync` slouží pro stav synchronizace a detekci změny systémových hodin; po přijetí snímku se nesmí používat spolu s aktuálními systémovými hodinami jako primární zdroj timestampů autentizovaných requestů.

Pro každý běžný autentizovaný request síťový pracovník načte aktuální monotónní čas a vypočte:

```text
safetyMargin = max(1000 ms, RTT / 2 + 250 ms)
requestTimestamp = serverTimeAtReceive
                   + (currentMonotonic - receiveMono)
                   - safetyMargin
```

Výsledek se zapíše v přesném milisekundovém UTC formátu vyžadovaném protokolem. Po úspěšné synchronizaci klient NESMÍ pro tento výpočet přímo použít aktuální systémové datum a čas. Změna wall clock proto sama neposune vytvářené autentizační timestampy. Její detekce vstupuje do rozhodnutí o obnově v sériové connected smyčce popsané níže.

V sériové connected smyčce `VpnEngine::runNetworkThread` síťový pracovník nejprve provede datový cyklus a vyhodnotí jeho výsledek. Při chybě `data` řeší chybu a případnou recovery, ke kontrole obnovy času v téže iteraci už nepřejde. Po úspěšném datovém cyklu kontroluje, zda chybí snímek, zda od jeho `synchronisedAtMonoMs` uplynulo alespoň `timeSyncIntervalSeconds`, nebo zda `TimeSync::systemClockChanged` zjistí změnu wall clock. Pokud ano, sériově provede nový `auth-none` `health`. Perioda se tedy měří od posledního úspěšně přijatého snímku, nikoli od posledního neúspěšného pokusu. Výchozích 300 s není vypršení odhadu ani deadline zastavení VPN.

Detekce wall clock porovnává aktuální systémový UTC čas s jeho očekávaným průběhem od snímku, s výchozí tolerancí 2000 ms. Provádí se v uvedeném místě connected smyčky, nezajišťuje událostní prioritu před každým autentizovaným requestem. Synchronizační `health` se nepřekrývá s `data` requestem téhož VPN kontextu. Izolované diagnostické health/info smějí běžet souběžně s VPN daty.

Po dokončení obnovovacího `health` se `lastHealthVerified` nastaví na `yes` při úspěchu a na `no` při neúspěchu. Pouze úplný úspěch nahradí celý ověřený časový snímek. Neplatná, neúplná nebo kryptograficky neověřená odpověď ani chyba vytvoření kandidáta nesmí změnit předchozí snímek. Samotné selhání tohoto `health` nespouští recovery ani její backoff. Další iterace pokračuje datovým cyklem s předchozím snímkem. Pokud v následné kontrole stále platí podmínka obnovy, zkusí další `health`. Recovery po chybě datového requestu je samostatná cesta. Částečně vypočtené RTT, timestamp ani offset se nepublikují. Do logu NESMÍ zapsat timestampy requestů, přesný časový offset, klíče, HMAC nebo GCM tagy ani celé požadavky či odpovědi; smí uvést pouze bezpečné stavové informace, například že synchronizace uspěla, selhala nebo čeká na opakování.

## Povinné testovací scénáře synchronizace času

1. Výchozí konfigurace použije `timeSyncIntervalSeconds = 300`; kladná celá uživatelská hodnota projde a nula, záporná, necelá nebo nereprezentovatelná hodnota je odmítnuta před prvním `health`.
2. Před prvním `info` a `data` proběhne právě jeden úspěšně ověřený `health`. Chybějící, změněný nebo cizí `requestId`, neplatný GCM tag či neplatné pole zabrání vytvoření počátečního časového snímku a žádný autentizovaný request se neodešle.
3. Pro pevné `sendMono`, `receiveMono` a autentizovaný serverový timestamp test ověří přesné `RTT = receiveMono - sendMono`, `serverTimeAtReceive = timestamp + RTT / 2` a rozdíl vůči lokálnímu UTC času v okamžiku synchronizace.
4. Known-answer test vytvoří běžný autentizační timestamp přesně jako `serverTimeAtReceive + (currentMonotonic - receiveMono) - max(1000 ms, RTT / 2 + 250 ms)`. Ověří větev s minimální rezervou 1000 ms i větev s rezervou zvětšenou vysokým RTT.
5. Změna systémových hodin po synchronizaci nezmění timestamp odvozený ze stejného monotónního průběhu. Detekce wall clock rozliší shodný průběh a skok hodin. Simulovaný zpětný chod monotónních hodin pokus zneplatní.
6. Obnovu po uplynutí 300 sekund od ověřeného snímku a při detekci změny wall clock posuzovat na místě kontroly po úspěšném datovém cyklu. Ověřit sériovost health/data a nahrazení celého snímku po úspěchu, bez požadavku na prioritu před každým autentizovaným requestem.
7. Neúspěšný kandidát časového snímku zachová předchozí úplný snímek. Tento test časové matematiky není důkazem provozního lifecycle enginu.
8. Logovací test ověří, že úspěch, chyba ani diagnostika neobsahují request timestamp, přesný offset, klíč, HMAC/GCM tag, celé tělo požadavku ani celou odpověď.

## Odchozí tok paketů a plánování requestů

Virtuální rozhraní dodává kompletní IPv4 pakety. Před zařazením musí vstupní pracovník provést úplnou strukturální validaci podle následující podkapitoly. Vnitřní zdroj musí přesně odpovídat lokální virtuální IP a vnitřní cíl musí být platná VPN IP s existujícím `communicationContract`; výběr fronty i payload klíče proto vždy vychází ze stejné uspořádané dvojice `(lokální IP, vnitřní cíl)`. Paket určený vlastní virtuální IP, paket s neplatnou hlavičkou nebo paket bez platného kontraktu se přes relay neodesílá; zahození se loguje pouze souhrnně po důvodu a cíli.

Odchozí per-peer fronta se účtuje podle cílové VPN adresy paketu. Pokud by vložení nového paketu porušilo globální `maxOutboundQueueBytes` nebo logickou per-peer rezervaci, vstupní pracovník zahodí pouze tento nový paket. NESMÍ kvůli němu odstranit ani přeuspořádat již zařazené pakety. Zahození eviduje agregovaně podle stabilního bezpečného důvodu a cílového peeru, bez obsahu paketu, klíčů, tagů, ciphertextu nebo jiných citlivých hodnot.

Síťový pracovník pro každý request vybírá pouze requestově velký prefix front. Jeden datový element patří přesně jedné uspořádané dvojici `src`, `dst` a nese dávku paketů jen pro tento cíl. Binární plaintext, byte order a validační pravidla jsou normativně definované v `protocol.md`. Síťový pracovník jej šifruje AES-256-GCM příslušným `PAYLOAD_KEY` a vytváří normativní řádek `data`.

### Úplná validace vnitřních IPv4 paketů

Klient považuje IPv4 paket za platný pouze tehdy, pokud má alespoň 20 bajtů, první nibble udává verzi 4, `IHL` je alespoň 5 a délka hlavičky nepřesahuje délku bufferu. Pole `total length` musí být alespoň tak velké jako délka hlavičky a musí se přesně rovnat délce celého bufferu; klient nesmí akceptovat přívěsné ani chybějící bajty. Kontrolní součet IPv4 hlavičky musí být platný. Implementace před každým čtením pole ověří jeho hranice a nesmí z neověřených hodnot provádět alokaci ani výpočet ukazatelů.

Klient fragmenty znovu neskládá ani je neinterpretuje jako neúplný paket. Platný IPv4 fragment smí projít jako samostatný celý paket, pokud splňuje výše uvedenou strukturální kontrolu a kontrolu vnitřních adres. Fragmenty nikdy nesmějí obcházet vazbu adres ani vytvářet vlastní stav skládání.

Při odesílání musí být vnitřní zdroj shodný s lokální virtuální IP a vnitřní cíl shodný s cílem kontraktu, do jehož fronty byl paket zařazen. Po přijetí musí být vnitřní zdroj shodný s `src` datového řádku a vnitřní cíl shodný s lokální virtuální IP, která je současně `dst` datového řádku. Kontrola se provede po úspěšném AES-GCM dešifrování a rozbalení dávky, ale před vložením kteréhokoli paketu do příchozí fronty nebo zápisem do tunelu. Je-li nevyhovující byť jediný paket, je neplatná celá dávka: klient ji zahodí, žádný její paket nepředá a chybu eviduje pouze souhrnně.

### Pollingový interval

Schválené maximum běžného pollingového intervalu zůstává **5000 ms (5 s)**, dolní mez je 20 ms. Současný Windows runtime po ověřené odpovědi `info` používá v `NetworkWorker::nextPollDelayMs` tyto meze:

```text
low = max(20, minDataPollIntervalMs)
high = min(5000, maxDataPollIntervalMs)
```

Při provozu vrátí interval na `low`, při nečinnosti jej zdvojnásobuje směrem k `high`. Pomocná funkce `clampToRange` při `low > high` vrací `low`. Tento výpočet není bezpečný oboustranný clamp všech serverových extrémů, například serverové minimum nad 5000 ms může vést k čekání delšímu než 5 s. Oprava obou mezí na `clamp(serverValue, 20, 5000)` a ověření hran patří k budoucí práci B03 podle [plánu pre-poll backpressure](Plans/2026-09-12-02-29-09/plan-v003.md#b03-pětisekundová-mez-čekání).

Síťový pracovník provádí polling i při prázdných odchozích frontách. Doba requestu včetně případného timeoutu může skutečný odstup zahájení prodloužit, klient kvůli tomu neotevře paralelní request. Maximum běžného intervalu není povinnost odeslat data nejméně jednou za 5 s při kapacitní blokaci. Plánovaná ochrana bude moci přeskočit více intervalů, dokud se kapacita neuvolní. Dosud není zapojena do runtime a za dodanou ji lze označit až po implementaci a akceptaci B05. Backpressure zůstává posledním samostatným implementačním blokem.

Na Windows se každý skutečně zahájený polling `data` započítá právě jednou v okamžiku, kdy je jeho úplné serializované tělo předáno transportu. Současně se klasifikuje právě do jedné kategorie: `empty`, neobsahuje-li žádný odchozí řádek `data`, nebo `withPayload`, obsahuje-li alespoň jeden odchozí řádek `data`. Samotný povinný řádek `auth-full` payload netvoří. Prázdný autentizovaný polling použitý při bootstrap kontrole `ACCESS_KEY` se proto započítá jako `empty`. V každém vnitřně konzistentním snímku MUSÍ platit `dataPollsTotal = dataPollsEmpty + dataPollsWithPayload`.

### Velikostní a spravedlivé plánování

Pracovník používá rozpočet `maxRequestBodyBytes - 1024`. 1 KiB je pevná rezerva nad očekávanou serializační režií. Současně respektuje `maxDataRecordsPerRequest` z ověřené odpovědi `info`, tedy nejvyšší počet odchozích záznamů `data` v jednom requestu. Početní mez je další limit a nenahrazuje přesné měření těla v bajtech. Konečná kontrola vždy změří skutečně sestavené tělo v bajtech. Pokud paket nebo z něj vytvářený datový element z čela per-peer FIFO nelze vložit do aktuální dávky, ale vešel by se do samostatného jinak prázdného platného requestu, zůstane na čele této FIFO fronty pro další request.

Pokud se paket nebo datový element z čela per-peer FIFO nevejde ani do samostatného jinak prázdného platného requestu po započtení všech přesných režijních bajtů šifrování, kódování, NDJSON a autentizačního řádku, síťový pracovník jej atomicky odstraní z čela fronty a trvale zahodí. Toto odstranění NESMÍ změnit vzájemné FIFO pořadí zbývajících paketů. Klient zahození agregovaně eviduje podle důvodu a cíle; do logu NESMÍ zapsat obsah paketu, klíče, tagy, ciphertext ani jiné citlivé hodnoty. MTU tunelu a nakonfigurovaná nebo odvozená maximální velikost datového elementu jsou preventivní limity, ale toto povinné runtime rozhodnutí a přesné změření skutečně sestaveného requestu nenahrazují.

Výběr je spravedlivý: pracovník vede kruhové pořadí cílů, v první fázi se pokusí zařadit alespoň jeden paket z každé neprázdné fronty v mezích počtu záznamů a bajtového rozpočtu. V dalších průchodech doplňuje pakety do již vybraných záznamů opět kruhově, dokud zbývá bajtový rozpočet. Po každém requestu posune počáteční cíl. Jedna dlouhá fronta tak nevytlačuje krátké fronty. Pakety v každé konkrétní frontě zůstávají FIFO. FIFO určuje neměnné pořadí paketů uvnitř jedné peer fronty, zatímco kruhové plánování určuje pouze spravedlivé střídání mezi různými peer frontami při sestavení requestu. Kruhové plánování NESMÍ měnit admission účetnictví, obcházet logické rezervace ani přeuspořádat pakety uvnitř fronty.

Tato pravidla popisují současné odchozí plánování. Maximum běžného pollingu zůstává 5 s. Předběžný odklad pollingu podle kapacity a rezervací příchozích front, tedy plánované pre-poll admission backpressure, dosud není zapojen do runtime. Jeho popis v části Příjem dat představuje budoucí požadavek. Současné limity odchozího requestu ani admission jednotlivých přijatých paketů jeho dodání neprokazují.

## Příjem dat

Následující plné zpracování je povinné pro normální bootstrap, recovery i provozní polling, s výjimkou výslovně plánované ochrany v bodu 7. Jedinou oddělenou diagnostickou cestou je `wizard-check-access` v ProbeClient podle obecné diagnostické výjimky `protocol.md` 9.5. Po úplném ověření obálky a nulového výsledku všechny payloady zahodí bez GCM a bez jakéhokoli použití, nemění tunel, fronty, čas, bootstrap body ani provozní čítače.

Odpověď na `data` je NDJSON: nula nebo více řádků `data`, právě jeden `data-result` a poslední `data-mac`.

1. Transport nejprve průběžně uplatní `maxResponseBodyBytes` a `responseTimeoutSeconds`. NDJSON parser potom průběžně uplatní `maxNdjsonLineBytes` ještě před base64 dekódováním příliš dlouhého řádku, počítá řádky typu `data` a odmítne celou odpověď, jakmile jejich počet překročí `maxDataRecordsPerResponse`; překračující řádek nesmí před odmítnutím kryptograficky zpracovat. Poté klient ověří strukturu odpovědi, `data-result` a závěrečný `data-mac`. Ten chrání počet, pořadí a úplnost datových řádků.
2. U každého řádku nejdříve ověří, že `dst` je jeho lokální virtuální IP. Cizí řádek zahodí ještě před výběrem payload klíče.
3. Podle přesné dvojice `src`, `dst` vyhledá kontrakt. Neexistuje-li, řádek zahodí a souhrnně zaloguje.
4. Ověří kanonický base64url, délky IV a tagu a provede AES-GCM dešifrování s příslušným `PAYLOAD_KEY` a normativním AAD. Neplatný GCM tag znamená zahození pouze daného řádku.
5. Ověří formát binární dávky: hlavičku počtu, tabulku délek, přesný počet a hranice surových bajtů. Nesmí předat částečně rozbalenou nebo neověřenou dávku.
6. U každého rozbaleného paketu provede úplnou validaci IPv4. Navíc vyžaduje, aby jeho vnitřní zdroj přesně odpovídal `src` datového řádku a vnitřní cíl lokální virtuální IP, tedy `dst` datového řádku. Nevyhoví-li byť jediný paket, zahodí celou dávku ještě před vložením kteréhokoli jejího paketu do příchozí fronty.
7. **Plánováno, dosud nedodáno:** pre-poll ochrana má před běžným pollingem posoudit globální prostor `maxInboundQueueBytes` i logické rezervace možných zdrojových peerů a při nedostatku kapacity polling odložit. Současný helper `DirectionQueues::canAdmitAnotherPacket` nemá runtime call site. Jeho oprava a napojení patří k B01–B02, hraniční intervaly k B03 a ověření a potvrzení dodání k B04–B05. Předběžná kontrola není rezervací celé odpovědi ani zárukou bezeztrátovosti. Runtime admission každého přijatého paketu podle bodu 8 zůstává dodaná a povinná.
8. Příchozí per-peer fronta se účtuje podle `src` datového řádku. Pokud by vložení již ověřeného paketu porušilo globální `maxInboundQueueBytes` nebo logickou per-peer rezervaci, klient zahodí pouze tento nový paket. NESMÍ odstranit ani přeuspořádat již zařazené pakety a zahození agregovaně eviduje podle bezpečného důvodu a zdrojového peeru, bez obsahu paketu nebo citlivých hodnot.
9. Výstupní pracovník zapíše pouze takto platné IPv4 pakety do tunelu sekvenčně v pořadí, v jakém byly v dávce uvedeny.

Protokol je at-most-once na serverovém bufferu. Ztracená HTTP odpověď nebo pád po převzetí může znamenat ztrátu dávky; klient nemá předstírat garantované doručení. Výchozí hodnota `65535` pro `maxDataRecordsPerResponse` je vysoký klientský kompromis bez změny protokolu. Uživatel smí limit zmenšit, ale tím může způsobit odmítnutí odpovědi obsahující dávky, které server již atomicky vyzvedl a z bufferu odstranil. Aplikační vrstvy nad VPN mohou používat vlastní retransmise.

## Povinné testovací scénáře front a per-peer kvót

1. Chybějící `vpnCidr` použije výchozí hodnotu `10.99.99.0/24`, odvodí přesně 252 vzdálených peerů a výchozí hodnoty obou 64MiB globálních limitů a 128KiB logické rezervace projdou validací bez fyzického vytvoření 252 front nebo bufferů. Ověřit všechny podporované `/24` až `/29`, pro `/29` přesně čtyři peery, také na dolní a horní hranici IPv4. Nekanonický CIDR s nenulovými host bity, síť, první host, broadcast, `virtualIp` mimo prefix nebo kontrakt mimo prefix se odmítne před prvním `health`. `/16` až `/23` a `/30` až `/32` se odmítnou jako neplatný CIDR, nikoli až kvůli rozpočtu front.
2. Pro odchozí i příchozí směr samostatně projde konfigurace s `maxQueueBytes = maxRemotePeers × minPerPeerQueueBytes` a hodnota o jeden bajt menší je před `health` odmítnuta. Stejný test se provede pro `/24` i `/29` s počtem peerů odvozeným z prefixu, v plném i repair režimu. Ověřit nejvyšší reprezentovatelnou rezervaci i odmítnutí násobení, které by přeteklo.
3. Při výchozích hodnotách lze jednu peer frontu naplnit přesně na 32.625 MiB (`34209792` bajtů), pokud ostatní možné fronty zůstávají prázdné; další bajt je odmítnut kvůli logické rezervaci, aniž by se změnily již zařazené pakety.
4. Odchozí fronty se odděleně účtují podle `dst` a příchozí podle `src`. Paket na hranici globálního limitu i logické rezervace projde, paket o jeden bajt nad příslušnou hranicí se zahodí jako nový a zachová obsah i FIFO pořadí všech existujících front.
5. Kruhové plánování obsluhuje neprázdné odchozí peer fronty spravedlivě, ale v každé zachová FIFO a nikdy nepřesune kapacitu vyhrazenou admission invariantem. Agregovaná diagnostika rozliší globální limit a logickou rezervaci a uvede peer, aniž by obsahovala paket nebo citlivé hodnoty.
6. Současná runtime admission ověří každý přijatý paket proti globálnímu limitu i logickým rezervacím. Nepřijatý paket nezvýší příchozí IPv4 čítače a jeho odmítnutí neodstraní ani nepřeuspořádá dříve zařazené pakety. Existující testy front a runtime příjmu nejsou důkazem předběžného odkladu pollingu.

**Budoucí akceptace B04, dosud nedodaná:** samostatně ověřit pre-poll kontrolu globální kapacity i rezervací, odklad a obnovení pollingu, FIFO, účetnictví a přerušení čekání při Disconnect/stop. Hraniční intervaly musejí odpovídat budoucí opravě B03 na 20–5000 ms. Při trvající blokaci se nevyžaduje odeslání do 5 s. Předběžná ochrana nenahrazuje per-packet admission při souběžné změně obsazenosti nebo neočekávaném rozdělení odpovědi. Tyto scénáře patří k poslednímu samostatnému implementačnímu bloku backpressure, jejich plán není výsledkem testu ani potvrzením dodání.

## Bezpečnostní model a přijatá rizika

- Relay server nemá payload klíče a nemůže dešifrovat IP obsah; důvěrnost a integritu jednoho payloadu zajišťuje AES-256-GCM mezi klienty.
- `health` autentizuje serverový čas a veřejná pole pomocí `SERVER_SECRET`; `info` a `data` vyžadují přesnou protokolovou autentizaci.
- HTTP zůstává záměrně podporovaným provozním režimem. Jsme si vědomi, že aktivní útočník může zachycený platný polling v časovém okně zopakovat, vyzvednout ciphertext z příchozí fronty oběti a nenávratně jej z relay odstranit, i když bez payload klíče nepřečte plaintext. Toto riziko replay útoku a související ztráty dostupnosti vědomě přijímáme; klient bude implementován s podporou HTTP a bez mechanismu, který by tento protokolový replay sám potlačoval.
- Pokud `trustAnyTlsCertificate` zůstane `true`, HTTPS nechrání klienta spolehlivě proti podvržení serveru na úrovni TLS. Nastavení je vědomě akceptované kompatibilitní riziko a musí být zřetelně viditelné v konfiguraci.
- Řídicí named pipe je záměrně dostupná každé lokální aplikaci bez ověřování uživatele, skupiny, procesu nebo Windows tokenu. Každý lokální proces proto může číst stav a diagnostiku služby, vyžádat si `info` a úplnou konfiguraci včetně jejích tajných hodnot, uložit novou konfiguraci a odeslat povolené příkazy včetně `connect` a `disconnect`. Toto riziko neoprávněného lokálního ovládání, změny konfigurace a zpřístupnění jejích údajů vědomě přijímáme. Validace formátu zpráv, verze smlouvy a whitelist příkazů tím nejsou zrušeny.
- Protokol nebrání replayi uvnitř platného časového okna, neposkytuje exactly-once, potvrzení ani ochranu dostupnosti. Klient nemá vytvářet vlastní replay cache, pokud se současně nezmění normativní specifikace.
- Klíče, tagy, ciphertexty, celé requesty a interní cesty se nesmí zapisovat do logů. Konfigurační soubor má mít omezená přístupová oprávnění jako ochranu proti přímému čtení ze souborového systému; tato oprávnění však neomezují záměrně veřejné `get-config` a `set-config` přes named pipe.

### Logování a diagnostika

Služba po bezpečné přípravě úložiště zapíná lokální textový log `phpvpn-service.log` v podadresáři `logs` svého datového adresáře. Produkční datový adresář `PHPVPN` odvozuje ze systémového ProgramData přes Windows API, nejde o natvrdo předpokládanou absolutní cestu.

Rotační práh je **8 MiB (8388608 bajtů)**. Před zápisem dalšího celého formátovaného řádku včetně jeho CRLF logger zkouší rotaci, pokud by součet překročil práh. Při přesné rovnosti nerotuje. Uchovává nejvýše **pět historických souborů** `phpvpn-service.1.log` až `phpvpn-service.5.log`, kde `.1.log` je nejnovější historie. Zápis a rotaci v procesu serializuje mutex a po každém řádku provede flush streamu.

Tato politika není zárukou úspěšného diskového I/O, zachování diagnostiky při jeho selhání ani pevnou mezí velikosti souboru při libovolně dlouhé jediné zprávě. Zprávu logger nezkracuje ani nedělí, takže jediný formátovaný řádek může přesáhnout práh i po rotaci. Flush streamu sám nezaručuje odolnost vůči výpadku napájení.

Logger přijímá již bezpečný text a **není automatický filtr tajemství**. Volající musí dodržet zákaz citlivého logování včetně klíčů, HMAC/GCM tagů, ciphertextu, obsahu paketů, timestampů requestů, přesného časového offsetu, celých těl a interních cest. Výjimky pro konfigurační odpovědi a pole oken tento zákaz pro log nerozšiřují.

## Společný HTTP transport

Implementované kapacity IPC spojení a front, velikost zprávy a I/O deadline stanoví [Implementační meze lokálního řízení](#implementační-meze-lokálního-řízení). Kapacitu a retenci receipts i celkový rozpočet Next stanoví [Životnost a limity Wizard IPC](#životnost-a-limity-wizard-ipc). [Konfigurační soubor](#konfigurační-soubor) stanoví `responseTimeoutSeconds` v rozsahu 1 až 2147483 sekund a vztah `maxNdjsonLineBytes <= maxResponseBodyBytes`. Pevné limity jsou 512 KiB konfigurace, 4 MiB zakódované IPC, nejvýše osm relací a heartbeat/lease 15/60 s. Tyto implementované meze nejsou výsledkem měření paměti, tolerance lease timeru ani odezvy při zátěži. Takové ověření musí uvést konkrétní scénář, prostředí a naměřené výsledky, neprovedené scénáře zůstávají NOT RUN. Vizuální a runtime akceptaci tray stanoví [UX14](tray_UX.md#ux14-ověření-a-velikost). Není slibována dostupnost při neomezeném zahlcení.

Transport a Windows implementace jsou společnou součástí VPN, get-info a Wizard probe. Windows adaptér `WinHttpTransport` používá asynchronní WinHTTP s explicitním vlastníkem requestu, bufferů a callback kontextu. Rušení synchronního volání zavřením handle z jiného vlákna není přípustné. Návrat `WinHttpCloseHandle` sám neznamená, že skončily callbacky. Kontext držet do závěrečného `WINHTTP_CALLBACK_STATUS_HANDLE_CLOSING` a dokončení všech jeho uživatelů. Callbacky nesmějí čekáním na sebe navzájem vytvořit deadlock. Podklad: [Microsoft: WinHttpCloseHandle](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/nf-winhttp-winhttpclosehandle).

Tentýž mechanismus musí pokrýt Connect během probe, globální Disconnect s aktivním provozním requestem, stop služby při restartu/aktualizaci/odinstalaci i Cancel, Reset, Escape a X Wizardu. Souběh dokončení, timeoutu a více rušicích událostí vybere právě jeden konečný výsledek a právě jedno zavření. Náhrada requestu, rekonfigurace transportu a uvolnění jeho objektů počkají na potvrzený terminální stav. Asynchronní WinHTTP transport čeká na `WINHTTP_CALLBACK_STATUS_HANDLE_CLOSING` pomocí `INFINITE`. Vlastnictví kontextu tím zůstává bezpečné, univerzální horní mez tohoto čekání však není doložená. Latenci rušení lze dokládat pouze pro konkrétní měřený scénář. Zabránit použití zavřeného handle, dvojímu dokončení a dvojímu účtování přečtených bajtů.

Každý request dostane při zahájení jediný absolutní deadline z monotónních hodin a `responseTimeoutSeconds`, výchozí hodnota je 30 s. Jeden rozpočet zahrnuje DNS, spojení, TLS handshake, odeslání requestu, příjem hlaviček i celé tělo. Dílčí bloky ani přechod do další transportní fáze jej neposouvají. Dílčí WinHTTP timeouty jsou doplňkové, samy celkový deadline nezajišťují. Podklad: [Microsoft: WINHTTP_OPTION_RECEIVE_TIMEOUT](https://learn.microsoft.com/en-us/windows/win32/winhttp/option-flags#winhttp_option_receive_timeout).

Po vypršení deadline ihned zahájit bezpečné rušení, počkat na potvrzené ukončení a vrátit timeout, nikoli pozdní úspěch. Deadline zahajuje rušení, nevymezuje horní mez následného čekání na closing callback. Zkontrolovat převody sekund, násobení i součet s monotónním časem a všechny návratové hodnoty nastavení timeoutů. Velké podporované hodnoty obsloužit bezpečným dělením platformních čekání, nebo nereprezentovatelnou hodnotu explicitně odmítnout před HTTP. Nikdy ji nepřetočit na záporný či nekonečný timeout ani tiše změnit význam konfigurace. Konfigurační maximum 2147483 sekund zajišťuje bezpečný převod na milisekundy pro WinHTTP.

Po timeoutu a cancel musí být transport bezpečně znovu použitelný. VPN nadále účtuje přesně jednou i částečné tělo a blok přes limit, před dokončeným Disconnectem účetnictví uzavře. Diagnostika a probe do VPN čítačů nevstupují. Asynchronní transport zachovává tři sériové VPN role a jejich ownership. Existující [testy WinHTTP](client/tests/unit/test_winhttp_accounting.cpp) obsahují `WinHttpDeadline.HeadersTlsAndTrickleBodyShareOneAbsoluteBudget`, `WinHttpDeadline.BoundarySettingsNeverBecomeInfinite` a `WinHttpLifecycle.ConcurrentCancellationThenReuse` i účetnictví částečných a nadlimitních těl. [Platformní probe](client/tests/platform_plan3_probe.cpp) kontroluje closing callback a měří rušení. Jejich existence ani jednotlivý běh nepotvrzují univerzální mez OS callbacku nebo izolované pokrytí všech DNS/send fází.

## Správa uložené konfigurace

### Omezené čtení, UTF-8 a snímky

Zavést `ConfigAvailability = missing | unreadable | encoding_error | too_large | invalid | repairable | valid`. Nedostupná služba je samostatný UI stav, nesmí se vydávat za missing. `unreadable` znamená chybu přístupu nebo čtení, `encoding_error` načtené bajty s nepodporovaným či poškozeným kódováním a `too_large` překročený limit čtení. `invalid` a `repairable` se určují až po úspěšném omezeném načtení a ověření UTF-8.

`StoredConfigSnapshot` obsahuje dostupnost, bezpečný kód důvodu, neprůhledný `revisionToken`, interní identitu souboru a pro úplně načtený obsah SHA-256 přesných vstupních bajtů. Pro platný UTF-8 text v limitu uchová skutečný text pro editor i při nevalidním JSON, pro valid/repairable navíc DOM pro Wizard. Při odmítnutí čtení, velikosti či kódování neposkytne editorový text ani DOM, neúplný hash nesmí vydávat za revizi obsahu. Token slouží k identifikaci snímku a potvrzené publikace, nikoli k odmítání zastaralého Save/Finish. Nesmí se odvozovat pouze z mtime, velikosti nebo `ClientConfig::generation`.

Jednorázové čtení konfigurace má limit `maxConfigFileBytes = 512 KiB` (524288 bajtů), včetně případného BOM. Limit vynutit v souborovém backendu před alokací podle deklarované velikosti a průběžně při čtení. I při růstu souboru načíst nejvýše limit plus jeden detekční bajt, větší obsah odmítnout jako `config_too_large` bez jeho úplného načtení, hashování nebo parsování. Stejný limit použít pro výsledný dokument před Save/Finish/create-if-missing. Volba ponechává rezervu i pro nejhorší šestinásobný JSON escaping textu pod 4MiB limitem IPC, skutečnou zakódovanou obálku přesto kontrolovat samostatně. Pomalé čtení běží mimo kapacitu get-status, Disconnectu a stopu služby. Nevzniká periodický refresh, watcher ani cache vyžadující opakované procházení disku.

`config.json` musí být platný jednoznačně dekódovatelný UTF-8 text. Striktní dekodér odmítne neplatné pokračovací bajty, neúplné a overlong sekvence, surrogate kódové body a hodnoty mimo Unicode. UTF-16/UTF-32 včetně jejich BOM a jiné nepodporované kódování vrátí `config_encoding_error`. Žádné nahrazování znaků, odhadování kódování, Unicode normalizace ani base64 přenos vadných bajtů. Platné UTF-8 je jediná interpretace vstupu, původní kódování bajtově totožného textu se neodhaduje. Samotný U+0000 je platný UTF-8 znak, takže při výskytu přímo v textu způsobí invalid JSON, nikoli chybu kódování. Protože Win32 EDIT neumí vložený NUL zobrazit, tento vzácný chybný dokument se v editoru zobrazí jako výslovně označený JSON string literal celého textu. Převod je bezeztrátový a Save jej striktně dekóduje před plnou validací. Nezměněný text editor předá z původních bajtů modelu, včetně původních konců řádků.

Jedinou vstupní normalizací je odstranění jednoho volitelného UTF-8 BOM `EF BB BF` na offsetu 0 před parsováním a předáním textu editoru. BOM jinde ani opakovaný BOM se jako značka kódování nepřijímá a neodstraňuje. U+FEFF uvnitř JSON stringu je znak hodnoty, nikoli BOM, a zachová se. Nezměněné ostatní znaky, whitespace a konce řádků se přenesou přesně. Save/Finish a šablona zapisují UTF-8 bez BOM. Samotné otevření nebo Cancel původní bajty na disku nemění. Striktní převody UTF-8/UTF-16 v tray nesmějí ztrácet znaky ani neplatné sekvence opravovat.

Navržená interní rozhraní:

```cpp

StoredConfigSummary ConfigStore::summary() const;
Result<WizardDocument> analyzeWizardDocument(std::string_view json);
Result<std::string> buildWizardDocument(
    const WizardDocument& original,
    WizardMode mode,
    const WizardFields& fields,
    bool createDefaultContracts);
Result<CommitReceipt> ConfigStore::commit(
    std::string_view completeValidatedJson,
    const CommitId& commitId);

std::string makeDefaultEditorDocument();
```

`CommitReceipt` obsahuje `commitId`, novou revizi a stav confirmed. Souborový backend nesmí při neurčitém výsledku operačního systému tvrdit ani úspěch, ani bezpečné nezapsání bez ověření skutečného stavu.

### Opravitelný dokument

Opravitelný dokument je jinak platná konfigurace, které chybí pouze `virtualIp`, `accessKey` nebo obě pole. Nesprávný typ, neplatná hodnota či jakákoli další chyba znamená invalid a ve Wizardu vyžaduje Reset nebo opravu přes editor. Neoslabovat `parseAndValidateConfig`. Samostatná analýza musí prokázat, že všechny nalezené chyby jsou výhradně absence obou povolených polí. Nestačí zachytit první chybu validátoru a prohlásit zbytek za platný.

Sdílená validace struktury, známých členů, URL, secretu, TLS, kanonického CIDR `/24` až `/29`, runtime limitů a kontraktů platí i pro repair. V režimu analýzy lze vynechat kontrolu chybějící IP/klíče a vazbu kontraktů na dosud neznámou vlastní IP. Tato vazba se povinně ověří při doplnění IP a znovu při Finish. Chybějící identita nikdy nezmění nepodporovaný CIDR na repairable. Typované neúplné údaje nesmějí vznikat jako falešně validní `ClientConfig` s dummy klíčem.

`masterSetup` přijímá tři volitelné striktní JSON booleany: `useDefaultServerSecretInWizard`, `autoDetectIpAddressInWizard` a `useDefaultAccessKeyInWizard`. Úplná šablona editoru i nový/resetovaný koncept Wizardu používají true. Při absenci se secret odvodí přesnou shodou s `CHANGE_THIS_SERVER_SECRET`, automatická IP jako false při platné uložené IP a true při chybějící IP, výchozí klíč jako false při platném uloženém klíči a true při jeho absenci. Každý příznak se odvozuje samostatně. Explicitní false má přednost i v repair bez konkrétní hodnoty, pole pak zůstane prázdné a editovatelné. Jiný typ, duplicita nebo neznámý člen je chyba. Metadata mění pouze Wizard, běžný runtime používá výhradně uložené konkrétní hodnoty secretu, IP a klíče.

### Zachování hodnot a Reset Wizardu

V režimu edit/repair patchovat čtyři konkrétní hodnoty a tři příznaky `InWizard` v původním DOM a při efektivní true aditivně doplnit chybějící kontrakty. Dokument nerekonstruovat z `ClientConfig`. Hodnoty, typy a přítomnost ostatních členů zůstávají zachované, změna whitespace a formátování JSON je povolená.

Reset Wizardu vytvoří nový koncept s URL `http://MODIFY-THIS-URL/phpvpn.php`, secretem `CHANGE_THIS_SERVER_SECRET`, `trustAnyTlsCertificate=true`, `vpnCidr=10.99.99.0/24`, současnými runtime defaulty, třemi true příznaky InWizard a nově rozhodnutou sadou kontraktů. Runtime lze v JSON vynechat a využít sdílené defaulty. Původní obsah se po Resetu nepoužije pro slučování ani jako podmínka zápisu. Odlišný úplný default editoru je definován v části Edit Config: skutečný obsah, vytvoření a Reset.

Při unreadable se může po Resetu vyplňovat nový koncept, ale Finish nesmí obejít souborovou chybu přístupu. Pokud služba při publikaci stále nemůže bezpečně pracovat s aktuálním cílem a obnovou po chybě, zápis odmítne a navede na opravu přístupu. Nevyžaduje shodu s revizí při otevření. Reset neopravuje ACL ani nepřesměrovává cestu.

### Jednorázová kontrola po akci a reakce menu

Start tray, jeho pravidelný timer ani pouhé otevření menu nenačítají konfiguraci. Pětisekundový tray timer dál čte pouze paměťový `get-status`. Žádný pravidelný pětisekundový `get-config-state`, předběžná menu kontrola, přímé `exists` na ProgramData ani automatický diskový refresh po Save/Finish. Menu nezakazuje konfiguračně závislé položky podle starého nebo neznámého stavu souboru. Connect/Disconnect se přepíná podle paměťového stavu VPN.

Po zvolení konkrétní akce služba jednou načte aktuální soubor v mezích části Omezené čtení, UTF-8 a snímky a tento snímek použije pro kontrolu i provedení akce. Connect, Show Info, Statistics a Contracts vyžadují validní snímek, jinak zobrazí konkrétní chybu nebo návod až po kliknutí. Connect a get-info mají kontrolu přímo v obsluze příkazu, Edit Config a ruční Contracts v jediném `get-config-document` a Wizard v `wizard-open`. Pro zvolené Statistics lze použít jednorázový `get-config-state`, jehož výsledek přímo rozhodne o otevření okna, bez druhého čtení konfigurace. Samotné otevření menu neposílá žádný z těchto příkazů. Další samostatná akce později načte nový snímek, žádná uložená revize neblokuje Save/Finish.

Editor přijme syntakticky chybný JSON jen jako platný UTF-8 text. `get-config` a get-info nesmějí po zjištění neplatného disku vracet nebo používat starou uloženou cache. Aktivní spojení si svůj již přijatý snímek ponechá. Disconnect nečte konfiguraci vůbec a použije nezávislou řídicí cestu tray podle pravidel nezávislého Disconnectu.

Všechny konfiguračně závislé položky zůstávají kliknutelné. Tabulka popisuje výsledek obsluhy po kliknutí, nikoli předběžné zakazování položek podle souboru:

Save úplně validuje odeslaný dokument včetně UTF-8 a velikosti a bezpečnost publikace, nikoli obsahovou platnost nebo revizní shodu dosavadního souboru. Smí tak opravit nevalidní obsah i uložit starší koncept podle pravidla poslední úspěšné publikace.

### Atomický zápis: poslední úspěšné uložení vyhrává

Všechny zápisy služby, včetně startup vytvoření, set-config, Finish a potvrzeného vytvoření výchozího souboru z editoru, procházejí jediným ConfigStore a stejnou serializační branou. Mezi Save a Finish rozhoduje pořadí úspěšné publikace celých dokumentů. Pozdější Save starého editoru smí přepsat Finish a pozdější Finish otevřeného Wizardu smí přepsat Save, stejně tak dvě relace stejného typu. Stará revize sama nezpůsobí konflikt, nové otevření, potvrzení přepsání ani automatické slučování. Cizí uložení nezneplatňuje koncept a jeho důkazy jen kvůli změně uložené revize. Wizard sestaví celý dokument ze svého originálu a konceptu podle edit/repair/reset, nikoli z mezitím uloženého cizího dokumentu.

Postup Finish:

1. Ověřit živou relaci, shodu instance služby, connection epoch, síťové důkazy a přesných sedm fields. Sestavit výsledný dokument a spustit úplný validátor ještě před vytvořením temp souboru.
2. Vstoupit do serializační brány zápisu. Zjistit aktuální existenci a bezpečnou identitu cíle a adresáře pro publikaci a obnovu po chybě. Nevyžadovat obsah, existenci ani revizi shodnou s otevřením okna. Save/Finish mohou uložit i po ruční editaci či běžném delete/recreate cíle, pokud je aktuální publikační operace bezpečná.
3. Nový soubor i dočasné soubory smějí vzniknout jen v autoritativním chráněném adresáři při schválené ukládací operaci: Finish, validovaný set-config/Save nebo potvrzené create-if-missing editoru. Dočasný název obsahuje náhodné ID, vzniká přes CREATE_NEW, nikdy sdíleným `config.json.tmp` s truncation. Zakázat reparse přesměrování cíle a neočekávanou identitu adresáře. Nastavit kanonickou ACL s Full Control pouze pro SYSTEM/Administrators a Read & Execute pro Users dříve, než se zapíší konfigurační bajty.
4. Zapsat celé tělo, ověřit počet bajtů a provést `FlushFileBuffers` nad skutečným file handle. Samotné `ostream::flush` nestačí pro tento účel. Viz [Microsoft: FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).
5. Bez síťové práce ověřit aktuální publikační podmínky. Save/Finish nemají create-only podmínku odvozenou od otevření okna. Zvolit atomickou publikaci pro aktuální stav cíle a bezpečně vyřešit změnu jeho existence během publikace. Jen výslovné `createDefaultIfMissing` nesmí přepsat mezitím vzniklý soubor, v tom případě načte skutečný aktuální obsah nebo vrátí konkrétní chybu. Pro existující cíl použít platformní replace se zálohou v témže adresáři, s kontrolou ACL a skutečného výsledku. `REPLACEFILE_WRITE_THROUGH` nepoužívat jako záruku, protože není podporován. Viz [Microsoft: ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).
6. Úspěch publikace je commit point. Teprve potom publikovat novou uloženou generaci v paměti a receipt. Aktivní konfigurace se tím nemění. Po commitu se již nesmí vrátit běžné cancelled, jako by disk zůstal nezměněný.
7. Při chybě odstranit pouze vlastní temp soubor, nikdy cizí `config.json`. U částečných chyb replacement API ověřit polohu původního souboru a zálohy, případně bezpečně obnovit původní cíl. Neprovádět slepé mazání zálohy ani cizího nového souboru. Restart musí umět rozpoznat vlastní nedokončený commit z minimálního záznamu bez klíčů a nesmí automaticky dokončit dosud neprovedený Finish.

Atomická publikace a ochrana před přepsáním staršího obsahu jsou odlišné vlastnosti. Druhá není požadována, poslední uložení smí mezitím provedené obsahové změny nahradit. Zůstává povinná serializace podporovaných IPC zapisovatelů a bezpečnost souborových operací i při přímém zásahu administrátora během publikační sekce. Testy musí prokázat, že nedojde k truncation způsobené službou, chybnému ACL, smazání nesprávného cíle při rollbacku nebo falešnému tvrzení, že se nic nezapsalo. Nevyžadovat compare-and-swap proti původnímu obsahu ani oplock pouze pro zabránění schválenému přepsání. Kontrakt tvoří postup publikace v této části a [omezené čtení, UTF-8 a snímky](#omezené-čtení-utf-8-a-snímky). Existující [testy ConfigStore](client/tests/unit/test_config_store.cpp) pokrývají revize, úplná serializovaná uložení a create-if-missing, [testy ConfigFiles](client/tests/unit/test_config_files_win.cpp) pokrývají identity, reparse, write/flush/publication chyby, crash hranice a souběh vytvoření. Skutečné Windows souborové scénáře vyžadují odpovídající NTFS prostředí a token, bez provedení se evidují jako NOT RUN. Users mají záměrně právo čtení, včetně záloh, nikoli právo zápisu.

Zálohy mají stejná omezení přístupu jako konfigurace. Ponechat nejvýše poslední vlastní známou verzi, nevytvářet neomezenou historii secretů. Záloha slouží k bezpečné obnově po chybě, ne k reviznímu blokování Save/Finish. Výpadek napájení a selhání média mají vlastní recovery výsledek, nelze slibovat obnovu na fyzicky nefunkčním disku.

### Edit Config: skutečný obsah, vytvoření a Reset

Existující `get-config-document` používají Edit Config i ruční Communication contracts. Jediné načtení pevné cesty vrací dostupnost a skutečný dokument ze stejného snímku. Contracts otevře model pouze pro validní dokument podle části Communication contracts: nativní editor a ukládání. Edit Config smí otevřít skutečný UTF-8 text v mezích části Omezené čtení, UTF-8 a snímky i při chybějících povinných polích, jiné konfigurační chybě nebo syntakticky chybném JSON. Jediná normalizace je odstranění počátečního volitelného BOM. Nevalidní JSON nenahradí defaultem ani starou cache. Původní přímý `get-config` zůstane pro platný konfigurační JSON, nevalidní dokument zpřístupní jen nová textová obálka. Nečitelnost existujícího souboru je chyba přístupu. Neplatné UTF-8 či jiné kódování vyvolá konkrétní chybu kódování bez dokumentu a bez náhrady znaků, odhadu nebo base64 fallbacku. Nadlimitní soubor vyvolá chybu velikosti. Žádná z těchto chyb nespustí vytvoření náhrady.

Při skutečné neexistenci zobrazí Edit Config Ano/Ne se skutečně vyhodnocenou absolutní cestou. Ano pošle `create-default-config`, služba společnou šablonu úplně zvaliduje a atomicky vytvoří chybějící soubor podle části Atomický zápis: poslední úspěšné uložení vyhrává. Editor otevře skutečný výsledek operace. Pokud cíl mezitím vznikl, nesmí být přepsán šablonou. Ne soubor nevytvoří a neotevře nový dokument. Cancel editoru po potvrzeném vytvoření již vzniklý soubor nemaže.

Konfigurační adresář na Windows MUSÍ mít vlastníka SYSTEM nebo Administrators a chráněnou DACL. SYSTEM a Administrators MUSÍ mít efektivní Full Control. BUILTIN\Users mají zděděné Read & Execute na celý datový strom, na všechny současné i budoucí soubory a podadresáře. Běžný lokální uživatel může bez UAC otevřít složku, vypsat obsah, procházet ji a přečíst či zkopírovat libovolný soubor. Přímý zápis, nahrazení, tvorba, mazání, přejmenování, změna ACL nebo vlastníka jsou pro běžného uživatele zakázané. Změny konfigurace nadále procházejí Edit Config, Configuration Wizard nebo podporovaným veřejným IPC a služba vždy validuje a atomicky publikuje výsledek. Přímé uložení původního souboru z neprivilegovaného editoru zůstává zakázané.

Jde o vědomý kompromis lokální důvěrnosti: čitelný je celý `config.json` včetně klíčů, hardlinková záloha `config.previous` včetně historických a odstraněných klíčů, rozpracované `config.stage.*.tmp`, `config.publish-journal`, `ownership.json` a jeho dočasné soubory, logy i další současní a budoucí potomci. Veřejné IPC již zpřístupňuje aktuální konfigurační dokument, širší filesystem přístup navíc odhaluje historické i dosud nepotvrzené konfigurace a interní metadata. Uživatel tento rozsah výslovně přijímá. Tato politika Users read platí také pro historii při každém startu služby, nejde o dočasnou výjimku pouze pro aktuální konfiguraci. Read-only přístup neuděluje přímý zápis ani neobchází validaci, serializaci a bezpečnou atomickou publikaci službou. Hardlinková záloha a její sdílená ACL zůstávají zachované, stejně jako žurnál, identity a recovery.

Validace posuzuje bezpečnostní vlastnosti oprávnění, nikoli přesný počet ACE. Dodatečná allow ACE smí poskytovat nejvýše bezpečné Read & Execute, včetně bezpečné dědičnosti. Nesmí omezovat plný přístup SYSTEM/Administrators. Neprivilegovaná práva zápisu, vytváření, mazání a změn zabezpečení včetně dědičných a inherit-only ACE za běhu vyvolají fail-closed chybu. Při každém startu privilegovaná služba vytvoří chybějící adresář a zkontroluje a podle potřeby obnoví kanonickou ACL existujícího datového stromu, včetně odstranění explicitního uživatelského Full Control přidaného Explorerem, bez změny konfiguračních bajtů. Shodný kanonický descriptor se nepřepisuje. Nejde o jednorázovou migraci. Čtení a kopírování ACL nemění a nejsou chybou. Pouhé smazání `config.json` administrátorem při zachovaných oprávněních nebrání novému potvrzenému vytvoření se stejnou běžící službou, ani při zbývajícím potvrzeném publikačním žurnálu a záloze.

Startup normalizace odmítá reparse pointy a hardlinky s názvem mimo datový strom, aniž by následovala odkaz nebo opravovala ACL takového souboru. Běžný interní hardlink zůstává podporovaný. Předky a objekty drží připnuté proti přejmenování, kontroluje jejich identity a počet interních názvů před a po opravě. Uživatel vědomě přijímá úzkou souběžnou výjimku platnou při kterémkoli startu: Windows dovoluje přidat nový externí hardlink i k připnutému inode. Pokud tento nový název vznikne přesně během skutečné opravy ACL, sdílí opravenou ACL téhož již prověřeného souboru. Následně zjištěná změna počtu linků zastaví inicializaci. Nejde o možnost podstrčit jiný externí soubor za připnutý název ani o povolení neprivilegovaného zápisu.

Úspěšně načtený descriptor adresáře, který neodpovídá této politice, vyvolá `config_directory_security_invalid` při konstrukci backendu, obnově i publikaci. Selhání API při načítání descriptoru zůstává `config_unreadable`, není důkazem změny oprávnění. Stav missing znamená pouze nepřítomnost souboru. Oprávnění se při zápisu znovu kontrolují i po úspěšném čtení, protože se mohou změnit během potvrzovacího dialogu.

Pro `config_directory_security_invalid` tray zobrazí autoritativní cestu ze služby a anglický návod požádat administrátora o restart služby PHPVPN. Start služby obnovuje očekávaná oprávnění adresáře. Restart přeruší aktivní VPN a při chybějícím cíli se pokusí vytvořit default. Po úspěšném startu zkontrolovat skutečný soubor přes Edit Config, další Yes nemusí být potřebné. Pokud se objeví další chyba obnovy nebo publikace, řeší se samostatně. Žurnál ani záloha se preventivně nemažou. Tray neprovádí restart ani automatickou změnu ACL, Reset ACL neopravuje. Pro tuto chybu nenabízí Wizard ani kopírování konfigurace jako nápravu. Souborové chyby mimo síťové kroky Wizardu neobsahují radu Next. Ostatní chyby zápisu nabízejí kontrolu chyby a aktuálního souboru a nové explicitní vyvolání akce po nápravě, bez automatického retry nebo tvrzení, že se určitě nic nezapsalo.

Tlačítko Reset v editoru vyžádá Ano/Ne k obnovení výchozí konfigurace. Ano nahradí pouze rozpracovaný text a označí jej jako změněný, Ne zachová dosavadní text. Disk se změní až po úspěšném Save se stejnou úplnou validací jako Connect. Cancel, Escape a X při změněném konceptu nejprve vyžádají potvrzení zahození. Během Save editor nezavřou. Tato pravidla editoru nenahrazují Reset Wizardu.

Vytvoření i Reset editoru používají jedinou továrnu `makeDefaultEditorDocument` ve společném klientském kódu. Služba poskytne tutéž šablonu přes `get-default-config`, tray nedrží vlastní kopii JSON. Wizard sdílí konstanty a algoritmus odvození klíčů, ale zachová svůj placeholder URL a volitelné aditivní doplnění kandidátní sady 13/14 kontraktů. Úplná šablona editoru je:

```json
{
  "masterSetup": {
    "serverUrl": "http://127.0.0.1/phpvpn.php",
    "trustAnyTlsCertificate": true,
    "serverSecret": "CHANGE_THIS_SERVER_SECRET",
    "useDefaultServerSecretInWizard": true,
    "autoDetectIpAddressInWizard": true,
    "useDefaultAccessKeyInWizard": true,
    "vpnCidr": "10.99.99.0/24",
    "virtualIp": "10.99.99.2",
    "accessKey": "0202020202020202020202020202020202020202020202020202020202020202"
  },
  "communicationContracts": {
    "10.99.99.3": {
      "payloadKey": "918c488528c2bc41a90f000b0a63bab0ba418790058ea7b448a3760aec16349d"
    }
  }
}
```

Sekce runtime je vynechána a používá sdílené defaulty včetně 30s timeoutu. Šablona musí projít syntaktickou i úplnou konfigurační validací bez výjimek. Loopback URL označuje relay na stejném počítači, nikoli ověřenou dostupnost serveru. Úspěšné vytvoření ani Save nenahrazují síťové ověření při Connect. Předvídatelné hodnoty a jeden kontrakt jsou závaznou součástí šablony.

## Configuration Wizard

Průvodce má čtyři pojmenované konfigurační kroky a podmíněný nultý krok globálního odpojení. Server URL má viditelný, ale zakázaný Back, také po dokončeném odpojení. Odpojovací gate Back nemá a nelze se na ni vracet. Služba vlastní načtení, uložení a všechny síťové kontroly. Před Finish Wizard nesmí zapisovat konfiguraci, zálohu ani temp JSON. Cancel a Reset původní soubor bajtově zachovají. Úspěšný potvrzený Finish pravdivě oznámí uložení, uzavře Wizard relaci a zavře průvodce. Communication contracts automaticky neotevře a VPN nepřipojí. Pozdější ruční otevření Communication contracts z tray menu je nová samostatná akce nad aktuálně uloženou konfigurací, nikoli pokračování Wizardu nebo handoff konkrétní publikace. Nezavádí se rezervace IP ani nové wire endpointy.

### Stavy průvodce

`WizardMode = create | edit | repair | reset`. Kroky jsou `disconnectGate`, `serverUrl`, `serverSecret`, `identity`, `contracts`. Vedle kroku model vede `loading`, `editing`, `checking`, `waitingDisconnect`, `interruptedByConnect`, `sessionExpired`, `committing`, `commitUnknown`, `completed` nebo `closed`. Zastaralá uložená revize nemá vlastní chybový stav.

Každý síťový krok má výsledek `pending | success | failed`. Výsledky jsou svázané s přesnými vstupy, ne s tím, že uživatel již jednou stiskl Next. První URL krok má viditelný zakázaný Back. Sidebar má čtyři informativní kroky a nedovoluje přeskakování. Interní událost Next znamená jednu ruční akci Verify & continue, v odpojovací bráně Disconnect & continue nebo Continue, pokud je již potvrzeno disconnected/idle.

| Událost | Předpoklad a výsledek |
|---|---|
| otevření | načíst službu, konfiguraci, epochu a nový sessionId. Aktivní VPN vede na disconnectGate, jinak na serverUrl nebo chybu vyžadující Reset. Explicitní useDefaultAccessKeyInWizard má přednost. Pouze při absenci tohoto metadata se existující accessKey načte jako vlastní hodnota s vypnutým switchem a chybějící klíč v novém/resetovaném nebo repair konceptu začne ve výchozím režimu. Shoda klíče s algoritmickým defaultem tento fallback nezmění. |
| Next na disconnectGate | Text předem vysvětlí globální dopad. Disconnect & continue je jediný souhlas, bez druhého Yes/No. Odeslat jeden disconnect a čekat současně na skutečný disconnected a idle, ne pouze přijetí IPC. Pak jedním wizard-resume přejít na serverUrl. Je-li VPN již disconnected/idle, výslovné Continue provede pouze resume. Focus brány začíná na Cancel. |
| Next serverUrl | lokální validace a check-url. Jen úspěch přejde na serverSecret. |
| Next serverSecret | check-secret s novým health a info. Jen úplný úspěch přejde na identity a případně jednou doplní chybějící návrhy. |
| Next identity | lokální validace, kontrola kolize kontraktu, upozornění na spotřebování zpráv a check-access. Jen úspěch přejde na contracts. |
| Back | contracts → identity → serverSecret → serverUrl. Zachovat koncept. Samotný Back nedělá síť ani zápis. Další Next opět ověří svůj krok. |
| změna URL | zneplatnit všechny síťové výsledky, ověřený čas, info a návrhy závislé na starém serveru. Ručně zadané hodnoty nezahodit. |
| změna secretu/default checkboxu | zneplatnit secret a access výsledky, čas a info. |
| změna IP/Access Key/default checkboxu | zneplatnit access výsledek, znovu spočítat kolizi s vlastním kontraktem a náhled počtu kontraktů. Je-li **Use default access key** zaškrtnutý, každá uživatelská i systémová změna IP současně okamžitě přegeneruje Access Key. Zaškrtnutí z vlastního režimu okamžitě přepíše textbox defaultem. Odškrtnutí zachová právě zobrazenou hodnotu a zpřístupní pole, nikdy neobnovuje dřívější vlastní hodnotu z `config.json`. |
| Reset | bezpečně zrušit vlastní kontrolu, po ukončení práce vytvořit nový koncept a vyčistit výsledky. Žádné diskové operace ani revizní podmínka pozdějšího Finish. |
| Cancel / Escape / X | mimo commit zrušit vlastní operaci a relaci, zavřít okno, vymazat koncept. Neodesílat Connect ani dodatečný Disconnect. |
| Finish | úplná službová validace a atomický zápis podle pravidla poslední úspěšné publikace, bez dalšího data pollingu. Během krátkého commitu nelze předstírat úspěšný Cancel. |
| úspěšný Finish | receipt confirmed → oznámit úspěšné uložení → jeden wizard-close → zavřít Wizard. Neotevírat Communication contracts ani jiné navazující okno, neodesílat Connect a nečíst další konfiguraci. Ztráta odpovědi close nemůže zvrátit potvrzenou publikaci. |
| chyba Finish | zůstat na contracts, zachovat koncept a zobrazit konkrétní nápravu. Samotná zastaralá revize není chybou a nevyvolá potvrzení přepsání. |
| ztracená odpověď Finish | commitUnknown, výslovné Verify save odešle jeden wizard-get-commit pro původní commitId. Neopakovat Finish, neověřovat automaticky a netvrdit, že soubor nebyl změněn. Potvrzený receipt pokračuje stejnou jedinou sekvencí oznámení a close. |
| expirace pronájmu | sessionExpired, zastavit kontroly i Finish, oznámit zánik relace a nabídnout nové otevření. Neobnovovat starou relaci opožděným potvrzením, výsledek rozpracovaného commitu ověřit samostatně. |

Každý Next založí jeden aktuální pokus. Zelený výsledek a postup jsou dovoleny až po doručení a ověření úspěchu tohoto pokusu v tray. Chyba kdekoli v řetězci tray → služba → server → služba → tray pokus ukončí, zobrazí červenou hlášku na stejném kroku a zachová texty. Nedodání v konečném časovém limitu je timeout, ostatní chyby mají skutečnou příčinu. Nepoužívat dřívější úspěch, automaticky neopakovat start ani žádnou část kontroly, včetně health/info a retry po 401. Další pokus vznikne výhradně novým Next a může znovu spotřebovat zprávy, i když předchozí na serveru uspěl.

Po chybě nebo timeoutu tray označí pokus lokálně za uzavřený a pozdní úspěch ignoruje. Pokud práce ve službě ještě běží, vyžádá její zrušení, je-li operace známa. Při ztraceném start acknowledgement použije korelaci aktuálního pokusu a rušení podle části Konfigurační a Wizard příkazy, start znovu neodesílá. Další Next může začít až po potvrzeném ukončení předchozí práce, nebo obdrží busy. Průběžné čtení dosud běžící operace není nový pokus. Reset a Cancel jsou dostupné i při chybě načtení, kromě krátké nerozhodnuté commit sekce.

### Místní Wizard lifecycle rozhraní pro Exit a konec relace

WizardWindow poskytuje nemutující WizardLifecycleSnapshot: open, dirty, committing, commitUnknown, generaci okna, relace, konceptu, pokusu a operace, aktuální attemptSequence, connectionEpoch a původní absolutní commitDeadlineMs, pokud Finish již začal. Snapshot nečte IPC ani nativní text a neobsahuje klíče nebo dokument. Načtený koncept je clean. Přijatá editace, přepnutí volby, Reset nebo změna polí ověřeným návrhem IP označí draft dirty a posune jeho generaci. Undo nesmí obnovit staré oprávnění k zahození. Otevření nového okna dostane novou identitu i po zániku předchozí instance. Open, Reset a Resume invalidují místní generaci relace a staré výsledky, bez změny službových pravidel attemptSequence, epoch a důkazů.

Finish založí jednu absolutní monotónní deadline za 15000 ms. Snapshot ji zpřístupňuje i v commitUnknown. Polling, heartbeat, čtení snapshotu ani požadavek Exit ji neobnovují. Nový koordinátor musí během committing asynchronně sledovat původní termín a terminální výsledek. approvedDiscard přijme pouze přesný stále platný snapshot mimo committing a probíhající oznámení potvrzeného úspěchu. Po společném potvrzení zruší místní okno bez dalšího dialogu a bez IPC, včetně Finish, get-commit, čtení konfigurace, retry, Connect, Contracts a Disconnect. Odvolá doručování dosavadních čteček. Tato cesta využije vzdálený lease pro úklid a není rollback již přijaté publikace. Běžný interaktivní Cancel a potvrzený Finish nadále používají vlastní wizard-close.

endSession je terminální a idempotentní rozhraní pouze pro účastníka Wizard. WM_QUERYENDSESSION vrací TRUE bez mutace, WM_ENDSESSION(FALSE) zachová koncept a WM_ENDSESSION(TRUE) zavolá endSession. To zneplatní generace, odvolá doručování čteček, zastaví místní timer, vyprázdní nativní pole a undo, uvolní koncept a zavře okno bez dialogu, synchronního wizard-close, čekání na IPC, reader join nebo deadline. WizardReader i WizardStatusReader používají existující samostatný shared stav CommandReaderu. Worker drží vlastní request a endpoint, nemá this, WizardWindow ani TrayApplication callback. Odvolání drží pouze krátký mutex publikace výsledku a signalizuje cancel, dokončení I/O a uvolnění posledního sdíleného stavu patří workeru. Již zařazené zprávy nemají pointer nebo výsledkový payload a nemohou vyzvednout opuštěnou operaci. Pending Wizard pole a transportní buffery se best-effort přepíší, nativní text/undo a původní model se uvolní. Nejde o záruku přepsání všech interních kopií modelu, alokátoru, OS nebo uživatelského clipboardu.

Wizard gate má stále 400ms status read a nejvýše jeden nevyzvednutý požadavek. Wizard IPC zachovává 5000ms rozpočet a heartbeat 15 s / lease 60 s. TrayApplication používá wizardLifecycleSnapshot, approvedDiscardWizard a endWizardSession ve společné koordinaci popsané v části Společný Exit a systémový konec relace. Samostatné testy Wizard participant nejsou samy důkazem úplného aplikačního logoff, ten má vlastní izolovaný broadcast test.

### Cizí Connect a epochy

Služba zavede interní nezáporný 64bitový `connectionEpoch`, zvýšený při přijetí každého nového logického Connect. Idempotentní Connect v aktivním stavu epochu nezvyšuje. Epochu resetuje pouze nová instance služby, která má nové `serviceInstanceId`. Při vyčerpání číselného rozsahu fail-closed, nikoli přetečení.

Wizard zaznamená epochu při otevření a po potvrzeném odpojení. Každá kontrola a commit kontrolují shodu. Tím se zachytí i Connect a Disconnect dokončené mezi dvěma UI pollingy. Událost nesmí být odvozena pouze z aktuálního názvu stavu.

Text informace: `A VPN connection was started while setup was open. Your entries are kept, but the checks must be repeated.` Neuvádět vymyšleného uživatele ani proces, veřejné IPC identitu nesleduje.

Při přerušení zachovat vyplněné texty, ukončit vlastní probe, označit síťové výsledky pending a nabídnout odpojovací bránu. Pokud je v době obsluhy již opět disconnected, stále zobrazit informaci o proběhlém Connect a vyžadovat opakování kontrol od serverUrl, ale další zbytečný Disconnect není nutný. Po výslovném odpojení a převzetí nové epochy provést všechny kontroly znovu až jednotlivými ručními Next. Originální dokument konceptu se cizím uložením nepřepíná a jeho revize Finish neblokuje.

Guard commitu a přijetí Connect mají jednoznačné pořadí. Connect přijatý před commitem zneplatní uložení. Connect přijatý až po commitu načte nově uloženou konfiguraci. Žádné z těchto pořadí nesmí vyžadovat blokování Connect po celou dobu průvodce.

## Síťové kroky Wizardu a pravidla dat

### Server URL

Použít existující `parseServerUrl`: HTTP/HTTPS, bez userinfo, query a fragmentu. Zachovat podporu jiného názvu skriptu a cesty, protože stávající validátor i testy přijímají například `vpn.php` a `relay.php`. Nápověda doporučí úplnou URL phpvpn.php, nevytvoří nové povinné pravidlo přípony. Placeholder `MODIFY-THIS-URL` odmítnout v průvodci s konkrétní nápovědou před DNS.

TLS politika a limity pocházejí z zachovaného kontextu nebo nových defaultů. Nikdy nezměnit `trustAnyTlsCertificate=false` na true jen proto, aby kontrola prošla. Nepovolit redirect, proxy ani automatickou přenosovou autentizaci oproti dnešnímu transportu.

Probe odešle jeden nový `auth-none`. Rozdělit ResponseParser na `parseHealthSyntax` a `verifyHealth`, používané společně i běžným NetworkWorker. První krok ověří HTTP status, tvar odpovědi, status running, korelaci UUID, syntaxi času a kanoničnost/délky IV a tagu. Neověřuje GCM tag, nepřijímá serverový čas do TimeSync a neoznačuje server za kryptograficky ověřený.

### SERVER_SECRET

Checkbox secretu se řídí `useDefaultServerSecretInWizard`, pouze při absenci přesnou shodou s `CHANGE_THIS_SERVER_SECRET`. True zobrazí tento default v zakázaném poli, false přesnou uloženou hodnotu v editovatelném poli. Zapnutí přepíše koncept defaultem, vypnutí ponechá zobrazený text. Každé přepnutí zneplatní secret/access důkazy a Finish uloží hodnotu i příznak.

Zachovat přesné UTF-8 bajty bez trimu, změny velikosti písmen nebo Unicode normalizace. Win32 převod nesmí potichu ukončit secret na NUL. Pro existující řídicí znaky použít výslovně označené zobrazení jako JSON string literal a striktní dekódování v tomto režimu, pro běžný text obyčejné pole. Zobrazení escape sekvencí nesmí zaměnit doslovné znaky `\n` se skutečným koncem řádku. Nezměněná hodnota se bere z původních bajtů modelu.

Next provede nový health, ověří GCM, sestaví samostatný TimeSnapshot podle normativního RTT a bezpečnostní rezervy, potom odešle info, ověří obálku a dešifruje. `InfoResponse::clients` je seznam `{Ipv4Address address, int64 lastSeenMs}`. Vyžadovat clients array, validní položky, kanonické adresy, unikátní adresy a platné milisekundové UTC lastSeen. Neznámá pole plaintextu info nadále ignorovat v souladu s protokolem. Statistický čas v budoucnosti je platná hodnota a může být výsledkem markeru, nesmí se automaticky zaměnit za chybějícího klienta.

### IP a Access Key

IP musí být kanonická a `vpnCidr.isValidClientAddress`, tedy ne síť, první rezervovaná host adresa ani broadcast. Klíč musí být přesně 64 malých hex znaků, žádné automatické lowercasing nebo odstraňování whitespace.

Původní automatický návrh IP zůstává v rozsahu `10.99.99.2–.15`. Při opravitelném souboru jej omezit na platné klientské adresy zachovaného CIDR a vyloučit kolize s existujícími kontrakty. Pokud je množina prázdná, vyžádat ruční IP s vysvětlením zachovaného CIDR. Rozšíření pravidla generování kontraktů na jiné `10.A.B.0/24` samo nepřidává nový protokol pro automatickou alokaci IP.

Z ověřených clients vybrat nejnižší adresu kandidátní množiny, která chybí. Jsou-li všechny přítomné, zvolit nejstarší lastSeen, při shodě nižší IP. Poslední oktet se porovnává jako číslo. `clients` není autoritativní evidence volných adres ani rezervace. Různé klientské počítače smějí mít stejnou virtuální IP, phpvpn její jedinečnost nevynucuje a systém takovou kolizi neodmítá. UI musí pravdivě říct, že návrh není rezervací, duplicita je technicky přípustná a případná kolize je odpovědností, respektive chybou konfigurace provozovatele. Služba sama nepřidává `ACCESS_KEYS` na vzdálený server. Samostatně platí: lokální `virtualIp` nesmí současně zůstat klíčem vlastního `communicationContract`, protože by kontrakt ukazoval na tento počítač samotný.

Pod IP polem je **Automatically detect IP address** podle `autoDetectIpAddressInWizard`. Při true je IP zakázaná a čeká na ověřený návrh z poslední úspěšné kontroly secretu. Návrh nahradí i neprázdnou placeholder IP, při false zůstane ruční IP zachovaná. Bez návrhu Next identity nepokračuje, UI vysvětlí možnost vypnout automatiku a zadat IP nebo se vrátit ke kontrole secretu. Zapnutí použije pouze stále platný návrh, samo nespouští HTTP. Změna URL/secretu, Reset, Connect, expirace či resume návrh a příslušné důkazy zneplatní. Back/Next zachová volby, resume zachová rozpracované hodnoty a všechny volby, ale vyžádá nové kontroly.

Pod polem Access Key je **Use default access key** inicializované z `useDefaultAccessKeyInWizard` s výše uvedeným fallbackem pouze při absenci. Při true je pole zakázané a obsahuje `hex2(lastOctet)` opakované 32krát, například 32×`11` pro `.17`. Při false zůstává uložená hodnota editovatelná i při shodě s defaultem. Každá skutečná změna IP při true klíč přepočítá, neplatná IP včetně adresy mimo CIDR jej vyprázdní.

Uložené příznaky mají vždy přednost před odvozením. Shoda uloženého klíče s algoritmickým defaultem sama neaktivuje výchozí režim. Back/Next zachová aktuální volbu i text.

Dokud je checkbox zaškrtnutý, každá změna IP bez ohledu na zdroj změny okamžitě přegeneruje pole z nového posledního oktetu. Platí to pro psaní uživatele, návrh IP ze serverového `clients`, návrat Back/Next, Reset i jinou systémovou aktualizaci modelu. Neplatná nebo neúplná IP nesmí vytvořit zdánlivě platný klíč ani zachovat klíč od předchozí IP jako aktuální default. UI v takovém mezistavu zobrazí pole zakázané a validaci dokončí až po platné IP.

Po odškrtnutí checkboxu se pole zpřístupní a uživatel smí upravit právě zobrazenou hodnotu, která stále musí projít přesnou validací 64 malých hexadecimálních znaků. Zaškrtnutí bez dalšího potvrzení okamžitě zahodí jakýkoli ručně zadaný nebo původně načtený obsah a nahradí jej výchozím klíčem z právě platné IP. Následné odškrtnutí ponechá poslední vygenerovanou hodnotu jako editovatelný počáteční text a původní vlastní klíč z `config.json` neobnoví. Finish uloží konkrétní `accessKey` i `useDefaultAccessKeyInWizard`, služba ověří jejich soulad a přesné fields při check-access i Finish.

Před provedením kontroly je trvale viditelné upozornění: `Each Verify & continue check may permanently remove waiting messages for this IP, even if no result arrives. Messages are discarded, not delivered to the VPN. Checks are never retried automatically.` Tlačítko Verify & continue je výslovný souhlas s tímto jedním pokusem, bez dalšího povinného modálního potvrzení.

Každý pokus check-access získá čerstvý ověřený health a info ve vlastním kontextu, aby dlouhé vyplňování a změna systémového času nepoužily starý odhad či serverové limity. Potom provede nejvýše jeden prázdný data request. Všechny health používají auth-none. Žádný automatický retry žádného kroku sekvence, ani po 401. Další pokus je nové stisknutí Next a znovu začíná čerstvým health. Obnova ověřeného času po 401 ve Wizardu proběhne až v tomto novém výslovném pokusu. Recovery běžné VPN se tím nemění.

Prázdný request má pouze auth-full a LF. Vyžadovat HTTP úspěch, úplnou strukturu NDJSON, limity těla/řádku/počtu, správný requestId v data-result i data-mac, kanoničnost všech záznamů a správný HMAC. Pro prázdný odeslaný seznam navíc vyžadovat prázdné accepted/deferred ID seznamy a nulové acceptedRecords/acceptedBytes. Ověřovat shodu cílové IP a přípustnost směrovacích polí vrácených dat, nevydávat MAC za důkaz platného payload plaintextu.

Po tomto ověření všechny datové záznamy zahodit. `wizard-check-access` v ProbeClient používá výhradně obecnou jednorázovou diagnostickou výjimku z `protocol.md` 9.5. Nekontrolovat payload GCM ani nedešifrovat. Žádný přijatý payload neuložit, nedoručit síťové vrstvě, nezařadit do provozní fronty, nepředat jiné části klienta ani jinak nepoužít. Nevolat `ingestRecord`, nealokovat per-peer fronty, neodstranit položku z provozní odchozí fronty a nezměnit tunel, aktivní stav, čas, kontrolní body ani provozní čítače, včetně drop/ciphertext. Kontrola ověřuje Access Key a autentizovanou strukturu serverové odpovědi, neprokazuje autenticitu, integritu ani čitelnost plaintextu jednotlivých payloadů. Normální bootstrap, recovery i provozní data polling nadále po data-mac plně ověřují payload GCM a platná data zpracují podle běžných pravidel. MAC protokolu nehashuje celý ciphertext, UI proto nesmí tvrdit, že ověřilo end-to-end obsah zpráv.

Při 401 uvést, že autentizace byla odmítnuta a má se ověřit ACCESS_KEYS pro konkrétní virtuální IP v souboru na zadané serverové URL. Neoznačit timeout, 503 nebo chybný MAC automaticky za chybný Access Key. Webová URL neznamená, že je přes prohlížeč dostupný zdroj PHP. Nápověda má doporučit otevřít soubor ve správě hostingu nebo se obrátit na správce, nikoli vydávat URL za serverovou filesystem cestu.

### Kontrakty

Ve všech režimech create/reset/edit/repair se vždy zobrazí `Add missing default communication contracts`, při každém novém otevření zaškrtnuté i pro úplnou sadu. UI ukáže počet všech původních kontraktů, chybějících výchozích kontraktů a plánované doplnění. Při odškrtnutí je doplnění nula a původní obsah i přítomnost objektu zůstávají zachované. Mimo `10.A.B.0/24` je checkbox stále zaškrtnutý, ale zakázaný s vysvětlením a efektivní request je false. Služba podstrčené true pro jiný CIDR odmítne. Volba kontraktů se do JSON neukládá.

Sdílené `defaultContractCandidates()` a `missingDefaultContractPeers()` vybírají z `.2` až `.15` v podporovaném CIDR, vynechají vlastní IP a všechny původní peery. Kandidátů bez self je 13 nebo 14, počet nových položek je pouze chybějící rozdíl. Každý původní kontrakt a jeho přesný payload klíč zůstává i při změně vlastní IP a mimo výchozí rozsah. Doplnění úplné sady je obsahová no-op. Nový create/reset koncept původní kontrakty nepřebírá, při false má prázdný objekt. Nové payload klíče jsou SHA-256 přes ASCII `minNumericIp_maxNumericIp` s číselným pořadím, jedním podtržítkem a bez LF, výstup lowercase hex. Náhled i publikace vycházejí ze stejného původního session DOM, neslučují pozdější cizí Save. Poslední úspěšná úplná publikace vyhrává.

Vlastní IP nesmí kolidovat s existujícím kontraktem. Konflikt se ověří před check-access a znovu před publikací, automatické doplnění žádný původní kontrakt neodstraní.

Nezávisle vypočtené očekávané testovací vektory:

| Přesný vstup | SHA-256 |
|---|---|
| `10.99.99.2_10.99.99.3` | `918c488528c2bc41a90f000b0a63bab0ba418790058ea7b448a3760aec16349d` |
| `10.99.99.2_10.99.99.10` | `f41f0ed508411aef592228e9d73ae137a4d31933f038160c04ae1e8d70597ebe` |
| `10.20.30.2_10.20.30.20` | `3e0d09769e22926032c4dbf961e2d6bc7caa9c6f326af51362c827849358b265` |

Tyto klíče i výchozí Access Key jsou veřejně odvoditelné a určené pro výchozí konfiguraci pet projektu. Wizard to vysvětlí jednoduchou větou. Nesmí je označit za náhodné nebo bezpečné tajemství. Nezavádí se povinné bezpečnostní schvalování navíc.

## Rozšíření IPC v1

### Společná pravidla rozšíření IPC

Přijímání pipe spojení, čtení i odesílání odpovědi musí být asynchronní. Dispatch smí začít až po úplném přijetí a validaci zprávy. Čekání na neúplný request nebo neodebíranou odpověď nesmí obsadit kapacitu krátkého řízení. `get-status` a přijetí Disconnectu mají dostupnou kapacitu nezávislou na dlouhé diagnostice i pomalém čtení, dekódování, hashování či parsování konfigurace. Zámek paměťového stavu ani ConfigStore se nedrží během HTTP nebo kryptografie. Nejvýše jedna řídicí síťová operace, `get-info` nebo Wizard kontrola, smí běžet současně, další dostane `busy` bez neomezené fronty.

Počet spojení, velikost zpráv, fronty práce a I/O deadline určuje část [Implementační meze lokálního řízení](#implementační-meze-lokálního-řízení). Přebytečná spojení a práce se řízeně odmítnou. Samotné navýšení počtu synchronních workerů nestačí. Neomezený `FlushFileBuffers(pipe)` je zakázán a overlapped I/O kontext žije až do potvrzeného dokončení nebo zrušení. Stop služby má samostatnou cestu přes SCM nezávislou na pipe a bezpečně ukončí čekající IPC i HTTP. Pipe výslovně odmítá vzdálené klienty.

IPC používá `ipcVersion=1`, pevnou pipe `\\.\pipe\phpvpn-control-v1`, UTF-8 JSON, jeden request a response na spojení, UUIDv4 requestId a limit 4 MiB na kompletní zakódovanou zprávu. Všechny nové requesty mají uzavřenou sadu polí a přísné typy. Odmítnout duplicity, nadbytečné členy, neznámý příkaz, neplatné ID a operaci pro jinou relaci před jakýmkoli vedlejším efektem.

Nové příkazy nevyužívají přímé formáty get-config/get-info. Mají obálku `{ipcVersion, requestId, result}` nebo standardní `{ipcVersion, requestId, error}`. `result` je pro každý příkaz níže přesně definovaný objekt. Rozšířit buildery odděleně od původní acknowledgement obálky, která má `result:"ok"`.

Nesmí se změnit schema get-status kvůli cestě nebo secretům. `serviceInstanceId`, epochy a konfigurace patří do nových odpovědí. Existující parsery statusu musejí dále projít beze změny významu čítačů. Pořadí JSON členů není sémantické.

#### Implementační meze lokálního řízení

Windows IPC server má nejvýše **32 slotů včetně listenerů**. Každá z následujících tříd má samostatný sériový executor s vlastním vláknem:

| Třída práce | Implementační kapacita |
|---|---|
| `shortControl` | Nejvýše 16 čekajících úloh, právě vykonávaná úloha se do tohoto počtu nezapočítává. |
| `file` | Nejvýše 4 čekající úlohy, právě vykonávaná úloha se do tohoto počtu nezapočítává. |
| `diagnostic` | Nejvýše jedna úloha celkem, včetně právě vykonávané. |

`get-status` a `disconnect` používají `shortControl`, `connect`, `get-config` a `set-config` používají `file`. `get-info` používá `diagnostic` a stejnou kapacitu sdílí plánování síťových kontrol Wizardu. Klasifikace probíhá až nad úplnou zprávou a validace schématu předchází účinkům příkazu.

Čtení požadavku a zápis odpovědi mají každý vlastní absolutní monotónní I/O deadline **5000 ms**. Dílčí přenos jej neobnovuje. Čtení jej počítá od zahájení prvního čtení po připojení, zápis od zahájení odesílání odpovědi. Čekání na uzavření klienta po zápisu používá původní výstupní deadline. Nejde o celkový rozpočet vykonání příkazu. Event loop plánuje maintenance tick po **250 ms** a při události nebo bližším I/O deadline se probudí dříve. Callback údržby nesmí blokovat ani provádět I/O.

Limit jedné kompletní zakódované zprávy je **4 MiB (4194304 bajtů)**, včetně JSON obálky a escapingu, samostatně pro požadavek i odpověď. Je odlišný od limitu 512 KiB konfiguračního dokumentu. Pipe je pouze lokální, Windows server ji vytváří s `PIPE_REJECT_REMOTE_CLIENTS` a vzdálené klienty odmítá.

Tyto kapacity omezují počet slotů, čekající práci a velikost zpráv. Samy neurčují celkový RSS procesu ani nezaručují dostupnost při libovolném zahlcení. Dostupnost krátkého řízení při definované zátěži ověřují existující testy `ipc_availability` v [test_ipc_availability_win.cpp](client/tests/unit/test_ipc_availability_win.cpp). Jejich existence není výsledkem běhu ani náhradou samostatného měření paměti.

### Konfigurační a Wizard příkazy

Povinná společná trojice je `ipcVersion:1`, `requestId` (UUIDv4) a `command` (přesný název řádku tabulky). Označení „relace“ v tabulce znamená dvě povinná pole `serviceInstanceId` a `sessionId`, nikoli vnořený objekt. Všechny uvedené členy výsledku jsou povinné, pokud nejsou výslovně označené jako volitelné. `null` je hodnota členu, ne jeho vynechání. Nejsou povolené další členy.

Každý řádek uvádí další request pole nad povinnou trojicí. Relace je vždy identifikována dvojicí `serviceInstanceId` a `sessionId`, obě UUIDv4.

| Příkaz | Další request pole | Úspěšný result |
|---|---|---|
| `get-config-state` | žádná | `availability`, `reasonCode` nebo null, `configPath`, `revisionToken` nebo null, `serviceInstanceId`, `connectionEpoch`, `vpnState`, `vpnPhase` |
| `get-config-document` | žádná | `configPath`, `availability`, `reasonCode` nebo null, `document` jako string nebo null, `revisionToken` nebo null |
| `get-default-config` | žádná | `document` jako string se společnou validní šablonou editoru |
| `create-default-config` | žádná, odeslat jen po Ano | `created` jako bool, `configPath`, `availability`, `document` jako string, `revisionToken` |
| `wizard-open` | žádná | `sessionId`, `serviceInstanceId`, `revisionToken` nebo null, `availability`, `mode`, `fields` nebo null, `context` nebo null, `contractCount`, `existingDefaultContractPeers`, `connectionEpoch`, `vpnState`, `vpnPhase` |
| `wizard-reset` | relace | stejný stav relace jako open, mode reset, nové defaulty, bez revizní podmínky Finish |
| `wizard-keepalive` | relace | `alive:true`, `leaseDurationMs:60000` |
| `wizard-check-url` | relace, `clientAttemptId`, `attemptSequence`, `serverUrl` | `operationId`, `operationState:"pending"` |
| `wizard-check-secret` | relace, `clientAttemptId`, `attemptSequence`, `serverUrl`, `serverSecret` | `operationId`, `operationState:"pending"` |
| `wizard-check-access` | relace, `clientAttemptId`, `attemptSequence`, `fields` | `operationId`, `operationState:"pending"` |
| `wizard-get-operation` | relace, `operationId` | aktuální typovaný OperationResult |
| `wizard-cancel-operation` | relace, `operationId` | `operationId`, stav cancelling/cancelled nebo již terminální stav |
| `wizard-cancel-attempt` | relace, `clientAttemptId`, `attemptSequence` | `attemptSequence`, `attemptState` z cancelling/cancelled/closed |
| `wizard-resume` | relace, `connectionEpoch` | aktuální relace po potvrzeném odpojení, všechny důkazy pending |
| `wizard-finish` | relace, `commitId`, `fields`, `createDefaultContracts` | `operationId`, `operationState:"pending"`, dokončení se čte stejným get-operation |
| `wizard-get-commit` | relace, `commitId` | `commitState` z pending/confirmed/failed/unknown, `receipt` nebo null, `error` nebo null |
| `wizard-close` | relace | `closed:true`, bez dopadu na VPN |

Při otevření create/reset konceptu nebo repair dokumentu jsou dosud chybějící IP či klíč v `fields` reprezentované prázdným stringem, nikoli falešně validní běhovou konfigurací. Odmítnutý původní dokument má fields/context null a neposkytne text přes tato pole. Výběr mode reset při odmítnutí obsahu sám Reset neprovádí, síť a Finish jsou zakázané do výslovného `wizard-reset`.

`fields` obsahuje právě čtyři stringy `serverUrl`, `serverSecret`, `virtualIp`, `accessKey` a tři povinné booleany `useDefaultServerSecretInWizard`, `autoDetectIpAddressInWizard`, `useDefaultAccessKeyInWizard`. `context` obsahuje právě `vpnCidr` jako string, `trustAnyTlsCertificate` jako bool a osm kladných celočíselných členů `maxOutboundQueueBytes`, `maxInboundQueueBytes`, `minPerPeerQueueBytes`, `maxResponseBodyBytes`, `maxNdjsonLineBytes`, `maxDataRecordsPerResponse`, `responseTimeoutSeconds` a `timeSyncIntervalSeconds`. Služba je odvodí z vlastního originálu nebo resetovaného konceptu, nesmí věřit klientem podstrčenému TLS nebo CIDR. `contractCount` je nezáporné celé číslo. `availability` je právě jedna hodnota ConfigAvailability, `mode` jedna hodnota WizardMode, `vpnState` a `vpnPhase` používají původní výčty get-status. `connectionEpoch` je nezáporné 64bitové celé číslo. `createDefaultContracts` je bool. `reasonCode` je bezpečný string nebo null, `configPath` je absolutní string pevného úložiště. `revisionToken` je neprůhledný náhodný identifikátor revize v rámci instance služby, nikoli zveřejněný hash secretu ani očekávaná revize commitu.

`existingDefaultContractPeers` je povinné pole nejvýše 14 kanonických, unikátních a číselně seřazených kandidátních IPv4 stringů z původního session DOM. Počet nesmí překročit `contractCount`, který zahrnuje všechny původní kontrakty. Mimo podporovaný CIDR je pole prázdné. Při fields/context null musí být pole prázdné a počet nula, stejně jako u create/reset konceptu bez kontraktů. Finish nepřijímá klientem tvrzené počty ani tento seznam. Sedmipoložkové fields tvoří access evidence i commit fingerprint. True default secret/key musí souhlasit s konkrétní hodnotou, true auto IP s návrhem uloženým službou při poslední platné secret kontrole. Změna kteréhokoli příznaku vyžaduje nový access důkaz. Stejný commitId s jinými fields je odmítnut, totožný receipt neopakuje zápis.

Služba a tray používají nové uzavřené schéma společně. Přesný historický čtyřstringový tvar je `wizard_unsupported`, ostatní vadná schémata `ipc_malformed`. Žádný downgrade, vynechání metadat ani přímý zápis tray. Staré konfigurace bez metadat jsou nadále přijímány, pouze pokud splňují aktuální úplnou validaci včetně `/24` až `/29`. Automatická migrace neprobíhá a původních sedm IPC příkazů se nemění.

`get-config-document` pro missing vrátí document/revisionToken null, pro UTF-8 text v mezích části Omezené čtení, UTF-8 a snímky skutečný text po odstranění případného počátečního BOM a dostupnost. Pro nečitelnost vrátí konkrétní chybu přístupu, pro neplatné či nepodporované kódování `config_encoding_error`, pro překročení velikosti `config_too_large`, vždy bez dokumentu. Textový string v obálce dovoluje syntakticky chybný JSON, pouze pokud je platným UTF-8 textem. IPC ani tray nesmějí bajty opravovat nebo převádět přes base64. `create-default-config` nepřijímá cestu ani obsah. Při souběžném vzniku souboru vrátí `created:false` a jeho skutečný UTF-8 text v limitu, případně konkrétní chybu přístupu, kódování nebo velikosti. Na validitu JSON tohoto cizího textu se neváže jeho otevření. Po úspěchu vytvoření vrací `created:true`. Save dále používá původní set-config s úplným dokumentem a jeho službovou validací včetně kódování a velikosti. Při nepodporovaných nových příkazech tray oznámí nutnost nové služby a nepoužije starou cache ani vytvoření přes fallback.

`get-config-state` má pouze jednorázové použití: obsluha zvolených Statistics a výslovné ověření nejasného Finish po restartu služby. Nevolá se při startu tray, na timeru, při otevření menu ani automaticky po Save/Finish. `wizard-open`, `get-config-document`, Connect a get-info provedou svou vlastní jedinou autoritativní kontrolu bez předřazeného get-config-state. Ruční Communication contracts používá jediný `get-config-document`. `availability` a bezpečný reasonCode v konfiguračních odpovědích rozlišují všechny stavy části Omezené čtení, UTF-8 a snímky, včetně chyby kódování a velikosti. `wizard-open` při odmítnutí obsahu vrátí fields/context null, contractCount 0 a mode reset, dovolí pouze nabídku Reset nebo nápravy podle části Jednorázová kontrola po akci a reakce menu.

`clientAttemptId` je UUIDv4 jednoho stisku Next a slouží ke korelaci, nikoli k automatickému obnovování startu. Každý ze tří wizard-check requestů navíc obsahuje `attemptSequence`, kladné 64bitové pořadové číslo pokusu v relaci. Tray ho zvýší při každém novém ručním Next, nikdy při pollingu výsledku. Služba drží pouze nejvyšší přijaté pořadí a aktuální pokus. Start se stejným nebo nižším pořadím se odmítne bez sítě, nikdy znovu neprovede vyřazený pokus. Vyšší pořadí během dosud běžící operace dostane busy a samo se později nespustí. I takto uzavřený validní start posune nejvyšší pořadí, aniž by změnil dosud běžící operaci. Reset a přerušení Connectem nemažou nejvyšší pořadí, nové sessionId začíná novou řadu. Přetečení se odmítne. Nevzniká historie UUID ani důvod nutit uživatele znovu otevřít Wizard po běžném počtu pokusů. Lokální `attemptSequence` omezuje opakované spuštění řídicí operace a není wire replay cache podle `protocol.md` 6.3.

Tray start posílá právě jednou. Při ztracené odpovědi jej neopakuje. `wizard-cancel-attempt` umožní uzavřít pokus i bez doručeného operationId: služba zapamatuje jeho pořadí, zruší odpovídající práci a odmítne opožděný start tohoto či nižšího pořadí. Staré rušení nesmí zasáhnout novější pokus a neshodné ID stejného aktuálního pořadí se odmítne. Pokud zrušení nelze doručit, HTTP deadline a pronájem dál omezují životnost práce. Nový Next respektuje busy a čekání na potvrzené ukončení. Úspěšně doručené průběžné get-operation pouze čte stav již známé operace a nespouští novou kontrolu.

Finish má samostatná nezměněná pravidla idempotence: stejné commitId se shodným úplným vstupem vrací stejný výsledek, změněný vstup se odmítne a zápis se neopakuje. Ztracené potvrzení se čte přes get-operation nebo wizard-get-commit, nikoli novým zápisem. Toto pravidlo se nesmí zaměnit za zrušenou obnovu síťových pokusů.

`OperationResult` obsahuje `operationId`, `kind` z pevného výčtu url/secret/access/finish, `operationState` z pending/running/cancelling/succeeded/failed/cancelled/interrupted, `connectionEpoch`, `clientAttemptId` a `attemptSequence` pro kontroly (pro finish null), `error` nebo null a `payload` nebo null. Payload je uzavřený podle kind. Pro úspěch `url` obsahuje právě `verified:true` (ověření dostupnosti a syntaxe, nikoli kryptografické identity). Pro `secret` obsahuje právě `verified:true` a `suggestedIp` jako kanonický IPv4 string nebo null. Pro `access` obsahuje právě `verified:true` a `discardedRecordCount` jako nezáporné celé číslo. Pro `finish` je payload přímo receipt s povinnými `commitId` (UUIDv4), `revisionToken` (string) a `commitState:"confirmed"`. Pro ostatní stavy je payload null. Error je null při úspěchu a neukončené bezchybné operaci, při selhání obsahuje strukturovanou chybu popsanou níže. `wizard-get-commit` vrátí receipt jen při confirmed, error jen při failed, jinak jsou oba null. `wizard-cancel-operation` vrací právě `operationId` a `operationState` z výše uvedených povolených stavů. `wizard-reset` a `wizard-resume` vracejí stejnou uzavřenou strukturu jako `wizard-open`. Text klíče odvozeného z IP může UI spočítat společnou čistou funkcí, služba jej vždy nezávisle ověří jako vstup check-access.

Každý kontrolní důkaz uložený službou váže přesné relevantní hodnoty, generaci konceptu, TLS/runtime kontext, serviceInstanceId, connectionEpoch a aktuální pokus. Finish vyžaduje shodu se všemi potřebnými důkazy. Po návratu Back a změně textu tedy nelze přes IPC uložit jiné hodnoty než ty, které byly ověřené. Změna uložené revize cizím Save/Finish sama důkaz nezneplatňuje. `createDefaultContracts` nemění platnost přístupového ověření, ale služba při Finish ověří jeho přípustnost pro daný režim/CIDR.

`wizard-resume` nesmí odpojit sám od sebe ani přijmout klientem tvrzený disconnected. Služba ověří aktuální stav, fázi a nepřítomnost čekajícího Connect. Samotné globální odpojení zůstává původním příkazem disconnect.

### Životnost a limity Wizard IPC

Nejvýše osm rozpracovaných Wizard relací na službu, každá jeden koncept a jedna aktuální kontrola. Každá otevřená relace má obnovovaný pronájem, výchozí potvrzení každých 15 s a expiraci po 60 s bez platného kontaktu. Služba porovnává uplynulý monotónní čas, ne počet zmeškaných pingů. Platný požadavek k dané živé relaci smí kontakt obnovit. Při pouhém vyplňování tray odešle krátký wizard-keepalive. Obecné get-status/get-config-state ani provoz jiné relace její pronájem neobnovují.

Heartbeat je pouze lokální IPC, nespouští HTTP, nic nepersistuje a není retry Next. Neprodlužuje HTTP deadline ani limit doručení výsledku do tray. Použít existující správu relací a službový časovač, nezavádět kvůli pronájmu nové vlákno nebo sledování PID. Změna intervalů vyžaduje současnou aktualizaci normativní dokumentace a testů.

Po expiraci nejprve relaci označit za neplatnou, poté bezpečně zrušit rozpracovanou kontrolu a po jejím terminálním stavu uvolnit koncept i prostředky. Objekt používaný callbackem nebo vláknem se neuvolní předčasně. Místo v limitu zůstane započítané do dokončení úklidu. Opožděný request relaci neoživí. Běžné interaktivní zavření vyžádá úklid ihned. Výslovně schválené místní approvedDiscard a systémové endSession neposílají IPC a vzdálený úklid ponechají lease. Také při pádu/zamrznutí tray, odhlášení nebo výpadku IPC nastane nejpozději po době pronájmu plus stanovené toleranci časovače a konečné době rušení. Po resume služba vyhodnotí uplynulou dobu před dalším obnovením pronájmu, použitý časový zdroj musí zohlednit dobu uspání. Expirace není důkazem smrti procesu a neodpojí globální VPN ani jiný Wizard.

Čekání tray na výsledek jednoho Next má samostatný konečný monotónní rozpočet od stisku, zahrnující IPC start, maximálně 1/2/3 HTTP requesty pro URL/secret/access, lokální zpracování a doručení výsledku. Celkový rozpočet je `1/2/3 × responseTimeoutSeconds × 1000 + 15000 ms` pro URL/secret/access v tomto pořadí. Při výchozích 30 sekundách na HTTP request jde o **45/75/105 s**. IPC start má vlastní limit **5000 ms**, který je zahrnutý v celkovém rozpočtu, nepřičítá se navíc. Výpočet rozpočtu je chráněn validací responseTimeoutSeconds a 64bitovou aritmetikou, přičtení k jedinému nezápornému monotónnímu počátku se kontroluje na přetečení. Polling ani keepalive konečný termín neobnovují. Timeout nebo jiná chyba kteréhokoli IPC volání kontroly ukončí aktuální Next v UI, zruší další čtení jeho výsledku a vyžádá bezpečné ukončení práce. Pozdní succeeded už krok nezmění. Nový Next je vždy ruční, může získat nová data a spotřebovat další zprávy.

Commit a jeho receipt mají bezpečnou životnost oddělenou od pronájmu editace. Expirace ani zavření nesmějí vrátit již publikovaný zápis nebo jej označit za neprovedený. Před publikační sekcí rezervovat místo pro záznam výsledku. Registr má nejvýše **128 receiptů**, včetně rezervovaných záznamů dosud probíhajících commitů. Při zaplnění nový commit odmítnout před zápisem, nikoli vyřadit potřebné potvrzení. Receipt se uchovává po celou živou relaci. Po jejím uzavření, včetně expirace, smí být terminální výsledek odstraněn nejdříve po **600000 ms** od uzavření. Pokud commit skončí až po uzavření relace, retence se počítá od jeho dokončení, tedy se nezkrátí. Pending commit ani záznam s neterminální operací se pouze kvůli uplynutí času neodstraní. wizard-get-commit může pouze přečíst existující záznam pod původní trojicí serviceInstanceId/sessionId/commitId, neobnoví pronájem ani nepovolí další zápis. Terminální potvrzení je neměnné, dokládá konkrétní publikaci, i když ji pozdější Save již přepsal. Vyřazené či expirované relace se přes opakovaný Finish nikdy nezaloží znovu.

Pád služby ruší relace a síťové důkazy. Při restartu během nejasného Finish klient v rámci řešení této rozpracované akce jednorázově načte nový config-state a zobrazí výslovné ověření výsledku, nezačne automaticky nový zápis. Nejde o kontrolu při běžném startu tray ani o periodický refresh. Trvalý commit recovery záznam identifikuje pouze publikaci a revizi, neobsahuje další kopii secretů. Nezjištěný výsledek zůstane unknown, nikdy se z něj neodvodí automatický retry. Tato pravidla zachovávají idempotenci Finish a řešení nejasného zápisu. Zákaz automatického retry se týká síťových kontrol.

Limit zprávy zahrnuje JSON escaping. Samostatný limit souboru a výsledného dokumentu je 512 KiB podle části Omezené čtení, UTF-8 a snímky a vynucuje se již při čtení před úplným hashováním a parsováním. Dokument, který se s obálkou nevejde do v1, odmítnout před další kontrolou a zápisem s informací o velikosti, nerozdělovat jej na nezdokumentované kusy. Doplnit testy obou horních hranic, escapingu a striktního UTF-8. Limity responseTimeoutSeconds se při převodu do WinHTTP nesmějí násobením přetočit na záporný nebo nekonečný timeout.

### Chyby a bezpečnost rozšíření IPC

Stabilní kódy zahrnují `config_unreadable`, `config_directory_security_invalid`, `config_encoding_error`, `config_too_large`, `wizard_session_expired`, `wizard_prerequisite_failed`, `wizard_attempt_closed`, `wizard_connection_interrupted`, `wizard_commit_unknown`, `wizard_contract_self_conflict` a `wizard_unsupported`, dále rozlišit busy, timeout a chybu souborové publikace. Nezavádět config_conflict pro zastaralou uloženou revizi. Původní chyby neměnit na raw systémové výpisy.

Wizard chyba má právě povinné členy `code`, hotové anglické `description`, `recoverable`, `field` nebo null, `httpStatus` nebo null, `suggestedAction` jako hotový bezpečný anglický string a pouze volitelné povolené `serverUrl`/`configPath` jako stringy. `code` a `description` jsou stringy, `recoverable` bool, `field` je null nebo jedna z hodnot serverUrl/serverSecret/virtualIp/accessKey/configuration, `httpStatus` je null nebo celé číslo 100–599. Nadbytečné pole se odmítne. URL a cesta pocházejí z konceptu a pevného úložiště, ne z neověřeného serverového těla. Síťovou příčinu mapovat na DNS, connect, TLS, timeout, odmítnutou autentizaci, neplatný formát a neplatné kryptografické ověření. Neočekávanou HTML odpověď nespouštět ani nezobrazovat jako HTML.

Zákaz citlivého logování platí i pro detail chyby. `Error::message()` přidává detail, proto se do běžného Error.detail nesmějí vložit requesty, klíče ani raw těla. Wizard diagnostika má vlastní povolená pole a nesmí prosakovat do get-status, progress, Statistics, tooltipu nebo loggeru. Konfigurační pole Wizardu a editoru samozřejmě smějí podle svého účelu zobrazit hodnoty, které uživatel zadává.

Zachovat vědomě veřejný přístup pro lokální aplikace, bez impersonace a bez kontroly PID. Pipe musí výslovně odmítat vzdálené klienty. Příkazy nepřijímají filesystem cestu, HTTP metodu, vlastní action, libovolné hlavičky ani spustitelný příkaz. UI nemá nové oprávnění zapisovat ProgramData. Nepřidávat síťový allowlist, který by zrušil existující podporu lokálních HTTP serverů.

## Sdílená Win32 infrastruktura

Normativní vzhled, anglické texty, přístupnost, focus, DPI a resize určuje [tray_UX.md](tray_UX.md), zejména UX00 až UX03 a testovací UX14. Sdílené `ui_style.h`, `layout.*`, `window_utils.*`, `ui_resources.*` a `ui_controls.*` oddělují přenosné DIP konstanty, texty a geometrii od Win32 oken, prostředků a message loop. Vrstva používá nativní EDIT/BUTTON a jen malé GDI kreslení, bez nové knihovny, bitmapového pozadí nebo vlastního GUI frameworku. Přístupná jména, role, checked/disabled stav, klávesnice, výběr, undo a clipboard řízený uživatelem zůstávají nativní. Změna layoutu nesmí obnovovat text ani vytvářet náhradní controls. Nativní rozhraní pro jiné platformy zůstává budoucí prací.

Všechna tray okna používají jediný sdílený helper výběru monitoru. Nové dítě použije monitor platného rodiče. Hlavní okno z tray menu použije monitor uloženého bodu, u kterého se menu skutečně zobrazilo. Bez rodiče i bodu menu následuje monitor platného foreground okna, potom monitor pod kurzorem a nakonec primární monitor. Okno se vystředí do pracovní plochy mimo taskbar. Souřadnice jsou podepsané, včetně monitorů vlevo či nad primárním. Rozměry se počítají pro DPI cílového monitoru, vnější rám se přičte ke klientské ploše uvedené v UX03 a celek se omezí na dostupnou pracovní plochu.

Reaktivace existující okno nepřesune na monitor nového kliknutí. Minimalizované okno obnoví. Je-li celé v použitelné pracovní ploše kteréhokoli dostupného monitoru, zachová přesnou polohu i velikost. Po odpojení monitoru nebo ztrátě použitelné polohy přesune okno na nejbližší dostupný monitor a změní geometrii jen o nezbytné minimum. Kontrola se provede při reaktivaci a změně DPI, rozlišení či pracovní plochy. Samotné připojení monitoru viditelné okno nepřesune. Rozměry v UX03 jsou přesné výchozí klientské plochy v DIP bez titulku a vnějšího rámu, nikoli fyzické rozměry PNG.

Každé okno vlastní malou RAII cache opakovaně používaných fontů, ikon, štětců a per. Vznikne při inicializaci pro cílové DPI a uvolní se při zániku okna. Fonty a ikony se obnoví při změně DPI nebo identity aktiv. Změna High Contrast či jeho systémové palety obnoví barevné prostředky i při stejném DPI. Běžný `WM_PAINT` nesmí načítat ikony ani vytvářet GDI prostředky. Invalidují se jen vizuálně změněné regiony. Úplná invalidace je dovolena při vytvoření, změně DPI, zásadním přepočtu layoutu nebo obnově po chybě dávkového přesunu. Tray uchová poslední skutečně publikovanou identitu ikony a přesný tooltip, `Shell_NotifyIcon(NIM_MODIFY)` volá jen při jejich změně, nikoli při každém shodném status snímku.

Tato verze tray je pouze anglická. Lokalizace, volba jazyka a reakce na jazyk Windows jsou mimo rozsah. Nevznikne překladový framework, resource katalog ani stabilní ABI lokalizačních klíčů. Anglické konstanty smí sdílet malý společný textový katalog. Layout nadále měří skutečný text a umožňuje zalamování, Statistics používají anglické seskupení tisíců nezávisle na systémovém locale. Budoucí lokalizace vyžaduje samostatnou specifikaci.

`apps/tray/layout.*` poskytuje čisté `selectMonitor`, `initialWindowRect`, `usableWindowRect`, `computeContentLayout` a `revealScrollPosition`. Win32 adaptér `window_utils.*` dodává skutečné monitory, cílové DPI, rodiče a menu kontext. `sizeAndCenter` připojí malý placement subclass s automatickým odpojením při WM_NCDESTROY. Opakované volání již inicializované okno necentruje. Reaktivaci nových adaptérů poskytuje `reactivateWindow`, minimalizované obnoví, maximalizované ponechá maximalizované. Změny rozlišení/pracovní plochy opravuje tentýž helper, DPI doporučený rect se přijme pouze s minimálním clampem. Bod menu má podepsané souřadnice skutečně předané TrackPopupMenu. Klávesnicové menu použije dostupnou polohu shell ikony. Bod se kopíruje k asynchronní akci, pozdější pohyb kurzoru nebo otevření dalšího menu jej nezmění.

`ui_style.h` obsahuje anglické prezentační konstanty, paletu, fontové role a přesné klientské DIP plochy UX03. `UiResources` vlastní fonty, ikony, štětce a pera a vytváří je mimo paint. Při neúspěchu přípravy zachová předchozí cache. Po změně DPI musí adaptér před dalším vykreslením přiřadit nové fonty controls a přepočítat layout. Systémové a stock handles jsou zapůjčené a nikdy se neuvolňují jako vlastněné. `UiResources::update` při každém volání porovná High Contrast a v aktivním High Contrast také aktuální systémové barvy. Při stejném DPI, HINSTANCE a požadavku na stavové ikony obnoví při změně jen paletu, štětce a pera, zachová handles fontů a ikon. Při shodě i palety cache nemění. Adaptéry Contracts, Password SHA, Editor, Connect a Statistics tuto aktualizaci volají také při `WM_SETTINGCHANGE` a `WM_SYSCOLORCHANGE`. Mimo High Contrast zůstává vlastní světlá paleta. `ui_controls.*` měří skutečný text, kreslí kartu z cache a přesouvá existující controls. Selhání Begin/Defer/EndDeferWindowPos zopakuje všechny individuální přesuny a plně invaliduje rodiče, běžná změna invaliduje jen určený region. Rodič používá WS_CLIPCHILDREN. Přesné uint64 formátování `englishInteger` nepoužívá double ani systémový locale.

`TrayApplication(TrayRuntime)` vlastní explicitně předaný endpoint, jméno mutexu, shell adaptér a volitelný přesný tooltip. Produkční hodnoty existují pouze v tenkém `wWinMain`. Všechny StatusReader, CommandReader a WizardReader, dále Editor Reset, Wizard cleanup a Progress dostávají tentýž explicitní endpoint bez produkční výchozí hodnoty nebo fallbacku. Prázdné runtime závislosti se odmítnou před IPC. Aplikace vlastní jednotlivá okna, ukončí čtečky a timer a odstraní ikonu před uvolněním resources, mutexu a shell adaptéru. `ShellIcon` porovnává poslední úspěšně publikovanou identitu ikony a celý tooltip, při shodě nevolá NIM_MODIFY, neúspěšná publikace zůstává opakovatelná. Opětovná konstrukce po zániku uvolní vlastní mutex, dvě odlišná jména dovolují izolované instance.

Specializovaná okna v `apps/tray` používají tento společný základ a explicitní runtime závislosti. Izolovaný runner je popsán v části [Izolovaný vývoj a náhled GUI](#izolovaný-vývoj-a-náhled-gui). Historickou evidenci zachovává [dokumentační audit uložený 8. září 2026](client/tests/implementation-plan3-fix3-wp07.md), jeho výsledky nejsou novým ověřením aktuálního stavu. Testovací backend a parser zůstávají výhradně v opt-in UI targetu mimo produkční EXE, testy používají syntetická data a soukromé endpointy. Úzké filtry TrayGeometry, TrayShell, TrayResources, TrayControls, TrayPlacement, TrayReaders a TrayApplicationSeam dokládají sdílené rozhraní, nikoli hotové všechny obrazovky. Plná vizuální a runtime brána je závazně v [UX14](tray_UX.md#ux14-ověření-a-velikost), včetně warmupu, tří běhů a pravdivého NOT RUN. Geometrický test nenahrazuje fyzický unplug, screen reader ani vizuální kontrolu.

## Win32 UI a texty pro začátečníka

UI zůstane anglické jako současné menu. Texty budou soustředěné a testovatelné, bez čísel řádků v PHP souboru. Jedno Wizard okno na tray relaci. Opakované otevření existující okno aktivuje, nezahodí koncept ani nevytvoří druhý sessionId. Jiná interaktivní relace může mít vlastní průvodce, každý ukládá svůj úplný koncept podle pravidla poslední úspěšné publikace.

Otevření menu nic nečte z disku a neposílá get-config-state. Konfiguračně závislé položky lze zvolit i při dosud neznámé nebo dříve chybné konfiguraci. Teprve obsluha konkrétní akce zobrazí čekání na její jedinou kontrolu a případně odpovídající chybu či návod z části Jednorázová kontrola po akci a reakce menu. Disconnect zůstává při aktivní VPN funkční i během čekajícího Show Info či jiné dlouhé diagnostiky. Tray ihned použije nezávislou řídicí cestu, viditelně sleduje odpojování až do skutečného dokončení a při chybě odeslání nebo potvrzení ukáže konkrétní příčinu. Obsazení diagnostické čtečky není důvod kliknutí ignorovat. Pozdní diagnostický výsledek nesmí přepsat stav odpojování nebo VPN znovu připojit.

Výchozí klientská plocha Wizardu je 1000 × 680 DIP při 96 DPI, sidebar má 230 DIP. Pod šířkou 760 DIP se čtyři kroky zobrazí vodorovně nad obsahem s názvem aktivního kroku. Reset je vlevo, Back, Cancel a primární akce vpravo v tomto pořadí. Naměřený nejdelší primární text určuje šířku tlačítka, při nedostatku místa přejde na další řádek patičky. Obsah scrolluje a akce jsou dostupné při 480 × 320 DIP. Sdílený helper `window_utils.*` podle UX03 umístí nové okno a opakované otevření zachová nebo minimálně opraví jeho geometrii. Resize a stavové překreslení zachovají stejné vstupní HWND, text, výběr a undo. Back zachová text i výběr příslušného pole.

Aktivní krok je tučný a označený, úspěšný má zelenou značku a textový význam, chyba červenou značku a popis. Barva není jediný nositel informace. Ovládání podporuje Tab, Shift+Tab, klávesové zkratky, Enter na povolené výchozí akci a Escape jako Cancel. Next při nevalidním poli nesmí spustit síť, fokus přejde na první chybu. Během kontroly zobrazit konkrétní činnost, zakázat změnu ověřovaných polí a opakované Next, ale umožnit Cancel/Reset s korektním zrušením operace.

Přesné stručné anglické texty určuje katalog UX08/UX09 v tray_UX.md a společná prezentační sada wizard_text.h. Nadpisy jsou Before setup, Server URL configuration, Server secret configuration, Virtual IP and access key a Communication contracts. Karty obsahují příslušná pole, switche pod poli a krátké nápovědy. Gate předem uvádí dopad na všechny uživatele a žádné automatické připojení. URL uvádí úplnou adresu, příklad a konkrétní chybu placeholderu. Secret zachovává přesnou hodnotu včetně JSON string literal režimu. Identity uvádí zachovaný CIDR, nezaručenou rezervaci, povolené duplicity, odpovědnost za kolize a celé trvale dostupné varování o spotřebě zpráv. Souhrn má Existing contracts, Missing defaults a To add on Finish, vždy pouze aditivní kandidáty 13/14. Pod ním je Finish saves the configuration and closes this wizard. It does not connect the VPN.

Příklad chybějícího souboru: `The configuration file does not exist at: {absolutePath}. Run Configuration Wizard to create it after you successfully finish all steps. If you already have a config.json from your administrator, you can copy it to this location.` Nečitelnost a neplatnost mají vlastní pravdivý úvod, nikdy text „does not exist“, pokud soubor existuje.

Edit Config má místo tohoto varování vlastní potvrzení s tlačítky Yes/No: `This application uses the configuration file at: {absolutePath}. The file does not exist. Create it now from the default template?` Nečitelnost otevře konkrétní chybu přístupu. Syntakticky chybný JSON se otevře k opravě pouze jako platný UTF-8 text v limitu. Chyba kódování zobrazí například `The configuration file at {absolutePath} is not valid UTF-8 text. Save it as UTF-8 in an external editor and try again.` Při překročení velikosti uvést limit 512 KiB. Neotevřít náhradní nebo částečně opravený dokument. Volitelný počáteční BOM se normalizuje podle části Omezené čtení, UTF-8 a snímky. Potvrzené vytvoření proběhne na disku již před otevřením editoru, Cancel soubor neodstraní.

The file will change only after you choose Save.` Ano načte stejnou šablonu služby jako create-default-config a označí obsah za změněný. Ne ani chyba získání šablony nesmějí ztratit rozpracovaný text. Zachovat výchozí plochu `1080 × 560` při 100% DPI, oba posuvníky a škálování. Při resize a změně DPI musejí zůstat viditelná a funkční všechna tři tlačítka, bez původního artefaktu vedle Cancel. Uložení nevyžaduje souhlas s přepsáním mezitím uložených změn.

Timeout: `The check timed out. Your entries have been kept. Choose Verify & continue to start a new check.` Expirace: `Contact with the service was lost and this setup session expired. Open the wizard again.` Nejasný Finish: `The save result is unknown. The file may already have changed. Verify the result before saving again.` Akce jsou Open again nebo Verify save podle stavu, bez automatického opakování.

Příklad kolize: `This IP address is already used by an existing communication contract. A contract cannot point to this computer itself. Choose another IP address, or cancel the wizard and use Edit Config to correct the conflicting contract before trying again.` Zobrazit konkrétní kolizní virtuální IP, žádný payloadKey. Hláška je vysvětlení, nikoli dodatečné schvalování automatického odstranění.

### Communication contracts: nativní editor a ukládání

Communication contracts se otevírá pouze explicitní volbou z tray menu. Jediné asynchronní get-config-document současně ověří dostupnost a dodá celý aktuální dokument, bez get-config-state nebo lokálního filesystemu. Pouze valid otevře model. Repairable nabídne Wizard nebo Edit Config, invalid pouze opravu přes Edit Config, missing existující cestu vytvoření přes Wizard nebo Edit Config bez automatického zápisu. Unreadable, encoding_error, too_large a bezpečnost adresáře mají vlastní bezpečnou chybu s pevnou autoritativní cestou. Neexistuje náhradní dokument ani obcházení ACL. Otevření menu nic nečte. Opětovná volba již otevřené instance pouze aktivuje stejné okno, zachová geometrii a koncept. Finish Wizardu Contracts neotevírá ani nepředává dokument.

Resizovatelný nemodální formulář používá plochu 1180 × 680 DIP, titul i nadpis Communication contracts, popis a Your virtual IP podle UX10. Má pevnou hlavičku Contract / Enabled / Key / Actions a patičku. Všech nejvýše 252 řádků má vlastní čtyři nativní ovladače Enabled, Key, Random, Password SHA. Posouvá se jejich společný obsah v ořezaném viewportu, žádný HWND se nerecykluje a žádný řádek není virtualizovaný. Nativní accessibility jména obsahují kanonický pár minIP_maxIP. Tab jde po řádcích a nakonec na OK, Shift+Tab opačně. Focus odkryje řádek i příslušný sloupec. Ctrl+End mimo textbox zaměří poslední řádek. Horizontal scroll posouvá též hlavičku. Resize a DPI zachovají nativní pole, text a výběr. Úplná validace zahrnuje i neviditelné řádky.

Configuration Wizard, Edit Config a Contracts mohou současně používat vlastní nezávislé koncepty. Random dočasně zakáže jen svůj rodičovský formulář a použije přesné potvrzení UX11 s výchozím No. Yes získá 32 bajtů CSPRNG, neúspěch ponechá klíč. Více nemodálních Password SHA oken smí mít stejný cíl. Jejich neměnný systémový titul Password SHA - Contract {minIP_maxIP} je dostupný nativnímu accessibility objektu i přepínači aplikací. Poslední potvrzené OK pro daný zachycený cíl a platnou generaci vyhrává, Enabled se nemění. Rodič zůstává dostupný. Heslo začíná prázdné, cue CHANGE-THIS-PASSWORD se nehashuje. Hash je lokální SHA-256 přes přesné UTF-8 bez normalizace. Nativní vstupní adaptéry kontrolují celou navrhovanou změnu před vložením. Pro heslo platí limit 255 Unicode skalárních hodnot, pro součet rozpracovaných Key samostatný limit 512 KiB. Nadlimitní změnu odmítnou celou a zachovají vstup, výběr i dosavadní platný výsledek. NUL, nepodporovaný řídicí vstup, chybný UTF-16 a crypto selhání nesmějí přenést starý hash jako aktuální.

ContractsSaveController rozlišuje loading, editing, invalid, saving, saveUnknown a closed. OK nejprve zmrazí úplný neměnný preserving DOM kandidát. Zachová typy, hodnoty a přítomnost všech nesouvisejících členů, neprovádí rekonstrukci z ClientConfig. Poté zavře neconfirmované Password SHA děti a zakáže pouze ukládaný formulář. ContractsEnvelopeSizer volá skutečný stávající builder a měří zakódovanou obálku, nikoli odhad délky JSON. Příprava validuje 524288 bajtů dokumentu a 4194304 bajtů IPC. Jediný asynchronní set-config používá ipcVersion:1, requestId UUIDv4, command:set-config a config string. Úspěch přijme jen přesnou tříčlennou korelovanou odpověď ipcVersion, requestId, result:ok a zavře daný editor. Operace nese místní generace okna, konceptu a Save a jedinou původní absolutní 30s deadline. Potvrzené odmítnutí před publikací nebo prokázané neodeslání obnoví editaci. Možné odeslání s chybnou, cizí, ztracenou či pozdní odpovědí přejde do saveUnknown. Žádný retry neběží automaticky.

V saveUnknown je text The save result is unknown. The file may already have changed. Check the current configuration before saving again. Jediná explicitní Check current configuration provede jeden get-config-document. Shoda celého validního DOM bez ohledu na pořadí objektových členů, se zachováním typů a absent/present, oznámí The current configuration matches your changes. a dovolí zavření. Není to historický receipt. Neshoda nebo missing zachová kandidáta a nabídne výslovně potvrzené Save draft again s novou operací a UUID. Jiná nečitelnost, encoding, velikost nebo ACL vyžaduje nejprve opravu, nepovoluje slepou publikaci. Běžné souběžné Save nemá CAS, merge ani dodatečné potvrzení revize. Poslední potvrzená publikace celého dokumentu vyhraje a může obnovit mezitím smazaný cíl. Aktivní VPN se nemění, zobrazuje se Changes take effect on the next connection.

### Společný Exit a systémový konec relace

TrayApplication koordinuje autoritativní lifecycle snapshoty Editoru, Wizardu a Contracts, nikdy obsah ani enabled stav nativních controls. Ruční Exit při ukládání asynchronně čeká na původní deadline každé operace nebo její dřívější terminální výsledek. Nezakládá nový termín ani zápis, nezakáže nezávislé editory či Disconnect a zahrne i nově zahájenou operaci. Po ukončení zápisů zobrazí jedno společné potvrzení pro všechny zbývající dirty nebo unknown koncepty, s výchozím No. Pro dirty používá Discard unsaved changes?, pro unknown The file may already have changed. Close without checking the save result?, pro souběh obě věty v jednom dialogu. No zruší celý Exit bez předchozího zahození. Po Yes znovu ověří celý schválený soubor generací, potom použije approvedDiscard bez druhých dialogů. Souhlas si ponechá při dočasném veto probíhajícího oznámení potvrzeného Finish, změna živého konceptu jej zneplatní. Již samostatně uzavřený účastník nový dialog nevyžaduje.

Produkční skrytý top-level host není HWND_MESSAGE a přijímá skutečný systémový session broadcast. WM_QUERYENDSESSION vrací TRUE bez mutace. WM_ENDSESSION(FALSE) koncepty zachová. WM_ENDSESSION(TRUE) terminálně odvolá doručování, zastaví timery, zavolá Editor, Wizard, Contracts, Progress a read-only Editor endSession před destrukcí a zavře místní okna. Nezobrazí dialog, nečeká na worker join, deadline ani IPC, nepublikuje, neopakuje požadavek a neodesílá Disconnect či rollback. Vzdálenou Wizard relaci v této cestě uklidí lease.

CommandReader a obecný StatusReader používají samostatný shared stav s hodnotovými capture endpointu a requestu, bez this nebo UI callbacku. Abandon odvolá notifikace pod krátkým mutexem, signalizuje cancel a vrátí se bez čekání. Worker vlastní prostředky do skutečného dokončení I/O. Běžný StatusReader nadále zachovává frontu explicitních požadavků a 400ms čtení, tray 5s a Progress 500ms polling se nemění. Progress před destrukcí opustí obě čtečky, jeho běžný stavový a zobrazovací model se nemění. Pozdní zprávy nenesou pointer a nemohou vyzvednout opuštěný stav. Vlastněné klíče, kandidát, DOM a dočasné adaptérové texty se best-effort přepíší, nativní EDIT obsah a undo se vyprázdní. Není garantováno přepsání všech interních kopií builderu, parseru, alokátoru, OS nebo uživatelského clipboardu. Služba, konfigurace na disku, globální VPN a ostatní relace jsou ukončením tray nedotčené.

Wizard může mít vlastní 500ms polling stavu dosud běžící operace a epochy pouze po dobu otevření. Když žádnou kontrolu neprovádí, jeho pronájem udržuje 15s keepalive, případně jiný platný požadavek dané relace. Původní pětisekundový tray timer pro paměťový get-status i 500ms timer Connecting progress window zůstávají nezávislé a nespouštějí čtení konfigurace. Epochu a stav otevřené relace služba kontroluje při každém jejím platném kontaktu. Změnu epochy ohlásí strukturovanou chybou `wizard_connection_interrupted`, i při keepalive, jehož běžná úspěšná odpověď zůstává `alive:true, leaseDurationMs:60000`. Probíhající get-operation vrací také aktuální epochu. Nevzniká nový příkaz ani diskové get-config-state pro polling epochy. Resume smí předat poslední epochu potvrzenou dané relaci nebo aktuální epochu služby, protože chyba keepalive aktuální epochu neobsahuje. Služba přijme Resume pouze při aktuálním disconnected/idle bez čekajícího Connectu, převezme aktuální epochu a zneplatní všechny předchozí důkazy. Libovolnou jinou epochu odmítne. Zavření Wizardu ukončí jeho polling i keepalive. Odpověď smí změnit UI jen při shodě windowGeneration, serviceInstanceId, sessionId, operationId, clientAttemptId a attemptSequence, a pokud pokus ještě neskončil a nevypršel jeho konečný termín. Staré potvrzení ani úspěch nesmějí ovlivnit nový pokus.


### Přenosné jádro Communication contracts

Datový kontrakt tvoří `ContractsDocument`, `ContractsModel` a `PasswordKeyModel`. Při vytvoření modelu se znovu ověří úplná konfigurace, repairable ani invalid dokument nevytvoří tabulku. Sdílený rozsah `/24` až `/29`, platnost vlastní adresy a počet nejvýše 252 peerů se kontrolují před alokací řádků. Výpočet používá první a poslední klientskou adresu s aritmetikou bez přetečení. Řádky jsou numericky seřazené podle remoteIp, self chybí, `/24` má 252 a `/29` čtyři peery. Zobrazený pár je kanonické numerické `minIP_maxIP`, JSON identita zůstává samotná remoteIp.

Přítomný validní kontrakt má Enabled true a zachová přesný payloadKey. Chybějící kontrakt má v konceptu prázdný Key a Enabled false. Otevření editoru klíč neodvozuje. Po zapnutí řádku musí uživatel doplnit platný klíč, jinak řádek blokuje uložení. Jde o celou sadu peerů, nikoli o aditivní Wizard defaults 13/14. Key je přesně `[0-9a-f]{64}`, bez trimování, lowercase převodu nebo truncování. Aktivní nevalidní hodnota blokuje kandidáta, neaktivní nevalidní hodnota má lokální chybu, ale nepublikuje se a neblokuje. Chyba je `Key must contain exactly 64 lowercase hexadecimal characters.`. Model poskytuje počet všech blokujících řádků a první remoteIp + sloupec Key, nezávisle na viewportu. Součet aktuálních UTF-8 textů Key má limit 524288 bajtů. Nadlimitní změna se odmítne celá a zachová původní hodnotu, dirty i focus. Nevalidních 65 znaků se ponechá k opravě.

Dirty vyjadřuje rozdíl výsledného publikovatelného stavu od původního. Řádek je dirty při změně Enabled nebo při odlišném klíči zapnutého řádku. Koncept je dirty, pokud je dirty alespoň jeden řádek. Shodný klíč po Random, dosazení defaultu nebo potvrzení Password SHA ani návrat k původnímu výsledku dirty nevynucují. Samotná editace klíče původně i nadále vypnutého řádku se nepublikuje a dirty nevytváří. Vypnutí původně zapnutého kontraktu je naopak změna. Generování nemění Enabled. Výsledkové dirty neruší saveUnknown ani ochranu generací při Save a společném Exit. Random No/Escape/X se do modelu předá jako nepotvrzená akce bez crypto volání. Potvrzený Random získá přesně 32 bajtů z `CryptoProvider::randomBytes`, chyba zachová klíč. Cíl akce `ContractTarget` nese neměnnou remoteIp, kanonický pár a identitu i generaci rodičovského modelu. Poskytuje přesné potvrzení `Replace the key for {contractId} with a new random key?` a titul `Password SHA - Contract {minIP_maxIP}` pro navazující pohled. Více cílů téhož řádku zůstává platných, poslední potvrzený klíč vyhrává. Focus jiné akce je nepřesměruje, cizí model ani vyřazená generace se neaplikují.

`PasswordKeyModel::update` synchronně hashuje přesné UTF-8 bajty zapůjčeného UTF-16 vstupu s explicitní délkou. Limit je 255 Unicode skalárních hodnot, nejvýše 510 UTF-16 jednotek nebo 1020 UTF-8 bajtů. Platný surrogate pair se počítá jednou, kombinující znak samostatně, nic se nenormalizuje, netrimuje ani nemění velikost písmen. Nadlimitní editace nevolá crypto a zachová předchozí výstup i počet, adaptér zachová vstup a výběr a zobrazí chybu. Nespárované surrogate a nepodporované jednorádkové řídicí znaky se odmítnou bez opravy nebo useknutí. Přesně jde o C0 U+0000 až U+001F, DEL/C1 U+007F až U+009F a oddělovače U+2028/U+2029. Neplatný UTF-16, řídicí znak nebo crypto chyba zneplatní výstup a zakáže jeho potvrzení. Prázdný skutečný vstup má standardní hash `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`, cue `CHANGE-THIS-PASSWORD` se nepředává. Heslo se neukládá do modelu ani neposílá službě. Pracovní UTF-8 buffer a digest se mažou po každém návratu přes `secureWipe`, výstup je vlastněný `SecureBuffer`.

Koncept vlastní jeden původní validní DOM a lehké řádky, bez DOM kopie na řádek. `prepareSave` vezme úplný snímek potvrzených řádků a vytvoří samostatný neměnný `ContractsCandidate`. Patch mění pouze communicationContracts, enabled vloží pod remoteIp jako objekt s payloadKey a unchecked odstraní. Ostatní hodnoty, typy a přítomnost členů včetně runtime, CIDR, TLS a Wizard metadat se zachovají. Původně absent communicationContracts zůstane absent bez přidání, původně present po odstranění všeho zůstane `{}`. Přísné schéma nepovoluje neznámé členy a výsledný dokument se nerekonstruuje z ClientConfig. Změna whitespace je dovolena.

Kandidát projde serializací a úplnou sdílenou validací v limitu 524288 bajtů. Povinný integrační adaptér `ContractsEnvelopeSizer` změří skutečnou zakódovanou obálku kandidáta existujícím builderem a uvolní svou dočasnou kopii. `validateContractsEnvelopeSize` odmítne více než 4194304 bajtů bez přetečení. Adaptér je synchronní, bez vedlejších efektů a nesmí během měření měnit model. Teprve úspěch zmrazí editace, zvýší save generation a vyřadí dřívější dětské cíle. Lokální chyba zachová koncept i generaci. Řadič po korelovaném definitivním odmítnutí nebo prokázaném neodeslání může volat `resumeEditing` se stejnou save generation. Unknown, skutečný přenos a deadline vlastní ContractsSaveController, uzavření dětí a potvrzení zavření jeho nativní ContractsWindow, model sám neukládá. `matchesDocument` ověří validní aktuální dokument a srovná celý DOM bez ohledu na pořadí objektových členů, se zachováním typů a absent/present rozdílů, nejde o historický receipt.

Modelové mutace mají jednoho vlastníka a volají se sériově. Řádkové texty a jejich výchozí srovnávací hodnoty jsou SecureBuffer, původní DOM i kandidát se best-effort mažou při zániku. Kandidát sdílený jako const žije do uvolnění posledního uživatele, takže zavření rodiče nepředběhne čtečku. Vstupy, kopie vytvořené stávajícím parserem, alokátorem, nativním textboxem a undo vyžadují vlastní omezení životnosti, nejde o záruku smazání všech kopií. Modely nic nelogují. Nativní a IPC adaptéry musí uklidit vlastní buffery. Lokální tvorba a patch mají omezený počet řádků i bajtů, synchronní UI použití musí později doložit výkonovou bránu [UX14](tray_UX.md#ux14-ověření-a-velikost), samotný unit test ji nepotvrzuje.

Stará ID, nižší či stejná attemptSequence, staré rušení i pozdní success neprovedou nový request ani nezmění nový pokus. Keepalive a polling neobnovují deadline.
10. Ověřit celý Access Key checkbox: explicitní useDefaultAccessKeyInWizard má přednost v obou hodnotách. Pouze při absenci metadata je nový/reset/repair bez klíče zaškrtnutý a existující klíč odškrtnutý i při shodě s defaultem. Zaškrtnutí text přepíše, odškrtnutí jej ponechá a neobnoví originál, každá změna IP jej při aktivní volbě přegeneruje, neplatná IP nenechá starý klíč jako platný. Vektory .2/.10/.15/.17 mají přesně 64 malých hex znaků.
11. Ověřit nejnižší chybějící IP a lastSeen tie-break, prázdnou kandidátní množinu, povolené duplicitní IP mezi počítači a odmítnutí self-kontraktu před odebráním zpráv. Kandidáti pro 10.A.B.0/24 mají bez self 13/14 položek, doplňuje se pouze chybějící rozdíl s uvedenými SHA-256 vektory. Jiný CIDR ponechá původní objekt beze změny, nový create/reset použije prázdný objekt.
12. Dvě relace, cizí Connect i Connect+Disconnect mezi pollingy zneplatní kontroly epochou. Connect bezpečně ukončí probe před bootstrapem a nikdy nepřekryje dva data requesty. Diagnostika nesmí otevřít tunel nebo změnit žádný VPN čas, frontu, bootstrap bod ani čítač.
13. Pád/zamrznutí tray, odhlášení, ztráta IPC a sleep/resume ověří monotónní 15/60s pronájem a úklid pouze dotčené relace po terminálním cancel. Pozdní kontakt relaci neoživí, slot zůstane obsazený do dokončení úklidu. Receipt je dostupný po expiraci podle části [Životnost a limity Wizard IPC](#životnost-a-limity-wizard-ipc), opakovaný commit nepíše znovu a změněný vstup selže.
14. Skutečná pipe s neúplnými requesty a neodebíranými odpověďmi ověří [Implementační meze lokálního řízení](#implementační-meze-lokálního-řízení), stejně jako pomalé get-info a file read. Z tray během Show Info i jiné diagnostiky skutečně odeslat Disconnect, změřit přijetí a dokončení teardown. Selhání odeslání/potvrzení má viditelnou chybu. Stop přes SCM funguje nezávisle. Spotřebu paměti a dostupnost ověřovat pro definované zatížení, neodvozovat je pouze z počtu slotů.
15. Každá HTTP fáze od DNS po neukončené tělo respektuje jeden deadline. Závody cancel/timeout/success/callback a opakované cancel nezpůsobí dvojí close, use-after-free, deadlock ani pozdní úspěch. Před dalším použitím je terminální stav potvrzen, částečné VPN tělo se účtuje jednou.
16. Oba směry všech uzavřených IPC schémat odmítnou duplicitní, nadbytečné, typově chybné členy, overflow, cizí relaci/operaci/epochu bez vedlejších účinků. Původních sedm příkazů zachová kompatibilitu. Nová tray se starou službou hlásí chybějící podporu bez fallbacku nebo vytvoření konfigurace.
17. Ručně ověřit přesné menu, anglické nápovědy, absolutní cestu z autoritativního úložiště, spotřebování zpráv, kontraktovou kolizi, klávesnici a resize na malé ploše a DPI 100/125/150/200 %. Všechna tlačítka editoru i Wizardu zůstanou viditelná. Potvrzený Finish oznámí úspěšné uložení, odešle právě jeden wizard-close a zavře Wizard, neotevře Contracts a nepřipojí VPN. Nad skutečnou produkční akcí TrayApplication s izolovanou syntetickou pipe změřit 1 Finish, 1 close, 0 automatických Contracts oken, 0 dalších config read a 0 Connect. Při ztrátě odpovědi Finish má výslovné Verify save právě 1 wizard-get-commit a nikdy druhý Finish. Ověřit také ztracenou odpověď close, Back na URL a gate, jediný souhlas s odpojením, současné disconnected/idle, celé varování a zachování HWND, výběru a undo při resize. Teprve pozdější explicitní volba Communication contracts provede právě jedno `get-config-document` a pro `availability=valid` otevře editor nad aktuálně uloženým dokumentem. Evidence obsahuje OS, build, DPI, scénář, výsledek a testera, žádné klíče ani screenshoty v repozitáři.

## Specifika platforem

### Windows

Cílem této etapy je pouze Windows AMD64 (x64). Windows x86 (32bit) a ARM64 jsou mimo rozsah, stejně jako implementace macOS a Linux. Windows je primární platforma. Klient MUSÍ používat výhradně Wintun jako L3 TUN pro IPv4. NESMÍ používat TAP, vlastní kernelový ovladač ani automaticky přejít na jiný tunelový backend, chybí-li nebo selže-li Wintun. Instalace, vytvoření či konfigurace adaptéru a změny rout vyžadují administrátorská oprávnění; samotný běh těchto operací patří výhradně Windows Service.

Službový režim je určený pro dlouhodobý běh a automatické obnovení. Konzolová aplikace zůstane lokálním klientem služby pro diagnostiku a podporované řídicí operace; sama nespouští VPN běh. Verze v1 používá výhradně split tunnel. Po úspěšném bootstrapu služba přidá lokální `virtualIp` s prefixem z `vpnCidr` a právě jednu explicitní routu přesného prefixu `vpnCidr` přes vlastní adaptér. Nepřidává výchozí routu, nemění DNS a nezavádí kill switch. Full tunnel, změny DNS a kill switch jsou mimo v1 a vyžadují budoucí samostatnou specifikaci. Relay server na nakonfigurované URL MUSÍ před změnou i po ní zůstat dosažitelný existující síťovou cestou mimo tunel phpvpn.

Platformní vrstva poskytne jeden sekvenční zdroj paketů pro vstupního pracovníka a jeden sekvenční cíl pro výstupního pracovníka. Případné asynchronní I/O dokončení se serializuje na těchto hranicích.

#### Wintun baseline a integrita distribuce

Baseline první verze je oficiální předkompilovaný a digitálně podepsaný Wintun (nejnovější stabilní verze) stažený z `wintun.net`, a to pouze pro architektury podporované konkrétním vydáním phpvpn. Projekt NESMÍ Wintun sám překládat, upravovat ani přejmenovat `wintun.dll`. Distribuce NESMÍ vyjímat ani samostatně dodávat soubory `.sys`, `.cat` nebo `.inf`; používá upstream architekturní `wintun.dll` v podobě a distribučním modelu určeném Wintunem a přikládá odpovídající upstream licenční text.

Podepsaný release manifest MUSÍ pro každou podporovanou architekturu uvést verzi Wintunu, očekávanou architekturu a SHA-256 přesných bajtů dodané `wintun.dll`. `install.bat` nebo jeho podepsaný pomocný instalátor MUSÍ před registrací služby a před jakoukoli změnou sítě ověřit podpis manifestu, shodu SHA-256, platný digitální podpis DLL a shodu architektury DLL s instalovanou službou a operačním systémem. Jakákoli neshoda je neobnovitelná chyba daného balíčku; instalace selže uzavřeně a NESMÍ vytvořit adaptér, nainstalovat službu ani změnit adresy, DNS nebo routy.

Oficiální ZIP Wintun (nejnovější stabilní verze) má publikovaný SHA-256 `07c256185d6ee3652e09fa55c0b673e2624b565e02c4b9091c79ca7d2f24ef51`. Tato hodnota ověřuje výhradně původní ZIP archiv při přípravě vydání; NENÍ hashem žádné jednotlivé `wintun.dll` a NESMÍ nahradit per-DLL hashe v podepsaném release manifestu klientského balíčku.

`wintun.dll` MUSÍ být uložena v instalačním adresáři chráněném proti zápisu neprivilegovaným uživatelem. Služba ji načítá pouze absolutní kanonickou cestou pomocí `LoadLibraryExW` s příznaky `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32`. NESMÍ ji načíst přes `PATH`, aktuální pracovní adresář, relativní cestu, uživatelský profil, dočasný adresář ani jiné zapisovatelné umístění.

Platformní vrstva má pevný allowlist API potřebných první verzí: `WintunCreateAdapter`, `WintunOpenAdapter`, `WintunCloseAdapter`, `WintunGetRunningDriverVersion`, `WintunStartSession`, `WintunEndSession`, `WintunGetReadWaitEvent`, `WintunReceivePacket`, `WintunReleaseReceivePacket`, `WintunAllocateSendPacket` a `WintunSendPacket`. Služba před první síťovou změnou bezpečně načte DLL a vyřeší všechny tyto symboly. Chybějící symbol, nesprávná architektura nebo jiná staticky zjistitelná nekompatibilita způsobí chybu bez vytvoření adaptéru, session, adresy nebo routy. Kompatibilitu skutečně běžící verze ověří bezprostředně po vytvoření nebo otevření adaptéru podle následující části a před zahájením session nebo změnou adres a rout; žádný fallback není dovolen.

#### Vlastnictví adaptéru a session

Wintun DLL, adaptér i session smí používat pouze Windows Service. Tray ani konzolová aplikace NESMĚJÍ načíst `wintun.dll`, volat její API, otevírat adaptér ani přímo měnit tunel; nadále komunikují pouze přes IPC. V jednom procesu a pro jednu instalaci phpvpn smí existovat nejvýše jeden otevřený adaptér a jedna aktivní session. Adaptér používá pevný název `phpvpn` a pevný typ tunelu `phpvpn`; implementace používá stabilní instalační identitu adaptéru a NESMÍ při opakovaném připojení vytvářet další adaptéry s odvozenými názvy.

Služba smí adaptér vytvořit nebo otevřít a session zahájit až po úspěšném bootstrapu `health`, `info`, prázdný `data` polling a po úspěšném fail-closed preflightu popsaném níže. Bezprostředně po vytvoření nebo otevření adaptéru ověří pomocí `WintunGetRunningDriverVersion`, že skutečně běžící Wintun patří do podporovaného kompatibilního rozsahu vydání. Nevyhovující výsledek zavře adaptér a skončí bez zahájení session a bez konfigurace adres a rout. Pro první verzi má `WintunStartSession` kapacitu ring bufferu přesně 4 MiB (`4194304` bajtů), tedy mocninu dvou uvnitř rozsahu povoleného API; jiná hodnota vyžaduje předchozí zátěžové, overflow a paměťové testy a aktualizaci této specifikace.

Před první síťovou změnou služba provede fail-closed preflight: načte perzistentní záznam vlastnictví, zjistí skutečný stav adaptérů, IPv4 adres a rout a ověří kolize zamýšlené adresy, prefixu, routy i cizích prostředků. Zjistí-li kolizi nebo nedokáže-li spolehlivě rozlišit vlastní a cizí prostředek, skončí bezpečnou chybou bez vytvoření, odstranění nebo změny síťového prostředku. Samotná shoda názvu adaptéru, VPN adresy nebo prefixu NESMÍ být důkazem vlastnictví.

Záznam vlastnictví je perzistentní soubor v chráněném adresáři Windows Service. Obsahuje verzi formátu a stabilní identitu instalace, stabilní identitu vlastního adaptéru, každou adresu a prefix vytvořený službou a každou vlastní routu včetně cíle a prefixu, next hopu, explicitního rozhraní a explicitní metriky. Pro každý síťový krok eviduje právě stav `planned`, `created` nebo `removed`. NESMÍ obsahovat klíče, secrety, payloady, obsah paketů, ciphertexty ani autentizační tagy.

Každé vytvoření nebo odstranění adaptéru, adresy či routy je malá perzistentně žurnálovaná transakce: služba před provedením kroku bezpečně zapíše a trvale uloží zamýšlenou operaci vytvoření nebo odstranění se stavem `planned`; po ověřeném úspěchu kroku atomicky uloží odpovídající potvrzený stav `created` nebo `removed`. Každá routa MUSÍ určit cílový prefix, next hop, konkrétní rozhraní a metriku. Implementace NESMÍ neurčitě vyhledat „nejlepší“ rozhraní nebo routu, měnit globální priority ani spoléhat na automaticky zvolenou metriku.

Po úspěšném vytvoření session a dokončení preflightu služba přidá pouze svou `virtualIp` s prefixem z `vpnCidr` a jedinou explicitně evidovanou split-tunnel routu přesného prefixu `vpnCidr` přes vlastní adaptér. Bezprostředně ověří, že výchozí routa a DNS zůstaly beze změny a že relay server zůstává dosažitelný přes ne-phpvpn rozhraní; selhání dokončí bezpečný rollback pouze jednoznačně vlastních kroků podle záznamu.

Recovery po pádu, restartu služby nebo systému je idempotentní: služba porovná skutečný stav s perzistentním záznamem a dokončí nebo vrátí pouze jednoznačně vlastní nedokončené kroky. Před novým úspěšným bootstrapem přitom NESMÍ vytvořit ani otevřít adaptér nebo zahájit session a nesmí slepě mazat stejně vypadající cizí síťovou konfiguraci. Pokud záznam chybí, je poškozený, má neznámou verzi nebo se jeho identita a skutečný stav neshodují tak, že vlastnictví nelze jednoznačně prokázat, reconciliation NESMÍ nic odstranit ani přepsat a služba přejde do bezpečného chybového stavu vyžadujícího zásah správce.

Windows startup reconciliation nepoužívá Wintun API. Nejprve ověří instalační identitu v journalu a nejvýše 5 s read-only čeká na dokončení úklidu OS. Neaktivní osiřelou PnP instanci lze odstranit pouze po shodě skutečného GUID, aliasu, LUID, přesné instance `SWD\WINTUN\{GUID}`, síťové třídy a ověřeného `IsPresent=false`. Nepoužívá se odstranění balíčku ovladače ani zásah do živého zařízení. Před vyřazením journalu se znovu ověří nepřítomnost identity a všech jejích řádků. Nejasnost nebo požadavek Windows na restart zachová journal a zablokuje start služby. Nativní SetupAPI odstranění nemá vlastní cancel/deadline ani atomickou podmínku proti souběžnému zásahu jiného administrátora. Lifecycle vlastní instance musí být serializovaný.

#### Sekvenční I/O a vlastnictví paketů

Vstupní pracovník je jediným volajícím `WintunReceivePacket`. Každý úspěšně vrácený buffer vlastní Wintun session a pracovník jej MUSÍ po zkopírování nebo dokončení validace právě jednou vrátit pomocí `WintunReleaseReceivePacket`, a to i při neplatném, ne-IPv4, příliš velkém nebo jinak zahozeném paketu. Ukazatel do receive ringu NESMÍ uložit do FIFO, předat jinému vláknu ani použít po `WintunReleaseReceivePacket`. Neplatné a non-IPv4 pakety se bezpečně zahodí a evidují pouze agregovaným čítačem; validace IPv4 a zařazení do per-peer FIFO se dále řídí společnými pravidly tohoto dokumentu.

Není-li paket okamžitě dostupný, pracovník čeká přerušitelně na událost z `WintunGetReadWaitEvent` společně s vlastní událostí ukončení. NESMÍ pollovat v busy-loopu. Disconnect, stop služby, chyba session, sleep/hibernate a recovery musí čekání probudit nebo jinak řízeně ukončit, aby bylo možné pracovníka připojit bez časově neomezeného blokování.

Výstupní pracovník je jediným volajícím `WintunAllocateSendPacket` a `WintunSendPacket`. Pro každý již ověřený IPv4 paket nejprve alokuje přesně potřebný buffer v send ringu, zkopíruje do něj paket a jediným `WintunSendPacket` předá vlastnictví session. Buffer NESMÍ odeslat dvakrát, použít po předání ani sdílet s jiným vláknem. Nedostatek místa v ringu nesmí vést k přepsání paměti ani busy-loopu; pracovník použije omezené přerušitelné čekání/backpressure a při zastavení bezpečně zahodí dosud nealokovaný paket podle existujících limitů a FIFO pravidel.

#### Disconnect, upgrade a rollback

Disconnect nečte konfiguraci a používá nezávislou řídicí cestu i během Show Info nebo jiné dlouhé diagnostiky. Stop služby přes SCM na pipe nezávisí. Všechny důvody stopu, Connect proti probe i Cancel/Reset/Escape/X Wizardu používají společné bezpečné HTTP rušení. Terminální stav requestu a callbacků musí být potvrzen před nahrazením či uvolněním prostředků, částečné VPN tělo se zaúčtuje právě jednou.

Disconnect MUSÍ proběhnout v tomto pořadí: zastavit zakládání nových `data` pollingů a zrušit nebo nechat bezpečně doběhnout jediný existující request; signalizovat ukončení síťového i obou tunelových pracovníků, probudit jejich čekání a všechna vlákna připojit; odstranit pouze vlastní routy a vlastní adresu; zavolat nejvýše jednou `WintunEndSession`; a nakonec zavolat nejvýše jednou `WintunCloseAdapter`. Jednotlivé kroky i celý postup jsou idempotentní, snesou částečnou inicializaci a po pádu se dokončí přes vlastnický reconciliation. Stav `disconnected` se nesmí oznámit před dokončením tohoto pořadí.

Upgrade používá stejný postup jako [současná instalace](#distribuce-a-instalace-ve-windows). Balíček se ověří před instalačními změnami, soubory se zkopírují do adresáře `releaseVersion` a `current.generation` se přepne ještě před zastavením původní služby. Instalátor neprovádí test vytvoření adaptéru a session před potvrzením instalace. Nejde o plně transakční upgrade, není implementován instalační journal, automatický rollback ani crash-safe společná obnova pointeru a registrace SCM. Selhání po zahájení zápisu může zanechat částečně změněnou instalaci. Start služby neověřuje podpis celé aplikační generace.

Současný instalátor nemá samostatnou cestu kompatibilního návratu ke starší aplikaci, nelze tedy slibovat ověřený rollback ani obnovu předchozího běžícího stavu. Instalace, upgrade ani běžná odinstalace automaticky nevolají `WintunDeleteDriver`, protože systémový Wintun může současně používat WireGuard nebo jiná aplikace. Návrat aplikace nesmí být důvodem ke slepému downgrade sdíleného kernelového ovladače.

#### Windows Service, konzole a tray

Pro běžný provoz je klient implementovaný jako Windows Service. Služba výhradně vlastní konfiguraci, stav připojení, Wintun adaptér a session, veškerý síťový provoz, všechny tři pracovní role a globální provozní čítače. Samostatná tray aplikace běží v uživatelské relaci a spolu s konzolovou aplikací je pouze lokálním IPC klientem služby. Obě aplikace smějí službu ovládat výhradně přes níže definované lokální IPC, nesmějí načítat Wintun DLL, otevírat tunel, provádět VPN provoz ani vést vlastní autoritativní kopii stavu či čítačů. Přes `get-config` a `set-config` však mohou dočasně přijmout nebo odeslat konfiguraci včetně `SERVER_SECRET`, `ACCESS_KEY` a `PAYLOAD_KEY`. Stejný přístup má každá lokální aplikace připojená k pipe.

Síťová pracovní role vzniká při úspěšném startu engine služby, obsluhuje bootstrap i provoz a její vlákno trvá až do shutdown engine. V odpojeném stavu čeká na příkazy bez VPN pollingu. Tunel a jeho session vznikají až po úspěšném bootstrapu `health`, `info` a prázdného autentizovaného `data`. Poté služba spustí dvě samostatné I/O role, jediného čtenáře a jediného zapisovatele tunelu. Jejich životnost je svázaná s tunelovou session. Dokončený Disconnect tyto dvě role a session ukončí, síťová role zůstává k dispozici dalšímu Connectu.

Na jednom počítači smí pro danou instalaci phpvpn běžet nejvýše jedna instance Windows Service a tato služba smí vlastnit nejvýše jednu globální instanci VPN. Singleton služby, stavový automat připojení, Wintun adaptér, session, pracovní role, fronty i provozní čítače jsou globální pro celou instalaci a NESMĚJÍ se vytvářet samostatně pro jednotlivé uživatele nebo interaktivní relace.

Diagnostické requesty `get-info` a ProbeClient se neúčtují do žádného z devíti provozních čítačů ani do provozních drop/ciphertext statistik.

Služba vede následující čítače pouze v paměti a poskytuje je všem tray i konzolovým relacím jako jeden globální snímek:

- `dataPollsTotal`
- `dataPollsEmpty`
- `dataPollsWithPayload`
- `serializedDataRequestBodyBytes`
- `serializedDataResponseBodyBytes`
- `ipv4PacketsSent`
- `ipv4PacketsReceived`
- `ipv4BytesSent`
- `ipv4BytesReceived`

`serializedDataRequestBodyBytes` je součet přesných počtů bajtů aplikačních těl requestů `data` předaných transportu. `serializedDataResponseBodyBytes` je součet přesných počtů bajtů aplikačních těl odpovědí `data` skutečně přečtených z transportu. Transport lokálně sčítá přečtené bloky a služba součet publikuje právě jednou při dokončení pokusu, při úspěchu i chybě. Probíhající čtení se do globálního čítače průběžně nepromítá. Započítají se i částečná těla před timeoutem, zrušením nebo chybou čtení, již přečtený blok přesahující velikostní limit, těla s neúspěšným HTTP statusem i následně odmítnutá těla. Počet přečtených bajtů se nesmí ztratit při návratu chybového výsledku. Účtování nevyžaduje další kopírování těla ani globální zamykání po bajtech. Ani jeden čítač nezahrnuje HTTP hlavičky, TLS režii, TCP/IP nebo nižší vrstvy, ani requesty a odpovědi `health` či `info`.

`ipv4PacketsSent` a `ipv4BytesSent` se pro každý původní validovaný IPv4 paket zvýší právě jednou při jeho zařazení do úplného serializovaného requestu `data`, který je předán transportu. Bajtový přírůstek je přesná délka původního IPv4 paketu před binárním zabalením, šifrováním, kódováním a NDJSON serializací. `ipv4PacketsReceived` a `ipv4BytesReceived` se zvýší právě jednou až po úplném ověření celé odpovědi a příslušné dávky, dešifrování, úplné validaci původního IPv4 paketu a jeho úspěšném přijetí do klientské příchozí fronty. Bajtový přírůstek je přesná délka takto přijatého původního IPv4 paketu. Opakované zařazení téhož paketu do nového skutečně odesílaného requestu se účtuje jako nový přenosový pokus, nikdy však více než jednou v rámci jednoho requestu. Statistiky tedy měří přenosové pokusy, nikoli unikátní pakety nebo jen potvrzená přijetí serverem. Paket o 100 bajtech předaný transportu ve dvou requestech zvýší odchozí čítače o 2 pakety a 200 IPv4 bajtů. Přijetí odpovědi nesmí totéž odeslání zaúčtovat znovu. Neověřený, odmítnutý nebo do příchozí fronty nepřijatý paket se jako přijatý nepočítá.

Všechny čítače se atomicky vynulují při vzniku nového logického `connect` ze stavu `disconnected` nebo `error`. Idempotentní `connect` během `connecting`, `connected` nebo `recovering` je nenuluje a recovery téhož logického spojení je zachová. Před dokončením `disconnect` se dokončí nebo zruší běžící request a zaúčtuje jeho přečtené tělo. Poté se dosavadní čítače zahodí a snímek odpojeného stavu vrací nuly. Opožděné dokončení nesmí zvýšit čítače odpojeného stavu ani nového logického spojení. Restart nebo pád služby je přirozeně vynuluje. Čítače NESMĚJÍ být uloženy do konfigurace, registru, logu ani jiného persistentního úložiště.

Tray aplikace SMÍ současně běžet v každé interaktivní uživatelské relaci a v každé relaci smí běžet i konzolová aplikace. Všechny tyto procesy jsou rovnocennými IPC klienty jediné existující služby: příkazem `get-status` čtou a zobrazují tentýž globální stav služby a VPN, nikoli stav vlastní relace nebo procesu. `connect` a `disconnect` jsou globální a idempotentní operace nad jedinou VPN instancí bez ohledu na to, který IPC klient nebo která relace je vyvolala. Souběžné nebo opakované příkazy NESMĚJÍ založit druhý bootstrap, druhý tunel, druhou session ani druhou sadu pracovních rolí.

Proces tray ani konzolové aplikace nevlastní službu, VPN, adaptér, tunelovou session ani globální Connect. Dočasné Wizard relace mají samostatný pronájem, jejich zavření nebo expirace uklidí jen jejich práci podle části Životnost a limity Wizard IPC. Odhlášení uživatele, ukončení nebo pád libovolné tray či konzolové aplikace proto NESMÍ odpojit VPN, zastavit Windows Service, změnit vlastnictví prostředků ani ovlivnit ostatní uživatelské relace. Windows Service MUSÍ fungovat autonomně i bez přihlášeného uživatele, NESMÍ zobrazovat okna, modální dialogy, tray ikonu ani jiné UI a NESMÍ pro bootstrap, provoz, recovery nebo teardown záviset na existenci či životním cyklu uživatelské relace.

Při každém novém interaktivním přihlášení se tray spustí v dané uživatelské relaci, připojí se k již existující Windows Service a bez vyvolání `connect`, `health`, `info` nebo `data` nejprve načte aktuální globální stav příkazem `get-status`. Pokud VPN již běží, tray tento stav pouze zobrazí a nepřebírá vlastnictví služby ani VPN.

Instalace, odinstalace, registrace, spuštění a zastavení samotné Windows Service nejsou operacemi IPC. Instalaci a odinstalaci zajišťují výhradně `install.bat`, `uninstall.bat` a Windows Service Manager. Konzolová aplikace nesmí tuto hranici obcházet řídicím příkazem poslaným přes pipe.

##### Veřejné lokální IPC

IPC je Windows named pipe s pevnou verzovanou smlouvou v1. Název pipe je pevná implementační konstanta obsahující verzi; klient nesmí vyhledávat pipe podle uživatelského vstupu ani přijmout neoznačenou nebo jinou verzi smlouvy. Zprávy jsou UTF-8 JSON a každý požadavek obsahuje `ipcVersion`, `requestId` a `command`; `set-config` navíc obsahuje právě jedno pole `config`. `ipcVersion` je pro tuto smlouvu celé číslo `1`, `requestId` je čerstvé UUIDv4 a `command` je právě jedna z povolených hodnot. Neznámá verze, neznámý příkaz, duplicitní pole nebo nadbytečné pole se odmítne stručnou bezpečnou IPC chybou bez provedení operace.

Instalátor nastaví na řídicí pipe explicitní Windows ACL, která umožní připojení každé lokální aplikaci bez ohledu na jejího uživatele, skupinu nebo efektivní Windows token. Přístup nesmí vyžadovat zvláštní účet, členství ve skupině ani oprávnění vytvořené instalátorem. Služba při připojení klienta neprovádí impersonaci ani autorizaci identity klienta a nesmí rozhodovat podle názvu procesu, PID, cesty spustitelného souboru nebo údajů ve zprávě. Jedinou ochrannou hranicí IPC zůstává pevná verzovaná smlouva, úplná validace zprávy a výhradní seznam povolených příkazů.

Smlouva v1 zachovává původních sedm příkazů uvedených níže a rozšiřuje whitelist pouze o přesné konfigurační a Wizard příkazy v části Rozšíření IPC v1:

- `get-status`;
- `connect`;
- `disconnect`;
- `get-info`;
- `get-config`;
- `set-config`;
- `get-diagnostics`.

Pipe NESMÍ podporovat průběžný odběr stavu, restart služby, spuštění libovolného procesu nebo příkazu ani obecný příkaz pro práci s klíči. Konfigurační a Wizard příkazy smějí přenášet pouze pole podle svých uzavřených schémat. Nesmí poskytovat obecný rozšiřující příkaz, kterým by bylo možné tato omezení obejít.

Úspěšné odpovědi kromě `get-info` a `get-config` obsahují `ipcVersion`, původní `requestId`, výsledek příkazu a pouze pole povolená pro daný příkaz. Chyba obsahuje původní `requestId`, stabilní stručný kód, bezpečný uživatelský popis a údaj, zda je chyba obnovitelná. Nesmí obsahovat detail výjimky ani systémový chybový text. Pevná konfigurační cesta a URL jsou povolené pouze v určených nových konfiguračních a Wizard odpovědích, nikoli ve statusu, statistice, běžné IPC chybě nebo logu. Odpovědi `get-info` a `get-config` mají zvláštní přímý formát popsaný níže.

`get-status` vrátí bezpečný lokální snímek obsahující:

- stav právě z množiny `disconnected`, `connecting`, `connected`, `recovering`, `error`;
- fázi právě z množiny `idle`, `health`, `info`, `access-key-check`, `starting-tunnel`, `running`, `stopping`;
- UTC čas poslední změny stavu;
- pevná pole `serverUrlCheck`, `serverSecretCheck` a `accessKeyCheck`, každé právě s hodnotou `pending`, `success` nebo `failed`, která uchovávají výsledky tří bootstrap kontrolních bodů pro aktuální nebo poslední logický pokus;
- samostatný stav dosažitelnosti serveru a stav jeho kryptografického ověření, každý jako `unknown`, `yes` nebo `no`;
- stav tunelu;
- bezpečnou poslední chybu, nebo `null`, není-li žádná;
- počet obnov a pevná celočíselná pole `dataPollsTotal`, `dataPollsEmpty`, `dataPollsWithPayload`, `serializedDataRequestBodyBytes`, `serializedDataResponseBodyBytes`, `ipv4PacketsSent`, `ipv4PacketsReceived`, `ipv4BytesSent` a `ipv4BytesReceived`;
- verzi klienta a verzi IPC smlouvy.

Pořadí členů JSON objektů místního IPC není závazné. Klienti vyhledávají pole podle názvu a testy významu odpovědi porovnávají strukturu a hodnoty nezávisle na pořadí členů. Serializace může být stabilně uspořádaná pro čitelnost. Toto pravidlo nemění pořadí prvků JSON polí, validaci typů, odmítání duplicit ani kanonický zápis síťových zpráv podle `protocol.md`.

Všech devět provozních polí jsou nezáporné celočíselné hodnoty s rozsahem nejméně 64 bitů. Implementace MUSÍ používat kontrolované přírůstky a NESMÍ připustit přetečení ani návrat k nižší hodnotě. Pokud nepoužije širší vnitřní typ, na nejvyšší reprezentovatelné hodnotě čítač saturuje. Trojice pollingových čítačů se při vyčerpání rozsahu atomicky zmrazí na poslední reprezentovatelné kombinaci splňující invariant. Celý `get-status` včetně stavu, fáze, kontrolních bodů a všech čítačů je jeden vnitřně konzistentní snímek. Zejména vždy platí `dataPollsTotal = dataPollsEmpty + dataPollsWithPayload` a žádný klient nesmí složit výsledek z hodnot odečtených v různých okamžicích.

Snímek `get-status` NESMÍ obsahovat URL ani její část, konfiguraci, VPN ani jiné IP adresy, klíče, autentizační nebo GCM tagy, ciphertexty, obsah requestů nebo paketů, interní cesty ani raw systémové či detailní síťové chyby. Bezpečný důvod chyby smí rozlišit nedostupný nebo neplatný endpoint, selhání ověření serveru či `SERVER_SECRET`, skutečně odmítnutý `ACCESS_KEY`, selhání spuštění tunelu a nedokončené ověření nebo komunikaci, včetně samostatného timeoutu. Služba vytváří `lastError` s bezpečným stabilním `code`, hotovým anglickým `description` a příznakem `recoverable`. Tray i konzole přebírají tentýž výsledek a neodvozují příčinu z kontrolních bodů. Raw interní kódy, například jednotlivé DNS nebo TLS chyby, se mapují na tyto bezpečné kategorie. Jde pouze o čtení již existujícího stavu a čítačů z paměti. Příkaz nesmí sám spustit `health`, `info`, `data`, tunel ani obnovu, změnit stav, blokovat pracovníky po dobu síťové nebo kryptografické operace ani čekat na síť. Režie pořízení snímku MUSÍ zůstat zanedbatelná.

`connect` zahájí v rámci služby bootstrap v přesném pořadí `health`, `info` a prázdný autentizovaný polling `data`. Bootstrap provádí již existující síťová role, jejíž vlákno vzniká při úspěšném startu engine a trvá až do jeho shutdown. Tunel, jeho session, dvě tunelové I/O role a pravidelný VPN provoz smí služba spustit až po úspěchu všech tří kroků. Pokud připojování, provoz nebo recovery již běží, příkaz je idempotentní a vrátí aktuální stav bez založení druhého bootstrapu, tunelu nebo sady pracovních rolí. Přijatý konfigurační snapshot a pravidla bootstrap checkpointů se tím nemění.

`disconnect` v rámci služby provede přesné pořadí z části „Disconnect, upgrade a rollback“: zastaví nové pollingy, ukončí pracovníky, odstraní pouze vlastní routy a adresu, ukončí Wintun session a zavře adaptér. Příkaz je idempotentní a recovery-safe; pokud je již odpojeno, vrátí aktuální stav. Dokončení příkazu nesmí být oznámeno dříve, než je další VPN polling zastaven a všechny tyto kroky bezpečně dokončeny.

`get-info` jednou načte a úplně validuje aktuální soubor, pak provede v oddělené omezené diagnostické cestě služby jednorázový `health` a po jeho úspěšném ověření jednorázový `info`. Služba ověří a dešifruje obě odpovědi. Použije vlastní dočasný transport a časový kontext, nesdílí proměnný VPN stav, fronty ani čítače. Nejvýše jedna dlouhá řídicí diagnostika `get-info` nebo Wizard smí běžet současně, další dostane `busy`. Příkaz nesmí spustit tunel, pracovní role ani `data` polling a nesmí měnit stav odpojeného klienta na připojený. Žádná část této jednorázové diagnostiky se po chybě včetně 401 automaticky neopakuje. Při úspěchu služba pošle přes pipe bez vlastní IPC obálky přesně validovaný dešifrovaný plaintext objekt `info` ze serveru, tedy objekt s poli `serverVersion`, `generatedAt`, `clients` a `limits`. Nevrací šifrovaný obal odpovědi, klíče, tagy ani ciphertext. Při selhání vrátí pouze stručnou bezpečnou IPC chybu. Služba, tray ani konzolová aplikace NESMĚJÍ kvůli tomuto příkazu zapisovat nebo vytvářet lokální soubor s výsledkem; tray a konzolová aplikace plaintext přímo zobrazí.

`get-config` jednou načte aktuální soubor a vrátí přes pipe bez vlastní IPC obálky jeho platný konfigurační JSON po jediné povolené počáteční BOM normalizaci. Neplatný soubor odmítne a nevrací starou cache. Skutečný platný UTF-8 text v limitu při neplatném JSON zpřístupňuje výhradně nová obálka `get-config-document`. Smí jej vyžádat každá lokální aplikace bez ohledu na uživatele, skupinu nebo Windows token. Po otevření Connecting progress window jej tray jednou použije a z platného JSON převezme pouze zobrazované `serverUrl` a lokální `virtualIp`. Celý přijatý dokument včetně citlivých hodnot nesmí logovat a jeho dočasné kopie mají omezenou životnost. Protože `get-config` čte aktuálně uložený dokument a Connect používá vlastní neměnný aktivní snímek, při souběžné externí změně může zobrazená URL/IP patřit novější uložené konfiguraci než právě aktivnímu spojení. Tento trade-off je vědomě přijatý za účelem zachování stávajícího IPC. Konfigurační JSON se neposílá v logu ani v chybové odpovědi, ale jeho zpřístupnění přes veřejnou pipe je vědomě přijaté riziko tohoto klienta.

`set-config` přijme v poli `config` celý konfigurační JSON. Služba před zápisem ověří syntaxi JSON a úplnou platnost konfigurace stejnými pravidly jako při připojení; při chybě nic nezapíše a vrátí bezpečnou IPC chybu. Při úspěchu služba konfiguraci atomicky uloží do pevného konfiguračního souboru, publikuje uložený snímek a vrátí běžnou úspěšnou IPC odpověď. Celý dokument uloží přes společný ConfigStore podle poslední úspěšné publikace, bez revizního konfliktu, dalšího potvrzení přepsání či slučování. Aktivní VPN si ponechá svůj neměnný snímek. Příkaz sám neodpojí ani nepřipojí VPN; uložená konfigurace se použije při následujícím pokusu o připojení.

`get-diagnostics` vrátí rozšířený jednorázový bezpečný snímek místního stavu. Obsahuje stav, verzi a dobu běhu služby; výsledek validace konfigurace a bezpečná varování; výsledky posledního ověření `health`, `info` a `data` a poslední obnovy; připravenost tunelu; pro vstupní i výstupní fronty počet položek, obsazené bajty a platný limit; agregované provozní čítače; a bezpečnou poslední chybu včetně údaje o její obnovitelnosti. Příkaz je pouze čtecí, nespouští nové síťové požadavky, tunel ani obnovu a NESMÍ vrátit URL, VPN ani jiné IP adresy, klíče, tagy, ciphertexty, obsah paketů, interní cesty ani detailní systémové nebo síťové chyby.

Tray získává stav příkazem `get-status` v základním pevném intervalu 5 sekund a navíc ihned po každém příkazu `connect` nebo `disconnect`. Connecting progress window má po celou dobu otevření vlastní pravidelný `get-status` každých 500 ms. Tento timer základní interval neposouvá, nenahrazuje ani nezastavuje a po zavření okna zaniká. Oba intervaly se adaptivně nemění. Po jednorázové službové kontrole platnosti aktuální konfigurace vyvolané kliknutím smí Statistics použít poslední dostupný paměťový snímek nebo vyvolat jediný okamžitý `get-status`, který základní timer neovlivní. Otevřené Statistics se dále aktualizuje z pravidelných pětisekundových snímků. Smlouva nepoužívá streamování ani odběr změn stavu.

Tray používá tři varianty ikony Material Symbols `shield_lock` pod licencí Apache 2.0 a distribuce MUSÍ zachovat všechny její licenční podmínky a požadovaná oznámení. Šedý štít znamená `disconnected`, oranžový štít znamená `connecting` a zelený štít znamená `connected`. Každá výsledná ikona je čtvercová, má neprůhledné bílé pozadí a po celém obvodu zřetelný černý rámeček. Geometrie, rozměry, umístění štítu, pozadí i rámeček jsou ve všech třech variantách shodné a mění se pouze barva štítu. Ikony MUSÍ zůstat ostré, jednoznačně rozlišitelné a čitelné v běžných rozměrech Windows tray, při všech podporovaných hodnotách DPI a na světlém i tmavém pozadí.

#### Distribuce a instalace ve Windows

Autoritativní a závaznou metodiku sestavení distribuce, její strukturu, úplnost a ověření stanoví [distribution.md](distribution.md). Následující pravidla určují chování instalace a provozu klienta, požadavky na Wintun a integritu zůstávají v části Wintun baseline a integrita distribuce tohoto dokumentu.

Instalátor nevlastní JSON šablonu. První úspěšná inicializace služby po instalaci vytvoří chybějící default, každý další start zachová existující bajty. Za běhu lze smazaný soubor vytvořit potvrzením v Edit Config nebo úspěšným Finish Wizardu. Službu i tray je nutné aktualizovat společně.

[make-dist.ps1](client/tools/make-dist.ps1) připravuje úplný offline balíček: `phpvpn-service.exe`, `phpvpn-tray.exe`, konzoli `phpvpn.exe`, nepřejmenovanou `wintun.dll` odpovídající architektury, licenci Wintun, licenci a NOTICE Material Symbols, instalační a odinstalační BAT/PowerShell skripty. `release-manifest.json` je kompaktní jednořádkový UTF-8 JSON bez BOM se seznamem souborů a SHA-256. Oddělený RSA-PKCS1-SHA256 podpis je v `release-manifest.sig`, veřejný certifikát v `release-signing.cer`. Volba `SignBinaries` při sestavení navíc podepisuje tři EXE, nenahrazuje podpis manifestu. Balíček obsahuje potřebné součásti bez jejich stahování při instalaci.

`install.bat` předává argumenty přibalenému [install.ps1](client/tools/package/install.ps1). Běžná instalace vyžaduje administrátorská oprávnění, skript si při jejich absenci vyžádá zvýšení. Současný postup má toto pořadí:

1. Ověří přítomnost manifestu, podpisu a certifikátu, jednořádkovou podobu manifestu bez BOM, JSON a `manifestVersion = 1`. Vyžaduje algoritmus RSA-PKCS1-SHA256, shodu připnuté identity `ExpectedThumbprint` s certifikátem, podpisovým záznamem i manifestem a platný podpis přesných bajtů manifestu. Vývojový pin není trvalou identitou specifikace.
2. Ověří přítomnost a SHA-256 každého souboru uvedeného v manifestu. Vyžaduje všechny tři názvy EXE v seznamu a odmítá neuvedené `.exe` a `.dll` v kořeni balíčku. Nejde o zákaz všech nadbytečných souborů, neuvedený textový soubor tato kontrola neodmítá.
3. Ověří platný Authenticode podpis `wintun.dll` a subjekt vydavatele obsahující `WireGuard`. Porovná PE architekturu služby a DLL navzájem a s architekturou z `PROCESSOR_ARCHITECTURE`.
4. Spustí přibalenou službovou binárku s `--verify-tunnel` a vyžaduje návratový kód nula. Tento režim načte DLL a ověří povinné API bez vytvoření adaptéru nebo session. `install.bat -VerifyOnly`, případně `install.ps1 -VerifyOnly`, po tomto kroku skončí. Nevyžaduje zvýšení oprávnění a nepokračuje k instalačním zápisům, registraci služby ani autostartu. Chyba ověření před těmito zápisy odmítne balíček.
5. Připraví instalační kořen pod `ProgramFiles\phpvpn` a podadresář podle `releaseVersion` s instalačním ACL. Zkopíruje do něj soubory manifestu a tři ověřovací artefakty. Existující cílové soubory kopíruje s přepsáním, nejde o samostatnou neměnnou staging generaci. Datový strom ProgramData připravuje služba, installer jej rekurzivně nepřepisuje pomocí ACL.
6. Zapíše verzi do `current.generation.new` a přes `Move-Item -Force` ji přesune na `current.generation`. Teprve potom začne správa služby. Toto přepnutí samo nezaručuje transakční obnovu celé instalace.
7. Pokud služba `phpvpn` existuje, pokusí se ji zastavit a zavolá `--uninstall` z nové generace. Následuje její `--install`, kontrola návratového kódu a `Start-Service`. Služba sama vytváří veřejnou lokální pipe `phpvpn-control-v1`, installer kontroluje její přítomnost nejvýše 50 pokusy s 200ms čekáním. Chybějící pipe ukončí instalaci chybou bez automatického rollbacku.
8. Teprve po dostupnosti pipe nastaví položku `phpvpn-tray` v `HKLM\Software\Microsoft\Windows\CurrentVersion\Run` na uvozovanou cestu tray v nové generaci pro další interaktivní přihlášení. Nakonec se pokusí spustit tray v aktuální relaci. Tento poslední krok potlačuje chyby spuštění a není potvrzením viditelné ikony.

[uninstall.ps1](client/tools/package/uninstall.ps1), volaný přes `uninstall.bat`, vyhodnotí generaci podle pointeru. Je-li dostupná konzole a běžící služba, požádá přes `phpvpn.exe disconnect` o odpojení a počká dvě sekundy. Potom ukončí procesy tray, odregistruje službu přes službovou binárku, případně použije Stop-Service a SCM fallback. Odebere HKLM Run položku a instalační adresář, přičemž instalační kořen označený jako reparse point ponechá. Běžná odinstalace zachová konfiguraci, ownership journal i logy v ProgramData. Jejich odstranění vyžaduje explicitní `uninstall.bat -RemoveData` nebo `uninstall.ps1 -RemoveData`. Skript nevolá `WintunDeleteDriver`. Tento popis neposkytuje záruku transakční odinstalace ani nedodané obnovy při pádu.

### macOS

V macOS je doporučené použít nativní síťový mechanismus podporovaný systémem, typicky Network Extension s packet tunnel providerem. Ten vyžaduje správné podepisování, entitlementy a uživatelské schválení. Společné C++ jádro zůstává stejné; malý host/provider obstará čtení a zápis paketů a předá je přes stabilní C nebo C++ rozhraní.

`NEPacketTunnelFlow` může předávat dávky paketů v callbacku. Provider je předá vstupnímu pracovníkovi v pořadí dávky; výstupní pracovník může zapisovat dávky, aniž by tím změnil FIFO pořadí jednotlivých paketů.

Alternativy založené na `/dev/tun` nejsou na moderním macOS obecně přenositelné ani doporučené pro distribuovaný produkt. Je nutné počítat s pravidly sandboxingu, životním cyklem rozšíření a omezeními distribuce.

### Linux

Na Linuxu je přirozeným rozhraním TUN zařízení `/dev/net/tun`. Klient vytvoří TUN rozhraní, přiřadí virtuální IP a nastaví potřebné routy přes netlink nebo spolehlivý systémový integrační modul. Operace vyžadují oprávnění `CAP_NET_ADMIN` nebo vhodně omezený privilegovaný pomocný proces.

Produkční služba může běžet pod systemd s minimálními capability, restartovací politikou a ochranou konfiguračního souboru před přímým přístupem přes souborový systém. Tato ochrana nemění záměrně veřejný přístup ke konfiguraci přes IPC. Implementace nemá předpokládat jeden konkrétní firewall ani síťový manažer; jejich integrace má být volitelná.

Základní implementace používá jeden TUN file descriptor a tři společné pracovní role. Linuxový multiqueue TUN je volitelná optimalizace; nesmí změnit společná pravidla FIFO, limitů front ani vlastnictví paketů.

## Doporučené pořadí další práce

Současné Windows jádro, WinHTTP/CNG adaptéry, tři VPN role, fronty, agregovaný payload, Wintun integrace a nativní tray jsou již součástí implementace. Jejich opětovná implementace není dalším krokem. Existence těchto částí neznamená splnění všech integračních, vizuálních nebo výkonových testovacích povinností.

1. Při změně dodaných částí ověřit příslušný kontrakt existujícími cílenými testy. Skutečné Windows I/O, služba, VPN, instalace a vizuální/runtime akceptace mají samostatné prostředí a datovanou evidenci RUN/NOT RUN podle výše uvedených testovacích oddílů a [UX14](tray_UX.md#ux14-ověření-a-velikost).
2. Budoucí pre-poll admission backpressure zůstává nedodané. Jeho požadavek v části Příjem dat se smí označit za dodaný až po implementaci a odpovídajícím ověření. Odložené rozhodnutí R04 o integritě a síťovém vlastnictví Wintun zůstává otevřené, nyní bez realizace a nových testů, viz [T08](Plans/2026-09-12-02-29-09/T08.md).
3. Budoucí porty mohou doplnit Linux TUN a macOS Network Extension a potřebné transportní, kryptografické a systémové adaptéry. Jejich návrh v platformních částech není tvrzením o dodaném portu ani ověřené distribuci.

Agregovaný payload není kompatibilní se starším pravidlem jednoho IPv4 paketu v ciphertextu. Kompatibilní klienti a server musí používat shodný formát podle [protocol.md](protocol.md).
